# ADR-068: The audit log, and undo of any change by id (amends ADR-007)

## Status

Implemented

- **Status:** accepted 2026-10-20. No migration: it reads `change_log` and `change_log_records` as ADR-007 wrote them.
- **Context:** undo reached only the signed-in user's most recent change, through the toast. The log was written in full (actor, kind, affected records, before/after summary) but nothing read it except a short list on the person and partnership pages.
- **Decision:**
  - **Undo names its change.** `undoChange(treeId, changeId)` reverses that change; `undoLast` finds the user's latest undoable change and calls it, so there is one path. The toast's Undo passes the id of the change it announced, so it can never reverse a different one. The ADR-007 refusals apply unchanged: a later change wrote the same records, the records have changed since, or other records now depend on it. Any change that is not the newest simply meets the first of these more often.
  - **What cannot be undone:** an undo row (still no redo) and a row with no inverse. A change that already has an undo row is refused as already undone. An id from another tree is not found.
  - **Who may undo.** Anyone with the edit rights the change's operations need (as before) may undo their own changes. Managers and owners may also undo other people's. This is a default, not a measured need: an editor can be allowed to undo a colleague's change by loosening one condition in `canUndoChange`.
  - **Who may read the log.** Only roles that see every record, as `listRecent` already required (`record:edit`). A change's summary is prose naming whoever it touched, so a restricted viewer (contributor, viewer, outsider) gets no history and no undo, as the person page already does.
  - **The audit query** pages newest first by page number with a total count, filtered by a person or partnership (picked in the form, or `?record=` from a history list), by actor, and by an inclusive range of days. Offset paging was chosen over a cursor because the log is append-only and its size is modest, and numbered pages need the total anyway; the cost is that a change made while someone is reading shifts entries by one between pages. A page past the end is the last page, one below 1 the first. A day is the reader's local day: the filter form sends the browser's time zone as `tz`, and the server turns From into the start of that local day and To into the end of that local day (the start of the next, exclusive) from each day's own offset, so a daylight-saving day is 23 or 25 hours. A missing or unknown `tz` falls back to UTC, and the page says which zone the days are in. A person's or partnership's filter also matches changes to its facts and names (through `change_log_records`, joined to `events` and `person_names`), because a non-vital fact edit writes only the event row; it matches what the record's own history list shows. Facts and names deleted since cannot be traced back to their owner, so their changes drop out of the filter. Filters and the page live in the address. Each entry carries the `changes_json` summary, who undid it (derived from the revert row, never stored), and a server-computed `canUndo` so screens do not repeat the rule.
- **Not covered:** a filter by kind; redo; imports and merges that write no log rows.
- **Consequences:** the person, drawer and partnership history lists gain the same Undo button and a link to the audit log filtered to the record. A history entry is also marked as undone, so the button disappears once used.
