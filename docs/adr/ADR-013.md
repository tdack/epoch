# ADR-013: Person names (Phase 3, S6)

## Status

Implemented

- **Context:** A person may have several `NAME` records (birth, married, aka, ...). Import kept only the last, export wrote one, and `NPFX`, `NICK`, `SPFX`, `NSFX`, `TYPE` and anything else under a `NAME` was lost, which broke the no-loss rule.
- **Decision (import and export):**
  - **Every `NAME` is a `person_names` row, in file order; the first is the preferred one** and its given name and surname are mirrored on `individuals`. Migration 0009 (expand-only) adds `version`, `nickname`, `surname_prefix`, `gedcom_type`, `gedcom_extra`, the from-date columns and `union_id`.
  - **Preserved sub-structures live on the name row** (`gedcom_extra`, verbatim lines) and not in `gedcom_preserved`. That table is keyed by the owner's XREF and headed by a line, which is how ADR-009 re-attaches `FAMC` extras; a name has no stable head line (edits change it, two names can share one), and `gedcom_preserved` is outside `RECORD_TABLES`, so deleting or undoing a name could not carry its `NOTE` or `SOUR`. The mechanism is the same (verbatim lines written back inside the owning structure); the storage is the ADR-008 argument for `xref_aliases`. `FONE` and `ROMN` are preserved this way and not modelled.
  - **Types.** `TYPE` is read case-insensitively. A word that is not one of the seven known types becomes `other` and keeps the word in `gedcom_type`; a 7.0 `OTHER` keeps its `PHRASE`. Export writes lowercase words in 5.5.1 (a free-text type as itself) and uppercase in 7.0 (`OTHER` plus `PHRASE`). An untyped `NAME` is `birth` when first and `aka` after that.
  - **`birth` is the default TYPE** and is left out of the first name written, so single-name files export exactly as before. It is written on any later name, because an untyped later name would read back as `aka`.
  - **The preferred name is written first**, since GEDCOM treats the first `NAME` as primary; the rest keep their order.
  - **Legacy `_MARNM`** (level 1 on the `INDI`, `Given /Surname/` or a bare surname; the bare form takes the primary name's given name) becomes a `married` name with `gedcom_type = '_MARNM'` and is written back as `_MARNM`, not as a `NAME`, so a re-read does not see it twice. Sub-tag or level-2 spellings are not modelled and stay as preserved lines. This tag is not confirmed against webtrees' source: `Individual.php` does not mention it.
  - **Merge-mode re-import** skips a name the person already has with the same type and parts, and never adds a second preferred name.
- **When a name came into use, and from which partnership (S6).** Epoch keeps an optional "from" date (`date_raw` and the ADR-004 columns) and an optional `union_id` on a name. GEDCOM has nowhere standard for either, so export writes one human-readable `NOTE` under the `NAME`, and import reads it back:
  - `2 NOTE Name in use from 8 OCT 2001, through family @F3@.`
  - Either half may be missing: `Name in use from 1998.` or `Name in use through family @F3@.` The pattern is exact, so an ordinary note is never mistaken for it, and a note that carries children (a `CONT` chain) is left alone.
  - The date is the verbatim text; the family is the file's XREF for the union. A note that names a family the file lacks stays as written under `gedcom_extra`, date included, and no column is filled, so export writes it once and a re-import is stable.
  - There is no foreign key on `union_id`: a cascade or `SET NULL` would change the row outside the logged ops and undo could not restore it. `destroy_union`, `remove_partner_from_union` (for that person) and `merge_unions` (to the survivor) rewrite it as ordinary ops.
- **Display name.** `individuals.given_name` and `surname` remain the display name, mirrored from the preferred name in the same atomic change that alters it, and the person's version moves only when the mirrored text does. The person form edits the preferred name row (`update_person` plans both), and `create_person` now writes a preferred row, so every new person has one. A person created before this has none; the first name command materialises one from their fields. The last name of a person cannot be deleted. The "(née X)" suffix is display only: `personName` stays plain because it feeds stored change-log summaries; `displayNameWith` (shared) adds it when the person has a `maiden` name, else a `birth` name, that is not preferred and whose surname differs.
- **Names a pre-S6 person form left stale (S6).** Before this slice the person form edited `individuals` and left the imported name row alone, so a person whose name was edited then has a preferred row that still says the old name. Export and the person page now read the preferred row's given name and surname from `individuals`, which was the edited source; after S6 the two always agree (`update_person` and the name commands write both), so this is inert for new data. No backfill script was needed: the local database has no drifted rows (`SELECT ... WHERE i.given_name <> n.given_name ...` returned none), but a deployed database may, which is why the read-time rule exists. It is not a fix for the stored row, which the next edit of that person corrects.
- **Known losses on a round trip.** The `NAME` line is rebuilt from the parts, so a line that disagrees with its `GIVN` and `SURN` comes back in the canonical form, and a nickname written inside the line (`Julius "Jules" /Hibbert/`) comes back as the `NICK` sub-tag or, when there is none, inside the given name. Round-trip tests compare parsed models, not text.
- **Undo and a name's partnership.** Undoing the creation of a partnership deletes it. A later name that points at it is listed by `dependentsOfDeletions`, so that undo is refused as it is for links and events.
