# ADR-061: A source can own files, visible exactly when the source is (extends ADR-028 and ADR-050)

## Status

Implemented

- **Status:** built on `claude/source-files-dac2d6` on 2026-10-18 and deployed. No migration.
- **Context:** the owner wants sources managed on their own, with their scans attached, and reached from More > Research. Files hung off a person or a partnership only (ADR-050), and ADR-028 left the `OBJE` in a citation retained.
- **Decision:**
  - **The owner is still one id.** `media_items.entity_id` may now name a source. It has no foreign key and no owner-kind column, and ids are UUIDs, so the repository tells the kinds apart by lookup in the tree (`recordKindsOf`, `ownerOf`), as it already did for a person and a partnership. This needs no migration, so nothing is expand-and-contract.
  - **Visibility.** A file on a source is visible exactly when the source is: a restricted viewer sees the source if it supports a citation they can see, or they made it (ADR-028). `canReadRow` takes the file's owner as nothing, people or a source. The SQL is `visibleSourcesAmong` (the `andSourceVisible` predicate over a chunked id list), used by `requireRead` and by the Files listing. The row filter is `maskRows`, which now drops a file on a source the viewer cannot see, also when nobody is private. `source-files.test.ts` holds the list, the serve check and `maskRows` to one answer for a cited source, an uncited one, one the viewer made, and a tree with no private person.
  - **Writes go through the mutation runner.** `attach_media` accepts a source (its write scope seeds the source, which also loads that source's files). Detach, rename and undo are unchanged. Upload names the source as `entityId`, after `requireUpload` finds it in the tree. The row is inserted by the upload route as it is for a person's file.
  - **Delete and merge.** Deleting a source detaches its files, as deleting a person does (the bytes stay, undo hangs them back). A source merge moves the merged sources' files to the survivor in the same change, and a preview says how many files a delete keeps. `delete_source` already loaded a scoped snapshot, so the loader reads the files of a seeded source (`write-scope` and the scoped row loader agree).
  - **Listing.** `/api/files` takes `entityId` and `owner=detached`, filtered in SQL, so the source page and the attach picker go through the same visibility rule and cursor as the Files manager instead of filtering one page on the client. The sources list shows a file count from one grouped count over the page's ids, with no privacy join, since a listed source has all of its files visible.
  - **Navigation.** Sources is the first entry of More > Research, and "More: Sources" shows on `/sources` and below it.
  - **`partnerIds` is tree-scoped.** It joins `unions` on the tree, closing the gap noted for ADR-052.
  - **GEDCOM.** An import creates no file (a `FILE` is a path, never bytes), and an export writes no attached file. The `OBJE` under a `SOUR` therefore stays a retained line, written once in 5.5.1 and 7.0, and a file attached to a source in Epoch adds nothing to an export (`evidence-roundtrip.test.ts`). Linking the two needs a file to resolve to, so it waits for media records.
- **Rejected alternatives:** a `media_item_owners` table or an owner-kind column (a migration for no extra correctness while ids are unique); filtering the Files page on the client for a source's files (a short page would miss rows); a privacy join in the sources count (redundant, and costly for a restricted viewer); linking the `OBJE` under a `SOUR` on import to a file Epoch does not hold (it would invent a file).
- **Consequences:** the Files manager lists a source's file, detaches it, and offers a source beside a person in its upload, attach and move dialogs (`FileOwnerPicker`, using the shared `SourcePicker`; the source choice is shown to roles that pass `canChangeEvidence`). `MediaService.move` accepts a person or a source as the destination, still not a partnership. The unmodelled `OBJE` is in [backlog.md](../backlog.md).
