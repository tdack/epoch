# ADR-012: Facts have their own columns and are addressed by id (Phase 3, S5)

## Status

Implemented

- **Context:** `events` held a place and a single `description` into which the importer folded a CAUS, a NOTE or the line value, and export wrote it back as `NOTE`. A generic fact editor needs the parts, and two births must be able to coexist.
- **Decision:**
  - Migration 0008 (expand-only) adds `value`, `cause`, `age`, `notes` and `sort_order` to `events`. The importer fills them, export writes each on its own tag, and merge-mode de-duplication counts them as part of a fact's identity.
  - Rows written before it keep `description`, shown as a note and folded into `notes` the first time the fact is edited. **Old descriptions are not backfilled**, so an already-imported occupation reads as a note until edited.
  - Fact commands (`create_fact`, `update_fact`, `delete_fact`, `reorder_facts`) address a fact by id and never by type. The person form's birth and death fields still act on the first event of a type (`upsertEvent`); the form says so when a person has more than one, and the other facts are edited on the person's page.
  - The timeline is date first; `sort_order` orders only facts that tie. Two facts of a type a person has once (birth, death, ...) that differ are flagged as a pair; nothing is merged or hidden.
  - A change to a birth or death bumps the person's version (as recording a death already does), so a stale person form conflicts. Other facts do not, to keep undo of earlier person edits possible.
- **Known gaps:** History on the person page is found by record, so changes to a fact that was later removed are not listed. The parser still drops sub-structures under an event other than DATE, PLAC, CAUS, AGE and NOTE (such as SOUR).
