# ADR-039: Uploaded media is sniffed from its bytes and served by allowlist; non-raster is a download

## Status

Implemented

- **Status:** accepted by the owner on 2026-10-10; built on `fix/security-media-xss-auth` and deployed. Checked by unit tests for the sniffer, the serve decision and the serve route, and by a route test for the upload path.
- **Context:** the upload route trusted `file.type` and took the object key's extension from the filename, and the serve route replayed the stored R2 type with `object.writeHttpMetadata` and answered `Cache-Control: private, max-age=31536000, immutable`. An authenticated uploader could therefore attach a `text/html` or `image/svg+xml` file and have a browser run it on Epoch's own origin — a stored XSS. The same review found the Access audience check failed open when `CF_ACCESS_AUD` was unset, and that the JWKS fetch had no timeout, no rotation recovery, and no recorded decision about sharing an in-flight fetch.
- **Decision:**
  - **Upload decides the type from the bytes.** `media-type.ts` sniffs a fixed set of magic bytes (JPEG, PNG, GIF, WEBP, AVIF, HEIC/HEIF and PDF, with the PDF magic searched in the first 1024 bytes) and refuses anything else. The declared `file.type` and the filename never participate, except that the filename is the title's fallback. The sniffed type also sets the object key's extension, so a key cannot disagree with the content.
  - **Serve decides the response from a server-side allowlist, never the stored type.** `mediaServeDecision` maps the R2 `httpMetadata.contentType` (passed in, not replayed) to a response: a raster type in `INLINE_MEDIA_TYPES` is served inline as itself; `application/pdf` is served as `application/pdf` with `Content-Disposition: attachment`; everything else, including a missing type, is served as `application/octet-stream` with an attachment filename. `writeHttpMetadata` is not used. Every served object response also carries `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Cross-Origin-Resource-Policy: same-origin` and `Referrer-Policy: no-referrer`.
  - **The D1 `media_items.mime_type` column is not on the serve path.** The serve route reads the type from R2 object metadata, so the column cannot influence a `Content-Type` or `Content-Disposition`. Legacy rows written under the old upload route therefore need no migration. The column is still read by the person page to choose a client-side thumbnail, which is a display decision, not a security one.
  - **The upload is capped at 25 MB.** `MAX_MEDIA_UPLOAD_BYTES` is `25 * 1024 * 1024`. The body is bounded while it streams, by a byte-counting `TransformStream` in `parseUploadForm`: it aborts once the body passes the file cap plus a 1 MB budget for the other form fields plus 64 KB of multipart framing, and then parses the bounded stream, so this bound does not trust `Content-Length`, which a client may omit or understate. The parsed non-file fields are re-checked against that 1 MB budget (`MAX_FORM_FIELDS_BYTES`), so a file sent with many or long fields is not refused while the body stays strictly bounded. HEIC and HEIF (any `heic`/`heix`/`hevc`/`heim`/`heis` brand, or a bare `mif1`/`msf1`) are accepted and stored but never served inline, since most browsers cannot render them; they download like a PDF. A `mif1` file listing `avif` among its compatible brands is AVIF. A declared `Content-Length` beyond that bound is refused before the body is read, as a cheap early exit. `assertUploadWithinSizeLimit(file.size)` remains the authoritative *file* cap. A malformed multipart body is a 400, and a non-`File` `file` field is a 400.
  - **Caching revalidates, and only after authorization.** A successful response is `Cache-Control: private, no-cache` with the object's ETag; a matching `If-None-Match` answers a manual 304 with the same security headers. A failed authorization or a missing object answers `Cache-Control: no-store`. The manual 304 is retained deliberately: SvelteKit's automatic 304 strips the security headers this route sets.
  - **The Access audience fails closed.** An empty `CF_ACCESS_AUD` rejects any non-bypass token rather than admitting a token whose signature happens to verify. This is an intended lockout, not a bug. The audience is read from `$app/env/private` with a Worker-binding fallback, and `CF_ACCESS_TEAM_DOMAIN` gets the same binding fallback (read from `$app/env/public`, falling back to the Worker binding), so a deployment that wires either value through `wrangler`/`.dev.vars` alone still works. An empty team domain still fails closed, because `validateAccessJwt` refuses a token when the domain is absent.
  - **JWKS fetches are bounded and rotation-aware.** A certs request has a 3-second timeout and no retry. An unknown `kid` triggers one forced refetch, at most once per 60 seconds. There is deliberately no cross-request coalescing: sharing an in-flight promise would run one request's I/O (and its abort signal) on behalf of another, a Cloudflare Workers anti-pattern. A failed forced refetch keeps the cached keys for up to 24 hours, but the TTL path has no stale fallback and fails closed on a certs outage.
- **Rejected alternatives:** a separate media host (defers the fix; the allowlist closes the hole now); a site-wide CSP (a broader change than the vulnerability needs, and recorded as later hardening); a migration of `media_items.mime_type` (unnecessary, because the column is not on the serve path).
- **Consequences:** every stored object is served through the new decision on its next request, and `MEDIA_URL_VERSION` in `PersonMedia.svelte` is bumped to 2 so a browser that cached the old immutable response re-fetches. The residuals the review accepted are recorded in [backlog.md](../backlog.md).
- **Amended by ADR-050:** new uploads are keyed `media/<treeId>/<mediaId>.<ext>`, and the owner is read from the row rather than the key. The sniffing, the serve allowlist and the headers are unchanged.
- **Amended by ADR-073:** a PDF is served inline without the sandbox CSP, and its magic must open the file.
