# ADR-075: One page per scope: Account, Tree settings and Administration (amends ADR-044, ADR-054, ADR-057, ADR-070)

## Status

Implemented

- **Status:** accepted on 2026-10-21 from a design critique of the settings surfaces (scored 20/40,
  snapshot in `.impeccable/critique/`), and built on 2026-10-21 (not deployed). No migration; the
  `trees.default_view_mode` column was dropped by migration 0043.

## Context

A control's place in the interface does not match what it changes. A setting can have one of four
scopes: **me** (everywhere), **me in this tree**, **this tree for everyone**, and **the whole
install**. None of them has a page of its own:

- Profile and Settings are about the person, but live at `/trees/<tree>/profile` and
  `/trees/<tree>/settings` "only to keep the header" (ADR-044, ADR-070). The tree's tabs render with
  nothing active, and the page says "these are yours, in every tree".
- The personal Settings page also carries the install's site default palette (ADR-054).
- The default tree is chosen on the Trees page (ADR-044), which is also the install owner's list of
  every tree and, below it, the sub-trees of whichever tree is in the URL (ADR-062). The menu shows
  that page only to the install owner or to someone in more than one tree, so a manager of a single
  tree can create a sub-tree but never rename, publish or delete it.
- A member's default view and the owner's "default view for everyone" sit in the toolbar's Display
  popover, next to throwaway toggles and a "Reset to defaults" that resets neither.
- The tree's address and subdomain, which make its name public (ADR-057), are in a dialog titled
  "Rename Tree". Who can see a tree is answered in six places.
- "Delete this tree…" is offered in the switcher to every signed-in reader; only the owner or the
  install owner can complete it.
- Settings says so itself, in an "Also yours" list that points elsewhere.

## Decision

Each scope gets one page, and each control lives on the page whose scope matches what it changes.

### `/account`: me (any signed-in person)

An app-level page, not under a tree. Each section is a tab (see "Tabs" below), in order:

1. **Profile:** picture, name, email (ADR-070, unchanged behaviour).
2. **My trees:** every tree the person belongs to, with their role, a **Default** choice (ADR-044's
   `is_default`, still `PUT /api/default-tree`), and **My default view** (`tree_memberships.view_mode`,
   still `PUT /api/trees/[id]/view-mode`). "Leave this tree" lands here when it is built (backlog).
3. **Appearance:** my colours and reduce animation (ADR-054's user layer). It follows My trees
   because the trees are what most people come here to change.
4. **Leave Epoch** (ADR-072), last, as the danger zone.

### `/trees/<tree>/settings`: this tree, for everyone (manager and above)

Reached from the gear beside the tree's name in the tree switcher. A tree's administration is one
row of tabs: **Settings | Sub-trees | Export | Members | Audit log**. A manager or owner sees all
five. An editor reads the audit log and administers nothing else, so they see that tab alone and
their gear opens it. Settings, Sub-trees and Export are tabs of this page; Members and the Audit log
are their own pages. The page's sections, each shown only to the roles that can use it:

1. **General:** the tree's name.
2. **Address:** the slug and the subdomain, with ADR-057's warning that the name becomes visible.
   The "Rename Tree" dialog goes; its fields move here.
3. **Visibility:** the living-person rules and the "Private" placeholder text (the Privacy page's
   content; `/trees/<tree>/privacy` redirects here), the tree's public status (read-only, with a
   link to Administration for the install owner, who alone changes it under ADR-041), and a note that
   one person's override is set on their page.
4. **Delete this tree:** owner or install owner only (`tree:delete`), moved out of the switcher,
   at the foot of the Settings tab.
5. **Sub-trees** (its own tab): the sub-tree manager (ADR-062, ADR-069), gated by
   `tree:manage_subtrees` only.
6. **Export** (its own tab): the GEDCOM export choices (`tree:export`), moved out of the switcher.

The page stays on a tree's own subdomain: everything on it is about that tree.

### `/admin`: the whole install (install owner only)

An app-level page, refused to everyone else with a 404. Each section is a tab:

1. **Trees:** every tree with its owners and counts, and rename, make public, delete (ADR-041,
   ADR-044's install-owner view) as icon buttons with a tooltip, on one line per tree.
2. **Site appearance:** the site default palette (ADR-054's site layer).

### Header and menus

- **Avatar menu:** Account; Administration (install owner only); Sign out.
- **Tree switcher:** switch tree or sub-tree, New tree, Import. Rename, Export and Delete leave it.
- **Tree switcher, each row:** a gear opening that tree's administration (settings for a manager or
  owner, the audit log for an editor), so it sits next to the tree's name rather than in a menu
  about the page.
- **Research menu** (was More): only the research pages, with **Files** added (any member,
  ADR-050). The Manage group, the Trees item and the audit log leave it; the tree's administration
  is the gear and its tabs.
- **Manage tab:** the last tab of a tree's navigation, after Research, for an editor or above who
  is a member. It opens settings (manager, owner) or the audit log (editor), and reads as active on
  the settings, members and audit pages.
- **Tabs:** Account, Administration and a tree's administration share one tab bar. A tab is a link,
  so it can be bookmarked; tabs within one page are its `#fragment`, and an old link to a section
  (`#visibility`) opens the tab that holds it.
- **One column:** `/account` and `/admin` use the tree pages' width and left edge, and the page
  reserves the scrollbar's gutter, so moving between a short page and a long one shifts nothing.
- `/account` and `/admin` share the app header through a SvelteKit layout group, the way `/`
  already renders it without a tree. ADR-044 rejected a *copied* header, not a shared one.

### The default view for everyone is removed

A member's own default and the `mode` a link carries are enough; a third, owner-set layer changed
every member's view silently from a chart popover. The view resolves as: the address, then the
member's own choice, then Flat.

- Code stops reading and writing `trees.default_view_mode`. `PUT /api/trees/[id]/default-view`,
  `TreeService.setDefaultViewMode`, the `tree:set_default_view` action and the toolbar's
  "Everyone" select are deleted.
- The column was dropped by migration 0043, after the code that ignores it was deployed
  (expand-and-contract).
- The member's own default is set on Account › My trees only. The toolbar's Display options hold
  the display toggles and "Reset display", which resets only those.

### Redirects

Old addresses keep working, with a 302 (the targets depend on the viewer):

| Old | New |
| --- | --- |
| `/profile`, `/settings`, `/trees/<t>/profile` | `/account` |
| `/trees/<t>/trees`, `/manage/trees` | `/admin` for the install owner, else `/account#trees` |
| `/trees/<t>/privacy` | `/trees/<t>/settings#visibility` |

On a tree host, `/account` and `/admin` are install-wide and go to the app host, as `/settings` did.

### One save model

- A checkbox, radio or select saves on change and says so in a polite live region or a toast.
- A text field saves with an explicit button.
- A change with consequences for other people confirms first: a member's role, making something
  public, deleting.

## Rejected alternatives

- **Keep the pages under a tree and tidy the menus.** The URL and the tree tabs would still say
  "this tree" on pages that are not about it, and every new setting would face the same choice.
- **One Settings page with tabs per scope.** It puts install controls one click from personal ones
  and needs role-dependent tabs; separate pages make the scope the address.
- **Keep the owner's default view and move it to Tree settings.** It would be in the right place,
  but nobody needs it: links carry their mode and each member can choose.
- **Let any manager publish the tree.** ADR-041 keeps one public tree per install as the install
  owner's call; this ADR moves controls, not rights.

## Consequences

- No role gains or loses a right, except that the per-tree default view is gone for everyone.
- Sub-tree management becomes reachable for every manager, on the tree's own host.
- The backlog's further settings (date format, name order, display defaults) have a home:
  Appearance for the user layer, Site appearance for the site layer.
- Changing a member's role now confirms inline before it applies. Role changes, removals,
  invitations, withdrawn invitations, a newcomer taking up an invitation, and Leave Epoch (one entry
  in each tree left) are written to the audit log in the same batch as the change, and only when it
  happened. They are not undoable, and their summaries name the member,
  never an email, because editors read the log and emails are manager-only (ADR-016).
- e2e and component tests that open Profile, Settings, Privacy or the Trees page by address change
  with them.

## Amendment: a starting person per tree

- Account › My trees gains **Start at** per tree (`tree_memberships.home_person_id`, still
  `PUT /api/trees/[id]/home-person`): the person a tree opens on when the address has no `focus`.
  The focus resolves as the address, then this person, then the last one viewed, then the tree's
  first. Inside a sub-tree the starting person is skipped, since it may lie outside the lens.
- The column has no foreign key. A person who is merged, deleted or hidden from the member falls
  through exactly as a stale remembered person does.
- Setting it refuses a person the caller cannot see, as if they did not exist. Migration 0043 only
  adds this column; the held drop of `media_items.entity_id` and `trees.default_view_mode` is now a
  hand-written 0044 (backlog), so the "dropped by migration 0043" line above reads 0044 once it
  lands.
