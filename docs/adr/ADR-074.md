# ADR-074: GEDZIP import and export with media, staged in R2 and processed by Workflow

## Status
Draft. Not started; no phase is built.

## Context

GEDCOM 7.0's GEDZIP format bundles a `gedcom.ged` dataset with media files in a single `.gdz` archive. Epoch imports a `.gdz` by unpacking its `gedcom.ged` and ignoring every other entry, and exports a `.gdz` holding `gedcom.ged` alone (ADR-036). Importing a `.gdz` with photos loses them, and files uploaded in Epoch never leave through GEDCOM.

Today a large import (decoded text over 2 MB, `LARGE_IMPORT_BYTES`) is decoded in the request, staged to R2 as `.ged` text under `staging/`, and sent to `GEDCOM_IMPORT_QUEUE`, whose consumer imports it. The upload is a multipart form bounded by `MAX_IMPORT_BYTES` (25 MB), parsed in memory, and the dataset by `MAX_DATASET_BYTES` (50 MB). The queue path has no job record, so the client cannot ask whether a queued import finished or why it failed. Export already runs as a Workflow (ADR-040); a tree over `LARGE_EXPORT_INDIVIDUALS` (5,000 people) always goes there.

Both paths hold a whole dataset in the Worker's 128 MB isolate. Adding media to either would breach it. Other Cloudflare limits that shape this: ~1,000 subrequests per invocation, 128 KB per queue message, 1 MiB per Workflow step result.

## Decision

**Process `.gdz` archives as objects in R2.** Import and export run as Workflow steps, each processing a small batch and returning only ids and counts. Import stages the archive, imports the dataset first, then media in batches of 25–50 entries per step. Export writes media and dataset as independent segments, which the download streams in order behind a final zip directory.

The four-phase rollout:

1. **Phase 1 (foundation):** Replace the queue consumer with a `GedcomImportWorkflow`, for the same imports the queue takes today (over 2 MB). Add an `import_job` table so a client can read an import's status and failure.
2. **Phase 2:** Import a `.gdz` from an upload session, resolving its media into the files the dataset names. Add `media_items.gedcom_path`.
3. **Phase 3:** Export a `.gdz` with media, written as segments.
4. **Phase 4:** Model `OBJE` so imported files attach to their owners. Requires the backlog's "Media records" item.

### Phase 1: Large import to Workflow

**The upload is unchanged.** `POST /api/import` keeps its form (`file`, `treeId`, `treeName`, `mode`, `mergeDuplicates`), its 25 MB bound and the 2 MB threshold. A `.gdz` is still accepted and still yields its dataset only, as ADR-036 built; Phase 1 must not regress it. The staged object stays the decoded `.ged` text under `staging/`, so the per-tree staging cap and the `staging/` lifecycle rule (ADR-040) still apply.

**Migration** (expand, its own migration, deployed before code reads it): an `import_job` table with `id` (uuid, PK), `tree_id`, `r2_object_key`, `status` (`pending`, `running`, `complete`, `failed`), `result` (JSON counts), `error`, `created_by`, `created_at`, `updated_at`. Index on `(tree_id, created_at)`.

**The route** writes the `import_job` row, stages the text and creates a `GedcomImportWorkflow` instance whose id is the job id, in place of `queue.send`. It returns `202 { status: 'queued', treeId, jobId }`.

**Workflow steps.**
- **Dataset step:** read the staged text, check the tree and the requester's role (as `requireExporter` does for export), then run the import. Return counts only.
- **Media steps:** none until Phase 2.
- **Close:** `run()` wraps the steps in `try`/`catch`. On success the last step marks the job `complete` with its counts; when a step exhausts its retries, the catch marks it `failed` with the error. Either way the staged object is deleted.

**Job status.** `GET /api/import/:jobId` returns `{ status, progress?, result?, error? }`, checked against the job's tree. The import screen polls it. While a `.gdz` import runs, `progress` is `{ done, total }`: entries handled of those in the archive, written by each media step. It is held in the job row's `result` column until `complete` overwrites it (shortcut: two numbers did not justify a migration; give it its own columns if more is ever reported).

**The queue is retired, not kept beside the Workflow.** Workflow steps retry on their own and a failed instance is recorded on its job, so there is no dead-letter queue. The `GEDCOM_IMPORT_QUEUE` producer and consumer are removed only after the queue has drained following the deploy, so a message sent by the old code is still consumed (expand-and-contract).

### Phase 2: Media from `.gdz`

**Built (tasks 3.3 and 3.5).** The archive goes up through an upload session (`gedzip_import`, chunked, staged under `staging/uploads/<treeId>/<sessionId>`), not as one raw body. Those bytes are outside `MAX_STAGED_BYTES_PER_TREE`, which counts only `staging/gedcom-<treeId>-*.ged`; `MAX_GEDZIP_UPLOAD_BYTES` caps the session. `POST /api/uploads/:id/import` with `{ mode, shouldMergeDuplicateFamilies }` starts the import: the session must be complete and belong to the caller, who needs `tree:import` on the session's tree. The Workflow payload carries the session's key (never one the client names) and `isArchive`; the steps refuse any key that is not under that tree's `staging/uploads/` folder. `media_items.gedcom_path` and its index exist (ADR-082).

**Steps** (`GedzipImportService`, called from `GedcomImportWorkflow`; each re-checks `tree:import` for the requester and throws before any write).
- **Dataset step:** reads the central directory from R2, inflates `gedcom.ged` under `MAX_DATASET_BYTES` and imports it through `runImport`, which creates objects and unresolved files (ADR-082).
- **Media steps** (`import-media-N`): each re-reads the directory and handles up to `MEDIA_BATCH_ENTRIES` (100) entries or `MEDIA_BATCH_BYTES` (256 MiB), whichever comes first; one larger entry runs alone. The count keeps a step near 500 of its 10,000 subrequests; the bytes keep the JavaScript CRC-32 (200-400 MB/s) to a second or two of the 30 s CPU default. A step returns a cursor and seven small counts, far under the 1 MiB result limit. For each entry it resolves the tree's unresolved files whose `FILE` resolves to it (`resolveFileReference`), streaming `openEntry` through a `FixedLengthStream` into `media/<treeId>/<fileId>.<ext>` and setting `r2_object_key`, `size_bytes`, `crc32` (verified by the reader), the sniffed `mime_type` and `status` null; `sha256` is left to the hourly fill. An entry no `FILE` names becomes a detached object with one resolved file whose `gedcom_path` is the entry name; its id is a hash of the tree id and the name, so a retry reuses the same key. A file with unresolved `FILE`s on `file:` or web addresses stays unresolved. Audio, video and WebVTT are stored download-only; a name claiming an image or PDF whose bytes are not one is skipped. Rows are written directly, with no change log, like the rest of import.
- **Idempotence:** a retried step finds resolved files and existing detached objects (by path) and skips them, and a fixed key makes a re-put overwrite itself. Counts are those of the attempt that succeeded, so a step retried after partly writing reports only what it did the second time.
- **Close step:** deletes the archive and counts files still unresolved. The job's result is the dataset's counts plus `media`: `resolved`, `unresolved`, `detachedAdded`, `skippedByType`, `overCap`, `overQuota`, `unreadable` (an entry that failed its size or checksum). A bad archive fails the job with a fixed message; the `finally` step still deletes the archive on every other end.
- **Preview and screen (3.4):** `GET /api/uploads/:id/preview` has the start route's access (the session's creator, `tree:import`, status `complete`; a second look after the import is a 409) and the same rate budget. It reads the central directory and `gedcom.ged` only and answers the usual dataset preview plus `media`: `entryCount` and `totalBytes` of the entries that will be stored, `quotaRemainingBytes`, `resolvableFiles`, `unresolvedFiles` (no matching entry, a web address, a path on another machine, or an entry that will be skipped), `extraEntries` (no `FILE` names them), `skippedByType`, `overCap`. A `.gdz` picked with a tree selected goes up through `startUpload` (purpose `gedzip_import`, with `UploadProgress` inside the confirm modal), is previewed in that modal, and on confirm calls the start route and polls the job, showing "Storing files: N of M handled." The result reads, for example, "Media: 4 files stored (2 not linked to any record); 3 files are still missing; 1 skipped as a type Epoch does not accept." With no tree selected (the import would create one) a `.gdz` still takes the plain `.ged` path and imports its dataset only, because an upload session belongs to a tree. The preview counts a merge's already-stored files as if new.
- **Known limits:** two entries claiming one `FILE` each get their own copy of the object (shortcut: share the object if duplicates show up); two starts of one session are not prevented; `DecompressionStream('deflate-raw')` was exercised only under Node (the fflate fallback is for tests), not yet on the Workers runtime.

### Phase 3: Export with segments

- **Dataset segment:** the export workflow writes `gedcom.ged` with one `OBJE` record per exported file (`FILE media/<name>`, `FORM <media type>`, `TITL`), pointed to from each record that `media_links` attaches it to. A detached file gets a record and no pointer.
- **Media segment steps:** each takes a batch of the tree's files and writes them as stored (uncompressed) zip entries with the data-descriptor flag, so CRC and size follow the data. Each segment is its own object under the export's key (ADR-040's `exports/<treeId>-<token>-<clientUuid>`), returning its size and its entries' CRCs and sizes.
- **Tail step:** compute every entry's offset from the segment sizes, and write the central directory and end-of-central-directory record as the last segment.
- **Download:** stream the segment objects in order, with `Content-Length` as their sum. The segments are never merged into one R2 object. They sit under `exports/`, so the 24-hour expiry and lifecycle rule (ADR-040) remove them.
- **Built (tasks 4.2, 4.3).** `GdzExportService` runs three kinds of step, each authorising again: `dataset` (segment 0, `gedcom.ged` deflated, plus the file plan), `media-<n>` (one segment per batch) and `tail` (central directory and end record as the last segment, then the manifest). A step returns only a byte length; a segment's start offset is the sum of the lengths before it. Each segment's zip entry records sit beside it as `part-<n>.json`, because 50,000 records exceed a step result's 1 MiB, and the tail reads them. The file plan (names, R2 keys, sizes, CRCs, batch ranges) is `plan.json`, so the media steps never recompute names; the same `planArchiveFiles` mapping writes the dataset's `FILE` lines and the entry names.
- **Batch bound:** at most 100 files or 64 MiB per media step (a larger file gets its own). 100 files is about 200 R2 calls (a `head` to skip a deleted file and take the size, then a `get`), far under 10,000 subrequests, and 50,000 files is 500 steps, under the 1,024 a Workflow instance may run. Bytes stream through, so memory and CPU are not the limit; the bound keeps a retry cheap. The CRC from `media_items.crc32` makes a complete local header; without it the writer computes it and writes a data descriptor.
- **Snapshot and retry:** copying the bytes is the snapshot. A file gone at copy time is left out of the segment and the directory (its `FILE` line stays, and re-imports as unresolved). Keys come from the instance, so a retried step overwrites its own object with identical bytes.
- **Caps:** media is written only up to 10,000 people and 50,000 resolved files; above either the `.gdz` is the dataset alone, through the same segments. The writer still refuses 4 GiB or 65,535 entries.
- **Choosing it:** instance token `g7m` and `includeMedia` on `POST /api/export` (7.0 `.gdz` only). It always runs as a Workflow, even for a small tree.
- **Download:** `openSegmentedExport` streams segments in order through `fixedLengthBody`, with `Content-Length` their sum; a missing or resized segment errors the stream. Not yet exercised on the real Workers runtime: `FixedLengthStream` over several R2 bodies, and a media step's R2 `put` of a streamed body.
- 5.5.1 exports stay `.ged` and dataset-only (ADR-036).

### Phase 4: OBJE modelling

Deferred. Requires the backlog's "Media records" item. Until then an imported `OBJE` stays a retained line, and its file is matched to it only through `gedcom_path`.

## Constraints and trade-offs

- **R2 multipart wants equal-size parts.** All parts but the last must be the same size, and zip entries are not. Segments avoid this: each is a separate object, concatenated by the download.
- **No Zip64.** A tree's media is capped at 2 GiB (`MAX_TREE_MEDIA_BYTES`) and the dataset at 50 MB, well under the 4 GiB limit. An export with media is refused above 50,000 files, under the 65,535-entry limit. Zip64 is needed only if one of those caps is raised.
- **Media only in 7.0 `.gdz`.** A 7.0 export carries media only when the tree is under the cap (10,000 people, 50,000 files); above it the `.gdz` holds the dataset alone, as today.
- **Deterministic file ids.** A hash of `(jobId, entryPath)` makes retries idempotent. A second import of the same archive is a new job and so creates new files; the user deletes the first set to avoid duplicates.
- **Chunked uploads checksum as they stream.** Parts arrive concurrently and out of order, so `PUT …/parts/:n` computes each part's CRC-32 while it streams to R2 and keeps it beside the etag in `upload_session.parts_json` (a bare etag string, from a session opened earlier, still reads). Recording a media upload folds the part CRCs in part order with `crc32Combine` into `media_items.crc32`; a session with a part lacking a CRC leaves it null. SHA-256 cannot be folded this way, so a chunked upload leaves it null for the checksum fill (ADR-082).
- **Detached files first.** Attaching files to their `OBJE` owners needs `OBJE` modelled (Phase 4). Until then imported media can be found and attached by hand, and is not shown in the tree view.

## Consequences

- Every large import has a job record: its status, counts and failure reason can be read back.
- Media files never pass through the isolate whole: they move between R2 objects one entry at a time. The dataset is still parsed in memory, bounded by `MAX_DATASET_BYTES`.
- Media in `.gdz` files is imported and stored in Epoch.
- Exports can carry media, so files survive a round trip; their links to owners do once Phase 4 lands.

## Rejected alternatives

- **Keep the queue consumer:** steps cannot retry independently, and there is no record of an import's outcome.
- **Unpack the archive in memory in the dataset step:** breaches the 128 MB isolate once media is added.
- **Merge segments into one R2 object on export:** extra R2 writes and reads, and slower.
- **Attach imported files to `OBJE` owners now:** needs `OBJE` modelling, which is planned but not built.

## Platform limits (checked 2026-10-31)

Paid Workers plan. Documented figures only; where the docs are silent it says so.

- **Subrequests:** 10,000 per invocation, up to 10 million via `limits.subrequests`. Calls to R2, KV and D1 count. Workflows list the same figure per step. https://developers.cloudflare.com/workers/platform/limits/, https://developers.cloudflare.com/workers/wrangler/configuration/, https://developers.cloudflare.com/changelog/2026-02-11-subrequests-limit
- **CPU time:** 30 s default, 5 min maximum via `limits.cpu_ms`. Workflow steps: 30 s default, configurable to 5 min, wall time unlimited. Memory is 128 MB per isolate; the docs give no Workflow figure. https://developers.cloudflare.com/workers/platform/limits/, https://developers.cloudflare.com/workflows/reference/limits/
- **Workflows:** 10,000 steps per instance (up to 25,000), 1 MiB per step result, 1 GB state per instance, 10,000 retries per step, 50,000 concurrent instances per account, 300 creations per second. https://developers.cloudflare.com/workflows/reference/limits/
- **Request body:** set by the zone's plan, not the Workers plan: 100 MB Free and Pro, 200 MB Business, Enterprise up to 5 GB. The docs do not mention Access; it fronts the same zone, so assume the limit applies. https://developers.cloudflare.com/workers/platform/limits/
- **R2 multipart:** parts 5 MiB to 5 GiB, all but the last the same size, at most 10,000 parts. An incomplete upload is aborted after 7 days by default. A lifecycle rule can set this: `wrangler r2 bucket lifecycle add <bucket> <name> <prefix> --abort-multipart-days <n>`. https://developers.cloudflare.com/r2/objects/multipart-objects/, https://developers.cloudflare.com/r2/buckets/object-lifecycles/, https://developers.cloudflare.com/workers/wrangler/commands/r2/
- **R2 binding:** `get(key, { range })` takes an offset and length, or a suffix. `uploadPart` and `put` accept a `ReadableStream`. The docs never say whether the stream needs a known length, so wrap the request body in a `FixedLengthStream` sized from `Content-Length`. https://developers.cloudflare.com/r2/api/workers/workers-api-reference/, https://developers.cloudflare.com/workers/runtime-apis/streams/transformstream/
- **Streams:** `FixedLengthStream` is documented. `crypto.subtle.digest` is one-shot; `crypto.DigestStream` hashes a stream (SHA-256 among others). The `deflate-raw` format for `CompressionStream` and `DecompressionStream` appears only in the type definitions; the docs pages do not list formats, so test it. https://developers.cloudflare.com/workers/runtime-apis/web-crypto/
- **Local R2:** `wrangler dev` runs R2 against local storage by default. The docs do not say whether multipart uploads work there; test before relying on it. https://developers.cloudflare.com/r2/api/workers/workers-api-usage/

## Open questions

- ~~What is the subrequest limit per Workflow step?~~ Answered 2026-10-31: 10,000 on the paid plan, raised from 1,000 in February 2026, and configurable up to 10 million with `limits.subrequests`. R2 and D1 binding calls count. The docs list it per Workflow step ("per request"), though they never say a step is its own invocation. At about five subrequests per file (range read, put, `media_items` insert, with margin) it allows hundreds of files per step, so it does not bound the batch. CPU time, the 1 MiB step result and retry cost do; see "Platform limits". The "~1,000 subrequests" in Context is out of date.
- ~~Should the import and export screens show progress per media batch, or only the job's final status?~~ Import: yes, as above. Export: undecided.
