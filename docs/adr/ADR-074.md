# ADR-074: GEDZIP import and export with media, staged in R2 and processed by Workflow

## Status
Draft. Not started; no phase is built.

## Context

GEDCOM 7.0's GEDZIP format bundles a `gedcom.ged` dataset with media files in a single `.gdz` archive. Epoch imports a `.gdz` by unpacking its `gedcom.ged` and ignoring every other entry, and exports a `.gdz` holding `gedcom.ged` alone (ADR-036). Importing a `.gdz` with photos loses them, and files uploaded in Epoch never leave through GEDCOM.

Today a large import (decoded text over 2 MB, `LARGE_IMPORT_BYTES`) is decoded in the request, staged to R2 as `.ged` text under `staging/`, and sent to `GEDCOM_IMPORT_QUEUE`, whose consumer imports it. The upload is a multipart form bounded by `MAX_IMPORT_BYTES` (25 MB), parsed in memory, and the dataset by `MAX_DATASET_BYTES` (50 MB). The queue path has no job record, so the client cannot ask whether a queued import finished or why it failed. Export already runs as a Workflow (ADR-040); a tree over `LARGE_EXPORT_INDIVIDUALS` (5,000 people) always goes there.

Both paths hold a whole dataset in the Worker's 128 MB isolate. Adding media to either would breach it. Other Cloudflare limits that shape this: ~1,000 subrequests per invocation, 128 KB per queue message, 1 MiB per Workflow step result.

## Decision

**Process `.gdz` archives as objects in R2.** Import and export run as Workflow steps, each processing a small batch and returning only ids and counts. Import stages the archive, imports the dataset first, then media in batches of 25–50 entries per step. Export writes media and dataset as independent segments, which the download streams in order behind a final zip directory.

The four-phase rollout:

1. **Phase 1 (foundation):** Replace the queue consumer with a `GedcomImportWorkflow`, for the same imports the queue takes today (over 2 MB). Add an `import_job` table so a client can read an import's status and failure.
2. **Phase 2:** Stage a `.gdz` upload as raw bytes and import its media as detached files. Add `media_items.gedcom_path`.
3. **Phase 3:** Export a `.gdz` with media, written as segments.
4. **Phase 4:** Model `OBJE` so imported files attach to their owners. Requires the backlog's "Media records" item.

### Phase 1: Large import to Workflow

**The upload is unchanged.** `POST /api/import` keeps its form (`file`, `treeId`, `treeName`, `mode`, `mergeDuplicates`), its 25 MB bound and the 2 MB threshold. A `.gdz` is still accepted and still yields its dataset only, as ADR-036 built; Phase 1 must not regress it. The staged object stays the decoded `.ged` text under `staging/`, so the per-tree staging cap and the `staging/` lifecycle rule (ADR-040) still apply.

**Migration** (expand, its own migration, deployed before code reads it): an `import_job` table with `id` (uuid, PK), `tree_id`, `r2_object_key`, `status` (`pending`, `running`, `complete`, `failed`), `result` (JSON counts), `error`, `created_by`, `created_at`, `updated_at`. Index on `(tree_id, created_at)`.

**The route** writes the `import_job` row, stages the text and creates a `GedcomImportWorkflow` instance whose id is the job id, in place of `queue.send`. It returns `202 { status: 'queued', treeId, jobId }`.

**Workflow steps.**
- **Dataset step:** read the staged text, check the tree and the requester's role (as `requireExporter` does for export), then run the import. Return counts only.
- **Media steps:** none until Phase 2.
- **Close:** `run()` wraps the steps in `try`/`catch`. On success the last step marks the job `complete` with its counts; when a step exhausts its retries, the catch marks it `failed` with the error. Either way the staged object is deleted.

**Job status.** `GET /api/import/:jobId` returns `{ status, result?, error? }`, checked against the job's tree. The import screen polls it.

**The queue is retired, not kept beside the Workflow.** Workflow steps retry on their own and a failed instance is recorded on its job, so there is no dead-letter queue. The `GEDCOM_IMPORT_QUEUE` producer and consumer are removed only after the queue has drained following the deploy, so a message sent by the old code is still consumed (expand-and-contract).

### Phase 2: Media from `.gdz`

**Upload the archive raw.** A `.gdz` with media can exceed both the 25 MB form bound and the isolate, and a multipart form must be buffered to be parsed. So a `.gdz` is sent as the request body itself, with the import options as query parameters, and streamed into R2 under `staging/` by its `Content-Length`. Its own size cap replaces `MAX_IMPORT_BYTES` for this path; the staging cap per tree (`MAX_STAGED_BYTES_PER_TREE`) is raised for it or counted separately. A `.gdz` with no media keeps working through either upload.

**Migration** (expand): `media_items.gedcom_path` (text, nullable), the entry's path inside the archive. Index on `(tree_id, gedcom_path)`.

**Steps.**
- **Dataset step:** read the archive's central directory, range-read and inflate `gedcom.ged` with the existing bounded code (`MAX_DATASET_BYTES`), then import as in Phase 1.
- **Media steps:** each takes a batch of entries from the central directory. For each: range-read from R2, inflate, check its media type and size against the tree's media quota (`MAX_TREE_MEDIA_BYTES`), write the object, and insert a `media_items` row with `gedcom_path` set. No `media_links` row is written, so the file is detached (ADR-050) and visible to editors and above. Return `[count, totalBytes]`.
- **Ids are deterministic:** a file's id is a hash of the job id and the entry's path, so a retried step overwrites the same object and row.

### Phase 3: Export with segments

- **Dataset segment:** the export workflow writes `gedcom.ged` with one `OBJE` record per exported file (`FILE media/<name>`, `FORM <media type>`, `TITL`), pointed to from each record that `media_links` attaches it to. A detached file gets a record and no pointer.
- **Media segment steps:** each takes a batch of the tree's files and writes them as stored (uncompressed) zip entries with the data-descriptor flag, so CRC and size follow the data. Each segment is its own object under the export's key (ADR-040's `exports/<treeId>-<token>-<clientUuid>`), returning its size and its entries' CRCs and sizes.
- **Tail step:** compute every entry's offset from the segment sizes, and write the central directory and end-of-central-directory record as the last segment.
- **Download:** stream the segment objects in order, with `Content-Length` as their sum. The segments are never merged into one R2 object. They sit under `exports/`, so the 24-hour expiry and lifecycle rule (ADR-040) remove them.
- 5.5.1 exports stay `.ged` and dataset-only (ADR-036).

### Phase 4: OBJE modelling

Deferred. Requires the backlog's "Media records" item. Until then an imported `OBJE` stays a retained line, and its file is matched to it only through `gedcom_path`.

## Constraints and trade-offs

- **R2 multipart wants equal-size parts.** All parts but the last must be the same size, and zip entries are not. Segments avoid this: each is a separate object, concatenated by the download.
- **No Zip64.** A tree's media is capped at 2 GiB (`MAX_TREE_MEDIA_BYTES`) and the dataset at 50 MB, well under the 4 GiB limit. An export with media is refused above 50,000 files, under the 65,535-entry limit. Zip64 is needed only if one of those caps is raised.
- **Media only in 7.0 `.gdz`.** A 7.0 export carries media only when the tree is under the cap (10,000 people, 50,000 files); above it the `.gdz` holds the dataset alone, as today.
- **Deterministic file ids.** A hash of `(jobId, entryPath)` makes retries idempotent. A second import of the same archive is a new job and so creates new files; the user deletes the first set to avoid duplicates.
- **Detached files first.** Attaching files to their `OBJE` owners needs `OBJE` modelled (Phase 4). Until then imported media can be found and attached by hand, and is not shown in the tree view.

## Consequences

- Every large import has a job record: its status, counts and failure reason can be read back.
- Media files never pass through the isolate whole: they move between R2 objects one entry at a time. The dataset is still parsed in memory, bounded by `MAX_DATASET_BYTES`.
- Media in `.gdz` files is imported and stored in Epoch.
- Exports can carry media, so files survive a round trip; their links to owners do once Phase 4 lands.

## Rejected alternatives

- **Keep the queue consumer:** steps cannot retry independently, and there is no record of an import's outcome.
- **Unpack the archive in memory in the dataset step:** breaches the 128 MB isolate once media is added.
- **Merge segments into one R2 object on export:** extra R2 writes and reads, and slower.
- **Attach imported files to `OBJE` owners now:** needs `OBJE` modelling, which is planned but not built.

## Open questions

- What is the subrequest limit per Workflow step? (1,000 is assumed here; verify against the docs.) It bounds the media batch size.
- Should the import and export screens show progress per media batch, or only the job's final status?
