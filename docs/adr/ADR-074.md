# ADR-074: GEDZIP import and export with media, staged in R2 and processed by Workflow

## Status
Draft. Phase 1 starts as a feature branch. The complete four-phase build is not yet committed.

## Context

GEDCOM 7.0's GEDZIP format bundles a `gedcom.ged` dataset with media files in a single `.gdz` archive. Epoch currently ignores all entries except the dataset on import, and writes only the dataset on export. Importing a `.gdz` with photos loses them, and files uploaded in Epoch never leave through GEDCOM.

The current import path holds the whole dataset in memory (`MAX_DATASET_BYTES` = 50 MB), and the export path holds the whole tree (`LARGE_EXPORT_INDIVIDUALS` = 5,000 threshold). Both fit in the Worker's 128 MB isolate, but adding media to the path would breach it. Cloudflare's limits: 128 MB memory, ~1,000 subrequests per invocation, 128 KB per queue message, 1 MiB per Workflow step result.

## Decision

**Process `.gdz` archives as objects in R2.** Import and export through Workflow steps, each processing a small batch and returning only ids/counts. Import stages the archive and imports the dataset first, then media in batches of 25–50 entries per step. Export writes media and dataset as independent segments, stitched into a valid zip by a final step.

The four-phase rollout:

1. **Phase 1 (foundation):** Move large `.ged` import (>2 MB) onto the R2 → Workflow path. Add `import_job` table for status, with a DLQ for failed steps. Unblock #2 and #3 from the audit.
2. **Phase 2:** Import `.gdz` media as detached files. Add `media_items.gedcom_path` (expand-only migration). Link files by filename inside the archive.
3. **Phase 3:** Export with segments. Write independent `exports/<id>/seg-N` objects, then a final tail with the zip directory. Download streams them in order.
4. **Phase 4:** Model OBJE so imported files attach to their owners. Requires the backlog's "Media records" item.

### Phase 1: Large import to Workflow

**Migrate the 2 MB threshold.**
- Migrations `0040` (expand): add `import_job` table with columns: `id` (uuid, PK), `treeId`, `r2ObjectKey`, `status` ('pending', 'running', 'complete', 'failed'), `result` JSON (counts), `createdAt`, `updatedAt`, `createdBy`. Index on `(treeId, createdAt)`.
- Replace the queue consumer with a Workflow entry `GedcomImportWorkflow`.

**Upload to R2 without buffering.**
- `POST /api/import` accepts only a `.ged` file (single part), no form data. Sends multipart parts directly to R2 via `bucket.multipartUpload`. Returns `{ status: 'queued', treeId, jobId }`.
- For `.gdz`, return `413 not_yet_implemented` (can be checked by magic bytes or extension).

**Workflow steps.**
- **Step 1 (dataset):** Read and decompress `gedcom.ged` with the existing bounded code. Parse, check the tree and user role, then run `importFile`. Return counts only.
- **Step 2+ (media, when Phase 2 lands):** Each step reads a batch of entries from the zip's central directory. For each: range-read from R2, inflate, validate, write to `media/<tree>/<id>.<ext>`. Return `[count, totalBytes]`.
- **Final step (onFailure or explicit):** Mark the job `complete` or `failed`. Delete the staged archive from R2.

**Job status.**
- `GET /api/import/:jobId` returns `{ status, result?, error? }`.
- The import route polls this instead of the queue.

**DLQ.**
- Configure `GEDCOM_IMPORT_QUEUE` consumer with a DLQ. A step that exhausts retries marks the job `failed`.

### Phase 2: Media from `.gdz`

- Migrations `0041` (expand): add `media_items.gedcom_path` (text, nullable). Index on `(treeId, gedcom_path)`.
- Extend the zip read to enumerate media entries.
- Each media step: batch-read entries, write to R2, create detached `media_items` rows with `gedcom_path` set to the filename in the archive.
- Link is deterministic: id is a hash of the job id and entry name, so retries overwrite the same key.

### Phase 3: Export with segments

- Each segment is a stored (uncompressed) zip entry. Entries use the data-descriptor flag: CRC and size follow the data.
- **Segment step:** Take a batch of the tree's files. For each, write `FILE media/<name>`, `FORM <media type>`, `TITL` as OBJE records, then write the media files themselves as zip entries.
- **Tail step:** Compute cumulative offsets from segment sizes. Write the central directory and end-of-central-directory record. Merge into one `exports/<id>.gdz` object (or keep as `.ged` for 5.5.1).
- **Download:** Stream segment objects in order, with `Content-Length` as the sum. No merging in R2.

### Phase 4: OBJE modelling

Deferred. Requires the backlog's "Media records" item.

## Constraints and trade-offs

- **R2 multipart requires equal-size parts.** Segments avoid this. Each segment is a separate object, and they're concatenated in the download.
- **Zip64 deferred.** The tail step must handle >65,535 entries and >4 GB, but it's written when the first large export is seen.
- **Media only in `.gdz`.** 5.5.1 exports stay dataset-only. A 7.0 export can carry media, but only if the tree is under a size cap (e.g., 10,000 people, 50,000 files).
- **Deterministic file ids.** A hash of `(jobId, entryName)` makes retries idempotent. A second import of the same archive creates the same ids; the user must delete the first if they want to re-import.
- **Detached files first.** Attaching to OBJE owners requires modelling OBJE, which is deferred. For now, imported media is available but not linked in the tree view.

## Consequences

- Large imports no longer buffer the dataset in memory; they move it through R2.
- Media in `.gdz` files is imported and stored in Epoch.
- Exports can carry media, making round trips lossless for the first time (pending Phase 4 for OBJE links).
- The pipeline is observable: job status, segment counts, and failure reasons are recorded.

## Rejected alternatives

- Keep the queue consumer: steps can't retry independently, and state is harder to track.
- Stream the zip into memory during the dataset step: breaches the 128 MB limit once media is added.
- Merge segments into one object in R2 on export: the extra R2 writes and reads are slower.
- Attach imported files to OBJE owners immediately: requires OBJE modelling, which is planned but not yet built.

## Open questions

- What is the actual Cloudflare limit for subrequests per step? (Used 1,000 here; verify against docs.)
- Should Phase 3 handle Zip64 on first delivery, or defer it?
- Is the segment-concatenation download observable enough, or should the UI show progress per segment?
