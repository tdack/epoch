# ADR-050: A file's owner lives in D1, not its key; the Files manager (amends ADR-039, extends ADR-041)

## Status

Implemented

- **Status:** built on `claude/media-management-file-system-0f02e1` on 2026-10-14 and deployed. Migration 0029 must be applied before the code is deployed. It rebuilds `media_items` and fills the new columns with defaults, and nothing references `media_items`, so the code it replaces reads only columns it already had. Checked by unit and route tests for the key parser, the read path, the row operations, tree deletion, the unlinked scan, the listing and the Files page.
- **Context:** a file's owner was embedded in its R2 key (`media/<treeId>/<entityId>/<uuid>.<ext>`). A person merge moved the row but not the key, so a restricted viewer of the surviving person got a false 404, because the read check parsed the old id from the key. Moving or detaching a file, or deleting its owner, would have meant copying or removing the bytes. The Files manager needed attach, detach, move and delete that never touch the bytes.
- **Decision:**
  - **Ownership is the row.** New uploads are keyed `media/<treeId>/<mediaId>.<ext>`: the key names the file, not its owner. `media_items.entity_id` names the owner, a person or a partnership, or is null for a detached file. Legacy keys (`media/<treeId>/<entityId>/<file>`) are still read and are not moved. `parseMediaKey` accepts both shapes and reads only the tree from them.
  - **Read order.** `requireRead` parses the tree from the key, runs the tree-scope check, and only then looks up the row by `(tree_id, r2_object_key)`. A caller outside the tree is refused before the row is read, so a key's existence is not revealed. No row is a 404. The owner comes from the row.
  - **One visibility rule.** `canReadRow` decides for both `requireRead` and the Files list, so the two cannot disagree. Unrestricted roles see every file. A restricted viewer sees a file only when every person it hangs off is visible; a partnership's files need every partner visible, and a partnership with no partners is hidden. A detached file is shown to editors and above only.
  - **Nullable owner.** A detached file stays in the tree until someone attaches it. Attach needs a person or partnership in the same tree. Move is a detach and an attach in one request, within one tree.
  - **Columns (migration 0029).** `size_bytes` (null until backfilled), `uploaded_by` (no foreign key, as in `change_log`), `version` (default 1), `updated_at`, and the index `(tree_id, r2_object_key)`. The upload writes the object before its row, and deletes the object again if the row write fails.
  - **Logged changes.** Rename, attach, detach and move are row operations in the mutation runner, so the change log records them and undo reverses them. Each checks `version`, and a stale version answers 409. `size_bytes` and `uploaded_by` are derived columns, left out of row images, so an undo image written before 0029 still matches its row.
  - **Delete is outside the log.** Delete removes the row first, then the object. If the object cannot be removed, the file is still gone for everyone, the orphaned object is left for the unlinked scan, and the response says so. Delete is not undoable. An earlier change that touches the row refuses its undo once it is gone, and the confirm dialog says so.
  - **Unlinked scan.** One R2 listing, and an object is unlinked when no row in its tree names its key. Objects younger than an hour are skipped, because an upload writes its object before its row. Only managers and owners can list or delete, in trees they may manage, and deletion works on a fresh listing rather than a list the client sends.
  - **Tree deletion.** The rows go first, which the database cascades. Then the tree's `media/` objects and its staged GEDCOM uploads are swept in batches of up to 1,000 keys. A failed sweep is logged, not thrown, so the leftover bytes have no row and no one can read them.
  - **Person and partnership changes.** Deleting a person, or the last partner of a partnership, and destroying a partnership, detach its files rather than delete them. Undo hangs each file back on its record. Merging two partnerships moves their files to the survivor in the same change.
  - **Roles.**
    - Viewer and contributor browse and preview files attached to people they can see. They have no actions.
    - Editor (`media:manage`) uploads, renames, attaches, detaches and moves, and deletes the files they uploaded. A file with no recorded uploader, which is every file from before 0029, is not an editor's to delete.
    - Manager and owner (`media:delete_any`) delete any file, and see the uploader's name.
    - Public visitor and outsiders get no Files page. Uploader names never reach them, as ADR-041 requires.
    - Install owner sees names, sizes, counts and totals for trees they are not in (via `TreeRepository.listAll`), and nothing that would show or change a file there. The install-wide total is shown to the install owner only. This keeps ADR-041's rule that a non-member has no access to a tree's content, and extends it to metadata.
    - Per-tree usage and quota totals are shown to editors and above only.
  - **Quota.** The usage bar is the R2 total for the tree, since that is what an upload refusal enforces. Each file's own size comes from its row, shown as unknown until backfilled.
  - **Preview.** Images preview inline through the serve route (ADR-039). A PDF opens in a new tab (ADR-073).
  - **Size backfill.** `scripts/backfill-media-sizes.mjs` (`npm run db:backfill:media-sizes`) is a one-off, idempotent script. It writes only rows with no size, and never runs on a GET.
- **Rejected alternatives:** copying or renaming R2 objects when a file moves between records (a copy per file, and a window where the key and row disagree); keeping the owner in the key and rewriting keys on merge (the same copy); deleting a deleted person's files (the bytes would be lost and undo could not restore them); letting editors delete any file (a manager's call, as with members in ADR-016); logging deletes in the change log now (undo would have to keep the bytes until the window closed, which is not built).
- **Rollback caveat:** `wrangler rollback` restores the code, never the schema. The previous parser reads a key as `<tree>/<entity>/<file>` and answers 404 for every `media/<treeId>/<mediaId>.<ext>` key. Files uploaded after this deploy are unreachable under the old code until it is deployed again. Roll back only with that in mind, or redeploy this code instead.
- **Consequences:** files from before 0029 have no uploader, so editors cannot delete them, and their sizes show as unknown until the backfill runs. A restricted list reads up to 500 rows per request, and an undo of a pre-0029 `delete_person` can point at an object the unlinked scan has removed. All are recorded in [backlog.md](../backlog.md), with the other open file gaps.
