# ADR-045: Trees have a readable address; the id still works and redirects to it

## Status

Implemented

- **Status:** built on `claude/ui-tweaks-navigation-674a2c` on 2026-10-13 and deployed. Migration 0028.
- **Context:** tree pages were addressed by UUID (`/trees/b8ea1a57-…?focus=…`). The owner wants `/trees/the-windsors?focus=…&mode=rings`, with the id still accepted.
- **Decision:**
  - **`trees.slug`,** nullable text with a unique index. It is made from the name (`slugifyTreeName`: accents dropped, lower-case `a-z0-9` words joined by single hyphens, at most 60 characters) when a tree is created or a GEDCOM import creates one, with `-2`, `-3`… on a clash. A name with nothing Latin in it gets no slug, and the tree keeps its id as its address. A slug can never be shaped like a UUID, so an id and a slug cannot be confused.
  - **The migration backfills** existing trees in SQL, with replacements that approximate `slugifyTreeName`. A repeated name takes the first six characters of its id as a suffix instead of a counter, so the backfill cannot collide with another tree's slug and fail the migration.
  - **The slug is stable.** Renaming keeps it, so bookmarks survive. It changes only when someone who may rename the tree (`tree:update_settings`, or the install owner) edits the Address field in the rename dialog, through `PATCH /api/trees/[id]` with the version check. An empty field gives the slug up. The old slug is not kept as an alias: after a change, links to it stop working, and the dialog says so.
  - **One resolution point on the server.** `treeHandler` turns the address segment into the tree id (`id = ? OR slug = ?`) before the service runs, so no service sees a slug. A segment that names no tree is passed on unchanged and refused exactly as an unknown id is: a stranger gets the same answer for an existing tree's slug, its id, and a slug that names nothing, so a guessable slug reveals no more than an unguessable id did. `tree-slug.test.ts` covers it.
  - **The anonymous page gate (ADR-041)** compares the segment with the public tree's id or slug (`isPublicTreeSegment`), so a slug link to the public tree opens for a visitor who is not signed in.
  - **Links use the slug.** `treePath({ id, slug })` builds every tree address. Components that build links take an optional `treeSlug` prop beside `treeId`, which stays the id for API calls and keys. Without the prop a link falls back to the id, which still works.
  - **The id address redirects.** The tree layout's load answers an address by id (or any non-canonical segment) with a 302 to the same path and query under the slug, so the address bar shows one form. It is not permanent, since a browser would cache a 308 past a later change of slug. Changing the open tree's slug moves the page to its new address rather than reloading the old one.
- **Rejected alternatives:** SvelteKit `reroute` (every link would still need the slug, plus a client-side lookup cache that goes stale when a slug changes); regenerating the slug on rename (breaks bookmarks); keeping old slugs as aliases (a table and a lookup for a case the owner can avoid by not changing the address).
- **Consequences:** deploy the migration before the code. Invitation emails still link by id, which redirects. Each tree API request makes one extra indexed read to resolve the segment.
