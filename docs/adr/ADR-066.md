# ADR-066: Abuse limits are Workers Rate Limiting bindings, not dashboard rules

## Status

Implemented

- **Status:** built on 2026-10-19. No migration. It replaces the rulesets-API setup step that ADR-065 suggested for this item.
- **Context:** the backlog assumed a Worker cannot enforce a rate limit, so `/api/media/upload`, `/api/import` and `/api/csp-report` were left to dashboard rules that nothing in source records or restores. The Workers Rate Limiting binding (`ratelimits` in the wrangler config) counts in the Worker and needs no Durable Object.
- **Decision:**
  - **One binding per endpoint**, in `wrangler.jsonc` and the setup template. `generateDeployConfig` clones the tracked file, so every deploy config carries them with no setup change; they need no provisioning call, and reconcile, doctor and token scopes have nothing to check. `namespace_id` is a number we chose (1001–1003).
  - **Keys:** upload and import by the signed-in user's id; the CSP report by `cf-connecting-ip`, since a report carries no credential. The import preview (PUT) shares the import budget.
  - **Limits, all per 60 seconds:** upload 60, import 10, CSP report 60 (`rate-limit.ts`; a test fails if they differ from `wrangler.jsonc`, because a binding cannot read its own limit). A real user cannot reach them: a folder of photos goes up one at a time, and an import needs a preview and an import per tree.
  - **Over the limit:** `RateLimitedError`, a 429 `{ error, code: 'RATE_LIMITED', details: { retryAfterSeconds } }` with `Retry-After: 60`, checked before the body is read. The client shows `error` as it does for any failure, so the messages are "Too many uploads; try again in a minute" and so on.
  - **A missing binding allows the request** and logs once per binding per isolate: tests and local dev have none, and failing closed would break them.
- **Rejected alternatives:** dashboard rate-limiting rules (not in source, and not restored by setup); a Durable Object counter (exact, but a new resource and a hop on every upload); keying uploads by IP (shared by a household or office).
- **Consequences:** counters are per Cloudflare location and eventually consistent, so the limit bounds abuse and is not exact; a user spread over locations can exceed it a little. The period can only be 10 or 60 seconds. Installs on one account share `namespace_id` counters, which only matters for the CSP report's per-address key. The limits do not stop a user making many trees ([backlog.md](../backlog.md)). Nothing is needed in the Cloudflare dashboard: the bindings arrive with the next deploy.
