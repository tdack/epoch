# ADR-014: Recents and favourites are per-user D1 rows (Phase 3, S7)

## Status

Implemented

- **Context:** The focus box and the tree pages should offer the people a user opened lately and the ones they chose to keep. They could live in the browser (`localStorage`, which Epoch already uses for the remembered focus) or on the server.
- **Decision:** A `person_marks` table (migration 0011, expand-only: a new table and two indexes), one row per `(user, tree, kind, person)` with `kind` `favorite` or `recent` and a `touched_at`. Recents keep the newest 20; a repeat moves the person to the front.
  - **Why the server, not the browser.** A favourite is something a person expects to follow them across their devices and survive clearing site data; `localStorage` does neither, and a private window or blocked storage would silently lose it. The remembered focus stays in `localStorage` because losing it costs nothing.
  - **Keyed by the internal user id.** The plan says "keyed by the stable Access `sub`". `users.id` is the row upserted from that `sub` (`users.access_sub` is unique and never reused), and every other table that belongs to a user (`tree_memberships`, the change log's actor) keys on `users.id`, so a mark uses it too. The `sub` itself stays the only link to Cloudflare Access.
  - **Cascade from the user and the tree, not from the person.** `user_id` and `tree_id` cascade, so deleting a tree or a user removes their marks. `person_id` deliberately has **no foreign key**: a cascade would delete the row outside the logged ops, so deleting a person and undoing it would silently lose their favourite (the reason `person_names.union_id` has none, ADR-013). Reads join `individuals`, so a mark for a person who is gone is not shown, and returns when the person does.
  - **Only `tree:view` is needed**, because a mark changes nothing in the tree; it is not logged and cannot be undone.
  - **A recent is recorded by an explicit `POST` from the page**, never by a `GET` or a load function. `app.html` sets `data-sveltekit-preload-data="hover"`, so a load that logged would record people whose links the pointer merely passed over.
- **Shared in place, not reloaded.** The mark endpoints answer with the user's lists, and the tree layout keeps them in a store the screens update from the response. Invalidating the layout load instead would refetch the tree summary (a linear count) on every person view and, on the tree page, the graph window behind `parent()`.
- **Consequences:** Marks are per user and so not in a GEDCOM export. Nothing prunes marks of people who were deleted for good; the newest-20 rule bounds recents, and favourites are a user's own list. Privacy (Phase 4) reaches marks through the same seam as search: a favourite of a person the user may no longer see must be filtered there.
