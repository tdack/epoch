# ADR-078: Places get a location; maps use Leaflet and OSM tiles, and geocoding uses Photon only

## Status

Implemented

- **Status:** accepted and built on 2026-10-26 (not deployed).

## Context

Places are text on facts, grouped into derived records (ADR-018, ADR-019). Imported `PLAC.MAP`
coordinates sit on each fact (ADR-051), and nothing reads them. webtrees maps places
(webtrees-comparison.md 1.9). The research is in [maps-research.md](../maps-research.md). The owner
wants to stay within free OpenStreetMap (OSM) services and not offer Google as an option.

## Decision

- **A location is its own record, `place_locations`, one row per place record.** It holds:
  - `latitude` and `longitude` in decimal degrees
  - `status`: `confirmed` or `ignored`
  - `source`: `gedcom`, `photon` or `manual`
  - `osm_type`, `osm_id` and `display_name` from the geocoder
  - `version` and `updated_at`

  It is a change-log record table like `subtree` (ADR-062). Setting, clearing or ignoring a
  location is a command, logged, previewed and undoable. The derived `places` table stays
  command-free, as ADR-019 requires. The location's id is its place's id, because a place has at
  most one location. Commands never delete a place record, so a location's place exists. A
  replace-mode import deletes the old place records, and their locations with them.
- **Editors and above set locations** (`record:edit`, which is stricter than the mutation runner's
  default). Restricted viewers never see location ops in the change log, because a location row
  holds a place id, not text that could be checked against what they may see.
- **Geocoding never changes a fact's text.** "Accept and rename" is a second, explicit
  `rewrite_place` in the same review step, with its own preview and undo.
- **The file wins.** Coordinates from a fact's `MAP` seed the place's location with source
  `gedcom`, through a backfill that is safe to re-run. The same seed runs on import. Commands
  accept only `photon` or `manual` as a source. The review screen never offers a geocoder
  suggestion for a place that already has a `gedcom` or `manual` location. An editor's explicit
  set may still replace it. Export is unchanged: `PLAC.MAP` is still the fact's own value.
- **Photon only, through Epoch's Worker.** The browser calls `/api/trees/[id]/geo/search`. The
  route sits under the tree so that the membership check denies by default, and it needs
  `record:create`. The Worker calls Photon (`photon.komoot.io` by default) and sends a fixed
  `User-Agent` that names Epoch. It caches every successful answer in D1, keyed by the Photon URL,
  the normalised query, the language and a rounded bias point. Nominatim is not used. Its policy forbids search as you
  type, and a second service would add a second policy, rate limit and code path for no gain.
  Photon's public server allows only reasonable use with no guarantee. The proxy keeps its own
  throttle, and self-hosting Photon is the fallback.
- **Site settings switch it.** The install owner's `site_settings` hold:
  - whether geocoding is on
  - the Photon base URL
  - the tile URL template, defaulting to `https://tile.openstreetmap.org/{z}/{x}/{y}.png`
  - its attribution

  Turning geocoding off takes effect without a deploy. Moving to a different tile host does not:
  the CSP (ADR-048, `vite.config.ts`) is fixed at build time and allows only the default tile
  host in `img-src`.
- **Only place text leaves Epoch, and only for places that may be shown.** A query sends no
  person, date or tree id. The place-matching job sends only places with a fact by someone the
  living rule treats as dead, or by a public person. Text that looks like a street address (it
  starts with a house number, or the fact has an address) is never sent.
- **Match places is a manager's job** (`tree:update_settings`). `PlaceMatchWorkflow` looks up
  unlocated places on Photon, 10 to a step with a second's pause between steps, at most 2,000 a run,
  one run per tree. Selection uses the tree's own living cutoff, never the public tree's "show
  everyone". Facts of people marked private, and facts with an address, never count. Candidates
  live in `place_match_candidates`. They are working data: not logged, and cleared when a run
  starts. "Accept all High" writes one change per 100 places. With no workflow bound (`vite
  dev`), a run of up to 20 places happens in the request.
- **Maps show what the place list shows.** Markers and cluster counts come from the place list's
  visibility predicates (ADR-018). Living people's residence and census facts are left off maps.
- **Leaflet 2.0, pinned at `2.0.0-alpha.1`.** It suits Epoch's ES-module stack. One component owns
  the map's lifecycle, so moving to a stable release touches one file. The library loads only on
  pages with a map. Clustering is a small grid clusterer (`components/maps/cluster.ts`), not
  `Leaflet.markercluster`, which targets 1.x's global `L`. `@types/leaflet` describes 1.x, so a
  minimal ambient declaration covers only the calls Epoch makes.
- **The Places page load carries the map data**, not a separate endpoint. It reuses the place
  list's visibility query. `RESI` and `CENS` facts count only for people the tree's living rule
  shows as dead or who are marked public, for every viewer, the owner included.

## Consequences

- One more record table for every command's tree load. It is small: one row per located place.
- The Places tab becomes a map with the list beside it. The place page gains a pin and "Set
  location", and the person page a map of the person's facts.
- Photon availability is a dependency with no SLA. When it is off or down, typing still suggests
  the tree's own places and "Pick on map" still works.
- Whether stored and exported OSM coordinates fall under ODbL share-alike is undecided. Until it is
  decided, Epoch credits "© OpenStreetMap contributors" wherever it shows them and does not
  export them.
