# ADR-036: GEDCOM 7.0 is the default export; import detects version and character set; GEDZip

## Status

Implemented

- **Status:** complete; built on 2026-10-09 and deployed. Checked by unit tests, by a 5.5.1-to-7.0 conversion test, and once by hand on the owner's 314-person family file (a webtrees 5.5.1 export). That check covered what this change converts: no `CONC`, `CHAR`, 5.5.1 date syntax, unescaped leading `@`, lowercase enumeration, `RELA` or 5.5.1 `FORM`/`TYPE` remained, all 314 people read back, and 5 hand-typed dates were kept as `PHRASE`. It is not a full 7.0 validation; the gaps are listed below.
- **Context:** the tree menu offered only "Export GEDCOM 5.5.1", although a 7.0 serializer existed. That serializer replayed 5.5.1 lines kept from an import unchanged, so its output was not valid 7.0 (`CONC`, `@#DJULIAN@`, dual years, `SCHMA` listing `FAM` and `INDI`). Imports were read with `File.text()`, which decodes UTF-8 only, so ANSEL and ANSI files (most GEDCOM 5.5 files) lost every accented letter.
- **Decision:**
  - **Import detects, with no choice to make.** The bytes are read, not the text. A GEDZip archive is unpacked to its `gedcom.ged`. A byte-order mark or a UTF-16 null pattern decides first. Otherwise valid UTF-8 is read as UTF-8 whatever `HEAD.CHAR` says, because files that claim ANSI or ANSEL but were saved as UTF-8 are common, and a real legacy file is almost never valid UTF-8. Other bytes are ANSEL when the header says so (LoC MARC-8 table plus GEDCOM 5.5's additions, diacritics moved after their letter, then NFC), and Windows-1252 otherwise. The large-file queue threshold uses the decoded text's length, since a `.gdz` is compressed. Legacy encodings are decoded in code, because the Workers runtime does not promise them in `TextDecoder`. `detectGedcomVersion` answers `5.5`, `5.5.1` or `7.0`. 5.5 is read as 5.5.1, of which it is very nearly a subset.
  - **7.0 is the default export,** in the menu, the API (`format` absent) and `buildGedcomString`. 5.5.1 is offered as the legacy choice. A workflow instance queued earlier with no format still means 5.5.1.
  - **7.0 output is made valid line by line** (`toGedcom7Lines`). `CONC` is folded into the line or `CONT` it continues. Dates are converted: calendar escapes become words, `B.C.` becomes `BCE`, long keywords (`ABOUT`, `CIRCA`) become short ones, and full month names become their codes. Where 7.0 cannot say what the text said, the date gets a `PHRASE`: a dual year becomes its later, Gregorian year with the original as the phrase; `INT date (phrase)` splits into both; and text that is no 7.0 date becomes an empty `DATE` with the text as its phrase. A model text with a leading `@` is already escaped where its line is built (ADR-042); the dialect pass converts only and no longer escapes, and a line kept verbatim is left exactly as the file wrote it. The 5.5.1 structures 7.0 renamed are rewritten: a file's `FORM jpeg` becomes `FORM image/jpeg`, its `FORM.TYPE` becomes `MEDI` (a kind 7.0 lacks, such as webtrees' `certificate`, becomes `OTHER` with the word as `PHRASE`), `ASSO.RELA` becomes `ROLE OTHER` with the word as `PHRASE`, and `STAT`, `RESN`, `ADOP` and `PEDI` are written in capitals. `SCHMA` lists only Epoch's own extension tags, with URIs into `docs/gedcom-extensions.md`.
  - **Stored dates stay 5.5.1 text.** A 7.0 import folds `DATE` plus `PHRASE` back into 5.5.1's `INT date (phrase)` or `(phrase)`, so nothing is lost, and the next 7.0 export splits them out again. A 5.5.1 export writes a 7.0 file's calendar words and `BCE` the 5.5.1 way. `parseDateValue` now sorts `INT date (phrase)` on its date.
  - **GEDZip** (`.gdz`, `application/vnd.familysearch.gedcom+zip`) is offered for 7.0 only. The 7.0 specification ties a GEDZip's version to its dataset's, and 7.0 was GEDZip's first, so a 5.5.1 archive would be non-standard. The service refuses one, and the menu disables the checkbox for 5.5.1. Epoch exports no media yet, so the archive holds `gedcom.ged` alone. `fflate` (already in the lockfile through three.js's types) became a direct dependency.
  - **Menu:** "Export GEDCOM 7.0" exports in one click. The chevron beside it shows the version and a "Compress to .gdz" checkbox (unchecked). The label follows the choice, and the choice resets each time the menu opens, so the one-click export is always 7.0.
- **Known gaps in 7.0 output, deliberately not fixed:** an embedded 5.5.1 `OBJE` (no pointer) is written as it came, though 7.0 wants a pointer to an `OBJE` record; a non-standard tag without an underscore that another program wrote (webtrees' `URL`, `CEME`) is kept, and 7.0 does not allow it; an empty `FORM` stays empty; `RELA` words that 7.0 has a role for (`FATHER`, `GODP`, `WITN`) still go to `OTHER`.
- **Known losses, deliberately not fixed:** 5.5.1's `@#DROMAN@` and `@#DUNKNOWN@` calendars have no 7.0 word, so such a date travels as a phrase. A 5.5.1 text with `@@` in the middle is still stored as written. A line kept verbatim is not escaped, so its own leading `@` stays a lone `@` (ADR-042). A 7.0 file's structures with no 5.5.1 form (`SNOTE` aside, which ADR-029 handles) are kept and written back verbatim in a 5.5.1 export. IBMPC and MACINTOSH character sets are read as UTF-8 or Windows-1252.
- **Dual dates:** `parseDateValue` once sorted `1648/49` on the earlier (Julian) year while a 7.0 export writes the later one; that is now fixed, with a backfill for stored rows (ADR-004 addendum).
