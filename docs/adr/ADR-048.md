# ADR-048: Content-Security-Policy ships report-only first, with transport and framing headers (fixes F7)

## Status

Implemented

- **Status:** built on `claude/security-concerns-validation-3bcb9c` on 2026-10-14 and deployed. No migration.
- **Context:** the app sent no Content-Security-Policy and no HTML hardening headers; only the media route set its own. Nothing in `src/` loads script, style or fonts from another origin, and there is no `{@html}`, so the policy can be strict. Nothing in CI can load the real UI against a policy, though, and an enforced policy that blocks one component (a three.js texture, a Splash background) would break the deployed app with no test to catch it.
- **Decision:**
  - **`kit.csp` in report-only mode** (`vite.config.ts`): `default-src`, `script-src`, `style-src`, `img-src`, `font-src`, `connect-src`, `worker-src` (blob, for three.js), `object-src 'none'`, `base-uri`, `form-action`, `frame-ancestors 'none'`. Kit's `mode: 'auto'` adds nonces to the inline bootstrap on dynamic pages.
  - **Headers from `handle`** (`src/lib/server/http/security-headers.ts`): HSTS (`max-age=31536000`, with neither `includeSubDomains` nor `preload`, since the app is open source and may run beside sibling subdomains it does not control; only over https and never on a local host), `X-Frame-Options: DENY` (the only clickjacking control, since `frame-ancestors` is ignored in report-only), `Referrer-Policy`, `X-Content-Type-Options`, `Permissions-Policy`. A route's own header wins, so media keeps `Content-Security-Policy: sandbox`.
  - **A report endpoint** (`/api/csp-report`) because Kit refuses a report-only policy without `report-uri` or `report-to`. It logs a summary of each violation (the directive, the blocked origin or keyword, the document path, never the query string) and answers 204.
  - **Rejected alternatives:** enforcing from the start (no way to verify the UI against it here); a header set in the Cloudflare dashboard (outside the repository, so it would drift from the code and the tests); `preload` on HSTS (a commitment for the whole domain, not made by this change).
- **Before switching to enforcing** (rename `reportOnly` to `directives` in `vite.config.ts`):
  - Open each main view in the browser with the console open (Flat, the whole tree, the four WebGL views, the tree editor dialogs, Splash, sign-in) and check for `Content-Security-Policy` messages. Any blocked script, style, image, font or worker needs a fix or a narrow source, not `'unsafe-inline'` on script.
  - Check the `/api/csp-report` log lines (`Content-Security-Policy violation (report-only)`) over a few days of real use, including the WebGL views, where three.js is the likeliest source of `worker-src` or `img-src` reports.
  - Confirm the report endpoint receives reports from a browser (the reports from a signed-out visitor and a signed-in one both arrive, since the endpoint takes anonymous POSTs).
  - Only then switch, and keep the report target so enforcing violations still reach the log.
- **Consequences:** the policy is not enforced yet, so a violation changes nothing for a visitor but the log. HSTS takes effect on the first https response a browser receives, and the host that sent it is pinned to https for a year (its subdomains are not, since `includeSubDomains` is off). The endpoint takes anonymous POSTs (the hook does not refuse them, and a report carries no credential), so anyone can write to its log. The body is read through a byte-counting reader capped at 16 KB (a chunked body has no `Content-Length`), each POST logs one summary line, and a Cloudflare rate-limit rule for the path is listed in `docs/backlog.md`; until it exists the log can still be flooded at the platform's request rate.
