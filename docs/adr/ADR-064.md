# ADR-064: Under Vitest the adapter's platform proxy keeps no state on disk, and one full suite runs at a time

## Status

Implemented

- **Status:** built on `claude/elegant-wing-38ff6e` on 2026-10-19.
- **Context:** full `npx vitest run`s failed a different set of server tests each time, and every failing file passed alone. Three lone full runs before this change failed no server tests, so the per-test failures were not reproduced. What was found:
  - **Shared on-disk state (shown).** Vitest starts a Vite server for each of its two projects, and `@sveltejs/adapter-cloudflare` boots a `getPlatformProxy` in each server's `configureServer` hook with default persistence. Every run's proxies, and `npm run dev`, open the same `.wrangler/state/v3/*/metadata.sqlite` in the checkout. Two full runs at once in one checkout crashed one of them at startup with `SQLITE_BUSY (SQLITE_BUSY_RECOVERY)`. Two single-file runs at once crashed 6 times in 30 tries. The tests' own D1s were never involved: `createTestDatabase` passes `persist: false`, and miniflare gives each of those a private temp directory.
  - **Memory (inferred).** One full run peaks at 8–9 workerds and 4.2–4.7 GB RSS on the 10-core, 16 GB host, about 3 GB of it in Vitest's node processes. The timeouts and ECONNRESETs in random files came when several agent sessions ran the suite at once, and a later five-way run took down the login session, which looked like running out of memory. Memory pressure from concurrent suites is the likely cause of the scattered failures, but it was not reproduced in isolation.
- **Decision:** `vite.config.ts` passes `platformProxy: { persist: false }` to the adapter when `VITEST` is set, so those proxies keep their state in memory. With it, the two single-file runs at once crashed 0 times in 30, and a run creates no `.wrangler/` directory. Run one full suite at a time on this host. The per-file workerd from `getPlatformProxy` stays, and so does `maxWorkers: '50%'`: a lone run passed three times in a row.
- **Rejected alternatives:** retries, which would hide the startup crash rather than prevent it; higher timeouts, since the plan tests already allow 120–600 s and no lone run timed out; one proxy per worker shared across files, which would save workerd memory but give up each file's fresh database, while most of the peak is in Vitest's own processes anyway.
- **Consequences:** two idle in-memory workerds still start with each run, since the adapter's hook cannot be turned off from the config. Concurrent full runs, in one checkout or across worktrees, can still exhaust the host's memory; nothing here guards against that.
