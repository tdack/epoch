# ADR-062: A tree can have sub-trees rooted at a person

## Status

Implemented

- **Status:** built on `claude/tree-subtrees-exploration-dcc030` on 2026-10-18 and deployed. Migration 0034 adds the `subtree` table (expand only). The design is in [proposal-subtrees.md](../proposal-subtrees.md).
- **Context:** a tree of several hundred people is several family lines in one file. A reader who wants one family line should not have to start from the whole tree. The owner decided three things: a sub-tree is a *lens* (a root plus scoped lists), not an access boundary; it is a part of a tree, owned by the tree; and a manager makes it from a person. The lens had to be reachable from a link, so it needed an address of its own.
- **Decision:**
  - **Membership rule.** A sub-tree rooted at R has the members: R; every child of a member through `parent_child` of any type (biological, adoptive, foster, guardian, unknown) whose status is not `disputed`; and every partner of anyone in those two sets. Partners' parents and kin are not members. The recursion uses `UNION`, so a cycle in bad data ends. A disputed link does not pull a family in, and an adopted child does belong to the line.
  - **Computed, not stored.** Membership is a SQL predicate, `inSubtree(alias, treeId, rootPersonId)`, in the style of `visibility.ts`. It is ANDed with `tree_id` and the visibility predicate, so totals, `hasMore`, page fill, surname counts and ordering are computed in scope, never by filtering a finished page. A stored member table would be rebuilt by every `parent_child`, `union_partner` and person mutation. The plan test (`list-plans`) holds the predicate to `idx_parent_child_parent` and the union-partner indexes, and two planner nudges stay in the code: a `cross join` fixes the join order, and a unary plus on `tree_id` keeps `idx_parent_child_tree` from winning. A stored table is the answer if measured plans fail on a tree of tens of thousands of people.
  - **The root, not the sub-tree id.** `inSubtree` takes the root person's id, so the predicate needs no join to the `subtree` row. `isMemberOf`, `andInLens` and `andUnionInLens` are the forms the scoped reads use.
  - **Addressing: `tree~sub`, not `reroute`.** The sub-tree rides inside the tree's path segment: `/trees/dacks~bouvier-line/people`, and `/api/trees/dacks~bouvier-line/…` for the API. `~` cannot appear in a slug or a UUID, so the separator is unambiguous, and `encodeURIComponent` leaves it alone. Every positional check in `hooks.server.ts` and `tree-host.ts` keeps working. ADR-057 rejected `reroute` because `event.url` keeps the original path and those checks would all need translating; a separate `/~sub/` segment would break the same checks. `splitTreeSegment(segment)` in `shared/tree-slug.ts` is the only code that knows the separator, and `subtreePath` builds links that keep it. `treeHandler` resolves the sub-tree and passes it to the handler next to `treeId`, and only scoped endpoints read it.
  - **What the lens scopes.** Scoped: the chart's default focus (the root) and whole-tree mode, the people, surname, union and place lists, search and the person finder, the header counts (people only), and the "is in this sub-tree" note on a person page. Not scoped: sources, repositories, notes, files, tasks, quality, privacy, members, settings, every write, the change log and undo, and GEDCOM export, which always exports the whole tree. A place page with nothing in scope under a lens is a 404. A person outside the lens is still shown, with a note and a link to the whole tree, and the chart can be navigated past the lens's edge. The lens chooses where a reader starts and what lists show; it hides no relatives.
  - **Privacy.** A sub-tree's name can reveal a living root, so the list is filtered per viewer: a sub-tree whose root the viewer may not see is left out of the list, and its address returns 404 with no hint that it exists. A shared address works for a public visitor when the root is visible to them and, from ADR-069, a manager has made the sub-tree public; the sub-tree list endpoint is open to public visitors on the same rule. The membership rule is not weakened by the lens: a restricted viewer still sees only people the visibility predicate allows.
  - **Permission.** `tree:manage_subtrees`, minimum role `manager` (ADR-062 adds it to `authorization.ts`). Every endpoint denies by default. The "Make sub-tree from here" action on a person page and the Trees page section use it.
  - **Writes go through the mutation runner.** A sub-tree is a logged, undoable row (`subtree-ops.ts`, the change log, `undo-scope.ts`), so creating, renaming, changing a root, and deleting are undoable like any other edit. Each has a `version` for optimistic concurrency.
  - **Lifecycle.** `root_person_id` has no foreign key. Person delete is a hard delete with undo, and a cascade or set-null would change the sub-tree row outside the logged operations, so an undo would not bring it back. A root that is gone reads as "anchor missing" on the Trees page, and opening the sub-tree shows the whole tree with a notice. A person merge repoints `root_person_id` from the merged-away person to the survivor in the same change (`person-merge.ts`). Deleting a tree cascades to its sub-trees.
  - **GEDCOM is not exported.** A sub-tree is a view over the tree, not genealogy, so it is not written to GEDCOM, as tasks are not. No GEDCOM extension is planned: export sticks to the spec, and sub-trees are an app feature.
- **Rejected alternatives:**
  - *A stored member table.* Every parent-link, partnership and person change would rebuild it. A recursive read over indexed edges costs one extra lookup per member, which the plan test holds in check.
  - *`reroute` through `event.url` (ADR-057).* Every positional check would need translating.
  - *A separate `/~sub/` segment.* It breaks the same checks and gives a second tree-like address to keep canonical.
  - *An access boundary.* A lens that hid people would need a rule for every relative the chart draws, and the owner wanted the rest of the tree one click away and still editable.
- **Given up:**
  - The switcher lists only the current tree's sub-trees, because they arrive with its summary. Listing every tree's sub-trees would make the tree-list endpoint resolve visibility for every tree.
  - No stored member table, so a scoped read costs a recursive lookup, and a very large tree may need one.
  - No GEDCOM export of sub-trees, so a sub-tree does not survive a trip through another program.
  - Moving a sub-tree up or down is two PATCHes, and it has no Undo. Drag-to-reorder saved as one batch is a follow-up ([backlog.md](../backlog.md)).
  - Sub-trees are not in the e2e suite yet for a tree host, a public visitor, or the remembered-focus order ([backlog.md](../backlog.md)).
