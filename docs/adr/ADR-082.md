# ADR-082: A Deploy to Cloudflare button, finished by a one-time `/setup` page on the Worker

## Status

Proposed

- **Status:** built on 2026-10-30 on `claude/deploy-button-setup`. Not yet deployed or tried with a
  real button install. Migration `0052` adds nullable columns to `install_meta`.

## Context

A [Deploy to Cloudflare button](https://developers.cloudflare.com/workers/platform/deploy-buttons/)
clones a public repository into the visitor's GitHub account, connects it to Workers Builds,
provisions the D1 database, R2 bucket and queue named in `wrangler.jsonc`, and deploys. It does
nothing else, so on its own it gives a Worker nobody can use:

- `validateAccessJwt` fails closed without `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD`, and only
  `./setup` creates the Access application that supplies them.
- No install owner is recorded, so even a valid sign-in is turned away (ADR-034).
- `npm run deploy` stops without `wrangler.deploy.jsonc` or `EPOCH_DEPLOY_VALUES` (ADR-043).
- The button offers every key in `.dev.vars.example` as a production secret, which would have
  offered `ACCESS_BYPASS_DEV=true`.

Questions settled before building:

- **OAuth.** Cloudflare opened self-managed OAuth clients to every account in June 2026
  ([changelog](https://developers.cloudflare.com/changelog/post/2026-06-03-public-oauth-clients/)).
  A client is private to its own account until its client URL's domain is verified and it is made
  public, which cannot be undone. Redirect URLs are registered per client, and the docs give no
  wildcard form, so each install's own callback could not be registered ahead of time. Epoch would
  need one public client under its maintainer's name and a relay page on epochgenealogy.app passing
  codes on to any install. Rejected: that client's verified name would appear on a consent screen
  granting Access and Workers rights to whatever address asked, which makes it a consent-phishing
  tool, and the relay is a shared service every install depends on, which Epoch exists not to have.
- **An API token instead.** Cloudflare's documented
  [token template URLs](https://developers.cloudflare.com/fundamentals/api/how-to/account-owned-token-template/)
  open the dashboard with the permissions already chosen. The owner creates an account token there
  and pastes it once.
- **Who may claim the install.** An open `/setup` on a fresh address belongs to whoever reaches it
  first, and a token only proves the visitor has *a* Cloudflare account. Each account's workers.dev
  subdomain is unique, so `/setup` accepts a token only if its account owns the subdomain in the
  request's host. No claim secret is needed, which also leaves the button nothing to prompt for.
- **Custom domains.** Whether a Workers Builds deploy keeps a custom domain absent from the config
  is not documented, so `/setup` runs on `*.workers.dev` only. `./setup` stays the way to a custom
  domain or subdomain trees.
- **Writing back to GitHub.** Not needed: everything `/setup` learns is kept in D1. A GitHub App able
  to commit to each install's repository would be the widest grant in the design, for nothing D1
  cannot hold.
- **Bindings the button does not list.** Workflows and rate limits are created by the deploy itself.
  `send_email` is dropped in button mode: its placeholder sender would be refused, and without it
  invitations are saved but not emailed, as already documented. Queues need a paid Workers plan, as
  Epoch already does.

## Decision

- **`/setup` is served only while the install has no owner** (`install_meta` empty), read fresh on
  every request to it, and only on a `*.workers.dev` host. Otherwise it is a bare 404.
- **The owner pastes an account API token** with Access: Apps and Policies (edit), Access:
  Organizations, Identity Providers, and Groups (read) and Workers Scripts (read). It is used for the
  one request and never stored, logged or returned to the page.
- **One submission does everything,** in an order that is safe to repeat:
  1. find the account whose workers.dev subdomain matches the host, or refuse;
  2. read the Zero Trust organisation's team domain and its identity providers, or say what to
     create first (Epoch never creates an organisation, as with `./setup`);
  3. reuse or create the owner-only Allow policy and the Access application on `<host>/login`, by
     the names `./setup` would use;
  4. insert the `install_meta` row with the owner, team domain and AUD, only if no row exists, so
     two submissions at once cannot both claim the install.
- **The Access settings are read from D1 when the Worker has none,** and the vars still win, so an
  install made by `./setup` is unchanged. A found row is cached for the isolate; "none yet" is not,
  so the first sign-in after `/setup` works.
- **The deploy script has a button mode,** used only by `npm run deploy` on Workers Builds when
  neither `wrangler.deploy.jsonc` nor `EPOCH_DEPLOY_VALUES` exists. It writes the deploy config from
  `wrangler.jsonc` without `send_email`. `./setup builds` sets the build to `build:worker` and
  `deploy:worker`, which never take this path, so a `./setup` install that loses its variable still
  fails loudly.
- **The local secrets example is renamed** to `.dev.vars.local-example`, so the button prompts for
  nothing.

## Consequences

- A button install is on workers.dev, sends no invitation email until a sender is configured, and
  is unknown to `./setup doctor`, `allow` and `teardown`, which read `.epoch/install.json`.
- While the token exists, its permissions are wider than the one step needs. The page tells the
  owner to delete it afterwards.
- Untested against live Cloudflare: the API calls are unit-tested against the documented response
  shapes only. The first button install should be watched.
- OAuth stays possible later if Cloudflare documents per-install redirect URLs or dynamic client
  registration.
