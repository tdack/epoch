# ADR-082: A GEDCOM OBJE is a media record with files and links (amends ADR-050, ADR-061 and ADR-074)

## Status

Proposed

- **Status:** drafted on 2026-11-01 as task 2.1 of [gedcom7-gdz-plan.md](../gedcom7-gdz-plan.md). Nothing is built. The owner answered its open questions on 2026-11-01 (see "Owner decisions").

## Context

Epoch keeps `OBJE` as retained lines (ADR-003, ADR-028). An import creates no file. An export writes none of the files a tree holds. A 7.0 export renames an embedded 5.5.1 `OBJE` to `_OBJE`, because 7.0 allows only a pointer there, and nothing in Epoch can show the file inside it.

What 7.0 says an `OBJE` is:

- **A record** (`0 @O1@ OBJE`) with one or more `FILE`s, `RESN`, notes, citations, `REFN`, `EXID`, `UID`, `CHAN` and `CREA`. Each `FILE` has a path or URL, one `FORM` (a media type, with an optional `MEDI` for the kind of source), an optional `TITL`, and any number of `TRAN` translations (other-format copies).
- **A pointer** (`n OBJE @O1@`) under a person, a family, a source record, a submitter and every fact and citation. The pointer carries an optional `CROP` (`TOP`, `LEFT`, `HEIGHT`, `WIDTH`) and an optional `TITL` that overrides the file's title for that use.
- **Not under** a name, a parent-child link, an association or an LDS ordinance.

5.5.1 differs. An `OBJE` is usually embedded, with its own `FILE`, and the same photo on three people is three copies. `FORM` may be missing or free text, `FILE` is any text (often a Windows path), and there is no `CROP`.

Today a file is a `media_items` row. `media_links` joins it, many to many, to a person, a partnership or a source, with no foreign key on the owner (ADR-050, ADR-061). One visibility rule (`canReadRow`) serves the serve route and the Files list. Undo, the quota, the unlinked scan and the Files page all treat the row as one stored object with a key, a type and a size.

ADR-074 imports a `.gdz`'s media as detached files and models `OBJE` last. The plan reverses that order, on the owner's decision of 2026-10-31. Otherwise a real archive lands as hundreds of unowned files, and the export has nothing to point its `OBJE` records at.

## Decision

### Shape: a media record owns files

- **A `media_object` table is the record.** One row per `OBJE`. A new row has a UUID, never the xref, so a merge or a second import cannot collide (ADR-002). Columns:
  - `id`, `tree_id` (cascade), `xref` (null for an embedded 5.5.1 `OBJE`)
  - `privacy` (`auto`, `private`, `public`, as ADR-015 does for people)
  - `gedcom_extra` (JSON lines)
  - `version`, `created_at`, `updated_at`, `created_by` (no foreign key)
- **`media_items` stays the file.** One row per `FILE`: the key, the type, the size, the title, the bytes' state. It gains `object_id` and `sort_order` (the order of the `FILE`s).
- **`media_links.media_id` now means an object.** For the life of the expand phase an object's id equals the id of its first file, so a legacy link needs no rewrite. See Migrations for why.
- **`RESN`.** `privacy` and `confidential` import as `private` and export as `RESN privacy`. `locked` is kept in `gedcom_extra`. `public` travels as `_EPOCH_PRIVACY public`. This is ADR-015's rule; the line is not also kept.
- **Identifiers are retained lines.** `EXID`, `UID`, `REFN`, `CHAN` and `CREA` live in `gedcom_extra`, as plan task 1A.4 tests them. Epoch's own `CHAN` and `CREA` are written from `updated_at` and `created_at`. No screen needs them modelled.
- **Notes and citations use the existing tables.** `media_object` becomes a subject kind for `note_attachments` and `citations`. The kind lists are `text(..., { enum })` value lists in the Drizzle schema, checked in code and not by SQLite, so this needs no migration. A citation on an object is visible exactly when the object is.
- **A `FILE.TRAN` and the `MEDI.PHRASE`** stay in the file's `gedcom_extra`. A translation is a second path to a second file. Modelling it needs a file kind, and nothing in Epoch would use one.
- **A `FORM` is the file's `mime_type`.** `MEDI` is a new nullable `medium` column. A 5.5.1 `OBJE` with an empty, missing or non-media-type `FORM` gets the type its path implies (`withFileForm`, already in `dialect.ts`).

Why a record, not one `OBJE` per file:

- **The unit that is shared is the record.** Two people pointing at one `OBJE` is the normal 7.0 case. With one record per file row, several files under one `OBJE` mean extra `FILE`s kept as lines on the first file. Those lines hold paths that nothing resolves, so the second file of a `.gdz` could never be imported and the two files could never be shown together.
- **Everything else in 7.0 hangs off the record,** not the file: `RESN`, notes, citations, `EXID`, `UID`. They need a home that is not "the first file".
- **The cost is small because most code already works on links.** Privacy, undo and the Files list all go through `media_links`, so they move from "file" to "object" by changing what an id names. The serve route and the quota still work per file.

### Links: `media_links` carries the 7.0 pointer

New columns on `media_links`, all nullable or defaulted:

- `fact_id`: the event the pointer sits under. `entity_id` stays the fact's person or partnership.
- `sort_order`: the pointer's place among its siblings. Nullable with no default; null means 0 (see the undo note under "Columns on `media_items`").
- `crop_top`, `crop_left`, `crop_height`, `crop_width`: whole numbers of pixels. All null means no crop.
- `title`: the `TITL` override.
- `gedcom_extra`: extension lines under the pointer, and a `CROP` with no children.

Details:

- **A fact link keeps its owner in `entity_id`.** The privacy rule, the person page, a merge and a person delete therefore find the link with no change. `fact_id` only says where it is written back and where the UI shows it.
- **Link id.** A record-level link keeps `<mediaId>:<entityId>`. A fact-level link is `<mediaId>:<entityId>:<factId>`. The unique index changes from `(media_id, entity_id)` to `(media_id, entity_id, coalesce(fact_id, ''))`, so one photo can sit on a person and on one of their facts.
- **A second pointer to the same object from the same place** (for example two crops of one group photo) is kept as a line in the host's `gedcom_extra`. It is rare. Modelling it needs `sort_order` in the key, and it would make every link id longer.
- **Which kinds can link.** A person, a partnership, a source and a fact. These are all the places where 7.0 allows a pointer and where Epoch already has a record that can show it.
- **Which stay retained.**
  - A citation's `OBJE` (ADR-028 retained it, and a citation has no page of its own to show a file on).
  - A submitter's `OBJE` (a `SUBM` is a kept root record).
  - Any pointer under a structure Epoch keeps whole.

  A retained pointer is remapped to the object's xref as every kept pointer is, so it still resolves. The object is a normal record, and the pointer does not count as a link. If it is the only reference, the object is detached.

### Files Epoch does not hold

- **A `FILE` with no bytes is a `media_items` row with `status = 'unresolved'`.** `status` is `resolved` or `unresolved`; a null status means `resolved` (no default, see Columns on `media_items`), so every existing row is right. The row keeps `gedcom_path` as the file wrote it, `mime_type` from its `FORM`, `title` from its `TITL`, and no size. It is written back on export, so no import drops a file reference.
- **`gedcom_path` is the text as written.** Nothing rewrites it. The export decides how to write it (see Import and export).
- **A `.gdz` resolves a row.** Phase 3 matches each `FILE` to an archive entry by path, streams the entry into `media/<treeId>/<itemId>.<ext>`, and sets `status`, `r2_object_key`, the size and the checksums in one write. A retry finds the row by `(tree_id, gedcom_path)` and does the same again, so it is idempotent, and the key is fixed by the row's id. This replaces ADR-074's "hash of job id and entry path" as the id: the row already exists before the archive is read.
- **An entry no `FILE` names is imported as a detached object** (owner decision 4). Nothing in the archive is lost. It counts against the quota, is listed in the job report, and an editor can delete it from the Files page.
- **What the UI shows.** The Files list and a person's media section show the file as a tile or row with a "missing file" icon, its title or the last segment of its path, and the badge "Not stored in Epoch". Details show `gedcom_path` as plain text. It is a link only when it is an `http:` or `https:` URL, opened in a new tab with `rel="noopener noreferrer"`. A `file:` URI, a Windows path and a relative path are text. The server never fetches the path and no page uses it as an `<img>` source, so a hostile file cannot make Epoch request anything (the CSP's `img-src` agrees). The preview, download and quota treat the row as empty. An editor can "Add file…" to an unresolved row, which uploads bytes into it and resolves it, through the same upload path as any file.
- **Visibility is the same as any object.** A path such as `john-smith-1923.jpg` can name a private person, so an unresolved file is shown to a restricted viewer only when its object is readable.

### Columns on `media_items`

All added by `ALTER TABLE … ADD COLUMN`:

- **Every new column on an existing table is nullable with no default.** A change image written before this migration has no key for the column. ADR-051's null-fill (`withAllColumns`) reads that missing key as null, so a column whose live value is a non-null default would differ from the image and refuse the undo of every earlier media change. The default is held in code instead: null `sort_order` is 0, null `status` is `'resolved'`. The new `media_object` table is new and has no history, so it keeps its defaults.

| Column | Type | Meaning |
| --- | --- | --- |
| `object_id` | text, null, references `media_object` (cascade) | The record this file belongs to. Null only before the backfill. |
| `sort_order` | integer, null, no default. Null means 0 | The file's place among the `FILE`s of its object. |
| `gedcom_path` | text, null | The `FILE` text as written. Null for a file uploaded in Epoch. |
| `status` | text, null, no default. `resolved` or `unresolved`; null means `resolved` |
| `medium` | text, null | `MEDI`. |
| `sha256` | text, null | Hex digest of the bytes. For the backlog's checksum item. |
| `crc32` | integer, null | Unsigned 32-bit CRC. The Phase 4 zip writer needs it for the stored entry header without re-reading the bytes. |
| `gedcom_extra` | JSON, null | Kept lines under the `FILE`, `FORM` and `MEDI` (`TRAN`, `MEDI.PHRASE`, extensions). |

- **`sha256` and `crc32` are derived columns.** Like `size_bytes`, they are left out of undo row images (`DERIVED_COLUMNS`). Both are null until an upload or the fill computes them. The form upload computes both from the bytes it already holds. A chunked upload stores the CRC (combined from per-part CRCs, ADR-074) and leaves the SHA-256 null. `fillMissingChecksums` (the hourly cron, at most 5 files and 256 MiB a run, picked in random order so a row whose object is gone cannot starve the rest) and `npm run db:backfill:media-checksums` fill what is still null, reading each object once. None of these writes goes through the change log, and none touches an unresolved row. The Phase 4 zip writer must fall back to reading the object when `crc32` is null. A stored CRC is a cache, not a promise.
- **`r2_object_key` stays `NOT NULL`, and an unresolved row holds `unresolved/<itemId>`.** SQLite cannot drop `NOT NULL` without rebuilding the table. A rebuild means dropping `media_items`, which `media_links` references with `on delete cascade`, so it would delete every link. ADR-050 could rebuild only because nothing referenced the table then. The placeholder names no R2 object: `parseMediaKey` refuses it, so the serve route answers 404 for it, the unlinked scan never lists it, and delete skips the bucket call when `status = 'unresolved'`. The contract migrations below remove it.
- **The existing index `(tree_id, r2_object_key)` stays.** A new index on `(tree_id, gedcom_path)` serves the `.gdz` match.

### Privacy

ADR-050's rule, `canReadRow`, is extended and keeps one implementation for the serve route and the Files list.

- **Unrestricted roles** (owner, manager, editor) read every object.
- **A restricted viewer** (contributor, viewer) reads an object when all of these hold:
  - its `privacy` is not `private`
  - it has at least one link
  - every link's owner is visible: every linked person, every partner of a linked partnership, every linked source (ADR-028's source rule), and for a fact link the owner of the fact

  This is ADR-050's "every person it hangs off is visible", which now reads "every record the object hangs off". A group photo with a private person in it stays hidden. An object with a `privacy` of `public` is not a bypass: a person's override beats it, because a photo of a private person is not public.
- **A fact link is judged by its owner,** not by the fact. A fact-level `RESN` is still a retained line with no meaning (ADR-051), and this ADR does not give it one. That is the same position as the fact's address and phones.
- **A retained pointer is not a link,** so an object that only a citation or a submitter points to is detached. A detached object is shown to editors and above only, as ADR-050 says.
- **Files of an object.** A secondary file is readable exactly when its object is. The serve route finds the file by `(tree_id, r2_object_key)`, then its object through `object_id` (or, before the backfill, the item's own id), then applies the rule.
- **Export** is manager-only and carries everything (ADR-015), so the rule above is not applied to it. If a filtered export is built, it uses this rule for objects.
- **Citations and notes on an object** are visible exactly when the object is.

### Import and export mapping

**Import.**

- **A 7.0 `OBJE` record** becomes a `media_object` and one `media_items` row per `FILE`, in order. The record's `xref` is kept.
- **A 5.5.1 embedded `OBJE`** becomes an object with no xref and one file per `FILE`. `TITL` at the `OBJE` level, which 5.5.1 allows, becomes the first file's title.
- **Embedded copies are merged.** An embedded `OBJE` whose first normalised `FILE` equals the path of an object already made in this import is not a new object. It adds a link to that object, and a differing `TITL` becomes the link's `title`. 5.5.1 has no sharing, so one photo on three people is three copies, and the user wants one file with three links. Normalising does not change case, because paths are case-sensitive in 7.0 and on R2.
- **A pointer** becomes a `media_links` row: `entity_id` from the host, `fact_id` when the host is a fact, `sort_order` from the line's position, `CROP` children into the four columns, `TITL` into `title`. A pointer to `@VOID@` or to a missing record is kept as a line on the host (it points at nothing).
- **Merge mode** matches an object by xref, then by the first file's `gedcom_path`, as ADR-028 matches sources. A matched object gets only the links and files it lacks.
- **Replace mode** deletes the tree's objects with the rest, bytes included, as it does now.
- **Import never fetches.** A URL or a path never makes a request. It is stored as text.

**`FILE` path forms.** The stored text is never rewritten. Each form is handled where it is written:

| Form | Example | Meaning | Written in 7.0 | Written in 5.5.1 |
| --- | --- | --- | --- | --- |
| Relative reference | `media/a%20b.jpg` | An archive entry or a path beside the file | As stored | Percent-decoded |
| `file:` URI (RFC 8089) | `file:///C:/a/b.jpg` | A path on the author's machine | As stored | As stored |
| `http:`/`https:` URL | `https://x.org/a.jpg?s=1` | A remote file | As stored | As stored |
| Windows or bare path | `C:\Photos\a b.jpg`, `a b.jpg` | 5.5.1 free text | Converted by the dialect: `\` to `/`, a drive to `file:///C:/…`, percent-encoded | As stored |

The 7.0 conversion happens in `toGedcom7Lines`, the same layer that makes everything else valid. The database keeps the author's text, so a 5.5.1 export of an imported file is byte-exact.

**Export 7.0 (`.ged`).**

- One `OBJE` record per object, with its xref (a short one when the object has none or has a UUID, per task 1A.6), `FILE` lines in `sort_order`, each with `FORM` (`mime_type`), `MEDI`, `TITL`, then the kept lines, then `RESN`, notes, citations and the kept `EXID`, `UID`, `REFN`.
- A pointer is written under each host, in `sort_order`, with `CROP` and `TITL` when set, and its kept lines.
- `FILE` is `gedcom_path` through the dialect conversion when the file has one. A resolved file with no path is written as the relative path `media/<slug>-<first 8 of id>.<ext>`, so a later hand-made zip lines up. This path is never saved to `gedcom_path`.
- An embedded `OBJE` no longer becomes `_OBJE`. That rule in `dialect.ts` and the known gap in ADR-036 go away.

**Export 7.0 (`.gdz`).** Same dataset, but a resolved file's `FILE` is an archive path:

- Its `gedcom_path`, if that is a valid relative reference that is not yet taken in the archive (so a round trip keeps the author's folders).
- Otherwise `media/<slug>-<first 8 of id>.<ext>`, made unique.
- Each segment is percent-encoded. Never `gedcom.ged`, `MANIFEST.MF` or anything under `META-INF/`.
- An unresolved file keeps its stored text. An external URL stays a URL, and a relative path that no entry satisfies stays dangling. Phase 4 lists these in its report.

**Export 5.5.1.** `OBJE` records and `OBJE @x@` pointers, both of which 5.5.1 has, with `FILE`/`FORM`/`MEDI`/`TITL`. 5.5.1 has no place for `CROP` or a pointer's `TITL`, so both are dropped, and ADR-036's known losses say so. `RESN` follows ADR-015's wording for 5.5.1. Media bytes are never in a 5.5.1 export.

### Mutations and undo

New or changed commands in the mutation runner. All check `version`, are logged, previewed and undoable, as ADR-050 sets out for the rest:

- **`link_media`** gains `factId`, `sortOrder`, `crop` and `title`. `unlink_media` gains `factId`.
- **`update_media_link`** edits a link's `title`, `crop` and `sortOrder`.
- **`reorder_media_links`** takes a host and its fact and an ordered list of object ids, and writes the new `sort_order`s as one change (ADR-076's batch form).
- **`update_media_object`** sets `privacy`.
- **`resolve_media_file`** sets the key, size, checksums and `status` of an unresolved file. The object is written before the row, as an upload is. Undo restores the unresolved row and leaves the object for the unlinked scan, which already skips anything younger than an hour.
- **`rename_media`** is unchanged and renames the file's title. Citations and notes on an object use the existing evidence and note commands.
- **Fact delete and fact merge.** Deleting a fact removes its fact-level links in the same change, as `citationCascadeOps` does for its citations. The object and its files stay, and if that was the last link the object is detached. A person or partnership merge moves links with the records, and a fact the merge keeps carries its links.
- **Not in the log:** creating an object by upload, by the route, as now; creating objects and links by import, through the import batch; **deleting an object**, which removes its rows and its files' bytes and is not undoable, as ADR-050 says delete is. The confirm dialog names the count of links and files. Removing a single file from an object is the same kind of delete.
- **Versions.** The link ops and `update_media_object` check `media_object.version`. `rename_media` and `resolve_media_file` check the file's. The backfill copies each file's version to its object, so a client with a version in flight still works.
- **Change log.** The table map gains `media_object`, with row images. The new columns on `media_items` and `media_links` are editable, except `sha256` and `crc32`. An undo image written before the migrations still matches its row, because `withAllColumns` fills the missing keys with `null` (ADR-051). Restricted viewers see an op on `media_object` or `media_links` only when they could read the object.
- **Write scope.** A command that names an object loads its files and links, and the hosts of those links, so privacy and cascades are planned over complete rows.

### Quota, scan and Files page

- **Quota and the unlinked scan are per file and unchanged.** An unresolved row has no object and no size, so it costs nothing and is never listed as unlinked.
- **The Files page lists objects.** A row is the object's first file. An object with more files says "+n files", and its details list them. The quota bar is unchanged.
- **Delete.** Deleting an object removes the rows first, then each resolved file's bytes, as ADR-050 does now, and leaves any bytes it could not remove for the scan.
- **Roles are ADR-050's.** `media:manage` links, edits and uploads. `media:delete_any` and the uploader rule delete. Setting `privacy` needs `media:manage`.

### Migrations, in expand-and-contract order

Numbers are the next free ones when written. Each is its own commit and is deployed before any code reads it.

1. **Expand: tables and columns.** Create `media_object`. `ALTER TABLE ADD COLUMN` on `media_items` (the eight above) and on `media_links` (`fact_id`, `sort_order`, four `crop_*`, `title`, `gedcom_extra`). Add the new unique index on `media_links`, then drop the old one. This is safe for the code that is live: its primary key is still `<mediaId>:<entityId>`, which refuses a duplicate by itself. Add the `(tree_id, gedcom_path)` index.
2. **Code that writes objects and reads with a fallback.** An item with a null `object_id` is read as an object whose id is its own. Uploads insert the object, then the file, then the link. The write order matters: `object_id` is a foreign key.
3. **Backfill, idempotent, after that deploy: `npm run db:backfill:media-objects`.** One object per file with a null `object_id`: `id` = the file's id, `version` = the file's, `created_at`/`updated_at`/`created_by` from the file. Then `object_id` = `id`. Run it again once the deploy has fully rolled out, to catch a file the old code inserted meanwhile. A second run does nothing. The checksum backfill (task 2.6) is a separate script.
4. **Code stops reading the fallback and the placeholder,** and the Phase 2 import and export land.
5. **Contract: rebuild `media_links`.** It points `media_id` at `media_object`, nothing references `media_links`, and every `media_id` is an object id by step 3. This ends the rule that an object's id equals its first file's id.
6. **Contract: rebuild `media_items`.** Now nothing references it either. `r2_object_key` becomes nullable and the placeholders are set to null, and `object_id` becomes `NOT NULL`. This waits until no code reads the placeholder. `wrangler rollback` restores code, never schema, so steps 5 and 6 are deployed only once step 4 is stable.

Steps 1 to 3 are expand-only and any of them can be rolled back by redeploying the code of the step before.

### Amendments to other ADRs

- **ADR-050.** "A file's owner" becomes "an object's links". `canReadRow` takes an object's links and `privacy` and applies the extended rule above. The Files page lists objects. Delete and the scan are per file, as before.
- **ADR-061.** A source's files are a source's links to objects, with the same visibility. `OBJE` under a source record is now modelled, no longer a kept line.
- **ADR-074.** Its Phase 4 ("model `OBJE`") moves ahead of its Phases 2 and 3. Specifically:
  - The `.gdz` import (its Phase 2) does not create detached files. It resolves the unresolved rows the dataset created. "Detached files first" and the deterministic `hash(jobId, path)` id are dropped. The `gedcom_path` column moves to Phase 2 of the plan's migrations.
  - The export (its Phase 3) writes one `OBJE` record per object, not per file, with the pointers `media_links` carries.
  - Its Phase 4 is done by this ADR. ADR-074's "Detached files first" constraint and its Phase 4 text are rewritten when that ADR is next edited.
- **ADR-028.** A citation's `OBJE` is still retained. The object it points to is now a record.
- **ADR-036.** The known gap "an embedded 5.5.1 `OBJE` is written as it came" closes.

## Rejected alternatives

- **One `OBJE` per `media_items` row, extra `FILE`s kept as lines.** It needs no new table. But `RESN`, notes, citations and `EXID` have no honest owner when an object has two files, and the second file can never be imported, shown or resolved from a `.gdz`. It also makes "one object, many files" depend on which file is first.
- **`media_items` becomes the record and a new `media_file` table holds the bytes' columns.** It keeps `media_links` untouched. But `r2_object_key`, `mime_type` and `size_bytes` would move off the table that the serve route, the quota and the scan read, and every one of those readers would change in the same migration for the benefit of a case (several files per `OBJE`) that is rare. The record table adds a table and touches the readers of links, which are fewer.
- **Rebuild `media_items` now to make the key nullable.** It deletes every link through the cascade (see above), and `wrangler rollback` could not undo it.
- **A separate `media_link_kind` column.** `entity_id` has no foreign key and no owner kind, and ids are UUIDs, so the repository tells the kinds apart by lookup (ADR-061). Adding `event` to that lookup would work, but `fact_id` beside the owner is simpler and keeps every existing privacy path.
- **Make a fact's link carry `entity_id` = the fact id.** The privacy rule would have to find the fact's owner, which means a fifth lookup in every read, and a merge would have to rewrite it.
- **Fetch an external `FILE` URL into R2.** It makes Epoch a request proxy for whatever an uploaded file names, and it is unnecessary: the URL stays valid as text.
- **Merge nothing on embedded import.** Three copies of one photo would be three objects, three files in R2 after `.gdz` import, and three times the quota.
- **Model a citation's `OBJE` now.** A citation has no page, so the scan of a record would have no place to show. The link kind can be added later because the object is already a record.

## Consequences

- An import creates objects and links, with every file unresolved until a `.gdz` supplies bytes. `maximal70.ged`'s `OBJE` structures round-trip as records and links.
- Every 7.0 export of a tree with files writes valid `OBJE` records. The `_OBJE` rewrite goes.
- `media_links` rows are wider. Reads that only need the owner are unaffected.
- Until step 5, an object's id equals its first file's id, and a reader must not assume anything else about object ids. After step 5 nothing depends on it.
- The unresolved file with a placeholder key is a row the unlinked scan, the serve route and delete must each be told about. Tests for all three are part of task 2.3.
- Audio, video and transcripts in a `.gdz` are outside `UPLOAD_MEDIA_TYPES`. The `.gdz` import accepts them as download-only files (owner decision 2).
- Citations' and submitters' `OBJE` pointers stay retained. Their files appear in Files, as detached objects if nothing else points to them.
- Task 2.2 is the migrations 1 above. Task 2.6 is the checksum compute and backfill. Tasks 2.3 to 2.5 follow the sections above. The plan's tables need no change.

## Owner decisions (2026-11-01)

1. **Citation-level `OBJE`** stays a retained line for now. A `citation_id` link kind can be added
   later without loss.
2. **Audio, video and WebVTT** in a `.gdz` are stored as files and served as downloads, not inline.
   The `.gdz` import accepts them beyond `UPLOAD_MEDIA_TYPES`, so the official `maximal70.gdz`
   round-trips.
