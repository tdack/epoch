# ADR-034: Only the install owner, members and invitees are admitted (amends ADR-016 and ADR-026)

## Status

Implemented

- **Amended by ADR-041:** the install owner may also rename and delete any tree, and publish one as the public tree.
- **Context:** ADR-016 meant a broad Access policy to be safe, with the invitation as the real gate. In practice anyone Access verified became a full user: they got a `users` row, could start trees of their own (`TreeService.createTree` needed only a signed-in caller), and nothing named one person as the owner of the install. The CLI setup plan (open question 2, option B) proposes recording the owner and turning everyone else away.
- **Decision:**
  - **An install owner.** Migration 0025 adds `install_meta` (install UUID, owner email, created date). The setup tool writes the row after migrations; the app only reads it, so signing in can never make someone the owner (the rule ADR-015 set when it stopped "first caller owns ownerless trees"). Should there be several rows, the oldest wins.
  - **Admitted** means one of: the install owner (the address Access asserts, compared lower-cased); someone holding any tree membership; or someone with an unexpired invitation, which is redeemed on that same request. `UserRepository.admitFromAccess` replaces `upsertFromAccess` and decides this before writing anything.
  - **A stranger is not stored.** Someone Access names but Epoch does not admit gets no `users` row; who they are lives in `locals.notAdmitted` for that request only, for the welcome page to show. `locals.user` stays null for them, so every handler and load that checks it stays closed. A known user who no longer holds a membership keeps their row (change history points at it) but is not updated. Rows already stored for strangers before this change are left alone; removing them is a separate, deliberate cleanup.
  - **Turned away in the hook,** before the signed-out rules (`notAdmittedOutcome` beside `signedOutRedirect`): a GET or HEAD page load gets a 303 to `/welcome?reason=not-invited`; any `/api` call gets 403 with code `NOT_ADMITTED`, not the handler's 401, since signing in again would not help; a data request or a submission is served without a user and fails where it lands, as signed out. `/welcome` and `/login` stay reachable, so nothing loops: `/login` sends a not-admitted visitor to the not-invited page instead of rendering "we could not confirm your sign-in", whose link would lead back to "Sign in".
  - **The welcome page** decides its state from `locals`, never from `?reason=`, so a crafted link shows nothing. Not invited, it names the address they are signed in as, tells them to ask the owner for an invitation, and offers **Sign out** (`/cdn-cgi/access/logout`) instead of "Continue", which would bounce straight back. It now sends `cache-control: no-store`, since it names the visitor. It still ships no client code.
  - **Starting a tree** is limited to the install owner and anyone holding a membership; anyone else gets `NotAdmittedError` (403, `NOT_ADMITTED`), from `POST /api/trees` and from a GEDCOM import with no tree named. It is install-wide, so it is not a `TreeAction`. Whether the caller is the owner is decided once, at admission, and carried as `UserIdentity.isInstallOwner`; a context built anywhere else lacks it and fails closed. **UI:** everyone who reaches the tree shell is admitted and so may start a tree, so nothing is hidden; the rare refusal (a member removed from their last tree mid-session) shows in the create dialog's existing error line.
  - **No `install_meta` row** (an install before setup, or one set up by hand before this change): there is no owner, and only members and invitees are admitted. Never "the first to sign in": that would hand a fresh install to whoever arrives first. An existing install keeps working, because its owner already holds memberships; add the row to give them install-wide rights back if they lose all of them. **Local development:** under the dev bypass (already limited to local hosts, ADR-026) the default bypass identity, `developer@epoch.local`, stands in for the owner until a row exists. Any other `x-dev-user-email` must be invited, which is what the e2e tests already do, and adding a row lets the not-invited page be tried locally. With no database bound (unit tests, a bare preview) the identity is used as it is.
- **Amends:** ADR-016: Access is no longer the only thing between a stranger and the app, so a broad Access policy is now safe, as intended; redemption moves from `upsertFromAccess` to `admitFromAccess`. ADR-026: a signed-in visitor can now be turned back to `/welcome`, and `/login` redirects a not-admitted visitor there.
- **Consequences:** Deploy order is the usual expand-then-read: `npm run deploy` migrates first. Until setup writes the row, write it by hand (see [INSTALL.md](../../INSTALL.md)). The privacy matrix is unchanged: no endpoint was added and the 403 comes from the hook.
