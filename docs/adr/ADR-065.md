# ADR-065: Setup provisions Cloudflare itself; Terraform is not adopted

## Status

Implemented

- **Status:** considered and rejected by the owner on 2026-10-19. Nothing was built.
- **Context:** the setup tool (`tools/setup`, about 9k lines) provisions an install with `cf`, `wrangler` and the tracked `wrangler.jsonc`. Terraform's Cloudflare provider would give declarative state, plan, drift detection and destroy without writing them, and it covers the zone and Access configuration that wrangler cannot (Access applications and policies, DNS records, Worker-less routes, R2 lifecycle rules, rate-limiting rules).
- **Decision:** keep the setup tool, and do not add Terraform to it. The reasons:
  - **Setup already does what Terraform would.** The manifest is the state file, `reconcile` with markers and tags is import and adoption, `--plan` is plan, `doctor` is drift detection and `teardown` is destroy. They are written, tested and were run against a live account (ADR-057, ADR-063).
  - **It would bring back a token.** The provider needs a Cloudflare API token. Setup signs in to `cf` with OAuth, and ADR-043 depends on needing no token.
  - **It would bring back owner values on disk, or a second setup.** State must live somewhere: locally it is the owner's ids outside git again (ADR-043), and remotely (R2's S3 API, HCP) it is configured before setup can run. Workers Builds cannot run Terraform.
  - **Ownership would split.** `wrangler deploy` owns the Worker, its bindings, the wildcard route, the queue consumer and the workflow, and since ADR-043 it finds D1 by name. Terraform managing any of those would fight wrangler on each deploy, which leaves it D1, R2 and the queue, the resources wrangler can already make.
  - **Most of setup is not infrastructure.** The questions, email verification, D1 migrations, the `install_meta` writes, the Workers Builds variable and triggers, and adoption with confirmation stay in the tool either way.
  - **Upkeep.** The provider's v4 to v5 rewrite renamed and reshaped many resources. That is churn for an install run by one owner.
- **Rejected alternatives:** Terraform for everything (the split above); Terraform for D1, R2 and the queue only (no gain over `cf`, and a second state beside the manifest); an optional Terraform module for zone hardening such as WAF and rate-limit rules. That last one fits best, since nothing else owns those rules, but a setup step on the rulesets API keeps one tool and the OAuth sign-in, so it is the way to do the open rate-limit item in the backlog.
- **Revisit when** the setup tool's upkeep outweighs the features it adds, or Epoch becomes a multi-tenant deployment run by one operator rather than an install each owner runs from a clone.
- **Consequences:** new Cloudflare resources are added to setup (manifest, reconcile, `doctor`, `teardown`) as before.
