# ADR-049: Name search moves to an FTS5 table kept current by triggers (amends ADR-014's search costs, settles the normalised name column)

## Status

Implemented

- **Status:** built on 2026-10-14 (migration `0029_name_fts.sql`, `SearchRepository.rankedNames`). Passed locally: `search-plans.test.ts` and `privacy-reads.test.ts` with unchanged assertions (one plan-check exemption, below); the two-tree witness on the index (`name-fts.test.ts`); the trigger consistency check across create, rename, name add, rename and remove, merge and its undo, person removal, tree move, a replace-mode delete, a bulk insert, a tree delete, and the real GEDCOM importer in replace and merge modes (`The Simpsons.ged`, then `The Windsors.ged` merged in, then the Simpsons replaced); and "müller" finds "Müller" while "mueller" does not. Redo does not exist in this codebase (undo is the only reversal), so it is not covered. **Remote D1 check, 2026-10-14:** on a scratch production-class D1 database (since deleted), `fts5(… tokenize = 'trigram remove_diacritics 1')` was accepted; "müller" and "muller" matched "Hans Müller" and "mueller" did not; a `tree_id : "…" AND name : "…"` match was scoped to its tree; and an `AFTER INSERT` trigger writing to the FTS table made "angstrom" find "Zoë Ångström". The full migration and the bulk-insert cost were not run remotely, so the import cost stays the open measurement.
- **Deviations from the proposal, made while building it:**
  - *A key table beside the FTS table.* `name_fts_key (id, person_id, name_id)` gives each FTS row a stable integer rowid. The triggers find their row through it, indexed by `person_id` and `name_id`. Without it a trigger either scans the FTS table (its `person_id` column is unindexed) or uses a name table's rowid, which VACUUM can renumber. The triggers are per row (insert, update, delete), not delete-then-reinsert, so a replace-mode import does not scan the index once per person.
  - *Every word of three or more letters is in the MATCH, ANDed.* The proposal said the longest word. The other words cannot be checked afterwards with `LIKE`, since that does not fold: "zoe muller" would miss "Zoë Müller".
  - *Scoring uses the words as typed, not folded.* Folding them would drop an exact match that works today ("müller" against a stored "müller" would fall to the "contains" level). A stored name with a diacritic found by its folded form therefore ranks at the "contains" level. This is the fallback the brief allows.
  - *`search-plans.test.ts` changed one helper.* The plan check flags any `SCAN` line, and a MATCH-driven virtual-table read is printed as `SCAN … VIRTUAL TABLE INDEX n:M…`. The check now ignores exactly that form. A virtual-table scan without MATCH still fails. The assertions are unchanged. `schema-status.test.ts` skips the `name_fts*` tables, since the schema cannot declare them.
- **Context:** `docs/backlog.md` asks for a decision on "counters or a normalised name column before large trees". Name search reads about 4 to 8 rows per person (22,000 to 40,000 on the 5,324-person tree in `query-plans.md`), because a `LIKE '%…%'` cannot use an index and ranking happens before `LIMIT`. Rows are cheap on Workers Paid (25 billion a month included, so about 600,000 such searches), but on Workers Free the 5 million a day is about 125 searches. The defect people will notice first is not cost but matching: SQLite's `lower()`, `LIKE` and `NOCASE` fold only ASCII, so "müller" does not find "Müller", and there is no phonetic match. A fix has to keep three properties of today's search: one tree's work only (the two-tree witness in `search-plans.test.ts`), ranking before `LIMIT`, and privacy as a predicate in the same query (ADR-015).
- **Decision:**
  - **An FTS5 table of name text, inside D1.** D1 supports FTS5 (including `fts5vocab`). One row per candidate the search already ranks: each `person_names` row, and each person's own given name and surname (the display name, which ADR-014's search counts because a person created before S6 has no name row). Columns: the name text (prefix, given, nickname, surname prefix, surname, suffix, as `NAME_HAY` builds it), and unindexed `tree_id`, `person_id`, `name_id`.
  - **Diacritics fold in the index, not in SQL.** The tokenizer folds Unicode case and removes diacritics (`trigram remove_diacritics 1`, or `unicode61 remove_diacritics 2` if trigram is unavailable). SQL cannot do this in D1: there are no user functions, and SQLite's built-ins fold only ASCII. The query string is folded the same way in the service (`normalize('NFD')`, strip combining marks, lower-case) before it is matched.
  - **Trigram first, because it keeps today's substring semantics.** The search matches a word anywhere in a name (`%…%`); `trigram` does the same, and `unicode61` would only match whole tokens or prefixes. Trigram cannot match a term under three characters, so a one- or two-letter word keeps the existing `LIKE` path, whose cost is the same as today.
  - **Kept current by SQLite triggers, not by the writers.** `AFTER INSERT/UPDATE/DELETE` triggers on `person_names` and on `individuals` (when `given_name`, `surname` or `tree_id` change) rewrite the person's rows. ADR-015 rejected a stored column because every writer (the mutation runner, each command, import, merge, undo and redo) would have to maintain it; a trigger runs for all of them, since they all write these tables. These are the first triggers in the schema.
  - **The tree is part of the match.** `tree_id` filtered after a `MATCH` would read every tree's hits for a common name, which the two-tree witness exists to catch. The tree goes into the match itself: `tree_id` is an indexed column and the match names it (`tree_id : "<uuid>" AND name : "…"`). Measured on the two-tree corpus, small tree (419 people), "ann": the tree in the MATCH returns and reads 27 rows; the tree filtered after the MATCH reads 436, because every tree's matches are read before the tree is checked (436 rows for either tree). "ashson": 5 against 47. Both forms are recorded in `query-plans.md`. One FTS table per tree is rejected, because trees are created at run time and migrations are static.
  - **Ranking and privacy stay in SQL.** The FTS hits become the candidate set the existing ranking and `GROUP BY` best-name step run over, still before `LIMIT`; the visibility predicate (`andVisible`) is applied to those people in the same statement, so `hasMore`, page fill and counts stay correct for a restricted viewer.
  - **A hand-written migration.** Drizzle's schema cannot express a virtual table or a trigger, so the migration (expand-only: create the table, the triggers, and backfill with one `INSERT … SELECT`) is written by hand and the table is left out of the Drizzle schema; reads use raw `sql`. The backfill writes one row per name and person, billed as rows written.
  - **Rejected alternatives:**
    - *A normalised column on `person_names` and `individuals`.* It fixes folding only if the app computes it (SQL cannot fold Unicode), so every writer must set it, the ADR-015 objection. It still needs a `LIKE '%…%'` scan to match substrings, so it does not reduce rows read.
    - *Vectorize, or AI Search (hybrid BM25 and vector).* Names carry no meaning for an embedding to capture, so vector similarity is a poor stand-in for spelling and sound. The index returns ids that D1 must then filter for privacy, which breaks `hasMore`, page fill and counts (the design ADR-015 replaced). Living people's names would leave D1. Vectorize returns at most 50 results with metadata, AI Search allows 5 custom metadata fields and filters on the first 64 bytes of a string, and AI Search includes 1,000 hybrid queries a month, then $0.75 per 1,000 (billed from 2026-11-01), which does not suit search as you type. Both stay candidates for note and source search and for scanned-document text (OCR), where the wording varies and meaning matters, limited to what everyone may see or once privacy can be expressed as a filter.
    - *Surname counters.* They help the surname list, not search, and only for unrestricted roles, since a restricted viewer's count depends on who they may see.
- **Acceptance checks before this is "decided":**
  - D1 accepts the chosen tokenizer (`trigram` with `remove_diacritics` needs a recent SQLite; D1's docs list FTS5 but not its tokenizers). Test it against a deployed database, not only local `workerd` (done on 2026-10-14, see Status).
  - `search-plans.test.ts` and `privacy-reads.test.ts` pass unchanged, and the two-tree witness holds: a search of the small tree reads no row of the big one. How D1 counts `rows_read` for an FTS query is undocumented, so record it in `query-plans.md` beside the S7 table.
  - A trigger test per writer path: create, rename, add and remove a name, import (both modes), merge, delete, undo and redo each leave the FTS rows equal to a rebuild from the base tables.
  - "müller" finds "Müller". "mueller" does not, because folding is not transliteration; that is the phonetic step.
- **Consequences:**
  - **`wrangler d1 export` refuses a database that holds a virtual table.** Cloudflare's workaround is to drop the virtual tables, export, and recreate them. The D1 recovery runbook in the backlog must say so and ship a rebuild script (drop, export, recreate, repopulate with the backfill `INSERT … SELECT`). Time Travel is not affected.
  - Every name write also writes FTS rows (more rows written per name change, and more again for an import). Measured locally, a raw insert of 5,000 people took 1.5 s with the triggers against 0.23 s without, and 50,000 took 69 s: the cost is superlinear as the index grows. `tree_id` is indexed too (it has to be, for the match), so each row also carries its tree's 34 trigrams. Before a large import is measured on the deployed database, this is the number to watch, along with rows written.
  - A `wrangler rollback` restores code that does not read the table; the triggers keep maintaining it, which is harmless. Dropping it later is a contract migration.
  - **Phonetic search builds on this.** A Soundex or Daitch-Mokotoff code is computed in the app (SQLite has no such function in D1), so it cannot come from a trigger. It is added as a second column of the same table, written by the writers or by a rebuild, in its own ADR.
  - Place search can follow the same pattern over `events.place`, once this is measured.
