# ADR-067: Read-only page data loads on the server, through the services

## Status

Implemented

- **Status:** built on 2026-10-19. No migration. It settles the "universal loads call the app's own API" item in the backlog.
- **Context:** every screen's data came from a universal `+page.ts` or `+layout.ts` that fetched `/api/...` with `event.fetch`. On a server render SvelteKit answers that fetch in-process, so the Worker's `handle` ran twice for one page view: schema check, Access JWT validation and user upsert, then the endpoint's own sign-in and visitor checks. The endpoints for those reads existed only for the loads.
- **Decision:**
  - **A read-only page load is a `+page.server.ts` (or `+layout.server.ts`) that calls a service.** It never touches D1 or a repository, and never fetches its own API. A server render passes `handle` once, and a client navigation makes one `__data.json` request for the layout and page loads together, where it made one API call per load.
  - **`treeServerLoad` and `serverLoad` (`server/http/page-load.ts`) are to a load what `treeHandler` and `apiHandler` are to an endpoint.** They take the caller from `locals`, refuse the signed-out (401) and the public visitor (403) unless the load says `allowPublicVisitor`, resolve the address's tree segment and sub-tree lens to ids, and turn a failure into the error page: a `DomainError` keeps its status and message, anything else is logged and becomes a 500 with the screen's own failure text. The caller and tree-scope checks are the same functions the handlers call (`assertCaller`, `resolveTreeScope` in `handler.ts`), so a load and an endpoint cannot disagree about who may read. Each load repeats its endpoint's `allowPublicVisitor` and lens argument, and a service is called with the resolved id, never the address's slug.
  - **Invalidation is unchanged.** `treeServerLoad` calls `depends(DATA_KEY)` (now in `shared/data-key.ts`); `invalidate(DATA_KEY)` makes SvelteKit re-request the server loads that registered it. The settings page still registers `SETTINGS_DEPENDENCY`.
  - **The tree layout moves first.** `parent()` in a server load returns only server loads' data, and the files, source, settings and trees pages read the viewer's role from the layout's summary, so the layout must be a server load too.
  - **What stays universal:** the tree canvas (`trees/[id]/+page.ts`). It has `ssr = false`, reads the remembered focus from `localStorage`, and reads only some address parameters so that toggling a display option redraws without a request. None of that works on a server. It therefore keeps `event.fetch` and `GET /api/trees/[id]/graph`, which the canvas also calls from the browser as the focus changes. There is no server render for it, so there is no second `handle`.
  - **Endpoints removed** (their only caller was a load, and the data shape is unchanged): the GETs of `marks`, `lists/individuals`, `lists/surnames`, `lists/unions`, `charts/pedigree`, `charts/descendants`, `relationship`, `search`, `quality`, `privacy`, `settings`, `tasks` (the list), `subtrees`, `unions/[unionId]` and `admin/trees`. The PUT, POST and DELETE handlers in the same files stay.
  - **Endpoints kept:** the ones the browser still calls (the person page, whose drawer and editor refetch it; `lists/notes`, `lists/sources` and `lists/repositories` for the pickers and dialogs; `places`, for the fact editor's suggestions; `people-search`; `files` and `files/usage`; `members`; `sources/[sourceId]`; `graph`), and three the end-to-end specs call to check the API's own privacy answers or to read a tree's counts: `GET /api/trees`, `GET /api/trees/[id]/summary` and `GET /api/trees/[id]/notes/[noteId]`. A server load for any of these still calls the service, not the endpoint.
- **Rejected alternatives:** keeping universal loads and calling the handlers' functions directly (a universal load also runs in the browser, and the services must not); a shared `loadX` function used by both the endpoint and the load (no second caller left for most endpoints, so it would be an indirection with one user); removing the three e2e-used endpoints and rewriting those specs as page tests (churn for no runtime gain).
- **Consequences:** server load data is serialised with devalue, not JSON, so a service result that held a class instance would fail to serialise; the DTOs are plain objects, and the e2e run covers it. A client navigation to a tree screen now re-runs the layout's loads on the server only when they are invalidated or their inputs change, as before. Tests of the removed endpoints move to the service or to the load. The cost of resolving the tree segment is paid once per load, as it was once per endpoint call.
