# ADR-043: The deploy config is git-ignored; Workers Builds gets its values as one build variable (supersedes ADR-038)

## Status

Implemented

- **Status:** accepted by the owner on 2026-10-12. Built on `claude/admiring-planck-t2xc7q`. The adoption run of the live install on 2026-10-12 used it: it deployed without a D1 id and set the build variable on the production trigger through `cf`.
- **Context:** ADR-038 tracked `wrangler.deploy.jsonc` so Workers Builds could deploy from a fresh clone. The owner wants a clean repository instead: anyone can clone it, run `./setup` and deploy their own install, and none of the owner's values (team domain, install id, sender address, D1 id) live in git. ADR-038 rejected the alternatives because they needed an API token or wrangler's beta auto-provisioning. Neither objection holds now:
  - **The D1 id is not needed.** In wrangler 4.131 to 4.148, `wrangler deploy` with a D1 binding that has no `database_id` keeps the binding the deployed Worker already has, if that database's name matches `database_name`. Otherwise it looks the database up by name, and creates it only if none exists. Remote `d1 migrations apply` and `d1 execute` look the database up by name too. The owner confirmed a deploy without the id on 2026-10-12.
  - **Setting build variables needs no API token.** The Builds API has `PATCH /builds/triggers/{uuid}/environment_variables`, and `cf` 1.0.0-beta.13 wraps it as `cf builds triggers environment-variables upsert`. Setup already signs in to `cf` with OAuth, and cf's OAuth client lists a `workers-ci.write` scope (with the legacy `workers_builds:write`).
- **Decision:**
  - **`wrangler.deploy.jsonc` is git-ignored again**, and was removed from the index. `npm run setup` writes it locally as before.
  - **No D1 id anywhere.** The tracked `wrangler.jsonc`, the setup template and the generated file all name the database only. The generator sets `database_id` to undefined, so editing an older file removes its stale id.
  - **One build variable, `EPOCH_DEPLOY_VALUES`.** It holds this install's values (Worker name, hosting, hostname, team domain, install id, sender, R2 jurisdiction, AUD) as JSON in a fixed key order. It is not the whole config: the build regenerates the file from the current tracked `wrangler.jsonc`, so a binding added to the tracked file reaches the next push without re-running setup. It is visible rather than secret, because nothing in it is a credential (ADR-038) and a secret cannot be read back to see whether it is current.
  - **The generator has no package dependencies** (`tools/setup/deploy-values.ts`), so `scripts/deploy-config.mjs` can import it on the build host, where only the root packages are installed. Node 24 (`.nvmrc`) strips the types. The raw tracked file is read with wrangler's `experimental_readRawConfig`.
  - **Build once.** `build:worker` writes the file from the variable (when it is set), checks the build fields and runs `vite build`. `deploy:worker` migrates and deploys with no build. `deploy` runs both, so a local deploy needs no variable. The Workers Builds commands are `npm run build:worker` and `npm run deploy:worker`. Migrations stay ahead of the deploy: a database renamed or missing in config then fails the migration with "Couldn't find a D1 DB named …", rather than letting the deploy create an empty one.
  - **Setup sets the variable.** After deploying, setup finds the Worker's script id and its Builds triggers, and upserts the variable on every trigger. `./setup builds` re-runs only this step, for after the repository is connected in the dashboard. `workers-ci.write` is requested but optional, like the tag scopes. Without it, before the repository is connected, or on any Builds API error, setup prints the value and the commands to paste instead. It never fails the run.
  - **Setup configures the production trigger.** It is the single trigger whose branch filters name branches rather than a `*` pattern. Setup sets its build and deploy commands to the two above, its path includes to `src/**`, and its path excludes to `node_modules/**`, `.git/`, `docs/`, `.agents/` and `.claude/` (the owner's choice, so documentation and tooling pushes cost no build minutes). It does this with `cf builds triggers update`, which the owner confirmed on 2026-10-12. Preview triggers keep their commands and paths: their deploy command uploads a version, and `deploy:worker` there would send every branch to production. If more than one trigger looks like production, nothing is changed and the commands are reported.
  - **The Worker's id comes from `cf workers list`**, which gives the 32-hex id the Builds and tags APIs key on as `id`, beside `name`. It replaces the raw `GET /workers/scripts` read.
  - **The invitation sender is a var, `EPOCH_EMAIL_SENDER`.** The generator writes it beside `allowed_sender_addresses` from the same value, and the mailer reads it rather than a constant, so no install's address is in the source. With no var, invitations are saved but not emailed, as with no binding.
  - **History was rewritten on 2026-10-12** to drop every `wrangler.deploy.jsonc` and `wrangler.deploy.example.jsonc`, rename the setup fixture to `tools/setup/fixtures/deploy-config.jsonc`, and replace the owner's team domain, install id, D1 id, mail domain, workers.dev subdomain and surname (a test tree's name) with placeholders throughout, in file contents and commit messages.
- **Rejected alternatives:** a pre-push hook that generates the file (hooks run only on the owner's machine, and getting the file to the build host would mean committing it); storing the whole generated config as the variable (it would go stale against the tracked file); one variable per value (more to set and keep consistent, for no gain); a separately created API token (the existing `cf` sign-in covers it).
- **Consequences:** a fresh clone deploys only after `./setup` (locally) or once the variable is set (on Workers Builds). With the `src/**` path filter, a push that touches only `drizzle/`, `workers/`, `static/`, `wrangler.jsonc` or `package.json` (a migration, a binding or a dependency on its own) builds nothing. It deploys with the next push that touches `src/`, or by `npm run deploy`. Connecting the repository before the variable exists starts a first build that fails with a message naming `./setup builds`. The behaviour depends on wrangler's resource provisioning, which is on by default but behind a hidden `--x-provision` flag, so it belongs on the re-check list for each wrangler upgrade. Local D1 state was keyed by the placeholder id and is now keyed by the binding name `DB`, so one `npm run db:migrate:local` (and `npm run seed`) is needed after pulling this. The owner's values are still in the history of the commits made while the file was tracked; rewrite it before the repository goes public.
