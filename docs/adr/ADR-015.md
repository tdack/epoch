# ADR-015: Who is private, and where it is decided (Phase 4, S8)

## Status

Implemented

- **Context:** Phase 4 must keep living people from collaborators who should not see them, and a viewer must not be able to infer a private person through search, counts, lists, charts, exports or errors. S7's `filterForViewer` runs after the SQL page is chosen, so it cannot correct `hasMore`, page fill or a surname count.
- **Decision:** Privacy is a predicate in the query, beside `tree_id`, for the roles that are restricted. It is derived at read time from the person's events, not stored.
  - **Derived, not stored (measured).** The alternative was columns on `individuals` (a has-death flag, a birth upper bound) kept up to date by every writer: the mutation runner, each command, import, merge, undo, and a backfill that would also have to run remotely before any deploy. Two correlated lookups on `idx_event_entity` cost about 4.5 index rows per person, measured on the two-tree harness: a first page of the people list reads 217 (419-person tree) and 259 (5,324) rows against 51 for the unfiltered page; a page 100 deep reads 1,793 and 23,285 rows (about 4.3 per person), against 419 and 5,001. No `events` row of another tree is read, because the lookup is by the person's own id. The cost is paid only by contributors and viewers; owners, managers and editors run the unfiltered query. If a tree outgrows this, the stored column is the next step and the predicate is the only thing that changes.
  - **Living state.** A person is not living when they have a death, burial or cremation event (dated or not), or when the latest upper bound of their birth, christening or baptism dates is before a cutoff. The cutoff is computed in the service from an injected `now` and the tree's maximum-alive age, and passed as a parameter; SQL never calls `date('now')`, so tests are deterministic. A birth with no upper bound (`AFT 1900`, an undated `BIRT`) counts as unbounded, so the person stays private. `BEF 1900` is bounded and can make a person not living. Everyone with no such fact is indeterminate and therefore private.
  - **The threshold is Epoch's own choice, 120 years, configurable per tree.** It matches webtrees' `MAX_ALIVE_AGE` default (120, `app/Tree.php`), which was read from the source. webtrees also treats any event older than the threshold, and the ages of parents, children and partners, as evidence of death; Epoch uses only the person's own birth facts and so errs toward private.
  - **Override.** `individuals.privacy` is `auto` (derive), `public` or `private`, set by owners and managers; an override always wins. GEDCOM `RESN privacy` or `confidential` on an `INDI` imports as `private` and is exported back as `RESN privacy`; the line is not also kept in `gedcom_preserved`, so there is one source of truth.
  - **What each role sees.** Owner and manager: everything, and they set overrides and the tree settings. Editor: everything (an editor can change any record, so hiding one from them would only hide what they can already alter). Contributor and viewer: private people are absent. They are not masked in search, lists, marks and relationship search; a "Private" hit for a surname would itself say a private person exists, and the surname disappears from the surname list rather than shrinking. A private person's page, edit endpoints and any command that names them answer exactly like an id that does not exist (same status and body). A contributor therefore cannot link a new record to someone they cannot see.
  - **Placeholders only where structure is shown.** In the graph, and in the family a person's page lists (not in search, the lists or favourites), a private person is "Private", with no name, dates, places, sex or notes, when the tree setting `should_show_private_structure` is on (default off, so the safe behaviour needs no action). Off, they are omitted. The partnership list and a partnership's page never show a partnership with a private partner at all, because its marriage date and place are facts about that partner. Unions, links, events, names and notes of a private person inherit it.
  - **Export is a manager action.** `tree:export` was `viewer`, so any viewer could download the whole GEDCOM, living people included. It is raised to `manager`; a filtered export for lesser roles is a later slice.
  - **Writes.** A restricted viewer's command is planned over the rows they can see (a private id fails as a missing one) and then over all rows; the real ops are refused with a missing-permission error if they touch a private person. A preview needs the rights of the change.
  - **Doors that are not reads of a record.** Media reads and uploads check the tree and the record (and `Cache-Control` is `private`); the export workflow re-checks the requester's role when it runs; the tree-wide change log, `GET /api/trees/[id]` and `GET .../individuals/[id]` need an editor; and a tree with no members is no longer given to the first caller, which would have handed a second invitee every ownerless tree.
  - **GEDCOM.** `RESN privacy` and `RESN confidential` import as `private` and are not also kept in `gedcom_preserved`; other words (`locked`) are kept. `private` exports as `RESN privacy` (GEDCOM 7: `PRIVACY`), so `confidential` comes back as `privacy`; `public` has no GEDCOM word and travels as `_EPOCH_PRIVACY public`, as X does as `_EPOCH_SEX`.
  - **Editors see everyone (decided 2026-10-01).** The owner of the tree chose to keep this rather than restrict editors like contributors.
  - **A contributor sees the people they created (decided 2026-10-01, migration 0013).** `individuals.created_by` is stamped by `create_person` with the acting user and is null for imported and earlier people. For a contributor (`ViewerScope.creatorId`) a person whose override is `auto` and who they created is visible while private, in the SQL and in the pure rule; a manager's `private` still hides them, and another contributor or a viewer never sees them. The exception is the person only: their private relatives and partnerships follow the usual rules. A demoted contributor has no `creatorId`, so they lose sight of what they added. No foreign key, so deleting a user cannot cascade to people.
- **Amended 2026-10-26: any old fact, and the recently dead.** The owner chose to widen the living rule after comparing it with webtrees (`docs/webtrees-comparison.md`), because imported ancestors known only from a census or a marriage were hidden from every restricted viewer.
  - **Any own fact counts.** A person is also not living when any of their own facts has an upper bound before the cutoff (a census in 1881, a residence ending in 1890), as webtrees' `isDead()` reads it. A birth counts like any other fact, so one old birth is enough even beside a conflicting recent one; the earlier rule needed every birth to be old. The SQL keeps one `exists` for "a death or any old fact" because D1 caps a statement's expression tree at 100 levels, counting each subquery's, and a separate birth lookup took the note and task reads over it. An undated or open-ended fact (`FROM 1850`) still proves nothing. Relatives' dates are still not read: that needs the stored inputs above. The `probably_dead_no_death` quality rule lists the people relatives' dates show are dead, for a manager to date or mark.
  - **The recently dead (migration 0046).** `trees.recent_death_years`, 0 to 100, default 0 (off), keeps a person private while a death, burial or cremation may have ended within that many years. An undated one counts as long ago, or every `DEAT Y` would hide an ancestor; one with a lower bound and no upper (`AFT 2000`) may be recent and counts. An override and a contributor's own people are unaffected. It is webtrees' `KEEP_ALIVE_YEARS_DEATH`; `KEEP_ALIVE_YEARS_BIRTH` is not taken.
  - **One string, as the public tree's sentinel is.** The window travels in the existing `cutoff` as `<lived>/<died>`, read only by `cutoffParts`, so every reader that threads the cutoff is unchanged. The SQL inlines both days as checked literals, as it does the event types, so the extra tests bind no parameters.
  - **Windows load the old facts.** The chart and focus windows load only some fact types, so they now also load any of a person's facts that ended before the cutoff (`oldFactsBefore`); without it a person the lists show would be hidden in the charts.
  - **A partnership with a partner who has no birth.** The old predicate's birth comparison was null for a person with no birth row, and `not null` let such a private partner pass the "every partner visible" test of the partnership counts. The single `exists` is never null, so this is gone.
  - **Not re-measured.** The predicate is now one correlated lookup on `idx_event_entity` that stops at the first deciding fact, two with the window on, for restricted viewers only. The plan tests' row budgets still hold; `query-plans.md` predates it.
- **Consequences:** A person a contributor adds with no dated fact stays visible to that contributor, and private to everyone else restricted, until someone dates them. Reads for restricted viewers cost a small multiple of the unfiltered reads; the plans are re-measured in `query-plans.md` per read as the predicate is added. Revisit storing the derived state if a tree's surname list or a deep page becomes slow.
