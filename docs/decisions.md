# Epoch Architecture Decisions (Phase 0)

## ADR-001: Identity, Cloudflare Access and User Management
- **Context:** Epoch is a private, single-owner family-tree application with invited collaborators behind Cloudflare Access.
- **Decision:**
  - Authenticated identity is verified via Cloudflare Access JWT assertions (`Cf-Access-Jwt-Assertion` request header or `CF_Authorization` cookie).
  - Validation checks JWT issuer (Cloudflare team domain), audience tag (`AUD`), and rotating JWKS from `https://<team-domain>.cloudflareaccess.com/cdn-cgi/access/certs`.
  - For local development and automated testing environments, a configurable mock identity or local public key verifier is supported when explicit development flags are provided, while denying anonymous access by default.
  - The local `users` record is keyed and upserted by the stable Access subject claim (`sub`), treating `email` as mutable profile metadata.
  - Tree-level access is controlled via `tree_memberships` supporting roles: `owner`, `manager`, `editor`, `contributor`, `viewer`. Every server endpoint and action denies access by default.

## ADR-002: Genealogy Identifiers vs GEDCOM XREFs
- **Context:** GEDCOM files use XREF tokens (such as `@I1@`, `@F1@`) that are tree- or file-scoped, frequently collide between different imports, and can be unstable across re-exports.
- **Decision:**
  - All Epoch internal entities (persons/individuals, unions/families, events, citations, media) use internally generated UUIDs as primary keys.
  - GEDCOM XREFs are preserved as tree-scoped import/export aliases (`xref_id`) rather than internal primary keys.
  - This allows cross-tree references, multi-source merging, and prevents XREF collision corruption while ensuring lossless round-trip export by re-attaching or re-mapping XREFs.

## ADR-003: Lossless GEDCOM Preservation
- **Context:** Epoch aims for full round-trip fidelity with supported structures and lossless retention of unsupported GEDCOM structures.
- **Decision:**
  - Supported structures map to normalized relational tables (persons, partnerships, parent-child links, events).
  - Unsupported tags, custom vendor extensions (`_ATTR`, etc.), and unhandled sub-trees are preserved in an unparsed/syntax-preservation payload (JSON or raw records linked to entity IDs) so they are preserved without silent loss upon export.

## ADR-004: Historical Date Representation
- **Context:** Genealogy dates are frequently incomplete (e.g. `1910`, `MAY 1920`), approximate (`ABT 1845`, `EST 1850`, `CAL 1900`), ranged (`BET 1860 AND 1865`, `FROM 1901 TO 1905`), or conflicting. Converting them into arbitrary exact dates (like `1910-01-01`) destroys historical accuracy.
- **Decision:**
  - Dates are stored with both `date_raw` (verbatim string from historical record or user entry) and structured date metadata:
    - Date type/modifier: `EXACT`, `ABOUT`, `ESTIMATED`, `CALCULATED`, `BEFORE`, `AFTER`, `BETWEEN`, `FROM_TO`.
    - Earliest sort key (`date_sort_start`) and latest sort key (`date_sort_end`) in `YYYY-MM-DD` format for sorting, indexing, and chronological filtering.
  - Incomplete dates (year only or month/year) preserve their granularity rather than claiming precision that does not exist.

## ADR-005: Concurrency and Versioning
- **Context:** Multiple invited collaborators may view or edit tree records simultaneously.
- **Decision:**
  - Optimistic concurrency control is implemented using a numeric `version` column and `updated_at` on mutable root entities (`trees`, `individuals`, `families`/`unions`, `events`).
  - Domain mutation commands verify that the client's provided version matches the stored version before writing. A mismatch returns a typed `ConcurrencyConflictError` (HTTP 409).
  - D1 atomic transactions (or batch operations) are used for multi-row mutation commands. Durable Objects are deferred until real-time multi-cursor collaboration demonstrates a clear need.

## ADR-006: Layered Architecture and Clean Boundaries
- **Context:** The prototype embedded database queries and runtime schema initialization directly inside SvelteKit route handlers and single-page components.
- **Decision:**
  - The application is decoupled into distinct architectural layers:
    1. **Domain Layer:** Pure domain models, command interfaces, typed error definitions (`DomainError`, `NotFoundError`, `UnauthorizedError`, `ConcurrencyConflictError`, `ValidationError`), and business invariant checks.
    2. **Persistence/Repository Layer:** D1 implementations implementing repository interfaces with versioning and audit trails.
    3. **Query/Service Layer:** Read and write services that coordinate domain commands, enforce tree authorization, and return DTOs.
    4. **Transport/UI Layer:** SvelteKit server hooks, actions, API endpoints, and component views. Route handlers only parse inputs, invoke application services, and format responses. Direct database operations inside routes are prohibited.

## ADR-007: Persisted, append-only change log and undo (Phase 2, S2)
- **Context:** Undo used to be an in-memory array on `RelationshipService`, and a new service is constructed per request, so it could never work. Destructive removals, person edits and union edits wrote nothing at all. Phase 4 needs an audit log and per-record history, and should build on the same rows rather than replace them.
- **Decision:**
  - Two tables, added by an expand-only migration: `change_log` (one row per user-visible change) and `change_log_records` (the records each change wrote). Neither is read by existing code, so the deploy order is migrate, then code. `schema-init.ts` is not extended; it is S4 debt.
  - **Append-only.** Rows are inserted and never updated. An undo is a new row whose `reverts_change_id` names the change it reverses; "already undone" is derived from that, and a partial unique index on `reverts_change_id` means two concurrent undos cannot both succeed.
  - **Ordering by `seq`** (autoincrement), not by timestamp, which collides within a millisecond. `id` is a UUID generated before the write so the batch can reference it without reading `seq` back.
  - **Row operations are the unit.** Every mutation is first planned in memory as a list of row operations (`table`, `id`, `before` image or null, `after` image or null). The inverse is the same list reversed with before and after swapped, so any change is undoable, including deleting a person or a union with its links, partners and events. The inverse is stored in `inverse_json`; the field-level before/after summary shown to people is in `changes_json`. This deliberately replaces per-command `inverseOf`, which lost context (re-creating a removed parent link dropped its union) and had no answer for `destroy_union` or deleting a person.
  - **Atomic.** The row operations, version guards and log rows are applied in one `db.batch`, as ADR-005 requires, so a change is either fully applied and logged or not applied. A guard is an `INSERT` into `change_log` of NULL for a NOT NULL column that runs only when the expected row version is absent; the constraint error aborts the whole batch and is reported as `ConcurrencyConflictError`.
  - **Undo rules.** Undo applies to the requesting user's most recent undoable change in that tree that has not been undone. It is refused, with a message naming what changed, when a later change (by anyone, including an earlier undo) wrote any of the same records, and when the records no longer look the way the change left them (for example an import touched them). Undo rows are not themselves undoable; there is no redo in Phase 2.
  - **Affected records** are the rows a change wrote (people, names, unions, partners, parent-child links, events, media links). A person edit does not lock the person's relationships against undo, and a relationship change does not lock the people.
  - **Tree deletion cascades** to its log (`change_log.tree_id` has `ON DELETE CASCADE`). Before/after images contain personal data, and deleting a tree must erase it. The deletion itself is therefore not in the log; it is only in the structured request log. Phase 4 may add an account-level audit stream if that is needed.
  - **Not covered:** GEDCOM import and merge write no log rows in Phase 2; they replace or extend whole trees and are not undoable. `actor_id` has no foreign key so the log survives a removed user.
- **Consequences:** Phase 4's audit view reads `change_log` and `change_log_records` directly and adds visibility rules; moderation (pending changes) can store proposed row operations in the same shape. Payloads grow with the size of a change, which is small except for deleting a very large union or person.

## ADR-008: Union merge and XREF aliases (Phase 2, S3)
- **Context:** A dirty GEDCOM carries several `FAM` records for one family. Every union's XREF is its id (`<treeId>:@F1@`), so deleting a merged union would delete the only record of that XREF, and a NOTE or CHAN preserved under it would no longer belong to anything on export.
- **Decision:**
  - **Aliases are a nullable JSON column, `unions.xref_aliases`, on the surviving union**, added by an expand-only migration (`ADD COLUMN`; nothing reads it until this deploy). The alternative, an `union_aliases` table, would have to join `RECORD_TABLES`, the loader, the labeller and the impact grouping to be undoable. A column rides the survivor's ordinary update op, so undo restores it with no new machinery.
  - **Aliases carry transitively.** Merging a union that already has aliases moves those aliases to the survivor as well as adding the merged union's own XREF. A union whose id is not an imported XREF (created in the editor) adds no alias, because no other record ever named it.
  - **Export emits the survivor once**, under its own XREF, and re-attaches structures preserved under any alias to it. Each alias is written on the survivor as `1 REFN <xref>` with `2 TYPE epoch-merged-family`; the importer reads those back into `xref_aliases`, so a re-import recovers them. Alias `FAM` records are deliberately not re-emitted: the merge dissolved which child belonged to which copy, so a regenerated copy would be a guess, and two `FAM` records for one family is the exact defect being fixed.
  - **`merge_unions` is one command through `MutationRunner`.** It deletes the merged unions and their partner rows, moves child links and events onto the survivor, drops events identical to one the survivor already has, and updates the survivor's aliases, status and version, so it is logged and undone like any other change.
  - **Conflicts are never resolved silently.** Two unions conflict when they carry the same event type with different date, place or description, or when their statuses differ. An event type or status present on only one side is not a conflict; merging fills the gap. The command refuses with a typed error listing every conflict unless the request names, for each conflicting event type and for the status, which union's fact to keep.
  - **Import-time merge is stricter than the command.** Only a group with two or more partners, the same partner set, identical facts (both empty counts) and no child recorded with two different pedigrees is merged automatically. A one-partner `FAM` is never merged automatically: two of them may be different, unrecorded, other parents. Everything else is listed as a possible duplicate for review.
- **Chronological labels ("1st partnership") need two recorded partners.** Two one-partner records are not known to be the same pair, so they get no chronology; previews number them ("1 of 2") and the merge dialog offers them, because the command allows it and the person decides.
- **Consequences:** Re-importing the same dirty file in merge mode used to bring back the merged-away `FAM` records, because the importer matched on XREF and did not look at `xref_aliases`. S4 closed that: in merge mode an incoming `FAM` whose XREF is an alias of an existing union is folded into that union (children and facts combined without repeats), in the preview counts as well as the import. A family the tree has never seen is still imported.

## ADR-009: PEDI is per child link, stored per parent (Phase 2, S3)
- **Context:** `PEDI` describes a child's link to a family, and the standard place for it is `INDI.FAMC.PEDI`. Epoch read and wrote it under `FAM.CHIL`, which no other program understands, and its parser dropped everything under `FAMC`.
- **Decision:**
  - **Read** `PEDI` from the child's `FAMC`. The old `CHIL.PEDI` is still read for files Epoch exported earlier, and `FAMC` wins when both are present. Values are case-insensitive (`adopted` in 5.5.1, `ADOPTED` in 7.0).
  - **Store** it as one `parent_child` row per parent, with the same type on each, because a `FAMC` names the family and not a parent.
  - **Write** `PEDI` under `FAMC`, lowercase in 5.5.1 and uppercase in 7.0, and stop writing it under `CHIL`. `birth` is the default and is omitted.
  - **`sealing` and `other`** have no neutral type. They are stored as `unknown` with the word in the nullable `parent_child.gedcom_pedi`, and written back from it. 5.5.1 has no `OTHER`, so `other` is dropped from a 5.5.1 export and kept in 7.0.
  - **Different types for the two parents** are legal in the model but cannot be said in one `PEDI`. The family's `PEDI` is the first parent's type, and each parent who differs is written as `2 _PEDI_PARENT @I2@` with `3 PEDI adopted`. Epoch reads it back; other programs ignore a user-defined tag.
  - **Other structures under `FAMC`** (`STAT`, `NOTE`, `SOUR`, custom tags) are kept, as of S4. The parser preserves each `FAMC`'s sub-structures other than `PEDI` and `_PEDI_PARENT` in `gedcom_preserved`, owned by the child and headed by the `1 FAMC @F…@` line. Export writes them inside the matching `FAMC`, after the `PEDI`, and not after the record. When a child was linked to several copies of a family that were merged, the blocks follow the surviving family and a line that appears in more than one is written once.
  - **Known losses, deliberately not fixed in S4.** A `guardian` link exports as `foster`, because neither dialect has a `PEDI` for it, and comes back as `foster`. An `unknown` link with no `gedcom_pedi` exports as the default (birth) and comes back as `biological`. `other` is dropped from a 5.5.1 export, which has no such value, so it also comes back as `biological`; 7.0 keeps it. Fixing them needs a lossless carrier like `_EPOCH_SEX` (ADR-010), which means a new pedigree value through the parser, the importer's type maps and the per-parent `_PEDI_PARENT` path. That is a change to how links round-trip, not a small one, and these values only arise from a 7.0 file, a hand edit or the editor's guardian type. The proposal is one custom `_EPOCH_PEDI <guardian|other>` line beside a standard `PEDI` (foster for guardian) that Epoch reads back.

## ADR-010: Sex X and the 5.5.1 fallback (Phase 1, S4)
- **Context:** The graph domain and the GEDCOM parser accepted `X`, but `individuals.sex` was typed `M | F | U`, the importer mapped `X` to `U`, and the person form, validation and card had no `X`. A GEDCOM 7 file with `SEX X` lost that on import.
- **Decision:**
  - **One list.** `src/lib/shared/sex.ts` holds `SEX_VALUES` (`M`, `F`, `X`, `U`), its labels and a guard. The Drizzle column, the zod schema, the person form and the drawer all read it, so they cannot drift.
  - **No migration.** The column is `text DEFAULT 'U'` with no `CHECK`; the enum was TypeScript only, so widening it changes no stored data and no deployed schema.
  - **Card.** `X` has its own symbol (⚧) and shares the neutral fill with unknown (○), as the tree design specifies. The legend lists Other and Unknown separately.
  - **Export in 7.0:** `1 SEX X`, which 7.0 defines.
  - **Export in 5.5.1:** `SEX` allows no `X`, so the export writes `1 SEX U` followed by `1 _EPOCH_SEX X`. `U` is a value every 5.5.1 reader accepts and is true (the file cannot say more); the user-defined line, which readers ignore, lets Epoch restore `X` on re-import. This is the same device as `_PEDI_PARENT` (ADR-009). The alternative, writing only `U`, would silently turn `X` into "unknown" on a round trip.
- **Consequences:** Another program that reads the 5.5.1 file sees `U`; only Epoch reads `_EPOCH_SEX`. Someone who edits the file elsewhere and changes `SEX` away from `U` wins over `_EPOCH_SEX`, since the tag only restores `X` when `SEX` is `U`.

## ADR-004 addendum: how the date columns are stored (Phase 1, S4)
- `events` gains nullable `date_sort_end`, `date_qualifier`, `date_precision` and `date_calendar` (migration 0007, expand-only). `date_sort` keeps meaning the inclusive lower bound, so nothing that read it changes. `date_raw` stays verbatim and is never rewritten.
- **One derivation.** `dateColumnsFor` (over `parseDateValue`) fills the columns on create, edit and import. `1900` is stored as year precision with bounds `1900-01-01`..`1900-12-31`, and `ABT 1900` keeps `ABOUT`; neither becomes a day. Text that is not a date is stored as `UNKNOWN` or `PHRASE` with no bounds, which is distinguishable from a row that has not been backfilled (all columns null while `date_raw` is set).
- **Old rows.** Readers use `eventDateValue`, which parses `date_raw` when the qualifier is null, so nothing depends on the backfill having run. `npm run db:backfill:dates` (add `-- --remote` for the deployed database) fills them; it leaves `version` and `updated_at` alone.
- **Undo.** Row-op images are generated from the Drizzle columns, so the new columns are in every before and after image. An image written before the migration lacks them and restores as null.
- **Deploy order.** The columns are nullable and defaulted, so the migration is safe before the code. The reverse order is not: the new code inserts the columns. The `deploy` script migrates first, and the request-time check (see `db/schema-status.ts`) answers 503 until every migration in the journal has been applied, so a mis-ordered deploy fails clearly instead of writing to columns that are not there.


## ADR-011: The bounded graph and the record pages (Phase 3, S5)
- **Context:** Every screen loaded the whole tree: the page fetched the tree details and an unfocused graph, and the drawer, dialogs and stats read from them. Phase 3 requires that test corpora do not need a whole-tree response.
- **Decision:**
  - **`GET /api/trees/:id/graph?focus=` answers a window, not the tree.** The parameters are the page's own (`up`, `down`, `siblings`, `step`, `exp`); the plan's `depth=` became `up`/`down` so the view's URL can be passed through. Without `focus` the endpoint still returns the whole-tree aggregate, for tests that assert on it; no screen calls that form.
  - **The window is built by the drawing rules, not by a second copy of them.** `loadFocusWindow` runs `selectFocusSubgraph` over what it has loaded, loads the neighbourhood of every person that selection draws and that is not yet loaded, and repeats until nothing new is drawn. What a neighbourhood means (partnerships with all their partners and child links, parents' unions with all children, parents' other partnerships for step-parents) is in `focus-window.ts`. People a union merely names are fetched as records and marked `isPartial`.
  - **Proof is equality, not size.** Tests compare `layoutFocusView` over the window with the same call over the whole tree, deep-equal, for every person as focus across depths, toggles, opened stubs and type filters, on The Simpsons, the representative scenarios and a generated 4,000-person corpus; a test that breaks the loader (drops step-parent data) fails.
  - **Reads are batched (one D1 round trip per stage), chunked under 100 parameters, and tree-scoped with a filter that cannot drive the query** (`+tree_id = ?`). SQLite otherwise picked the `(tree_id)` index and read the whole tree to return three rows; `docs/query-plans.md` records the measurement. No index was added.
  - **Row order is now explicit** (`ORDER BY rowid`) in `loadRows` and the window, because the union chronology tie-break, the default focus and the "first birth" depend on it.
  - **Person and partnership pages are read models over the same loader** (`PersonPageDto`, `UnionPageDto`), tested against the whole tree's derivation. Every DTO record carries `isPrivate`, always false until Phase 4 (`shared/privacy.ts`).
  - **One editor per tree.** `TreeEditor` (dialogs, confirmed removals, undo) and the toast store are created by `/trees/[id]/+layout.svelte` and read through context by the tree, person and partnership screens, because a toast after a delete must outlive the screen that was about the person.
  - **Navigation is serialised and optimistic.** With a load behind each address change the URL commits late; the tree page shows the new view at once, draws with the view its data was fetched for, and runs one navigation at a time so the history entry for a burst of clicks is still one.
- **Consequences:** Mutations still plan against a full `TreeRows` snapshot (`ChangeStore.loadRows`); bounding writes is the next scaling step. Counting people and partnerships for the header reads a covering index and is linear in the tree.

## ADR-012: Facts have their own columns and are addressed by id (Phase 3, S5)
- **Context:** `events` held a place and a single `description` into which the importer folded a CAUS, a NOTE or the line value, and export wrote it back as `NOTE`. A generic fact editor needs the parts, and two births must be able to coexist.
- **Decision:**
  - Migration 0008 (expand-only) adds `value`, `cause`, `age`, `notes` and `sort_order` to `events`. The importer fills them, export writes each on its own tag, and merge-mode de-duplication counts them as part of a fact's identity.
  - Rows written before it keep `description`, shown as a note and folded into `notes` the first time the fact is edited. **Old descriptions are not backfilled**, so an already-imported occupation reads as a note until edited.
  - Fact commands (`create_fact`, `update_fact`, `delete_fact`, `reorder_facts`) address a fact by id and never by type. The person form's birth and death fields still act on the first event of a type (`upsertEvent`); the form says so when a person has more than one, and the other facts are edited on the person's page.
  - The timeline is date first; `sort_order` orders only facts that tie. Two facts of a type a person has once (birth, death, ...) that differ are flagged as a pair; nothing is merged or hidden.
  - A change to a birth or death bumps the person's version (as recording a death already does), so a stale person form conflicts. Other facts do not, to keep undo of earlier person edits possible.
- **Known gaps:** History on the person page is found by record, so changes to a fact that was later removed are not listed. The parser still drops sub-structures under an event other than DATE, PLAC, CAUS, AGE and NOTE (such as SOUR).

## ADR-013: Person names (Phase 3, S6)
- **Context:** A person may have several `NAME` records (birth, married, aka, ...). Import kept only the last, export wrote one, and `NPFX`, `NICK`, `SPFX`, `NSFX`, `TYPE` and anything else under a `NAME` was lost, which broke the no-loss rule.
- **Decision (import and export):**
  - **Every `NAME` is a `person_names` row, in file order; the first is the preferred one** and its given name and surname are mirrored on `individuals`. Migration 0009 (expand-only) adds `version`, `nickname`, `surname_prefix`, `gedcom_type`, `gedcom_extra`, the from-date columns and `union_id`.
  - **Preserved sub-structures live on the name row** (`gedcom_extra`, verbatim lines) and not in `gedcom_preserved`. That table is keyed by the owner's XREF and headed by a line, which is how ADR-009 re-attaches `FAMC` extras; a name has no stable head line (edits change it, two names can share one), and `gedcom_preserved` is outside `RECORD_TABLES`, so deleting or undoing a name could not carry its `NOTE` or `SOUR`. The mechanism is the same (verbatim lines written back inside the owning structure); the storage is the ADR-008 argument for `xref_aliases`. `FONE` and `ROMN` are preserved this way and not modelled.
  - **Types.** `TYPE` is read case-insensitively. A word that is not one of the seven known types becomes `other` and keeps the word in `gedcom_type`; a 7.0 `OTHER` keeps its `PHRASE`. Export writes lowercase words in 5.5.1 (a free-text type as itself) and uppercase in 7.0 (`OTHER` plus `PHRASE`). An untyped `NAME` is `birth` when first and `aka` after that.
  - **`birth` is the default TYPE** and is left out of the first name written, so single-name files export exactly as before. It is written on any later name, because an untyped later name would read back as `aka`.
  - **The preferred name is written first**, since GEDCOM treats the first `NAME` as primary; the rest keep their order.
  - **Legacy `_MARNM`** (level 1 on the `INDI`, `Given /Surname/` or a bare surname; the bare form takes the primary name's given name) becomes a `married` name with `gedcom_type = '_MARNM'` and is written back as `_MARNM`, not as a `NAME`, so a re-read does not see it twice. Sub-tag or level-2 spellings are not modelled and stay as preserved lines. This tag is not confirmed against webtrees' source: `Individual.php` does not mention it.
  - **Merge-mode re-import** skips a name the person already has with the same type and parts, and never adds a second preferred name.
- **When a name came into use, and from which partnership (S6).** Epoch keeps an optional "from" date (`date_raw` and the ADR-004 columns) and an optional `union_id` on a name. GEDCOM has nowhere standard for either, so export writes one human-readable `NOTE` under the `NAME`, and import reads it back:
  - `2 NOTE Name in use from 8 OCT 2001, through family @F3@.`
  - Either half may be missing: `Name in use from 1998.` or `Name in use through family @F3@.` The pattern is exact, so an ordinary note is never mistaken for it, and a note that carries children (a `CONT` chain) is left alone.
  - The date is the verbatim text; the family is the file's XREF for the union. A note that names a family the file lacks stays as written under `gedcom_extra`, date included, and no column is filled, so export writes it once and a re-import is stable.
  - There is no foreign key on `union_id`: a cascade or `SET NULL` would change the row outside the logged ops and undo could not restore it. `destroy_union`, `remove_partner_from_union` (for that person) and `merge_unions` (to the survivor) rewrite it as ordinary ops.
- **Display name.** `individuals.given_name` and `surname` remain the display name, mirrored from the preferred name in the same atomic change that alters it, and the person's version moves only when the mirrored text does. The person form edits the preferred name row (`update_person` plans both), and `create_person` now writes a preferred row, so every new person has one. A person created before this has none; the first name command materialises one from their fields. The last name of a person cannot be deleted. The "(née X)" suffix is display only: `personName` stays plain because it feeds stored change-log summaries; `displayNameWith` (shared) adds it when the person has a `maiden` name, else a `birth` name, that is not preferred and whose surname differs.
- **Names a pre-S6 person form left stale (S6).** Before this slice the person form edited `individuals` and left the imported name row alone, so a person whose name was edited then has a preferred row that still says the old name. Export and the person page now read the preferred row's given name and surname from `individuals`, which was the edited source; after S6 the two always agree (`update_person` and the name commands write both), so this is inert for new data. No backfill script was needed: the local database has no drifted rows (`SELECT ... WHERE i.given_name <> n.given_name ...` returned none), but a deployed database may, which is why the read-time rule exists. It is not a fix for the stored row, which the next edit of that person corrects.
- **Known losses on a round trip.** The `NAME` line is rebuilt from the parts, so a line that disagrees with its `GIVN` and `SURN` comes back in the canonical form, and a nickname written inside the line (`Julius "Nick" /Vries/`) comes back as the `NICK` sub-tag or, when there is none, inside the given name. Round-trip tests compare parsed models, not text.
- **Undo and a name's partnership.** Undoing the creation of a partnership deletes it. A later name that points at it is listed by `dependentsOfDeletions`, so that undo is refused as it is for links and events.

## ADR-014: Recents and favourites are per-user D1 rows (Phase 3, S7)
- **Context:** The focus box and the tree pages should offer the people a user opened lately and the ones they chose to keep. They could live in the browser (`localStorage`, which Epoch already uses for the remembered focus) or on the server.
- **Decision:** A `person_marks` table (migration 0011, expand-only: a new table and two indexes), one row per `(user, tree, kind, person)` with `kind` `favorite` or `recent` and a `touched_at`. Recents keep the newest 20; a repeat moves the person to the front.
  - **Why the server, not the browser.** A favourite is something a person expects to follow them across their devices and survive clearing site data; `localStorage` does neither, and a private window or blocked storage would silently lose it. The remembered focus stays in `localStorage` because losing it costs nothing.
  - **Keyed by the internal user id.** The plan says "keyed by the stable Access `sub`". `users.id` is the row upserted from that `sub` (`users.access_sub` is unique and never reused), and every other table that belongs to a user (`tree_memberships`, the change log's actor) keys on `users.id`, so a mark uses it too. The `sub` itself stays the only link to Cloudflare Access.
  - **Cascade from the user and the tree, not from the person.** `user_id` and `tree_id` cascade, so deleting a tree or a user removes their marks. `person_id` deliberately has **no foreign key**: a cascade would delete the row outside the logged ops, so deleting a person and undoing it would silently lose their favourite (the reason `person_names.union_id` has none, ADR-013). Reads join `individuals`, so a mark for a person who is gone is not shown, and returns when the person does.
  - **Only `tree:view` is needed**, because a mark changes nothing in the tree; it is not logged and cannot be undone.
  - **A recent is recorded by an explicit `POST` from the page**, never by a `GET` or a load function. `app.html` sets `data-sveltekit-preload-data="hover"`, so a load that logged would record people whose links the pointer merely passed over.
- **Shared in place, not reloaded.** The mark endpoints answer with the user's lists, and the tree layout keeps them in a store the screens update from the response. Invalidating the layout load instead would refetch the tree summary (a linear count) on every person view and, on the tree page, the graph window behind `parent()`.
- **Consequences:** Marks are per user and so not in a GEDCOM export. Nothing prunes marks of people who were deleted for good; the newest-20 rule bounds recents, and favourites are a user's own list. Privacy (Phase 4) reaches marks through the same seam as search: a favourite of a person the user may no longer see must be filtered there.

## ADR-015: Who is private, and where it is decided (Phase 4, S8)
- **Context:** Phase 4 must keep living people from collaborators who should not see them, and a viewer must not be able to infer a private person through search, counts, lists, charts, exports or errors. S7's `filterForViewer` runs after the SQL page is chosen, so it cannot correct `hasMore`, page fill or a surname count.
- **Decision:** Privacy is a predicate in the query, beside `tree_id`, for the roles that are restricted. It is derived at read time from the person's events, not stored.
  - **Derived, not stored (measured).** The alternative was columns on `individuals` (a has-death flag, a birth upper bound) kept up to date by every writer: the mutation runner, each command, import, merge, undo, and a backfill that would also have to run remotely before any deploy. Two correlated lookups on `idx_event_entity` cost about 4.5 index rows per person, measured on the two-tree harness: a first page of the people list reads 217 (419-person tree) and 259 (5,324) rows against 51 for the unfiltered page; a page 100 deep reads 1,793 and 23,285 rows (about 4.3 per person), against 419 and 5,001. No `events` row of another tree is read, because the lookup is by the person's own id. The cost is paid only by contributors and viewers; owners, managers and editors run the unfiltered query. If a tree outgrows this, the stored column is the next step and the predicate is the only thing that changes.
  - **Living state.** A person is not living when they have a death, burial or cremation event (dated or not), or when the latest upper bound of their birth, christening or baptism dates is before a cutoff. The cutoff is computed in the service from an injected `now` and the tree's maximum-alive age, and passed as a parameter; SQL never calls `date('now')`, so tests are deterministic. A birth with no upper bound (`AFT 1900`, an undated `BIRT`) counts as unbounded, so the person stays private. `BEF 1900` is bounded and can make a person not living. Everyone with no such fact is indeterminate and therefore private.
  - **The threshold is Epoch's own choice, 120 years, configurable per tree.** It matches webtrees' `MAX_ALIVE_AGE` default (120, `app/Tree.php`), which was read from the source. webtrees also treats any event older than the threshold, and the ages of parents, children and partners, as evidence of death; Epoch uses only the person's own birth facts and so errs toward private.
  - **Override.** `individuals.privacy` is `auto` (derive), `public` or `private`, set by owners and managers; an override always wins. GEDCOM `RESN privacy` or `confidential` on an `INDI` imports as `private` and is exported back as `RESN privacy`; the line is not also kept in `gedcom_preserved`, so there is one source of truth.
  - **What each role sees.** Owner and manager: everything, and they set overrides and the tree settings. Editor: everything (an editor can change any record, so hiding one from them would only hide what they can already alter). Contributor and viewer: private people are absent. They are not masked in search, lists, marks and relationship search; a "Private" hit for a surname would itself say a private person exists, and the surname disappears from the surname list rather than shrinking. A private person's page, edit endpoints and any command that names them answer exactly like an id that does not exist (same status and body). A contributor therefore cannot link a new record to someone they cannot see.
  - **Placeholders only where structure is shown.** In the graph, and in the family a person's page lists (not in search, the lists or favourites), a private person is "Private", with no name, dates, places, sex or notes, when the tree setting `should_show_private_structure` is on (default off, so the safe behaviour needs no action). Off, they are omitted. The partnership list and a partnership's page never show a partnership with a private partner at all, because its marriage date and place are facts about that partner. Unions, links, events, names and notes of a private person inherit it.
  - **Export is a manager action.** `tree:export` was `viewer`, so any viewer could download the whole GEDCOM, living people included. It is raised to `manager`; a filtered export for lesser roles is a later slice.
  - **Writes.** A restricted viewer's command is planned over the rows they can see (a private id fails as a missing one) and then over all rows; the real ops are refused with a missing-permission error if they touch a private person. A preview needs the rights of the change.
  - **Doors that are not reads of a record.** Media reads and uploads check the tree and the record (and `Cache-Control` is `private`); the export workflow re-checks the requester's role when it runs; the tree-wide change log, `GET /api/trees/[id]` and `GET .../individuals/[id]` need an editor; and a tree with no members is no longer given to the first caller, which would have handed a second invitee every ownerless tree.
  - **GEDCOM.** `RESN privacy` and `RESN confidential` import as `private` and are not also kept in `gedcom_preserved`; other words (`locked`) are kept. `private` exports as `RESN privacy` (GEDCOM 7: `PRIVACY`), so `confidential` comes back as `privacy`; `public` has no GEDCOM word and travels as `_EPOCH_PRIVACY public`, as X does as `_EPOCH_SEX`.
  - **Editors see everyone (decided 2026-10-01).** The owner of the tree chose to keep this rather than restrict editors like contributors.
  - **A contributor sees the people they created (decided 2026-10-01, migration 0013).** `individuals.created_by` is stamped by `create_person` with the acting user and is null for imported and earlier people. For a contributor (`ViewerScope.creatorId`) a person whose override is `auto` and who they created is visible while private, in the SQL and in the pure rule; a manager's `private` still hides them, and another contributor or a viewer never sees them. The exception is the person only: their private relatives and partnerships follow the usual rules. A demoted contributor has no `creatorId`, so they lose sight of what they added. No foreign key, so deleting a user cannot cascade to people.
- **Consequences:** A person a contributor adds with no dated fact stays visible to that contributor, and private to everyone else restricted, until someone dates them. Reads for restricted viewers cost a small multiple of the unfiltered reads; the plans are re-measured in `query-plans.md` per read as the predicate is added. Revisit storing the derived state if a tree's surname list or a deep page becomes slow.

## ADR-016: Members and invitations (Phase 4, S9)
- **Context:** Identity comes from Cloudflare Access, roles are Epoch's own, and until now the only way to give someone a role was to write a row into the database. Privacy (ADR-015) is of no use until a second person can sign in with a role.
- **Decision:**
  - **An invitation is an email address and a role.** `tree_invitations` holds the tree, a lower-cased address, the role, the inviter and an expiry (14 days). There is one pending offer per tree and address; inviting again replaces the role and restarts the clock. It is taken up on **every** authenticated request, in `UserRepository.upsertFromAccess`, by an indexed lookup on the address Access asserts, so a person already signed up is given a second tree on their next request, not only on their first. An invitation never lowers a role the person already holds, and an expired one is not taken up (a manager sees it as expired and can invite again).
  - **Access is a separate gate.** An invitation does not let anyone past Cloudflare Access: the Access application policy must also allow the address. The app does not call the Access API, so it cannot add the address itself; the Members page says so. If the Access policy admits everyone with an address at a domain, the invitation is the only gate that matters, and that is the intended setup.
  - **Who may do what** (`shared/membership-policy.ts`, shared with the screen so it offers only what would succeed). Every call needs `tree:manage_members` (manager). An owner may give any role and act on anyone; a manager may give only roles below manager and act only on members below manager, never on a peer, an owner or themselves. Ownership therefore moves only by an owner's act. A tree may have several owners.
  - **The last owner cannot go.** Demoting or removing an owner is refused unless another owner remains, and the check is part of the `update`/`delete` statement itself rather than a count read first, so two owners demoting each other at once cannot both succeed (tested with a concurrent pair).
  - **Concurrency.** `tree_memberships.version` (migration 0014, default 1) is checked and bumped by every role change; a stale version answers 409 with the current one, and the screen reloads after every action.
  - **Who sees the list.** Only managers and owners. An address is personal data, and the list names who else has access; an editor or lower gets the same 403 as for any manager action.
  - **Effect is immediate.** Nothing caches a membership; every service reads it per request, so a removal or a role change applies to the next request (tested).
  - **No audit of membership changes yet.** They are not in the change log, which is a log of tree content. An audit entry (who invited, changed or removed whom) belongs to Phase 4 item 7.
- **Consequences:** The privacy matrix lists the four new endpoints. `e2e/privacy.spec.ts` now gets its second user by a real invitation. Deploying needs migrations 0013 and 0014 applied first (both expand-only: a nullable column, a new table, a defaulted column).

## ADR-017: Kinship and the charts (Phase 3, S10)
- **Context:** Phase 3 left a relationship calculator and ancestor and descendant charts open. Both follow descent, and both can reveal private people, so they share one bounded loader and one masking step.
- **Decision:**
  - **Routes, not a shortest path.** The calculator reports every way two people are related: the same person, a partnership, blood routes nearest first, then routes by partnership. A pedigree that folds back on itself, or a double cousin, has more than one, and each says through whom and by which link types (a non-biological link is named).
  - **Which common ancestors count.** Of the common ancestors of two people only the lowest do: one that is an ancestor of another common ancestor is the same relationship seen from further up. Two lowest ancestors at the same distance who are parents of one child are a couple and one route, which is what makes a sibling full and not half. A single lowest ancestor gives a half-sibling and a plain cousin: "half-cousin" is not used, because the route already names the one ancestor.
  - **Words.** M or F gives the gendered word (uncle, niece, grandson); anything else the neutral one ("parent's sibling"), because sex is a recorded fact, not a role. Cousins are "Nth cousin K times removed".
  - **By partnership.** A partner of the other person's relative, or a relative of their partner, is a route ("partner of 1st cousin", "step-parent", "sibling-in-law"). It is withheld only when the second person is a direct-line relative of the first (a grandfather is his wife's partner, and that says nothing new, and a real parent must never be called a step-parent). A step-parent who is also a cousin has both routes. Step relationships are not stored; they are this route.
  - **One loader, masked in memory.** `loadKinWindow` follows links generation by generation to a limit and a total of 3,000 people; the caller masks the rows for the viewer exactly as the record pages do (`maskRows`, `privatePeople`), so the SQL predicate of ADR-015 is not needed here and the cost is the same for every role. A private subject answers as a missing one. Omitting private people can hide a relationship that only a private ancestor makes, and says nothing about it; with the tree set to show private structure the route shows a "Private" step with no name or dates.
  - **Pedigree slots.** A person has two slots, parents in heap order (father before mother by sex, then id). Where more than two parents are recorded, biological parents come first, then adoptive, foster, guardian and unknown, and the chart shows two; the person page lists every one. A lone mother takes the second slot. The chart says when more generations exist beyond the limit.
  - **Descendants** list children below each person with every partner on the card (a person's children across partnerships appear together in birth order, not under the partnership they came from). Pages: `/people/[id]/pedigree` and `/descendants` with the depth in the address (default 4, at most 8); a card leads to that person's chart.
- **Consequences:** The calculator and charts are read-only and add no migration. The chart cards are links in a grouped SVG; ADR-020 added a text list of the ancestors, and later one of the descendants.

## ADR-018: A place is the text on a fact; no stored reference yet (Phase 1 `place_ref`, Phase 3 item 4, S10)
_Partly superseded by ADR-019: a place record now exists. The text stays the authority, as decided here._
- **Context:** Phase 1 asked for `place_ref` beside the literal place text, "initially allowing unresolved places"; Phase 3 asked for a place literal or reference in the fact editor; Phase 7 owns hierarchical, merged and geocoded places. A stored `events.place_id` would have to be written by every path that writes an event (person and fact commands, import in both modes, union merge, undo and redo), and an undo of a change logged before the column existed would drop it. ADR-015 turned down a stored privacy column for the same list of writers.
- **Decision:** Epoch has no stored place reference. A place is the text a fact carries, grouped without regard to ASCII case (SQLite `nocase`), so the text stays the single authority: export is byte-identical (no `PLAC` line changes), import and undo have nothing to keep in step, and no existing row needs filling in, so the migration is only an index (`idx_event_place (tree_id, place collate nocase)`, migration 0015, expand-only).
  - **Places list and place page** (`/places`, `/place?name=`): the places a tree's facts name, with the number of facts and people, and the facts at one place. A place is found by its text; `?q=` finds a substring (LIKE wildcards are escaped).
  - **Privacy.** Counts and lists are built from `andVisible` for a person's fact and an all-partners-visible test for a partnership's fact, so a place only private people or a couple with a private partner give is absent, and its page answers as a place nobody wrote does. A contributor's creator term is in the same predicate; the plan test holds viewer and contributor answers identical.
  - **Fact editor** suggests places already used as the user types, so one place keeps one spelling. A suggestion only fills the text.
  - **Facts link to their place** from the person page and the partnership page.
- **What this does not do:** it does not merge two spellings ("Cork" and "Cork, Ireland"), rename a place across facts, hold a hierarchy, coordinates or a historical name, or search by place hierarchy. Those are Phase 7, and are what a stored reference or a places table would be for; when it is built it should be keyed by tree and a normalised form of the text, with the fact's own text still authoritative.
- **Consequences:** The place list and a restricted viewer's version cost about one pass over the tree's events (query-plans.md, Places). Phase 1's wording is met in spirit (a place can be shared and looked up) and not in letter (there is no `place_ref` column); this is a recorded departure.

## ADR-019: Place records derived from the fact's text; rename and merge (Phase 1 `place_ref`, S11)
- **Context:** ADR-018 shipped places as grouped text and left a stored reference for later, because every writer of an event (commands, import, union merge, undo) would have to keep it right, and an undo of a change logged before the column existed would drop it. The owner then chose the record-backed version, with the fact's text staying authoritative and a merge being one undoable change.
- **Decision:** `places (id, tree_id, name_key, created_at)`, unique on `(tree_id, name_key)`, and a nullable `events.place_id` (migration 0016, expand-only, with a backfill that is safe to re-run). `name_key` is the place text in ASCII lower case, which is what `lower()` and `nocase` both mean (`placeKey`, not `toLowerCase()`).
  - **The reference is derived, never written by a command.** The change store, in the same batch as the ops, upserts a record for the text of every fact it writes and points the fact at it; the importer and test corpora do the same set-based (`pointFactsAtPlaces`). So commands, a union merge and an undo of a change logged before the column existed come out right without knowing about records. `placeId` is left out of row images (`EventRow`, `toImage`), so a logged image never has to match it and undo's "is the row unchanged" test is unaffected.
  - **A record is its text.** A new text is a new record; the old one stays, empty (never deleted), so an undo, which restores the old text, finds the same record and id. The place list and page are over facts, so an empty record shows nowhere. Export is byte-identical: `PLAC` is the fact's own text.
  - **Rename and merge are one command**, `rewrite_place`: every fact at the place gets the new text, as ordinary event ops, so one change, one preview and one undo. A name that another place already has is a merge, and the facts take that place's own spelling (visible to the caller only); a name with only a different case changes the case. Person versions move for a birth or death, as `update_fact` does, so a stale person form conflicts.
  - **Limits and privacy.** At most 200 facts per change (`MAX_PLACE_REWRITE_FACTS`): D1 counts each statement of a batch as a query and allows 1,000 per invocation, a fact costs up to four, and the change log keeps a change as one JSON value in a row capped at 2 MB. Editors and above only (`record:edit`), who see everyone; a contributor or viewer is refused, and a place they cannot see answers as a place nobody wrote (the refusal names the record id, never the text).
- **What this does not do:** hierarchy, coordinates, historical names and maps (Phase 7) and merging by anything but the text. Facts added to a place after a rename was planned stay at the old text; repeat the rename. `idx_event_place` (migration 0015) is kept for the suggestion search and can be dropped by a later contract migration if it stays unused.
- **Rollback:** code from before ADR-019 writes facts without pointing them at a record, so after a rollback and a roll forward, re-run the two backfill statements of migration 0016 (safe to repeat).
- **Consequences:** The place list is unchanged in cost; one place's facts cost about 1.5 times what they did (the record lookup), measured in query-plans.md. Phase 1's `place_ref` is now met in letter as well as spirit.

## ADR-020: Fan and hourglass charts, and a text list of ancestors (Phase 6 item 4, S12)
- **Context:** S10 shipped the pedigree and descendants charts as SVG over the privacy-masked kin window (ADR-017) and recorded two gaps: no fan or hourglass style, and no text version of a chart.
- **Decision:** two more styles over the same two reads, with no new endpoint and no migration.
  - **Fan** (`/people/:id/fan?generations=`): the pedigree's heap-ordered slots drawn as rings of wedges over a half circle, the person in the bottom-centre disc and each person's parents side by side in the wedge span above them. Pure geometry in `charts/fan-layout.ts`; at most 7 generations (`MAX_FAN_GENERATIONS`), where the outer ring's 64 wedges are about 3 degrees each. Text on the outer rings runs along the radius, turned so it never reads upside down, and is cut to the room a wedge has; the full name and dates are the wedge's `<title>` and link label, and the list below carries them all.
  - **Hourglass** (`/people/:id/hourglass?up=&down=`): descendants to the left of the person and ancestors to the right, on one canvas, at most 6 generations a side. It is the descendants and pedigree layouts side by side with the person's card shared (`layoutHourglass`), loaded with the two existing chart reads, so what a restricted viewer sees is exactly what the two charts show them.
  - **Style links** on all four pages (`ChartStyleNav`) carry the person and the depth between styles, and the depth steppers are one component (`GenerationStepper`).
  - **Text list** (`AncestorOutline`, on the pedigree and fan pages): the slots as a numbered list, a person's parents being twice their number and twice plus one, so the chart is available without the picture.
- **What this does not do:** a descendants-only fan, a compact or book layout, and printing or export of a chart (Phase 6). The descendants and hourglass charts first had no text version; a nested list of descendants (`DescendantOutline`) now sits on the descendants page, and the hourglass page carries both lists.
- **Consequences:** The new pages read exactly what the existing chart endpoints read, so the plans in query-plans.md (Kin window) apply unchanged and the privacy matrix needed only the two page loads.

## ADR-021: Data-quality report with stored dismissals (Phase 5 items 6 and 7, S13)
- **Context:** Phase 5 asks for checks that find impossible or implausible history, classed as errors, warnings or research suggestions, deterministic, explainable, privacy-aware and dismissible with a reason, and that never reject an unusual history for being unlikely.
- **Decision:** a report page (`/trees/:id/quality`, `GET /api/trees/:id/quality`) over findings that are computed on every request and never stored.
  - **Rules** are pure functions over the tree's rows (`domain/quality-checks.ts`), listed with severity and a "why this is flagged" sentence in `shared/quality.ts`. A date is the range of days it could mean (`boundsOf`); a rule fires only when the range makes it certain, so "ABT 1900" or "BEF 1900" never convicts. A person with two births is taken at the widest span. Parent age and birth-order rules apply to biological links only, since an adoption can follow a birth by years. Thresholds (under 12, over 120, a year after a death) sit far outside what happens, and a finding never blocks a save.
  - **Findings have a stable key** (rule plus the records it is about), so a dismissal keeps matching until the data changes shape. Dismissing stores the key and a required reason in `quality_dismissals` (migration 0017, a new table, expand-only), shared by the whole tree and not logged: it changes no record, there is nothing to undo, and restoring is one click. `dismissed_by` has no foreign key, so removing a user keeps their decision.
  - **Privacy:** the rows are masked first for a restricted viewer (the same `maskRows` as every other row reader), so a finding names nobody they cannot see and a rule cannot hint at a hidden person by firing. A dismissal is listed only while its finding still fires for the viewer. Anyone with `tree:view` reads; `record:edit` (editor) dismisses and restores. Dismissing a key that is not a current finding is refused as not found.
  - **Bounded output:** at most 100 findings a rule are returned, with the full count, so a badly tangled tree stays readable.
- **What this does not do:** unsourced key facts (no source records until the evidence slice), privacy-leak checks beyond the masking above, research tasks attached to findings (Phase 5 item 8), and a rule for every oddity. Partnership chronology warnings stay on the partnership page (`union-warnings.ts`).
- **Consequences:** The report loads every row of the tree once (`ChangeStore.loadRows`), like an export, and is linear in the tree; it is a page someone opens on purpose. A tree too large for that would need the checks moved to SQL, which the rules' pure shape allows one at a time.

## ADR-022: Merging two records of one person (Phase 5 item 5, S14)
- **Context:** An imported or hand-entered tree often holds one person twice. Phase 5 asks for explicit merge with field-by-field review, a relationship impact preview and reversible history, and for merge never to rely only on names and dates or silently lose links or evidence.
- **Decision:** `merge_people` is a relationship command like `merge_unions`: the record that stays (the survivor) absorbs the other (the merged record), which is deleted, in one change with one undo. Review and preview are read-only (`POST /people/:id/merge/impact`); the merge is `POST /people/:id/merge`. It needs the rights deleting needs (an editor).
  - **Nothing is picked for the user where both can be kept.** Facts are repeatable, so two different births are both kept and only a fact stated identically twice collapses. Names move as non-preferred names; the survivor stays the preferred one. A record whose name lives only on the person row keeps it as an "also known as". Parentage is re-pointed, and a link the survivor already asserts is the same assertion and is dropped. A sex that differs is the one thing that must be chosen, as a partnership merge makes the user choose. Privacy can only tighten: "private" on either record is kept.
  - **Who cannot be one person** is refused with a reason before any preview: the same record, an ancestor and a descendant at any distance, the two partners of one partnership. Siblings are allowed, since the commonest duplicate is one child entered twice under the same parents; the repeated parent links collapse.
  - **First birth.** "First" is the order rows were written, and cards and the person form read it. A moved birth or death (a singular fact) is therefore written anew behind the survivor's, so the survivor's stays the first on file; the review notes when a person ends up with two births. Other facts keep their row.
  - **Row order and cascades.** The store applies creates, then updates, then deletes, so every row that points at the merged person is re-pointed or deleted before the person is, and no foreign key cascade removes a row outside the log. A test requires the rows after an undo to equal the rows before the merge by content; undo of a delete recreates the row, so a recreated row can come back later in the table than it was, which is how undoing `delete_person` already behaves.
  - **XREF.** `individuals.xref_aliases` (migration 0018, an expand-only nullable column) keeps the merged record's XREF on the survivor, in the logged row so undo restores it. Export maps those aliases, and now every `@…@` pointer in a retained line, to the surviving record, so a retained `ASSO` or custom tag never points at a record that is gone. This also closes the same gap for merged partnerships.
  - **Marks.** Favourites and recents are per user and not in the change log, so a move could not be undone. They are copied to the survivor and the originals left; an undo brings the other person back with their own, and the survivor keeps a harmless copy.
  - **Size.** One merge writes at most 300 rows (`MAX_PERSON_MERGE_OPS`), from D1's 1,000 queries per invocation as for ADR-019; a test merges and undoes a person at the limit and refuses one more.
  - **Finding duplicates.** The quality report (ADR-021) gets one suggestion per group of people with the same name and births that could match, never for a name alone and never one per pair; it links to the people, and the merge starts from either person's page.
- **What this does not do:** merge more than two at once (repeat it), compare automatically on fuzzy names or places, re-point pointers inside raw lines that are not XREFs, or teach merge-mode GEDCOM import about person aliases: re-importing the same file in merge mode would add the merged person back, as it would after deleting them.
- **Consequences:** Undo restores every row with a higher version than the live one (the existing rule), so a stale editor cannot match it. The partnership merge stays the way to fold duplicate partnerships a person merge can leave behind, and the review says when it did.

## ADR-023: A file's evidence is kept whole before it is modelled (Phase 5 item 9, S15a)
- **Context:** Phase 5 asks for sources, repositories, citations and notes as records. Before modelling them, a round trip of a file that has them was measured, and it was not lossless: root `SOUR`, `REPO`, `NOTE` and `OBJE` records were kept in `gedcom_preserved` but never written back (only records with no XREF were); everything under an individual or family event other than `DATE`, `PLAC`, `CAUS`, `AGE` and its first note (a citation and its `PAGE` and `QUAY`, further notes, custom tags) was dropped on import; and a replace-mode import left the previous file's preserved lines in place, so a second import wrote them twice.
- **Decision:** make the round trip whole first, with no new model.
  - **Root records** are written after the last record, once each, in both GEDCOM versions. Only entries that start at level 0 are, so a person's retained extras are not mistaken for records, and structures kept under a person who has since been deleted still go with them.
  - **Event extras:** `events.gedcom_extra` (migration 0019, a nullable column, expand-only) holds every line under an event that has no column, verbatim from level 2 down and in order, for individual and family events alike. It is a column on the row, as for names (ADR-013), so a fact's extras follow it through edit, merge (a re-created birth copies them) and undo. A note with continuation lines, or a second note, is an extra; the first plain note stays the `notes` column.
  - **Pointers** in event extras and name extras go through the same remap as retained lines, so a pointer to a person merged away (ADR-022) is written against the survivor.
  - **Importing again:** replace mode now removes the previous file's preserved lines; merge mode does not keep the same lines under the same owner twice. A fact's extras are part of its identity for merge de-duplication, so the same fact with a different citation is a different fact.
- **Known limits, kept as before:** lines under a `DATE` or `PLAC` (a `PHRASE`, a `TIME`, a `MAP`) are not kept, and a family event's line value is written back as a note. Trees imported before this change lost what is described above and keep losing it until the file is imported again; the data cannot be recovered from the tree.
- **Consequences:** The baseline test (`evidence-roundtrip.test.ts`) holds the file's every non-header line, the placement of a citation inside its fact, name and family, a citation of a record that is not in the file, and that a second export, a replace import and a merge import change nothing. S15b models sources, repositories, citations and notes on top of it: what it models moves out of these lines and into tables, and what it does not stays where it is.

## ADR-024: A public welcome page, and the paths Access must let through
- **Context:** Every page sat behind Cloudflare Access, so a link to Epoch shared anywhere unfurled as the Access login screen, and a visitor whose token failed validation saw an error from the first API call a page made. The app also still carried the stock Svelte favicon.
- **Decision:** `/welcome` is the one page served without an identified user (`server/auth/public-routes.ts`).
  - **What it shows:** the Epoch mark, name and one line, as a full-window version of the link-preview card, with Open Graph tags pointing at `/brand/og-image.png`. It reads no tree, so there is nothing on it to hide; its load returns only whether someone is signed in. It ships no client code (`csr = false`), so it cannot later grow an API call by accident.
  - **Sign-in is a link to `/` (superseded by ADR-026: it links to `/login`).** Epoch has no login endpoint; following any protected path is what makes Access ask who you are. A signed-in visitor sees "Continue to your trees" instead.
  - **The hook sends a signed-out page load to `/welcome`** (303). API calls keep their 401, client-side data requests are left alone (a redirect would hand them HTML), and only GET and HEAD are redirected. Deny by default is unchanged: the redirect replaces an error, it grants nothing.
  - **Superseded by ADR-026:** *Access must bypass the page and what it loads.* No second, Bypass application is needed any more; one Access application covers only `/login`.
- **Brand assets:** the mark (two partners, their child, faded lines to the generation before) is drawn once in SVG under `static/` and `static/brand/`, and `npm run brand:render` rasterises the PNGs and ICO with the Playwright Chromium used for e2e. `EpochMark.svelte` draws the same geometry in the app.
- **Consequences:** Without the bypass Access still intercepts `/welcome`, which is safe (nothing becomes public) but means shared links unfurl as the Access screen. With the dev bypass on, every request has a user, so the welcome page shows its signed-in state locally; run without `ACCESS_BYPASS_DEV` to see the signed-out one.

## ADR-025: Lint and format toolchain (architecture review §4, Phase A)
- **Context:** AGENTS.md promises Prettier, a type-aware `@typescript-eslint/naming-convention` rule for booleans, Svelte-aware linting and a dead-code check, and none is installed (70 files use two-space indents, 285 use tabs). The Rust-based tools (oxlint, oxfmt, Vite+) are attractive, so they were checked against the docs on 2026-10-02 before the established tools were chosen.
- **Evidence, by question** (docs; none of the oxc/Vite+ claims below was exercised in this repo):
  1. **oxfmt and `.svelte`.** It lists Svelte as supported, but delegates to bundled Prettier and needs the `svelte` package and the `svelte` option ([language support](https://oxc.rs/docs/guide/usage/formatter/language-support.html)); only the `<script>` is formatted natively. It has `sortTailwindcss`, documented as "the same algorithm as prettier-plugin-tailwindcss" ([config reference](https://oxc.rs/docs/guide/usage/formatter/config-file-reference.html)). Whether that sorting reaches Svelte markup was not stated, and was not tried.
  2. **oxlint and `.svelte`.** It lints only the `<script>` blocks; it has no Svelte rules (no runes or a11y checks) ([linter overview](https://oxc.rs/docs/guide/usage/linter.html)). JS plugins (alpha) cannot load `eslint-plugin-svelte`: custom parsers such as Svelte are listed as unsupported ([JS plugins](https://oxc.rs/docs/guide/usage/linter/js-plugins.html)).
  3. **The boolean naming rule.** `naming-convention` with `types: ['boolean']` needs type information. oxlint's type-aware mode (tsgolint, stable, TypeScript 7) implements 60 of 62 targeted typescript-eslint rules, and `naming-convention` is one of the two that are not ([tsgolint README](https://github.com/oxc-project/tsgolint#implemented-rules)). JS plugins have no type information either. So oxlint cannot express the rule at all, and the smallest working set is a full ESLint with typescript-eslint beside it, for this rule alone.
  4. **Vite+** (1.0, MIT, [repo](https://github.com/voidzero-dev/vite-plus)). It claims SvelteKit support in general, but its docs say nothing on adapter-cloudflare, `getPlatformProxy`, `wrangler deploy workers/entry.ts`, the two-project Vitest config, or `nodeLinker`. It moves `dev`, `build`, `test` and `check` behind its own `vp` commands, and `lint` and `fmt` settings into `vite.config.ts`. It adds nothing for question 3, since it bundles the same oxlint. None of the build and deploy items could be verified without migrating the project.
- **Options:**
  - **A. oxlint + oxfmt + knip.** Cannot enforce the naming rule or lint Svelte; formatting `.svelte` still runs Prettier underneath. Fails two goals.
  - **B. Vite+ + knip.** Same linter gap as A, plus a migration of the dev, build and test entry points that AGENTS.md "Important Notes" 1–2 depend on, with the Cloudflare items unverified.
  - **C. Prettier (+ svelte and tailwindcss plugins) + ESLint flat config (typescript-eslint type-aware, eslint-plugin-svelte) + knip.** Meets every goal with documented, mature tools. Needs ESLint in any case (for 3 and for Svelte rules).
  - **Hybrids** (oxfmt for TS and Prettier for Svelte, or oxlint beside ESLint) each add a tool and still need ESLint and Prettier, to save time on a repository of about 350 files.
- **Decision:** option C. It is the one set with no moving part that exists only to be replaced: ESLint is required for the naming rule and Svelte rules whichever formatter is used, and Prettier is what AGENTS.md already documents and what the Tailwind and Svelte plugins target. One `npm run lint` runs the format check, ESLint and knip. `prettier-plugin-tailwindcss` is pointed at `src/app.css`, as Tailwind 4 has no config file to read.
- **Revisit when** (a) tsgolint implements `naming-convention`, and oxlint gains Svelte rules or a Svelte-capable JS-plugin parser (then ESLint can go and oxlint replace it), or (b) someone runs Vite+ in this repository through dev against local D1, build, `wrangler deploy workers/entry.ts --dry-run`, both Vitest projects and the e2e specs, and records the result. Until then neither is adopted.
- **Consequences:** Two more config files (`prettier`, `eslint`) and one for knip. ESLint's type-aware pass is slower than oxlint's would be (about 20 seconds over the repository); `npm run lint` is for the push gate, and `npm run format` and editor integration cover the edit loop. Knip reports as warnings until Phase B removes what it finds.

## ADR-026: One Access application on `/login`; the Worker gates everything else
- **Context:** ADR-024 needed a second Access application with a Bypass policy so the welcome page and its assets could be public, and anything Access did not cover was an easy misconfiguration. Two applications per host is more to keep in step than the app needs.
- **Decision:** exactly one Access application, covering only `<host>/login`. Every other path is ordinary Worker traffic, and the Worker is the gate.
  - **Flow:** a signed-out page load is redirected (303) to `/welcome?next=<path+search>`. "Sign in" links to `/login?next=…`; Access authenticates the visitor, sets `CF_Authorization`, and the request reaches Epoch's `/login`, which redirects to `next`. Later requests carry the cookie on every path and the hook validates it (signature, issuer, audience, expiry) as before.
  - **`next` is untrusted.** `safeNextPath` resolves it against a placeholder origin and keeps only a same-site path; `/login` and `/welcome` are refused so a redirect cannot loop.
  - **A token that fails validation goes to `/login`, not the splash:** the visitor has signed in before, so Access can usually renew the session silently. `/login` with no user never redirects: it renders a message, because Access let the request through but Epoch could not verify it (wrong AUD, clock skew) and a redirect would loop.
  - **The browser handles an expired session:** a 401 from the API makes the client do a full navigation to `/login?next=…` (not `goto`; Access has to see the request). API calls themselves still answer 401.
  - **The dev bypass is honoured only on `localhost`, `127.0.0.1` or `[::1]`.** Access used to catch a stray `ACCESS_BYPASS_DEV=true` at the edge; now it would open every path but `/login`, so the hook ignores the flag elsewhere and logs a warning.
- **Cloudflare behaviour relied on:**
  - *Verified in the docs:* the application's `CF_Authorization` cookie is scoped to the domain, so it is sent on every path, **unless the application's "Cookie Path Attribute" setting is on**, which restricts it to the application's path (`/login`). Leave it off. ([Authorization cookie](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/)) `<host>/cdn-cgi/access/logout` is documented per application domain. ([Session management](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/))
  - *Assumed, verify on first deploy:* `Cf-Access-Jwt-Assertion` is injected only on paths Access protects, so elsewhere the cookie is all there is (`extractAccessJwt` reads both, so the code is correct either way). Also leave "Binding Cookie" off: it is enforced only at Access, so on other paths it protects nothing and the docs warn of redirect loops with some products.
- **Given up:**
  - The Worker is now the only gate; a bug in the hook is no longer backed by Access at the edge.
  - Anonymous traffic reaches the Worker (and its cost) on every path.
  - Session expiry is handled by the app, through the redirects above, not by Access.
  - Service tokens only work against `/login`, so scripted API access with them is not possible until a design for it exists.
- **Consequences:** `/login` joins `/welcome` as a page served without a user (`PUBLIC_PAGE_PATHS`). The welcome page and `/login` share `Splash.svelte`. Access-application changes are made by hand in the dashboard; see the README.

## ADR-027: One person view, in two frames; the open drawer lives in the query string
- **Context:** the tree's drawer and the person page read one `PersonPageDto` but had grown into two half-editors: each did things the other could not (relative removal, partnership edits and media upload only in the drawer; names, facts, privacy, history, merge and favourites only on the page), and the same data was worded and laid out differently. Architecture-review step E5 was skipped for that reason, since sharing components would have changed one screen's output throughout.
- **Decision:**
  - **One view, deliberately converged.** `PersonView` composes section components in `src/lib/components/person/` (summary, family, names, facts, notes, evidence, media, privacy, history, actions). Each owns its actions and dialogs, and hides what the viewer's role cannot do (`person-permissions.ts`, the same rules as before). The screens were made alike on purpose, so every action exists in both frames.
  - **The one real difference is an input.** Clicking a relative selects in place on the canvas and follows a link on the page. `relativeTarget` (`select` or `link`) carries that, and `PersonLink` renders a `<button>` or an `<a>`. Merge reads it too, to land on the surviving record in the same way. No other per-frame prop exists.
  - **Two layouts.** `page` is two columns on a wide screen (records left; family, privacy and history right), one on a phone. `drawer` is one column of native `<details>`/`<summary>`, with the heading an `<h3>` inside the summary so axe and role queries still see it. Family and Facts start open. Which sections the viewer opened is kept in `localStorage` per section, not per person, behind try/catch.
  - **The drawer belongs in the URL as `person`,** beside `focus`, in `tree-url.ts`; an absent parameter means closed. Opening goes through the tree page's `navigate` and pushes an entry, so Back closes it, a reload keeps it, and a link can be shared. `person` is not among the parameters the load reads, so opening or closing refetches no graph. An unloadable person (a stale link, a deletion) closes the drawer with a replaced entry, so Back cannot return to a drawer that will not open.
  - **Not shallow routing.** Pushing `/trees/x/people/y` with `pushState` would move the path, but the tree page keeps its view in the query string and writes the resolved `focus` back from `page.url`; moving the path would fight that effect and lose depths, toggles and opened stubs.
- **Given up:**
  - The drawer is longer: every section is in it, though most are folded.
  - Relatives look the same on both screens, which changes both: the drawer lost its bordered cards for plain rows, and the page gained trash buttons and add links.
  - The person page's header buttons moved from the right of the name to beside it, and Privacy moved into the right column.
  - A docked side-by-side layout is not built; `PersonView` makes it a third `layout` value rather than another fork.
- **Consequences:** `PersonDrawer` is a frame only (fixed panel, Close, Escape, Open full page, focus to the heading on open, focus back to the opening card on close). The page is a breadcrumb and a `PersonView`. No API, DTO or schema changes. Supersedes the E5 skip in `docs/architecture-review.md`.

## ADR-028: Sources, repositories and citations are records (Phase 5 item 9, S15b)
- **Context:** ADR-023 made a file's evidence round-trip whole as retained lines. Phase 5 asks for sources, repositories and citations to be records: shown beside the facts they support, editable, privacy-aware and still lossless.
- **Model** (migration 0020, expand-only; nothing dropped):
  - `sources` (title, author, publication, abbreviation, text, XREF and aliases, `created_by`), `repositories` (name, address as text), `source_repositories` (a source's `REPO` links in order, with call number; a `REPO` with no pointer, or one the file does not resolve, is kept with its raw pointer).
  - `citations`: one `SOUR` substructure, **owned by exactly one subject** (`person`, `name`, `event`, `union`, `parent_child`), in `sort_order`. `source_id` is null for a 5.5.1 citation with inline text (`description`) or a pointer to a record the file lacks (`source_ref`, written back as it was). `page`, `quality` (`QUAY` 0 to 3), `DATA.DATE` in the ADR-004 columns, `DATA.TEXT`.
  - **Lossless by construction:** a structure is modelled only when it can be written back exactly. Every other line stays verbatim and in order in `gedcom_extra`; a second `PAGE`, a `DATA` with anything but one `DATE` and one `TEXT`, `OBJE`, notes and custom tags all stay there. `gedcom_layout` keeps a text field's own `CONT`/`CONC` split and is used only while it still says the column's text, so an edit always wins. Kept lines are moved to the level they are written at, so a citation can move between kinds of subject.
  - Roots, shared notes (`NOTE`, `SNOTE`), `OBJE` and citations under anything not in the subject kinds stay retained. A child's `FAMC` citations belong to the first parent's `parent_child` row and export once per link. A retained root whose XREF a row now holds is not written twice.
- **Import and identity:** sources and repositories are identified by XREF or an alias (merged sources keep the merged XREF as an alias); a citation by subject, source, inline text, page and text. A merge-mode import adds a citation a second file has on a fact the tree already holds, and writes nothing twice. A fact's identity no longer includes its citations (they were in its extras under ADR-023).
- **Backfill:** `scripts/backfill-evidence.mjs` moves the lines a tree kept before this change into records using the import's own parser and row builders (`gedcom/evidence-backfill.ts`), and removes what it stored; idempotent; a line it cannot place stays. A test requires an old-way import plus backfill to equal a fresh import in rows and in both exports. Until it runs, an old tree's evidence stays where it was and still exports.
- **Writes:** `EvidenceCommand`s go through the mutation runner (preview, log, undo, STALE_VERSION 409). Deleting a cited source answers `SOURCE_IN_USE` with the count unless told to remove the citations. A command that deletes a subject takes its citations (`citationCascadeOps`); person and partnership merges move them to the record that now says the same thing, and the citations of a fact a partnership merge did not keep go to the partnership, so none is dropped. Previews say how many carry over. A change that writes more than 300 records is refused (as ADR-022).
- **Roles:** the right is checked before a command is planned, so a lesser role is never told a domain fact (such as how many citations a source has). Adding a citation, a source, a repository or a link is `record:create` (contributor); editing, reordering and unlinking `record:edit`; removing a citation, deleting or merging is `record:delete` (editor). Adding a citation does not bump its subject's version.
- **Privacy:** a citation is visible only if its subject is (a partnership needs every partner visible). A source is listed and served only if it supports a visible citation or the viewer made it; a repository if a visible source is kept there or the viewer made it; otherwise a 404 like a private person. The SQL (`with vp` over visible people, a five-term compound select) and the row filter (`maskRows`) are held to the same answers by a test; the nested form passed D1's 100-level expression and 5-term compound limits. Export stays manager-only and carries everything.
- **Quality:** `unsourced_key_fact`, a research suggestion for a birth, death or marriage (`KEY_FACT_TYPES`) that no citation of the fact itself supports, one per fact.
- **Given up:** structured address parts are dropped when an address is edited (the layout is stale then); a restricted viewer's source list costs the visible-people set per request; the `OBJE` in a citation is retained, not linked.
- **Consequences:** `TreeRows` carries the four tables, so every mutation loads them. S15c models shared notes and tasks on this footing.

## ADR-029: Notes are records; research tasks are Epoch's own; privacy-leak checks (Phase 5 items 6, 8 and 9, S15c)
- **Context:** ADR-028 made sources and citations records and left every note as a retained line. Phase 5 also asks for research tasks and the last quality check, privacy leaks.
- **Notes** (migration 0021, expand-only):
  - `notes` is one root `NOTE`/`SNOTE` record: XREF and aliases, text, `MIME`, `LANG`, `gedcom_layout` for its `CONT`/`CONC` split, `gedcom_extra` for the rest, `created_by`. `note_attachments` puts a note on one **subject** (person, name, fact, partnership, parent link, source, repository or citation), in `sort_order`: inline (the attachment holds the text) or a pointer at a shared note (a 5.5.1 `NOTE @N1@` and a 7.0 `SNOTE @N1@` are the same attachment). A pointer at a record the file lacks keeps its pointer. Repositories have the model and GEDCOM, and no screen.
  - **Tag memory.** A record keeps the tag it came with. 5.5.1 export always writes `NOTE`; 7.0 writes `SNOTE`, except for a record that came as `NOTE`, which is written as it came, because `evidence-roundtrip.test.ts` (unchanged) requires `0 @N1@ NOTE …` in 7.0. A note made here is `SNOTE` in 7.0.
  - **Position.** As in ADR-028, a structure is written in one canonical order: fields, citations, kept lines, then notes. Notes keep their order among themselves, and every line returns, but a note that stood before a kept line is written after it. Existing order-sensitive tests (a `STAT` before a `NOTE` under `FAMC`) pass because notes come last.
  - **Not user notes.** Epoch's name-change `NOTE` (ADR-013) stays what it was, tested through import, edit and export beside a name's own notes. The header `NOTE` is the file's, and is not read.
  - **`events.notes` stops being read.** Import no longer writes it, the DTO and the fact editor read and write the fact's first inline note as a record, and a save that changes only the note still bumps the fact (so a stale form conflicts and the log says the fact was edited). A legacy `description` is still shown as "(imported note)" while the fact has no note; adding or attaching a note, or editing the fact, first turns it into the first note, so it is never hidden from export. **One read remains**: export still writes a non-null `events.notes`, so a tree not yet backfilled loses nothing; the backfill nulls it, and that line goes with the column in the contract migration.
- **Import and identity:** shared notes by XREF or alias; an inline note by subject, text and which occurrence of that text it is, so a second file adds what is new and two identical notes stay two.
- **Backfill:** `scripts/backfill-notes.mjs` (`npm run db:backfill:notes`), after the migration and after the evidence backfill (notes under sources, repositories and citations are reachable only once those are records). It uses the import's parser and row builders, never turns a note into a citation or source, leaves the name-change note, and is idempotent. Tests: old-way import plus backfill equals a fresh import in rows and both exports. The old order of a fact's notes is the column's first, then the kept lines'.
- **Writes** are `NoteCommand`s through the mutation runner (preview, log, undo, `STALE_VERSION`, 300 records). Roles are checked before planning: add, attach and create are `record:create`; edit, share (it rewrites the note on its record) and reorder `record:edit`; remove, delete and merge `record:delete`. Deleting a used shared note answers `NOTE_IN_USE` with the count unless told to detach; a merge moves every use and the merged XREF becomes an alias. A delete takes a subject's inline notes and detaches shared ones; person, partnership and source merges carry every note, and previews count them.
- **Privacy:** an inline note is visible only if its subject is (a note on a citation, source or repository follows that record); a shared note only if a visible record uses it or the viewer made it, else a 404. The SQL is named visible sets (`with vp, hu, vn, ve, vl, vc, vs, vr, vo`) and a flat test, because the nested form passed D1's 100-level limit; the row filter is `maskRows`; a test holds them to the same answers. Cost: a restricted viewer's note list or use count passes over those sets (about 24,000 rows on the 5,300-person corpus); see query-plans.md.
- **Research tasks** (migration 0022): per tree, title, details, `open`/`done`/`dropped`, optional assignee and due date, optional link to one person, partnership, fact, source or shared note and/or one quality finding (`finding_key`), `created_by`, `version`. **Not exported** (GEDCOM has no home for one); an imported `_TODO` stays retained verbatim, tested.
  - **Roles:** a contributor creates tasks and edits (including completing) their own; an editor or above edits any and deletes; a viewer none. `MutationRunner.run` takes a `requiredAction` for this.
  - **Assignees** must be current members (checked before planning); removing a member unassigns their tasks in the same batch, and reads treat a non-member assignee as nobody.
  - **Records change:** a merge moves the tasks of the record folded away (a fact it did not keep hands its tasks to the partnership); a delete keeps the task, clears its link and records the *kind* it was about, not its name (the task is then everyone's, and the name could be a private person's). A replace-mode import clears links to facts, whose ids the new file changes. Undo restores each.
  - **Privacy:** a task about a record the viewer cannot see is hidden, title included; an unlinked one is every member's. The SQL looks the record up task by task (a restricted open-task page reads 330 rows, not 123,244).
- **Quality, privacy leaks** (managers and owners only, since a finding names the private person): `public_override_likely_living` (override `public`, and `isLikelyLiving` says living); `note_names_private_person` (a note a restricted viewer can read, inline or shared, whose words hold a private person's full given name and surname as a whole phrase, where that person is not what the note is on); `source_names_private_person` (the same over a visible source's title, author, publication, abbreviation and words). A first name or a surname alone never counts. Citation pages and text are not examined. Findings are warnings with reasons and dismissals; a finding with a task says so, and completing the task does not dismiss it.
- **Given up:** unsaid order of a note against a kept line; repositories have no notes screen; the 7.0 tag of a 5.5.1-origin record; a fact's note shown from the old column only after the backfill; notes and tasks add two reads to every mutation's row load.
