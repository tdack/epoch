# Epoch Architecture Decisions (Phase 0)

## ADR-001: Identity, Cloudflare Access and User Management
- **Context:** Epoch is a private, single-owner family-tree application with invited collaborators behind Cloudflare Access.
- **Decision:**
  - Authenticated identity is verified via Cloudflare Access JWT assertions (`Cf-Access-Jwt-Assertion` request header or `CF_Authorization` cookie).
  - Validation checks JWT issuer (Cloudflare team domain), audience tag (`AUD`), and rotating JWKS from `https://<team-domain>.cloudflareaccess.com/cdn-cgi/access/certs`.
  - For local development and automated testing environments, a configurable mock identity or local public key verifier is supported when explicit development flags are provided, while denying anonymous access by default.
  - The local `users` record is keyed and upserted by the stable Access subject claim (`sub`), treating `email` as mutable profile metadata.
  - Tree-level access is controlled via `tree_memberships` supporting roles: `owner`, `manager`, `editor`, `contributor`, `viewer`. Every server endpoint and action denies access by default.

## ADR-002: Genealogy Identifiers vs GEDCOM XREFs
- **Context:** GEDCOM files use XREF tokens (such as `@I1@`, `@F1@`) that are tree- or file-scoped, frequently collide between different imports, and can be unstable across re-exports.
- **Decision:**
  - All Epoch internal entities (persons/individuals, unions/families, events, citations, media) use internally generated UUIDs as primary keys.
  - GEDCOM XREFs are preserved as tree-scoped import/export aliases (`xref_id`) rather than internal primary keys.
  - This allows cross-tree references, multi-source merging, and prevents XREF collision corruption while ensuring lossless round-trip export by re-attaching or re-mapping XREFs.

## ADR-003: Lossless GEDCOM Preservation
- **Context:** Epoch aims for full round-trip fidelity with supported structures and lossless retention of unsupported GEDCOM structures.
- **Decision:**
  - Supported structures map to normalized relational tables (persons, partnerships, parent-child links, events).
  - Unsupported tags, custom vendor extensions (`_ATTR`, etc.), and unhandled sub-trees are preserved in an unparsed/syntax-preservation payload (JSON or raw records linked to entity IDs) so they are preserved without silent loss upon export.

## ADR-004: Historical Date Representation
- **Context:** Genealogy dates are frequently incomplete (e.g. `1910`, `MAY 1920`), approximate (`ABT 1845`, `EST 1850`, `CAL 1900`), ranged (`BET 1860 AND 1865`, `FROM 1901 TO 1905`), or conflicting. Converting them into arbitrary exact dates (like `1910-01-01`) destroys historical accuracy.
- **Decision:**
  - Dates are stored with both `date_raw` (verbatim string from historical record or user entry) and structured date metadata:
    - Date type/modifier: `EXACT`, `ABOUT`, `ESTIMATED`, `CALCULATED`, `BEFORE`, `AFTER`, `BETWEEN`, `FROM_TO`.
    - Earliest sort key (`date_sort_start`) and latest sort key (`date_sort_end`) in `YYYY-MM-DD` format for sorting, indexing, and chronological filtering.
  - Incomplete dates (year only or month/year) preserve their granularity rather than claiming precision that does not exist.

## ADR-005: Concurrency and Versioning
- **Context:** Multiple invited collaborators may view or edit tree records simultaneously.
- **Decision:**
  - Optimistic concurrency control is implemented using a numeric `version` column and `updated_at` on mutable root entities (`trees`, `individuals`, `families`/`unions`, `events`).
  - Domain mutation commands verify that the client's provided version matches the stored version before writing. A mismatch returns a typed `ConcurrencyConflictError` (HTTP 409).
  - D1 atomic transactions (or batch operations) are used for multi-row mutation commands. Durable Objects are deferred until real-time multi-cursor collaboration demonstrates a clear need.

## ADR-006: Layered Architecture and Clean Boundaries
- **Context:** The prototype embedded database queries and runtime schema initialization directly inside SvelteKit route handlers and single-page components.
- **Decision:**
  - The application is decoupled into distinct architectural layers:
    1. **Domain Layer:** Pure domain models, command interfaces, typed error definitions (`DomainError`, `NotFoundError`, `UnauthorizedError`, `ConcurrencyConflictError`, `ValidationError`), and business invariant checks.
    2. **Persistence/Repository Layer:** D1 implementations implementing repository interfaces with versioning and audit trails.
    3. **Query/Service Layer:** Read and write services that coordinate domain commands, enforce tree authorization, and return DTOs.
    4. **Transport/UI Layer:** SvelteKit server hooks, actions, API endpoints, and component views. Route handlers only parse inputs, invoke application services, and format responses. Direct database operations inside routes are prohibited.

## ADR-007: Persisted, append-only change log and undo (Phase 2, S2)
- **Context:** Undo used to be an in-memory array on `RelationshipService`, and a new service is constructed per request, so it could never work. Destructive removals, person edits and union edits wrote nothing at all. Phase 4 needs an audit log and per-record history, and should build on the same rows rather than replace them.
- **Decision:**
  - Two tables, added by an expand-only migration: `change_log` (one row per user-visible change) and `change_log_records` (the records each change wrote). Neither is read by existing code, so the deploy order is migrate, then code. `schema-init.ts` is not extended; it is S4 debt.
  - **Append-only.** Rows are inserted and never updated. An undo is a new row whose `reverts_change_id` names the change it reverses; "already undone" is derived from that, and a partial unique index on `reverts_change_id` means two concurrent undos cannot both succeed.
  - **Ordering by `seq`** (autoincrement), not by timestamp, which collides within a millisecond. `id` is a UUID generated before the write so the batch can reference it without reading `seq` back.
  - **Row operations are the unit.** Every mutation is first planned in memory as a list of row operations (`table`, `id`, `before` image or null, `after` image or null). The inverse is the same list reversed with before and after swapped, so any change is undoable, including deleting a person or a union with its links, partners and events. The inverse is stored in `inverse_json`; the field-level before/after summary shown to people is in `changes_json`. This deliberately replaces per-command `inverseOf`, which lost context (re-creating a removed parent link dropped its union) and had no answer for `destroy_union` or deleting a person.
  - **Atomic.** The row operations, version guards and log rows are applied in one `db.batch`, as ADR-005 requires, so a change is either fully applied and logged or not applied. A guard is an `INSERT` into `change_log` of NULL for a NOT NULL column that runs only when the expected row version is absent; the constraint error aborts the whole batch and is reported as `ConcurrencyConflictError`.
  - **Undo rules.** Undo applies to the requesting user's most recent undoable change in that tree that has not been undone. It is refused, with a message naming what changed, when a later change (by anyone, including an earlier undo) wrote any of the same records, and when the records no longer look the way the change left them (for example an import touched them). Undo rows are not themselves undoable; there is no redo in Phase 2.
  - **Affected records** are the rows a change wrote (people, names, unions, partners, parent-child links, events, media links). A person edit does not lock the person's relationships against undo, and a relationship change does not lock the people.
  - **Tree deletion cascades** to its log (`change_log.tree_id` has `ON DELETE CASCADE`). Before/after images contain personal data, and deleting a tree must erase it. The deletion itself is therefore not in the log; it is only in the structured request log. Phase 4 may add an account-level audit stream if that is needed.
  - **Not covered:** GEDCOM import and merge write no log rows in Phase 2; they replace or extend whole trees and are not undoable. `actor_id` has no foreign key so the log survives a removed user.
- **Consequences:** Phase 4's audit view reads `change_log` and `change_log_records` directly and adds visibility rules; moderation (pending changes) can store proposed row operations in the same shape. Payloads grow with the size of a change, which is small except for deleting a very large union or person.

## ADR-008: Union merge and XREF aliases (Phase 2, S3)
- **Context:** A dirty GEDCOM carries several `FAM` records for one family. Every union's XREF is its id (`<treeId>:@F1@`), so deleting a merged union would delete the only record of that XREF, and a NOTE or CHAN preserved under it would no longer belong to anything on export.
- **Decision:**
  - **Aliases are a nullable JSON column, `unions.xref_aliases`, on the surviving union**, added by an expand-only migration (`ADD COLUMN`; nothing reads it until this deploy). The alternative, an `union_aliases` table, would have to join `RECORD_TABLES`, the loader, the labeller and the impact grouping to be undoable. A column rides the survivor's ordinary update op, so undo restores it with no new machinery.
  - **Aliases carry transitively.** Merging a union that already has aliases moves those aliases to the survivor as well as adding the merged union's own XREF. A union whose id is not an imported XREF (created in the editor) adds no alias, because no other record ever named it.
  - **Export emits the survivor once**, under its own XREF, and re-attaches structures preserved under any alias to it. Each alias is written on the survivor as `1 REFN <xref>` with `2 TYPE epoch-merged-family`; the importer reads those back into `xref_aliases`, so a re-import recovers them. Alias `FAM` records are deliberately not re-emitted: the merge dissolved which child belonged to which copy, so a regenerated copy would be a guess, and two `FAM` records for one family is the exact defect being fixed.
  - **`merge_unions` is one command through `MutationRunner`.** It deletes the merged unions and their partner rows, moves child links and events onto the survivor, drops events identical to one the survivor already has, and updates the survivor's aliases, status and version, so it is logged and undone like any other change.
  - **Conflicts are never resolved silently.** Two unions conflict when they carry the same event type with different date, place or description, or when their statuses differ. An event type or status present on only one side is not a conflict; merging fills the gap. The command refuses with a typed error listing every conflict unless the request names, for each conflicting event type and for the status, which union's fact to keep.
  - **Import-time merge is stricter than the command.** Only a group with two or more partners, the same partner set, identical facts (both empty counts) and no child recorded with two different pedigrees is merged automatically. A one-partner `FAM` is never merged automatically: two of them may be different, unrecorded, other parents. Everything else is listed as a possible duplicate for review.
- **Chronological labels ("1st partnership") need two recorded partners.** Two one-partner records are not known to be the same pair, so they get no chronology; previews number them ("1 of 2") and the merge dialog offers them, because the command allows it and the person decides.
- **Consequences:** Re-importing the same dirty file in merge mode used to bring back the merged-away `FAM` records, because the importer matched on XREF and did not look at `xref_aliases`. S4 closed that: in merge mode an incoming `FAM` whose XREF is an alias of an existing union is folded into that union (children and facts combined without repeats), in the preview counts as well as the import. A family the tree has never seen is still imported.

## ADR-009: PEDI is per child link, stored per parent (Phase 2, S3)
- **Context:** `PEDI` describes a child's link to a family, and the standard place for it is `INDI.FAMC.PEDI`. Epoch read and wrote it under `FAM.CHIL`, which no other program understands, and its parser dropped everything under `FAMC`.
- **Decision:**
  - **Read** `PEDI` from the child's `FAMC`. The old `CHIL.PEDI` is still read for files Epoch exported earlier, and `FAMC` wins when both are present. Values are case-insensitive (`adopted` in 5.5.1, `ADOPTED` in 7.0).
  - **Store** it as one `parent_child` row per parent, with the same type on each, because a `FAMC` names the family and not a parent.
  - **Write** `PEDI` under `FAMC`, lowercase in 5.5.1 and uppercase in 7.0, and stop writing it under `CHIL`. `birth` is the default and is omitted.
  - **`sealing` and `other`** have no neutral type. They are stored as `unknown` with the word in the nullable `parent_child.gedcom_pedi`, and written back from it. 5.5.1 has no `OTHER`, so `other` is dropped from a 5.5.1 export and kept in 7.0.
  - **Different types for the two parents** are legal in the model but cannot be said in one `PEDI`. The family's `PEDI` is the first parent's type, and each parent who differs is written as `2 _PEDI_PARENT @I2@` with `3 PEDI adopted`. Epoch reads it back; other programs ignore a user-defined tag.
  - **Other structures under `FAMC`** (`STAT`, `NOTE`, `SOUR`, custom tags) are kept, as of S4. The parser preserves each `FAMC`'s sub-structures other than `PEDI` and `_PEDI_PARENT` in `gedcom_preserved`, owned by the child and headed by the `1 FAMC @F…@` line. Export writes them inside the matching `FAMC`, after the `PEDI`, and not after the record. When a child was linked to several copies of a family that were merged, the blocks follow the surviving family and a line that appears in more than one is written once.
  - **Known losses, deliberately not fixed in S4.** A `guardian` link exports as `foster`, because neither dialect has a `PEDI` for it, and comes back as `foster`. An `unknown` link with no `gedcom_pedi` exports as the default (birth) and comes back as `biological`. `other` is dropped from a 5.5.1 export, which has no such value, so it also comes back as `biological`; 7.0 keeps it. Fixing them needs a lossless carrier like `_EPOCH_SEX` (ADR-010), which means a new pedigree value through the parser, the importer's type maps and the per-parent `_PEDI_PARENT` path. That is a change to how links round-trip, not a small one, and these values only arise from a 7.0 file, a hand edit or the editor's guardian type. The proposal is one custom `_EPOCH_PEDI <guardian|other>` line beside a standard `PEDI` (foster for guardian) that Epoch reads back.

## ADR-010: Sex X and the 5.5.1 fallback (Phase 1, S4)
- **Context:** The graph domain and the GEDCOM parser accepted `X`, but `individuals.sex` was typed `M | F | U`, the importer mapped `X` to `U`, and the person form, validation and card had no `X`. A GEDCOM 7 file with `SEX X` lost that on import.
- **Decision:**
  - **One list.** `src/lib/shared/sex.ts` holds `SEX_VALUES` (`M`, `F`, `X`, `U`), its labels and a guard. The Drizzle column, the zod schema, the person form and the drawer all read it, so they cannot drift.
  - **No migration.** The column is `text DEFAULT 'U'` with no `CHECK`; the enum was TypeScript only, so widening it changes no stored data and no deployed schema.
  - **Card.** `X` has its own symbol (⚧) and shares the neutral fill with unknown (○), as the tree design specifies. The legend lists Other and Unknown separately.
  - **Export in 7.0:** `1 SEX X`, which 7.0 defines.
  - **Export in 5.5.1:** `SEX` allows no `X`, so the export writes `1 SEX U` followed by `1 _EPOCH_SEX X`. `U` is a value every 5.5.1 reader accepts and is true (the file cannot say more); the user-defined line, which readers ignore, lets Epoch restore `X` on re-import. This is the same device as `_PEDI_PARENT` (ADR-009). The alternative, writing only `U`, would silently turn `X` into "unknown" on a round trip.
- **Consequences:** Another program that reads the 5.5.1 file sees `U`; only Epoch reads `_EPOCH_SEX`. Someone who edits the file elsewhere and changes `SEX` away from `U` wins over `_EPOCH_SEX`, since the tag only restores `X` when `SEX` is `U`.

## ADR-004 addendum: how the date columns are stored (Phase 1, S4)
- `events` gains nullable `date_sort_end`, `date_qualifier`, `date_precision` and `date_calendar` (migration 0007, expand-only). `date_sort` keeps meaning the inclusive lower bound, so nothing that read it changes. `date_raw` stays verbatim and is never rewritten.
- **One derivation.** `dateColumnsFor` (over `parseDateValue`) fills the columns on create, edit and import. `1900` is stored as year precision with bounds `1900-01-01`..`1900-12-31`, and `ABT 1900` keeps `ABOUT`; neither becomes a day. Text that is not a date is stored as `UNKNOWN` or `PHRASE` with no bounds, which is distinguishable from a row that has not been backfilled (all columns null while `date_raw` is set).
- **Old rows.** Readers use `eventDateValue`, which parses `date_raw` when the qualifier is null, so nothing depends on the backfill having run. `npm run db:backfill:dates` (add `-- --remote` for the deployed database) fills them; it leaves `version` and `updated_at` alone.
- **Undo.** Row-op images are generated from the Drizzle columns, so the new columns are in every before and after image. An image written before the migration lacks them and restores as null.
- **Deploy order.** The columns are nullable and defaulted, so the migration is safe before the code. The reverse order is not: the new code inserts the columns. The `deploy` script migrates first, and the request-time check (see `db/schema-status.ts`) answers 503 until every migration in the journal has been applied, so a mis-ordered deploy fails clearly instead of writing to columns that are not there.

## ADR-004 addendum: dual dates sort on their later year
- **Context:** A 5.5.1 dual date such as `30 JAN 1648/49` gives the year twice: first as the Old Style year, which began on 25 March, then the last digits of the year counted from 1 January. The parser sorted on the first, and its comment called that the Gregorian year. It is not: GEDCOM 7.0 writes the same date as `30 JAN 1649` (ADR-036's export does), so a tree round-tripped through 7.0 sorted every January-to-March dual date a year later than the original.
- **Decision:**
  - `parseDateValue` sorts a dual date on its later year. The suffix replaces the last digits of the first year, and the century rolls over when the result would not be later: `1648/49` is 1649, `1648/9` is 1649, and `1699/00` is 1700. The day is checked against that year, so `29 FEB 1647/48` is a date and `checkDateText` accepts it. Days are not converted between calendars. The calendar is still stored as `JULIAN`, and `date_raw` is still verbatim.
  - **Stored bounds move through the backfill.** `eventDateValue` trusts stored columns, so a dual date stored before this change keeps its old sort until `npm run db:backfill:dates` runs (`-- --remote` for the deployed database, after the deploy). The script now re-derives every `JULIAN` row in `events`, `person_names` and `citations` (only the dual-date parse yields `JULIAN`) as well as rows with no columns yet, writes only rows whose columns change, matches on the date text so a concurrent edit is left alone, and leaves `version` and `updated_at` alone.
- **Consequences:** Until the backfill runs, a stored dual date and a newly saved copy of it sort a year apart. Sorting, range filters, and anything computed from the bounds (ages, living-state spans, quality checks) move dual dates by one year. The date text shown on the page does not change.


## ADR-011: The bounded graph and the record pages (Phase 3, S5)
- **Context:** Every screen loaded the whole tree: the page fetched the tree details and an unfocused graph, and the drawer, dialogs and stats read from them. Phase 3 requires that test corpora do not need a whole-tree response.
- **Decision:**
  - **`GET /api/trees/:id/graph?focus=` answers a window, not the tree.** The parameters are the page's own (`up`, `down`, `siblings`, `step`, `exp`); the plan's `depth=` became `up`/`down` so the view's URL can be passed through. Without `focus` the endpoint still returns the whole-tree aggregate, for tests that assert on it; no screen calls that form.
  - **The window is built by the drawing rules, not by a second copy of them.** `loadFocusWindow` runs `selectFocusSubgraph` over what it has loaded, loads the neighbourhood of every person that selection draws and that is not yet loaded, and repeats until nothing new is drawn. What a neighbourhood means (partnerships with all their partners and child links, parents' unions with all children, parents' other partnerships for step-parents) is in `focus-window.ts`. People a union merely names are fetched as records and marked `isPartial`.
  - **Proof is equality, not size.** Tests compare `layoutFocusView` over the window with the same call over the whole tree, deep-equal, for every person as focus across depths, toggles, opened stubs and type filters, on The Simpsons, the representative scenarios and a generated 4,000-person corpus; a test that breaks the loader (drops step-parent data) fails.
  - **Reads are batched (one D1 round trip per stage), chunked under 100 parameters, and tree-scoped with a filter that cannot drive the query** (`+tree_id = ?`). SQLite otherwise picked the `(tree_id)` index and read the whole tree to return three rows; `docs/query-plans.md` records the measurement. No index was added.
  - **Row order is now explicit** (`ORDER BY rowid`) in `loadRows` and the window, because the union chronology tie-break, the default focus and the "first birth" depend on it.
  - **Person and partnership pages are read models over the same loader** (`PersonPageDto`, `UnionPageDto`), tested against the whole tree's derivation. Every DTO record carries `isPrivate`, always false until Phase 4 (`shared/privacy.ts`).
  - **One editor per tree.** `TreeEditor` (dialogs, confirmed removals, undo) and the toast store are created by `/trees/[id]/+layout.svelte` and read through context by the tree, person and partnership screens, because a toast after a delete must outlive the screen that was about the person.
  - **Navigation is serialised and optimistic.** With a load behind each address change the URL commits late; the tree page shows the new view at once, draws with the view its data was fetched for, and runs one navigation at a time so the history entry for a burst of clicks is still one.
- **Consequences:** Mutations still plan against a full `TreeRows` snapshot (`ChangeStore.loadRows`); bounding writes is the next scaling step. Counting people and partnerships for the header reads a covering index and is linear in the tree.

## ADR-012: Facts have their own columns and are addressed by id (Phase 3, S5)
- **Context:** `events` held a place and a single `description` into which the importer folded a CAUS, a NOTE or the line value, and export wrote it back as `NOTE`. A generic fact editor needs the parts, and two births must be able to coexist.
- **Decision:**
  - Migration 0008 (expand-only) adds `value`, `cause`, `age`, `notes` and `sort_order` to `events`. The importer fills them, export writes each on its own tag, and merge-mode de-duplication counts them as part of a fact's identity.
  - Rows written before it keep `description`, shown as a note and folded into `notes` the first time the fact is edited. **Old descriptions are not backfilled**, so an already-imported occupation reads as a note until edited.
  - Fact commands (`create_fact`, `update_fact`, `delete_fact`, `reorder_facts`) address a fact by id and never by type. The person form's birth and death fields still act on the first event of a type (`upsertEvent`); the form says so when a person has more than one, and the other facts are edited on the person's page.
  - The timeline is date first; `sort_order` orders only facts that tie. Two facts of a type a person has once (birth, death, ...) that differ are flagged as a pair; nothing is merged or hidden.
  - A change to a birth or death bumps the person's version (as recording a death already does), so a stale person form conflicts. Other facts do not, to keep undo of earlier person edits possible.
- **Known gaps:** History on the person page is found by record, so changes to a fact that was later removed are not listed. The parser still drops sub-structures under an event other than DATE, PLAC, CAUS, AGE and NOTE (such as SOUR).

## ADR-013: Person names (Phase 3, S6)
- **Context:** A person may have several `NAME` records (birth, married, aka, ...). Import kept only the last, export wrote one, and `NPFX`, `NICK`, `SPFX`, `NSFX`, `TYPE` and anything else under a `NAME` was lost, which broke the no-loss rule.
- **Decision (import and export):**
  - **Every `NAME` is a `person_names` row, in file order; the first is the preferred one** and its given name and surname are mirrored on `individuals`. Migration 0009 (expand-only) adds `version`, `nickname`, `surname_prefix`, `gedcom_type`, `gedcom_extra`, the from-date columns and `union_id`.
  - **Preserved sub-structures live on the name row** (`gedcom_extra`, verbatim lines) and not in `gedcom_preserved`. That table is keyed by the owner's XREF and headed by a line, which is how ADR-009 re-attaches `FAMC` extras; a name has no stable head line (edits change it, two names can share one), and `gedcom_preserved` is outside `RECORD_TABLES`, so deleting or undoing a name could not carry its `NOTE` or `SOUR`. The mechanism is the same (verbatim lines written back inside the owning structure); the storage is the ADR-008 argument for `xref_aliases`. `FONE` and `ROMN` are preserved this way and not modelled.
  - **Types.** `TYPE` is read case-insensitively. A word that is not one of the seven known types becomes `other` and keeps the word in `gedcom_type`; a 7.0 `OTHER` keeps its `PHRASE`. Export writes lowercase words in 5.5.1 (a free-text type as itself) and uppercase in 7.0 (`OTHER` plus `PHRASE`). An untyped `NAME` is `birth` when first and `aka` after that.
  - **`birth` is the default TYPE** and is left out of the first name written, so single-name files export exactly as before. It is written on any later name, because an untyped later name would read back as `aka`.
  - **The preferred name is written first**, since GEDCOM treats the first `NAME` as primary; the rest keep their order.
  - **Legacy `_MARNM`** (level 1 on the `INDI`, `Given /Surname/` or a bare surname; the bare form takes the primary name's given name) becomes a `married` name with `gedcom_type = '_MARNM'` and is written back as `_MARNM`, not as a `NAME`, so a re-read does not see it twice. Sub-tag or level-2 spellings are not modelled and stay as preserved lines. This tag is not confirmed against webtrees' source: `Individual.php` does not mention it.
  - **Merge-mode re-import** skips a name the person already has with the same type and parts, and never adds a second preferred name.
- **When a name came into use, and from which partnership (S6).** Epoch keeps an optional "from" date (`date_raw` and the ADR-004 columns) and an optional `union_id` on a name. GEDCOM has nowhere standard for either, so export writes one human-readable `NOTE` under the `NAME`, and import reads it back:
  - `2 NOTE Name in use from 8 OCT 2001, through family @F3@.`
  - Either half may be missing: `Name in use from 1998.` or `Name in use through family @F3@.` The pattern is exact, so an ordinary note is never mistaken for it, and a note that carries children (a `CONT` chain) is left alone.
  - The date is the verbatim text; the family is the file's XREF for the union. A note that names a family the file lacks stays as written under `gedcom_extra`, date included, and no column is filled, so export writes it once and a re-import is stable.
  - There is no foreign key on `union_id`: a cascade or `SET NULL` would change the row outside the logged ops and undo could not restore it. `destroy_union`, `remove_partner_from_union` (for that person) and `merge_unions` (to the survivor) rewrite it as ordinary ops.
- **Display name.** `individuals.given_name` and `surname` remain the display name, mirrored from the preferred name in the same atomic change that alters it, and the person's version moves only when the mirrored text does. The person form edits the preferred name row (`update_person` plans both), and `create_person` now writes a preferred row, so every new person has one. A person created before this has none; the first name command materialises one from their fields. The last name of a person cannot be deleted. The "(née X)" suffix is display only: `personName` stays plain because it feeds stored change-log summaries; `displayNameWith` (shared) adds it when the person has a `maiden` name, else a `birth` name, that is not preferred and whose surname differs.
- **Names a pre-S6 person form left stale (S6).** Before this slice the person form edited `individuals` and left the imported name row alone, so a person whose name was edited then has a preferred row that still says the old name. Export and the person page now read the preferred row's given name and surname from `individuals`, which was the edited source; after S6 the two always agree (`update_person` and the name commands write both), so this is inert for new data. No backfill script was needed: the local database has no drifted rows (`SELECT ... WHERE i.given_name <> n.given_name ...` returned none), but a deployed database may, which is why the read-time rule exists. It is not a fix for the stored row, which the next edit of that person corrects.
- **Known losses on a round trip.** The `NAME` line is rebuilt from the parts, so a line that disagrees with its `GIVN` and `SURN` comes back in the canonical form, and a nickname written inside the line (`Julius "Jules" /Hibbert/`) comes back as the `NICK` sub-tag or, when there is none, inside the given name. Round-trip tests compare parsed models, not text.
- **Undo and a name's partnership.** Undoing the creation of a partnership deletes it. A later name that points at it is listed by `dependentsOfDeletions`, so that undo is refused as it is for links and events.

## ADR-014: Recents and favourites are per-user D1 rows (Phase 3, S7)
- **Context:** The focus box and the tree pages should offer the people a user opened lately and the ones they chose to keep. They could live in the browser (`localStorage`, which Epoch already uses for the remembered focus) or on the server.
- **Decision:** A `person_marks` table (migration 0011, expand-only: a new table and two indexes), one row per `(user, tree, kind, person)` with `kind` `favorite` or `recent` and a `touched_at`. Recents keep the newest 20; a repeat moves the person to the front.
  - **Why the server, not the browser.** A favourite is something a person expects to follow them across their devices and survive clearing site data; `localStorage` does neither, and a private window or blocked storage would silently lose it. The remembered focus stays in `localStorage` because losing it costs nothing.
  - **Keyed by the internal user id.** The plan says "keyed by the stable Access `sub`". `users.id` is the row upserted from that `sub` (`users.access_sub` is unique and never reused), and every other table that belongs to a user (`tree_memberships`, the change log's actor) keys on `users.id`, so a mark uses it too. The `sub` itself stays the only link to Cloudflare Access.
  - **Cascade from the user and the tree, not from the person.** `user_id` and `tree_id` cascade, so deleting a tree or a user removes their marks. `person_id` deliberately has **no foreign key**: a cascade would delete the row outside the logged ops, so deleting a person and undoing it would silently lose their favourite (the reason `person_names.union_id` has none, ADR-013). Reads join `individuals`, so a mark for a person who is gone is not shown, and returns when the person does.
  - **Only `tree:view` is needed**, because a mark changes nothing in the tree; it is not logged and cannot be undone.
  - **A recent is recorded by an explicit `POST` from the page**, never by a `GET` or a load function. `app.html` sets `data-sveltekit-preload-data="hover"`, so a load that logged would record people whose links the pointer merely passed over.
- **Shared in place, not reloaded.** The mark endpoints answer with the user's lists, and the tree layout keeps them in a store the screens update from the response. Invalidating the layout load instead would refetch the tree summary (a linear count) on every person view and, on the tree page, the graph window behind `parent()`.
- **Consequences:** Marks are per user and so not in a GEDCOM export. Nothing prunes marks of people who were deleted for good; the newest-20 rule bounds recents, and favourites are a user's own list. Privacy (Phase 4) reaches marks through the same seam as search: a favourite of a person the user may no longer see must be filtered there.

## ADR-015: Who is private, and where it is decided (Phase 4, S8)
- **Context:** Phase 4 must keep living people from collaborators who should not see them, and a viewer must not be able to infer a private person through search, counts, lists, charts, exports or errors. S7's `filterForViewer` runs after the SQL page is chosen, so it cannot correct `hasMore`, page fill or a surname count.
- **Decision:** Privacy is a predicate in the query, beside `tree_id`, for the roles that are restricted. It is derived at read time from the person's events, not stored.
  - **Derived, not stored (measured).** The alternative was columns on `individuals` (a has-death flag, a birth upper bound) kept up to date by every writer: the mutation runner, each command, import, merge, undo, and a backfill that would also have to run remotely before any deploy. Two correlated lookups on `idx_event_entity` cost about 4.5 index rows per person, measured on the two-tree harness: a first page of the people list reads 217 (419-person tree) and 259 (5,324) rows against 51 for the unfiltered page; a page 100 deep reads 1,793 and 23,285 rows (about 4.3 per person), against 419 and 5,001. No `events` row of another tree is read, because the lookup is by the person's own id. The cost is paid only by contributors and viewers; owners, managers and editors run the unfiltered query. If a tree outgrows this, the stored column is the next step and the predicate is the only thing that changes.
  - **Living state.** A person is not living when they have a death, burial or cremation event (dated or not), or when the latest upper bound of their birth, christening or baptism dates is before a cutoff. The cutoff is computed in the service from an injected `now` and the tree's maximum-alive age, and passed as a parameter; SQL never calls `date('now')`, so tests are deterministic. A birth with no upper bound (`AFT 1900`, an undated `BIRT`) counts as unbounded, so the person stays private. `BEF 1900` is bounded and can make a person not living. Everyone with no such fact is indeterminate and therefore private.
  - **The threshold is Epoch's own choice, 120 years, configurable per tree.** It matches webtrees' `MAX_ALIVE_AGE` default (120, `app/Tree.php`), which was read from the source. webtrees also treats any event older than the threshold, and the ages of parents, children and partners, as evidence of death; Epoch uses only the person's own birth facts and so errs toward private.
  - **Override.** `individuals.privacy` is `auto` (derive), `public` or `private`, set by owners and managers; an override always wins. GEDCOM `RESN privacy` or `confidential` on an `INDI` imports as `private` and is exported back as `RESN privacy`; the line is not also kept in `gedcom_preserved`, so there is one source of truth.
  - **What each role sees.** Owner and manager: everything, and they set overrides and the tree settings. Editor: everything (an editor can change any record, so hiding one from them would only hide what they can already alter). Contributor and viewer: private people are absent. They are not masked in search, lists, marks and relationship search; a "Private" hit for a surname would itself say a private person exists, and the surname disappears from the surname list rather than shrinking. A private person's page, edit endpoints and any command that names them answer exactly like an id that does not exist (same status and body). A contributor therefore cannot link a new record to someone they cannot see.
  - **Placeholders only where structure is shown.** In the graph, and in the family a person's page lists (not in search, the lists or favourites), a private person is "Private", with no name, dates, places, sex or notes, when the tree setting `should_show_private_structure` is on (default off, so the safe behaviour needs no action). Off, they are omitted. The partnership list and a partnership's page never show a partnership with a private partner at all, because its marriage date and place are facts about that partner. Unions, links, events, names and notes of a private person inherit it.
  - **Export is a manager action.** `tree:export` was `viewer`, so any viewer could download the whole GEDCOM, living people included. It is raised to `manager`; a filtered export for lesser roles is a later slice.
  - **Writes.** A restricted viewer's command is planned over the rows they can see (a private id fails as a missing one) and then over all rows; the real ops are refused with a missing-permission error if they touch a private person. A preview needs the rights of the change.
  - **Doors that are not reads of a record.** Media reads and uploads check the tree and the record (and `Cache-Control` is `private`); the export workflow re-checks the requester's role when it runs; the tree-wide change log, `GET /api/trees/[id]` and `GET .../individuals/[id]` need an editor; and a tree with no members is no longer given to the first caller, which would have handed a second invitee every ownerless tree.
  - **GEDCOM.** `RESN privacy` and `RESN confidential` import as `private` and are not also kept in `gedcom_preserved`; other words (`locked`) are kept. `private` exports as `RESN privacy` (GEDCOM 7: `PRIVACY`), so `confidential` comes back as `privacy`; `public` has no GEDCOM word and travels as `_EPOCH_PRIVACY public`, as X does as `_EPOCH_SEX`.
  - **Editors see everyone (decided 2026-10-01).** The owner of the tree chose to keep this rather than restrict editors like contributors.
  - **A contributor sees the people they created (decided 2026-10-01, migration 0013).** `individuals.created_by` is stamped by `create_person` with the acting user and is null for imported and earlier people. For a contributor (`ViewerScope.creatorId`) a person whose override is `auto` and who they created is visible while private, in the SQL and in the pure rule; a manager's `private` still hides them, and another contributor or a viewer never sees them. The exception is the person only: their private relatives and partnerships follow the usual rules. A demoted contributor has no `creatorId`, so they lose sight of what they added. No foreign key, so deleting a user cannot cascade to people.
- **Consequences:** A person a contributor adds with no dated fact stays visible to that contributor, and private to everyone else restricted, until someone dates them. Reads for restricted viewers cost a small multiple of the unfiltered reads; the plans are re-measured in `query-plans.md` per read as the predicate is added. Revisit storing the derived state if a tree's surname list or a deep page becomes slow.

## ADR-016: Members and invitations (Phase 4, S9)
- **Context:** Identity comes from Cloudflare Access, roles are Epoch's own, and until now the only way to give someone a role was to write a row into the database. Privacy (ADR-015) is of no use until a second person can sign in with a role.
- **Decision:**
  - **An invitation is an email address and a role.** `tree_invitations` holds the tree, a lower-cased address, the role, the inviter and an expiry (14 days). There is one pending offer per tree and address; inviting again replaces the role and restarts the clock. It is taken up on **every** authenticated request, in `UserRepository.upsertFromAccess`, by an indexed lookup on the address Access asserts, so a person already signed up is given a second tree on their next request, not only on their first. An invitation never lowers a role the person already holds, and an expired one is not taken up (a manager sees it as expired and can invite again).
  - **Access is a separate gate.** An invitation does not let anyone past Cloudflare Access: the Access application policy must also allow the address. The app does not call the Access API, so it cannot add the address itself; the Members page says so. If the Access policy admits everyone with an address at a domain, the invitation is the only gate that matters, and that is the intended setup.
  - **Who may do what** (`shared/membership-policy.ts`, shared with the screen so it offers only what would succeed). Every call needs `tree:manage_members` (manager). An owner may give any role and act on anyone; a manager may give only roles below manager and act only on members below manager, never on a peer, an owner or themselves. Ownership therefore moves only by an owner's act. A tree may have several owners.
  - **The last owner cannot go.** Demoting or removing an owner is refused unless another owner remains, and the check is part of the `update`/`delete` statement itself rather than a count read first, so two owners demoting each other at once cannot both succeed (tested with a concurrent pair).
  - **Concurrency.** `tree_memberships.version` (migration 0014, default 1) is checked and bumped by every role change; a stale version answers 409 with the current one, and the screen reloads after every action.
  - **Who sees the list.** Only managers and owners. An address is personal data, and the list names who else has access; an editor or lower gets the same 403 as for any manager action.
  - **Effect is immediate.** Nothing caches a membership; every service reads it per request, so a removal or a role change applies to the next request (tested).
  - **No audit of membership changes yet.** They are not in the change log, which is a log of tree content. An audit entry (who invited, changed or removed whom) belongs to Phase 4 item 7.
- **Consequences:** The privacy matrix lists the four new endpoints. `e2e/privacy.spec.ts` now gets its second user by a real invitation. Deploying needs migrations 0013 and 0014 applied first (both expand-only: a nullable column, a new table, a defaulted column).

## ADR-017: Kinship and the charts (Phase 3, S10)
- **Context:** Phase 3 left a relationship calculator and ancestor and descendant charts open. Both follow descent, and both can reveal private people, so they share one bounded loader and one masking step.
- **Decision:**
  - **Routes, not a shortest path.** The calculator reports every way two people are related: the same person, a partnership, blood routes nearest first, then routes by partnership. A pedigree that folds back on itself, or a double cousin, has more than one, and each says through whom and by which link types (a non-biological link is named).
  - **Which common ancestors count.** Of the common ancestors of two people only the lowest do: one that is an ancestor of another common ancestor is the same relationship seen from further up. Two lowest ancestors at the same distance who are parents of one child are a couple and one route, which is what makes a sibling full and not half. A single lowest ancestor gives a half-sibling and a plain cousin: "half-cousin" is not used, because the route already names the one ancestor.
  - **Words.** M or F gives the gendered word (uncle, niece, grandson); anything else the neutral one ("parent's sibling"), because sex is a recorded fact, not a role. Cousins are "Nth cousin K times removed".
  - **By partnership.** A partner of the other person's relative, or a relative of their partner, is a route ("partner of 1st cousin", "step-parent", "sibling-in-law"). It is withheld only when the second person is a direct-line relative of the first (a grandfather is his wife's partner, and that says nothing new, and a real parent must never be called a step-parent). A step-parent who is also a cousin has both routes. Step relationships are not stored; they are this route.
  - **One loader, masked in memory.** `loadKinWindow` follows links generation by generation to a limit and a total of 3,000 people; the caller masks the rows for the viewer exactly as the record pages do (`maskRows`, `privatePeople`), so the SQL predicate of ADR-015 is not needed here and the cost is the same for every role. A private subject answers as a missing one. Omitting private people can hide a relationship that only a private ancestor makes, and says nothing about it; with the tree set to show private structure the route shows a "Private" step with no name or dates.
  - **Pedigree slots.** A person has two slots, parents in heap order (father before mother by sex, then id). Where more than two parents are recorded, biological parents come first, then adoptive, foster, guardian and unknown, and the chart shows two; the person page lists every one. A lone mother takes the second slot. The chart says when more generations exist beyond the limit.
  - **Descendants** list children below each person with every partner on the card (a person's children across partnerships appear together in birth order, not under the partnership they came from). Pages: `/people/[id]/pedigree` and `/descendants` with the depth in the address (default 4, at most 8); a card leads to that person's chart.
- **Consequences:** The calculator and charts are read-only and add no migration. The chart cards are links in a grouped SVG; ADR-020 added a text list of the ancestors, and later one of the descendants.

## ADR-018: A place is the text on a fact; no stored reference yet (Phase 1 `place_ref`, Phase 3 item 4, S10)
_Partly superseded by ADR-019: a place record now exists. The text stays the authority, as decided here._
- **Context:** Phase 1 asked for `place_ref` beside the literal place text, "initially allowing unresolved places"; Phase 3 asked for a place literal or reference in the fact editor; Phase 7 owns hierarchical, merged and geocoded places. A stored `events.place_id` would have to be written by every path that writes an event (person and fact commands, import in both modes, union merge, undo and redo), and an undo of a change logged before the column existed would drop it. ADR-015 turned down a stored privacy column for the same list of writers.
- **Decision:** Epoch has no stored place reference. A place is the text a fact carries, grouped without regard to ASCII case (SQLite `nocase`), so the text stays the single authority: export is byte-identical (no `PLAC` line changes), import and undo have nothing to keep in step, and no existing row needs filling in, so the migration is only an index (`idx_event_place (tree_id, place collate nocase)`, migration 0015, expand-only).
  - **Places list and place page** (`/places`, `/place?name=`): the places a tree's facts name, with the number of facts and people, and the facts at one place. A place is found by its text; `?q=` finds a substring (LIKE wildcards are escaped).
  - **Privacy.** Counts and lists are built from `andVisible` for a person's fact and an all-partners-visible test for a partnership's fact, so a place only private people or a couple with a private partner give is absent, and its page answers as a place nobody wrote does. A contributor's creator term is in the same predicate; the plan test holds viewer and contributor answers identical.
  - **Fact editor** suggests places already used as the user types, so one place keeps one spelling. A suggestion only fills the text.
  - **Facts link to their place** from the person page and the partnership page.
- **What this does not do:** it does not merge two spellings ("Cork" and "Cork, Ireland"), rename a place across facts, hold a hierarchy, coordinates or a historical name, or search by place hierarchy. Those are Phase 7, and are what a stored reference or a places table would be for; when it is built it should be keyed by tree and a normalised form of the text, with the fact's own text still authoritative.
- **Consequences:** The place list and a restricted viewer's version cost about one pass over the tree's events (query-plans.md, Places). Phase 1's wording is met in spirit (a place can be shared and looked up) and not in letter (there is no `place_ref` column); this is a recorded departure.

## ADR-019: Place records derived from the fact's text; rename and merge (Phase 1 `place_ref`, S11)
- **Context:** ADR-018 shipped places as grouped text and left a stored reference for later, because every writer of an event (commands, import, union merge, undo) would have to keep it right, and an undo of a change logged before the column existed would drop it. The owner then chose the record-backed version, with the fact's text staying authoritative and a merge being one undoable change.
- **Decision:** `places (id, tree_id, name_key, created_at)`, unique on `(tree_id, name_key)`, and a nullable `events.place_id` (migration 0016, expand-only, with a backfill that is safe to re-run). `name_key` is the place text in ASCII lower case, which is what `lower()` and `nocase` both mean (`placeKey`, not `toLowerCase()`).
  - **The reference is derived, never written by a command.** The change store, in the same batch as the ops, upserts a record for the text of every fact it writes and points the fact at it; the importer and test corpora do the same set-based (`pointFactsAtPlaces`). So commands, a union merge and an undo of a change logged before the column existed come out right without knowing about records. `placeId` is left out of row images (`EventRow`, `toImage`), so a logged image never has to match it and undo's "is the row unchanged" test is unaffected.
  - **A record is its text.** A new text is a new record; the old one stays, empty (never deleted), so an undo, which restores the old text, finds the same record and id. The place list and page are over facts, so an empty record shows nowhere. Export is byte-identical: `PLAC` is the fact's own text.
  - **Rename and merge are one command**, `rewrite_place`: every fact at the place gets the new text, as ordinary event ops, so one change, one preview and one undo. A name that another place already has is a merge, and the facts take that place's own spelling (visible to the caller only); a name with only a different case changes the case. Person versions move for a birth or death, as `update_fact` does, so a stale person form conflicts.
  - **Limits and privacy.** At most 200 facts per change (`MAX_PLACE_REWRITE_FACTS`): D1 counts each statement of a batch as a query and allows 1,000 per invocation, a fact costs up to four, and the change log keeps a change as one JSON value in a row capped at 2 MB. Editors and above only (`record:edit`), who see everyone; a contributor or viewer is refused, and a place they cannot see answers as a place nobody wrote (the refusal names the record id, never the text).
- **What this does not do:** hierarchy, coordinates, historical names and maps (Phase 7) and merging by anything but the text. Facts added to a place after a rename was planned stay at the old text; repeat the rename. `idx_event_place` (migration 0015) is kept for the suggestion search and can be dropped by a later contract migration if it stays unused.
- **Rollback:** code from before ADR-019 writes facts without pointing them at a record, so after a rollback and a roll forward, re-run the two backfill statements of migration 0016 (safe to repeat).
- **Consequences:** The place list is unchanged in cost; one place's facts cost about 1.5 times what they did (the record lookup), measured in query-plans.md. Phase 1's `place_ref` is now met in letter as well as spirit.

## ADR-020: Fan and hourglass charts, and a text list of ancestors (Phase 6 item 4, S12)
- **Context:** S10 shipped the pedigree and descendants charts as SVG over the privacy-masked kin window (ADR-017) and recorded two gaps: no fan or hourglass style, and no text version of a chart.
- **Decision:** two more styles over the same two reads, with no new endpoint and no migration.
  - **Fan** (`/people/:id/fan?generations=`): the pedigree's heap-ordered slots drawn as rings of wedges over a half circle, the person in the bottom-centre disc and each person's parents side by side in the wedge span above them. Pure geometry in `charts/fan-layout.ts`; at most 7 generations (`MAX_FAN_GENERATIONS`), where the outer ring's 64 wedges are about 3 degrees each. Text on the outer rings runs along the radius, turned so it never reads upside down, and is cut to the room a wedge has; the full name and dates are the wedge's `<title>` and link label, and the list below carries them all.
  - **Hourglass** (`/people/:id/hourglass?up=&down=`): descendants to the left of the person and ancestors to the right, on one canvas, at most 6 generations a side. It is the descendants and pedigree layouts side by side with the person's card shared (`layoutHourglass`), loaded with the two existing chart reads, so what a restricted viewer sees is exactly what the two charts show them.
  - **Style links** on all four pages (`ChartStyleNav`) carry the person and the depth between styles, and the depth steppers are one component (`GenerationStepper`).
  - **Text list** (`AncestorOutline`, on the pedigree and fan pages): the slots as a numbered list, a person's parents being twice their number and twice plus one, so the chart is available without the picture.
- **What this does not do:** a descendants-only fan, a compact or book layout, and printing or export of a chart (Phase 6). The descendants and hourglass charts first had no text version; a nested list of descendants (`DescendantOutline`) now sits on the descendants page, and the hourglass page carries both lists.
- **Consequences:** The new pages read exactly what the existing chart endpoints read, so the plans in query-plans.md (Kin window) apply unchanged and the privacy matrix needed only the two page loads.

## ADR-021: Data-quality report with stored dismissals (Phase 5 items 6 and 7, S13)
- **Context:** Phase 5 asks for checks that find impossible or implausible history, classed as errors, warnings or research suggestions, deterministic, explainable, privacy-aware and dismissible with a reason, and that never reject an unusual history for being unlikely.
- **Decision:** a report page (`/trees/:id/quality`, `GET /api/trees/:id/quality`) over findings that are computed on every request and never stored.
  - **Rules** are pure functions over the tree's rows (`domain/quality-checks.ts`), listed with severity and a "why this is flagged" sentence in `shared/quality.ts`. A date is the range of days it could mean (`boundsOf`); a rule fires only when the range makes it certain, so "ABT 1900" or "BEF 1900" never convicts. A person with two births is taken at the widest span. Parent age and birth-order rules apply to biological links only, since an adoption can follow a birth by years. Thresholds (under 12, over 120, a year after a death) sit far outside what happens, and a finding never blocks a save.
  - **Findings have a stable key** (rule plus the records it is about), so a dismissal keeps matching until the data changes shape. Dismissing stores the key and a required reason in `quality_dismissals` (migration 0017, a new table, expand-only), shared by the whole tree and not logged: it changes no record, there is nothing to undo, and restoring is one click. `dismissed_by` has no foreign key, so removing a user keeps their decision.
  - **Privacy:** the rows are masked first for a restricted viewer (the same `maskRows` as every other row reader), so a finding names nobody they cannot see and a rule cannot hint at a hidden person by firing. A dismissal is listed only while its finding still fires for the viewer. Anyone with `tree:view` reads; `record:edit` (editor) dismisses and restores. Dismissing a key that is not a current finding is refused as not found.
  - **Several at once (2026-10-13):** findings can be ticked, a rule's whole list at once, and dismissed with one reason that is stored on each. The request is all or none: one key that is no longer a finding refuses the lot, so a stale page never dismisses part of what its reader chose. The rows go in one D1 batch, chunked under the bound-parameter limit. No threshold: ticking works for two findings as well as a hundred, which is why it replaced a "dismiss all" shown only past ten.
  - **Bounded output:** at most 100 findings a rule are returned, with the full count, so a badly tangled tree stays readable.
- **What this does not do:** unsourced key facts (no source records until the evidence slice), privacy-leak checks beyond the masking above, research tasks attached to findings (Phase 5 item 8), and a rule for every oddity. Partnership chronology warnings stay on the partnership page (`union-warnings.ts`).
- **Consequences:** The report loads every row of the tree once (`ChangeStore.loadRows`), like an export, and is linear in the tree; it is a page someone opens on purpose. A tree too large for that would need the checks moved to SQL, which the rules' pure shape allows one at a time.

## ADR-022: Merging two records of one person (Phase 5 item 5, S14)
- **Context:** An imported or hand-entered tree often holds one person twice. Phase 5 asks for explicit merge with field-by-field review, a relationship impact preview and reversible history, and for merge never to rely only on names and dates or silently lose links or evidence.
- **Decision:** `merge_people` is a relationship command like `merge_unions`: the record that stays (the survivor) absorbs the other (the merged record), which is deleted, in one change with one undo. Review and preview are read-only (`POST /people/:id/merge/impact`); the merge is `POST /people/:id/merge`. It needs the rights deleting needs (an editor).
  - **Nothing is picked for the user where both can be kept.** Facts are repeatable, so two different births are both kept and only a fact stated identically twice collapses. Names move as non-preferred names; the survivor stays the preferred one. A record whose name lives only on the person row keeps it as an "also known as". Parentage is re-pointed, and a link the survivor already asserts is the same assertion and is dropped. A sex that differs is the one thing that must be chosen, as a partnership merge makes the user choose. Privacy can only tighten: "private" on either record is kept.
  - **Who cannot be one person** is refused with a reason before any preview: the same record, an ancestor and a descendant at any distance, the two partners of one partnership. Siblings are allowed, since the commonest duplicate is one child entered twice under the same parents; the repeated parent links collapse.
  - **First birth.** "First" is the order rows were written, and cards and the person form read it. A moved birth or death (a singular fact) is therefore written anew behind the survivor's, so the survivor's stays the first on file; the review notes when a person ends up with two births. Other facts keep their row.
  - **Row order and cascades.** The store applies creates, then updates, then deletes, so every row that points at the merged person is re-pointed or deleted before the person is, and no foreign key cascade removes a row outside the log. A test requires the rows after an undo to equal the rows before the merge by content; undo of a delete recreates the row, so a recreated row can come back later in the table than it was, which is how undoing `delete_person` already behaves.
  - **XREF.** `individuals.xref_aliases` (migration 0018, an expand-only nullable column) keeps the merged record's XREF on the survivor, in the logged row so undo restores it. Export maps those aliases, and now every `@…@` pointer in a retained line, to the surviving record, so a retained `ASSO` or custom tag never points at a record that is gone. This also closes the same gap for merged partnerships.
  - **Marks.** Favourites and recents are per user and not in the change log, so a move could not be undone. They are copied to the survivor and the originals left; an undo brings the other person back with their own, and the survivor keeps a harmless copy.
  - **Size.** One merge writes at most 300 rows (`MAX_PERSON_MERGE_OPS`), from D1's 1,000 queries per invocation as for ADR-019; a test merges and undoes a person at the limit and refuses one more.
  - **Finding duplicates.** The quality report (ADR-021) gets one suggestion per group of people with the same name and births that could match, never for a name alone and never one per pair; it links to the people, and the merge starts from either person's page.
- **What this does not do:** merge more than two at once (repeat it), compare automatically on fuzzy names or places, re-point pointers inside raw lines that are not XREFs, or teach merge-mode GEDCOM import about person aliases: re-importing the same file in merge mode would add the merged person back, as it would after deleting them.
- **Consequences:** Undo restores every row with a higher version than the live one (the existing rule), so a stale editor cannot match it. The partnership merge stays the way to fold duplicate partnerships a person merge can leave behind, and the review says when it did.

## ADR-023: A file's evidence is kept whole before it is modelled (Phase 5 item 9, S15a)
- **Context:** Phase 5 asks for sources, repositories, citations and notes as records. Before modelling them, a round trip of a file that has them was measured, and it was not lossless: root `SOUR`, `REPO`, `NOTE` and `OBJE` records were kept in `gedcom_preserved` but never written back (only records with no XREF were); everything under an individual or family event other than `DATE`, `PLAC`, `CAUS`, `AGE` and its first note (a citation and its `PAGE` and `QUAY`, further notes, custom tags) was dropped on import; and a replace-mode import left the previous file's preserved lines in place, so a second import wrote them twice.
- **Decision:** make the round trip whole first, with no new model.
  - **Root records** are written after the last record, once each, in both GEDCOM versions. Only entries that start at level 0 are, so a person's retained extras are not mistaken for records, and structures kept under a person who has since been deleted still go with them.
  - **Event extras:** `events.gedcom_extra` (migration 0019, a nullable column, expand-only) holds every line under an event that has no column, verbatim from level 2 down and in order, for individual and family events alike. It is a column on the row, as for names (ADR-013), so a fact's extras follow it through edit, merge (a re-created birth copies them) and undo. A note with continuation lines, or a second note, is an extra; the first plain note stays the `notes` column.
  - **Pointers** in event extras and name extras go through the same remap as retained lines, so a pointer to a person merged away (ADR-022) is written against the survivor.
  - **Importing again:** replace mode now removes the previous file's preserved lines; merge mode does not keep the same lines under the same owner twice. A fact's extras are part of its identity for merge de-duplication, so the same fact with a different citation is a different fact.
- **Known limits, kept as before:** lines under a `DATE` or `PLAC` (a `PHRASE`, a `TIME`, a `MAP`) are not kept, and a family event's line value is written back as a note. Trees imported before this change lost what is described above and keep losing it until the file is imported again; the data cannot be recovered from the tree.
- **Consequences:** The baseline test (`evidence-roundtrip.test.ts`) holds the file's every non-header line, the placement of a citation inside its fact, name and family, a citation of a record that is not in the file, and that a second export, a replace import and a merge import change nothing. S15b models sources, repositories, citations and notes on top of it: what it models moves out of these lines and into tables, and what it does not stays where it is.

## ADR-024: A public welcome page, and the paths Access must let through
- **Context:** Every page sat behind Cloudflare Access, so a link to Epoch shared anywhere unfurled as the Access login screen, and a visitor whose token failed validation saw an error from the first API call a page made. The app also still carried the stock Svelte favicon.
- **Decision:** `/welcome` is the one page served without an identified user (`server/auth/public-routes.ts`).
  - **What it shows:** the Epoch mark, name and one line, as a full-window version of the link-preview card, with Open Graph tags pointing at `/brand/og-image.png`. It reads no tree, so there is nothing on it to hide; its load returns only whether someone is signed in. It ships no client code (`csr = false`), so it cannot later grow an API call by accident.
  - **Sign-in is a link to `/` (superseded by ADR-026: it links to `/login`).** Epoch has no login endpoint; following any protected path is what makes Access ask who you are. A signed-in visitor sees "Continue to your trees" instead.
  - **The hook sends a signed-out page load to `/welcome`** (303). API calls keep their 401, client-side data requests are left alone (a redirect would hand them HTML), and only GET and HEAD are redirected. Deny by default is unchanged: the redirect replaces an error, it grants nothing.
  - **Superseded by ADR-026:** *Access must bypass the page and what it loads.* No second, Bypass application is needed any more; one Access application covers only `/login`.
- **Brand assets:** the mark (two partners, their child, faded lines to the generation before) is drawn once in SVG under `static/` and `static/brand/`, and `npm run brand:render` rasterises the PNGs and ICO with the Playwright Chromium used for e2e. `EpochMark.svelte` draws the same geometry in the app.
- **Consequences:** Without the bypass Access still intercepts `/welcome`, which is safe (nothing becomes public) but means shared links unfurl as the Access screen. With the dev bypass on, every request has a user, so the welcome page shows its signed-in state locally; run without `ACCESS_BYPASS_DEV` to see the signed-out one.

## ADR-025: Lint and format toolchain (architecture review §4, Phase A)
- **Context:** AGENTS.md promises Prettier, a type-aware `@typescript-eslint/naming-convention` rule for booleans, Svelte-aware linting and a dead-code check, and none is installed (70 files use two-space indents, 285 use tabs). The Rust-based tools (oxlint, oxfmt, Vite+) are attractive, so they were checked against the docs on 2026-10-02 before the established tools were chosen.
- **Evidence, by question** (docs; none of the oxc/Vite+ claims below was exercised in this repo):
  1. **oxfmt and `.svelte`.** It lists Svelte as supported, but delegates to bundled Prettier and needs the `svelte` package and the `svelte` option ([language support](https://oxc.rs/docs/guide/usage/formatter/language-support.html)); only the `<script>` is formatted natively. It has `sortTailwindcss`, documented as "the same algorithm as prettier-plugin-tailwindcss" ([config reference](https://oxc.rs/docs/guide/usage/formatter/config-file-reference.html)). Whether that sorting reaches Svelte markup was not stated, and was not tried.
  2. **oxlint and `.svelte`.** It lints only the `<script>` blocks; it has no Svelte rules (no runes or a11y checks) ([linter overview](https://oxc.rs/docs/guide/usage/linter.html)). JS plugins (alpha) cannot load `eslint-plugin-svelte`: custom parsers such as Svelte are listed as unsupported ([JS plugins](https://oxc.rs/docs/guide/usage/linter/js-plugins.html)).
  3. **The boolean naming rule.** `naming-convention` with `types: ['boolean']` needs type information. oxlint's type-aware mode (tsgolint, stable, TypeScript 7) implements 60 of 62 targeted typescript-eslint rules, and `naming-convention` is one of the two that are not ([tsgolint README](https://github.com/oxc-project/tsgolint#implemented-rules)). JS plugins have no type information either. So oxlint cannot express the rule at all, and the smallest working set is a full ESLint with typescript-eslint beside it, for this rule alone.
  4. **Vite+** (1.0, MIT, [repo](https://github.com/voidzero-dev/vite-plus)). It claims SvelteKit support in general, but its docs say nothing on adapter-cloudflare, `getPlatformProxy`, `wrangler deploy workers/entry.ts`, the two-project Vitest config, or `nodeLinker`. It moves `dev`, `build`, `test` and `check` behind its own `vp` commands, and `lint` and `fmt` settings into `vite.config.ts`. It adds nothing for question 3, since it bundles the same oxlint. None of the build and deploy items could be verified without migrating the project.
- **Options:**
  - **A. oxlint + oxfmt + knip.** Cannot enforce the naming rule or lint Svelte; formatting `.svelte` still runs Prettier underneath. Fails two goals.
  - **B. Vite+ + knip.** Same linter gap as A, plus a migration of the dev, build and test entry points that AGENTS.md "Important Notes" 1–2 depend on, with the Cloudflare items unverified.
  - **C. Prettier (+ svelte and tailwindcss plugins) + ESLint flat config (typescript-eslint type-aware, eslint-plugin-svelte) + knip.** Meets every goal with documented, mature tools. Needs ESLint in any case (for 3 and for Svelte rules).
  - **Hybrids** (oxfmt for TS and Prettier for Svelte, or oxlint beside ESLint) each add a tool and still need ESLint and Prettier, to save time on a repository of about 350 files.
- **Decision:** option C. It is the one set with no moving part that exists only to be replaced: ESLint is required for the naming rule and Svelte rules whichever formatter is used, and Prettier is what AGENTS.md already documents and what the Tailwind and Svelte plugins target. One `npm run lint` runs the format check, ESLint and knip. `prettier-plugin-tailwindcss` is pointed at `src/app.css`, as Tailwind 4 has no config file to read.
- **Revisit when** (a) tsgolint implements `naming-convention`, and oxlint gains Svelte rules or a Svelte-capable JS-plugin parser (then ESLint can go and oxlint replace it), or (b) someone runs Vite+ in this repository through dev against local D1, build, `wrangler deploy workers/entry.ts --dry-run`, both Vitest projects and the e2e specs, and records the result. Until then neither is adopted.
- **Consequences:** Two more config files (`prettier`, `eslint`) and one for knip. ESLint's type-aware pass is slower than oxlint's would be (about 20 seconds over the repository); `npm run lint` is for the push gate, and `npm run format` and editor integration cover the edit loop. Knip reports as warnings until Phase B removes what it finds.

## ADR-026: One Access application on `/login`; the Worker gates everything else
- **Context:** ADR-024 needed a second Access application with a Bypass policy so the welcome page and its assets could be public, and anything Access did not cover was an easy misconfiguration. Two applications per host is more to keep in step than the app needs.
- **Decision:** exactly one Access application, covering only `<host>/login`. Every other path is ordinary Worker traffic, and the Worker is the gate.
  - **Flow:** a signed-out page load is redirected (303) to `/welcome?next=<path+search>`. "Sign in" links to `/login?next=…`; Access authenticates the visitor, sets `CF_Authorization`, and the request reaches Epoch's `/login`, which redirects to `next`. Later requests carry the cookie on every path and the hook validates it (signature, issuer, audience, expiry) as before.
  - **`next` is untrusted.** `safeNextPath` resolves it against a placeholder origin and keeps only a same-site path; `/login` and `/welcome` are refused so a redirect cannot loop.
  - **A token that fails validation goes to `/login`, not the splash:** the visitor has signed in before, so Access can usually renew the session silently. `/login` with no user never redirects: it renders a message, because Access let the request through but Epoch could not verify it (wrong AUD, clock skew) and a redirect would loop.
  - **The browser handles an expired session:** a 401 from the API makes the client do a full navigation to `/login?next=…` (not `goto`; Access has to see the request). API calls themselves still answer 401.
  - **The dev bypass is honoured only in a dev build (`import.meta.env.DEV`) and only on `localhost`, `127.0.0.1` or `[::1]`.** Access used to catch a stray `ACCESS_BYPASS_DEV=true` at the edge; now it would open every path but `/login`, so the hook ignores the flag elsewhere and logs a warning. The build gate matters because the flag is also read from the runtime binding, which a deployed Worker can carry.
- **Cloudflare behaviour relied on:**
  - *Verified in the docs:* the application's `CF_Authorization` cookie is scoped to the domain, so it is sent on every path, **unless the application's "Cookie Path Attribute" setting is on**, which restricts it to the application's path (`/login`). Leave it off. ([Authorization cookie](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/)) `<host>/cdn-cgi/access/logout` is documented per application domain. ([Session management](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/))
  - *Assumed, verify on first deploy:* `Cf-Access-Jwt-Assertion` is injected only on paths Access protects, so elsewhere the cookie is all there is (`extractAccessJwt` reads both, so the code is correct either way). Also leave "Binding Cookie" off: it is enforced only at Access, so on other paths it protects nothing and the docs warn of redirect loops with some products.
- **Given up:**
  - The Worker is now the only gate; a bug in the hook is no longer backed by Access at the edge.
  - Anonymous traffic reaches the Worker (and its cost) on every path.
  - Session expiry is handled by the app, through the redirects above, not by Access.
  - Service tokens only work against `/login`, so scripted API access with them is not possible until a design for it exists.
- **Consequences:** `/login` joins `/welcome` as a page served without a user (`PUBLIC_PAGE_PATHS`). The welcome page and `/login` share `Splash.svelte`. Access-application changes are made by hand in the dashboard; see the README.

## ADR-027: One person view, in two frames; the open drawer lives in the query string
- **Context:** the tree's drawer and the person page read one `PersonPageDto` but had grown into two half-editors: each did things the other could not (relative removal, partnership edits and media upload only in the drawer; names, facts, privacy, history, merge and favourites only on the page), and the same data was worded and laid out differently. Architecture-review step E5 was skipped for that reason, since sharing components would have changed one screen's output throughout.
- **Decision:**
  - **One view, deliberately converged.** `PersonView` composes section components in `src/lib/components/person/` (summary, family, names, facts, notes, evidence, media, privacy, history, actions). Each owns its actions and dialogs, and hides what the viewer's role cannot do (`person-permissions.ts`, the same rules as before). The screens were made alike on purpose, so every action exists in both frames.
  - **The one real difference is an input.** Clicking a relative selects in place on the canvas and follows a link on the page. `relativeTarget` (`select` or `link`) carries that, and `PersonLink` renders a `<button>` or an `<a>`. Merge reads it too, to land on the surviving record in the same way. No other per-frame prop exists.
  - **Two layouts.** `page` is two columns on a wide screen (records left; family, privacy and history right), one on a phone. `drawer` is one column of native `<details>`/`<summary>`, with the heading an `<h3>` inside the summary so axe and role queries still see it. Family and Facts start open. Which sections the viewer opened is kept in `localStorage` per section, not per person, behind try/catch.
  - **The drawer belongs in the URL as `person`,** beside `focus`, in `tree-url.ts`; an absent parameter means closed. Opening goes through the tree page's `navigate` and pushes an entry, so Back closes it, a reload keeps it, and a link can be shared. `person` is not among the parameters the load reads, so opening or closing refetches no graph. An unloadable person (a stale link, a deletion) closes the drawer with a replaced entry, so Back cannot return to a drawer that will not open.
  - **Not shallow routing.** Pushing `/trees/x/people/y` with `pushState` would move the path, but the tree page keeps its view in the query string and writes the resolved `focus` back from `page.url`; moving the path would fight that effect and lose depths, toggles and opened stubs.
- **Given up:**
  - The drawer is longer: every section is in it, though most are folded.
  - Relatives look the same on both screens, which changes both: the drawer lost its bordered cards for plain rows, and the page gained trash buttons and add links.
  - The person page's header buttons moved from the right of the name to beside it, and Privacy moved into the right column.
  - A docked side-by-side layout is not built; `PersonView` makes it a third `layout` value rather than another fork.
- **Consequences:** `PersonDrawer` is a frame only (a panel over everything below 1024px, a card docked beside the canvas, which narrows and refits, from 1024px; a width the viewer drags from 384px up from 768px, kept in `localStorage`; Close, Escape, Open full page, focus to the heading on open, focus back to the opening card on close). The page is a breadcrumb and a `PersonView`. No API, DTO or schema changes. Supersedes an earlier decision to leave the drawer and page separate.

## ADR-028: Sources, repositories and citations are records (Phase 5 item 9, S15b)
- **Context:** ADR-023 made a file's evidence round-trip whole as retained lines. Phase 5 asks for sources, repositories and citations to be records: shown beside the facts they support, editable, privacy-aware and still lossless.
- **Model** (migration 0020, expand-only; nothing dropped):
  - `sources` (title, author, publication, abbreviation, text, XREF and aliases, `created_by`), `repositories` (name, address as text), `source_repositories` (a source's `REPO` links in order, with call number; a `REPO` with no pointer, or one the file does not resolve, is kept with its raw pointer).
  - `citations`: one `SOUR` substructure, **owned by exactly one subject** (`person`, `name`, `event`, `union`, `parent_child`), in `sort_order`. `source_id` is null for a 5.5.1 citation with inline text (`description`) or a pointer to a record the file lacks (`source_ref`, written back as it was). `page`, `quality` (`QUAY` 0 to 3), `DATA.DATE` in the ADR-004 columns, `DATA.TEXT`.
  - **Lossless by construction:** a structure is modelled only when it can be written back exactly. Every other line stays verbatim and in order in `gedcom_extra`; a second `PAGE`, a `DATA` with anything but one `DATE` and one `TEXT`, `OBJE`, notes and custom tags all stay there. `gedcom_layout` keeps a text field's own `CONT`/`CONC` split and is used only while it still says the column's text, so an edit always wins. Kept lines are moved to the level they are written at, so a citation can move between kinds of subject.
  - Roots, shared notes (`NOTE`, `SNOTE`), `OBJE` and citations under anything not in the subject kinds stay retained. A child's `FAMC` citations belong to the first parent's `parent_child` row and export once per link. A retained root whose XREF a row now holds is not written twice.
- **Import and identity:** sources and repositories are identified by XREF or an alias (merged sources keep the merged XREF as an alias); a citation by subject, source, inline text, page and text. A merge-mode import adds a citation a second file has on a fact the tree already holds, and writes nothing twice. A fact's identity no longer includes its citations (they were in its extras under ADR-023).
- **Backfill:** `scripts/backfill-evidence.mjs` moves the lines a tree kept before this change into records using the import's own parser and row builders (`gedcom/evidence-backfill.ts`), and removes what it stored; idempotent; a line it cannot place stays. A test requires an old-way import plus backfill to equal a fresh import in rows and in both exports. Until it runs, an old tree's evidence stays where it was and still exports.
- **Writes:** `EvidenceCommand`s go through the mutation runner (preview, log, undo, STALE_VERSION 409). Deleting a cited source answers `SOURCE_IN_USE` with the count unless told to remove the citations. A command that deletes a subject takes its citations (`citationCascadeOps`); person and partnership merges move them to the record that now says the same thing, and the citations of a fact a partnership merge did not keep go to the partnership, so none is dropped. Previews say how many carry over. A change that writes more than 300 records is refused (as ADR-022).
- **Roles:** the right is checked before a command is planned, so a lesser role is never told a domain fact (such as how many citations a source has). Adding a citation, a source, a repository or a link is `record:create` (contributor); editing, reordering and unlinking `record:edit`; removing a citation, deleting or merging is `record:delete` (editor). Adding a citation does not bump its subject's version.
- **Privacy:** a citation is visible only if its subject is (a partnership needs every partner visible). A source is listed and served only if it supports a visible citation or the viewer made it; a repository if a visible source is kept there or the viewer made it; otherwise a 404 like a private person. The SQL (`with vp` over visible people, a five-term compound select) and the row filter (`maskRows`) are held to the same answers by a test; the nested form passed D1's 100-level expression and 5-term compound limits. Export stays manager-only and carries everything.
- **Quality:** `unsourced_key_fact`, a research suggestion for a birth, death or marriage (`KEY_FACT_TYPES`) that no citation of the fact itself supports, one per fact.
- **Given up:** structured address parts are dropped when an address is edited (the layout is stale then); a restricted viewer's source list costs the visible-people set per request; the `OBJE` in a citation is retained, not linked.
- **Amended 2026-10-18: unsourced is not shown.** The first design drew a state word beside every fact and name, with Unsourced as the button that added a citation. Most facts in a family tree will never have a source, so the word was on nearly every row and said nothing. Now an unsourced claim draws nothing; a sourced one draws a quote icon and its count (stone ink, emerald on hover and when open), named for assistive tech by count and subject ("2 citations for the birth"); only a disagreement keeps a word (Conflicting, amber). The Quality report keeps `unsourced_key_fact`, so the gap is still findable on purpose.
  - **Citing moved into editing.** `FactDialog` and `NameDialog` have a collapsed "Source (optional)" section: the shared `SourcePicker` combobox (also used by `CitationDialog`), a page and a quality; it is shown only to a role that can cite, lists the record's citations when editing, and saves no citation while closed or empty. A subject with no edit dialog (a parent link, a person, a union-page event) gets a quiet "Add source" link beside its controls while it has no citation.
  - **One change, one Undo.** The fact and name create and update endpoints take an optional `citation`, run as a second `add_citation` command in the same `runner.run` call as the fact or name. The citation is planned over the rows the first command produced, so it can cite a record that does not exist yet. Its ops are inserts, so it needs `record:create`, which every role that can write a fact or name holds; a viewer is refused before either is written. A contributor can cite only a source they can see, as everywhere else in this ADR.
- **Consequences:** `TreeRows` carries the four tables, so every mutation loads them. S15c models shared notes and tasks on this footing.

## ADR-029: Notes are records; research tasks are Epoch's own; privacy-leak checks (Phase 5 items 6, 8 and 9, S15c)
- **Context:** ADR-028 made sources and citations records and left every note as a retained line. Phase 5 also asks for research tasks and the last quality check, privacy leaks.
- **Notes** (migration 0021, expand-only):
  - `notes` is one root `NOTE`/`SNOTE` record: XREF and aliases, text, `MIME`, `LANG`, `gedcom_layout` for its `CONT`/`CONC` split, `gedcom_extra` for the rest, `created_by`. `note_attachments` puts a note on one **subject** (person, name, fact, partnership, parent link, source, repository or citation), in `sort_order`: inline (the attachment holds the text) or a pointer at a shared note (a 5.5.1 `NOTE @N1@` and a 7.0 `SNOTE @N1@` are the same attachment). A pointer at a record the file lacks keeps its pointer. Repositories have the model and GEDCOM, and no screen.
  - **Tag memory.** A record keeps the tag it came with. 5.5.1 export always writes `NOTE`; 7.0 writes `SNOTE`, except for a record that came as `NOTE`, which is written as it came, because `evidence-roundtrip.test.ts` (unchanged) requires `0 @N1@ NOTE …` in 7.0. A note made here is `SNOTE` in 7.0.
  - **Position.** As in ADR-028, a structure is written in one canonical order: fields, citations, kept lines, then notes. Notes keep their order among themselves, and every line returns, but a note that stood before a kept line is written after it. Existing order-sensitive tests (a `STAT` before a `NOTE` under `FAMC`) pass because notes come last.
  - **Not user notes.** Epoch's name-change `NOTE` (ADR-013) stays what it was, tested through import, edit and export beside a name's own notes. The header `NOTE` is the file's and is not read as a note; the one thing read from it is a first line beginning `Tree: <name>`, which names the tree (ADR-042).
  - **`events.notes` stops being read.** Import no longer writes it, the DTO and the fact editor read and write the fact's first inline note as a record, and a save that changes only the note still bumps the fact (so a stale form conflicts and the log says the fact was edited). A legacy `description` is still shown as "(imported note)" while the fact has no note; adding or attaching a note, or editing the fact, first turns it into the first note, so it is never hidden from export. **One read remains**: export still writes a non-null `events.notes`, so a tree not yet backfilled loses nothing; the backfill nulls it, and that line goes with the column in the contract migration.
- **Import and identity:** shared notes by XREF or alias; an inline note by subject, text and which occurrence of that text it is, so a second file adds what is new and two identical notes stay two.
- **Backfill:** `scripts/backfill-notes.mjs` (`npm run db:backfill:notes`), after the migration and after the evidence backfill (notes under sources, repositories and citations are reachable only once those are records). It uses the import's parser and row builders, never turns a note into a citation or source, leaves the name-change note, and is idempotent. Tests: old-way import plus backfill equals a fresh import in rows and both exports. The old order of a fact's notes is the column's first, then the kept lines'.
- **Writes** are `NoteCommand`s through the mutation runner (preview, log, undo, `STALE_VERSION`, 300 records). Roles are checked before planning: add, attach and create are `record:create`; edit, share (it rewrites the note on its record) and reorder `record:edit`; remove, delete and merge `record:delete`. Deleting a used shared note answers `NOTE_IN_USE` with the count unless told to detach; a merge moves every use and the merged XREF becomes an alias. A delete takes a subject's inline notes and detaches shared ones; person, partnership and source merges carry every note, and previews count them.
- **Privacy:** an inline note is visible only if its subject is (a note on a citation, source or repository follows that record); a shared note only if a visible record uses it or the viewer made it, else a 404. The SQL is named visible sets (`with vp, hu, vn, ve, vl, vc, vs, vr, vo`) and a flat test, because the nested form passed D1's 100-level limit; the row filter is `maskRows`; a test holds them to the same answers. Cost: a restricted viewer's note list or use count passes over those sets (about 24,000 rows on the 5,300-person corpus); see query-plans.md.
- **Research tasks** (migration 0022): per tree, title, details, `open`/`done`/`dropped`, optional assignee and due date, optional link to one person, partnership, fact, source or shared note and/or one quality finding (`finding_key`), `created_by`, `version`. **Not exported** (GEDCOM has no home for one); an imported `_TODO` stays retained verbatim, tested.
  - **Roles:** a contributor creates tasks and edits (including completing) their own; an editor or above edits any and deletes; a viewer none. `MutationRunner.run` takes a `requiredAction` for this.
  - **Assignees** must be current members (checked before planning); removing a member unassigns their tasks in the same batch, and reads treat a non-member assignee as nobody.
  - **Records change:** a merge moves the tasks of the record folded away (a fact it did not keep hands its tasks to the partnership); a delete keeps the task, clears its link and records the *kind* it was about, not its name (the task is then everyone's, and the name could be a private person's). A replace-mode import clears links to facts, whose ids the new file changes. Undo restores each.
  - **Privacy:** a task about a record the viewer cannot see is hidden, title included; an unlinked one is every member's. The SQL looks the record up task by task (a restricted open-task page reads 330 rows, not 123,244).
- **Quality, privacy leaks** (managers and owners only, since a finding names the private person): `public_override_likely_living` (override `public`, and `isLikelyLiving` says living); `note_names_private_person` (a note a restricted viewer can read, inline or shared, whose words hold a private person's full given name and surname as a whole phrase, where that person is not what the note is on); `source_names_private_person` (the same over a visible source's title, author, publication, abbreviation and words). A first name or a surname alone never counts. Citation pages and text are not examined. Findings are warnings with reasons and dismissals; a finding with a task says so, and completing the task does not dismiss it.
- **Given up:** unsaid order of a note against a kept line; repositories have no notes screen; the 7.0 tag of a 5.5.1-origin record; a fact's note shown from the old column only after the backfill; notes and tasks add two reads to every mutation's row load.

## ADR-030: 3D tree views are CSS 3D over HTML planes, chosen by `mode` (S16)
- **Status:** superseded by ADR-047 on 2026-10-13: both views and their CSS 3D code are removed. Was accepted. Measured on Chromium at the spike; **WebKit re-checked at stage 7** (the 3D e2e specs pass and pan frame times match Chrome: see the plan's Status row 7). **Firefox is out of scope:** it was never measured (its builds would not start in the development environment) and the owner dropped it as a test requirement at stage 8, so the 3D views are supported and tested on Chromium and WebKit engines only.
- **Context:** two optional views beside the flat hourglass: `layers` (upright planes, one per band) and `floors` (one per generation).
- **Decision:**
  - **Renderer: CSS 3D transforms over HTML planes** (`perspective` and `transform-style: preserve-3d`), not WebGL. Each plane holds its own `<svg>` with the existing `PersonCard`, `UnionMarker` and `TreeEdge`, so cards stay real DOM: the browser hit-tests them, and roving tabindex, `aria-label`s, the context menu and the drawer work as today. One shared `PlaneStack` primitive; depth connectors are thin elements rotated into Z.
  - **Camera:** fixed presets only (`layers` rotates the stage a little about Y and X; `floors` tips it about X, 33° (first 50°, eased at the owner’s request)).
  - **Pan and zoom stay 2D on a wrapper outside the perspective,** so `tree-viewport.svelte.ts` keeps its maths. Zoom must be applied as layout (CSS `zoom`, or sizing the planes), never as `transform: scale()` on that wrapper (see the spike below).
  - **URL:** `mode` = `flat` (default, omitted) | `layers` | `floors`, in `tree-url.ts`. It is not a fetched parameter, so switching mode refetches nothing.
  - **Band model and step-child rule:** one pure module in `src/lib/tree-layout/` computes each drawn person's band (0 direct line, 1 sibling line, 2 cousin line) and anchors every step-child to a drawn parent with a view-independent tie-break (lower band, earlier `union_partner`, lower id). Flat uses it too, so the views agree.
  - **Deferred:** free orbiting, WebGL, printing or exporting the 3D views, and drag-to-relate through the projection (needs an inverse projection; decided at stage 6).
- **Spike (installed Google Chrome via Playwright, headless, macOS, device scale 2, the Simpsons layout; 294 synthetic cards for timing):**
  - **Hit-testing:** correct through the transforms once planes are `pointer-events: none` and only cards are `auto`. Without that, a translucent plane in front swallows clicks on cards behind it (35/55 and 45/55 correct). With it: `layers` 55/55; `floors` 53/55, both misses being a card that genuinely overlaps another on a nearer floor (so plane gaps and tilt must keep cards from overlapping).
  - **Focus:** arrow-key roving focus reached every card in both modes; the focus ring is drawn on the projected card. Cards pushed outside the viewport are the only ones off-screen.
  - **Text:** crisp at 1×, and at device scale 2 under tilt. At 3× via an outer `scale()` the planes are rasterised once and stretched, so text goes soft. With CSS `zoom` on the wrapper, the same 3× text re-rasterises sharply.
  - **Frame time panning 294 visible cards** (3 s sine pan, both modes): 60 fps, p95 16.7 ms, max 16.8 ms. Headless and vsync-capped, so it shows no dropped frames on this machine, not headroom on a low-end device. Stage 7 repeated it on 322 cards in Chrome and WebKit (60 fps, p95 under 20 ms) and found the spike's band 2 fade (0.78) below AA for muted text; it is 0.88 now, as a token.
- **Given up:** free orbiting; one more stacking-context hazard (a plane in front of another must not catch events); perspective makes far planes smaller, so text legibility falls with depth and back-band fading is a token to tune.
- **Consequences:** no new dependency, no schema or API change at this stage. Stage 4 adds fetch options (`side`, `origins`) and touches the privacy matrix; stage 8 added two expand-only nullable columns (`tree_memberships.view_mode`, `trees.default_view_mode`): the address wins, then the member's choice, then the tree's default, then flat, and the address always carries `mode`. The product default (`DEFAULT_VIEW_STATE.layoutMode`) is still flat; moving it needs the promotion checklist in the plan.

## ADR-032: The rings overview is WebGL with free orbiting; Layers and Floors leave the controls (amends ADR-030)
- **Status:** accepted by the owner, who accepted the departure from ADR-030 and the weaker accessibility of this one view. Built and deployed on 2026-10-08; checked in Chromium only (headless, SwiftShader WebGL).
- **Context:** the owner proposed a view that stacks generations as rings, oldest at the top, with each person a sphere and parental lines branching down to the next ring, seen from any angle. A prototype on the Simpsons fixture and a generated 170-person family showed what it is good at (a repeated ancestor is one sphere with converging lines; seen from above it is a fan chart; the whole depth of a family at once) and where it struggles (names crowd on a full ring, wide generations make huge rings, it cannot be a real-DOM card view). The owner is not yet sold on Layers and Floors and wants them out of sight, not deleted.
- **Decision:**
  - **`mode=rings`**, a fourth `LAYOUT_MODES` value, stored in the same `view_mode` columns (no migration: they are text, and the value list is shared).
  - **Renderer: three.js (WebGL), with free orbiting** (`OrbitControls`) and three camera presets (Angled, Side, Above). This view only: ADR-030 still governs Flat, Layers and Floors. three.js is loaded with a dynamic `import()` from `RingsCanvas.svelte`, so only someone who opens Rings fetches it.
  - **Data: the existing focus graph**, no new endpoint. `layoutRings` (`src/lib/tree-layout/rings.ts`, pure, tested) runs `selectFocusSubgraph` like every other view, so Rings draws exactly whom Flat or Layers would for the same address, under the same privacy rules. Arriving at Rings from the toolbar asks for five generations each way (`RINGS_ARRIVAL_DEPTH`) and the wider groups (`side=2`, `origins=1`), as Layers does; the steppers still go to eight.
  - **Placement:** one ring per selected generation; a ring's radius grows with its people; households (people joined by drawn partnerships, a person with two partners between them) take one arc each, centred under the partnerships they came from, then pushed apart until none overlap. Each person is drawn once, so pedigree collapse is converging lines, not a placeholder.
  - **Order and colour (revised by the owner the same day):** the youngest generation is at the top and the most distant ancestors at the bottom, so lines rise from a partnership to its children. Each generation stands on a see-through disc 12% wider than its circle of people. Spheres are coloured by sex, in the card borders' shades (`RING_TOKENS.male`, `.female`, `.unknownSex`); the focus is marked by size and a dark halo, and the focus line by its lines (ancestor, descendant and partnership colours, drawn 3 px wide against 1.5 px for everyone else, as three.js `Line2` fat lines because plain WebGL lines are one pixel). Everyone off the line fades (`RING_FADE`). The first build coloured spheres by lineage instead.
  - **Withdrawn, not removed:** the toolbar's layout control and both default-view pickers offer Flat and Rings (`layoutModeChoices`). A link or saved default naming Layers or Floors still opens it, and the control then shows that mode so it can be left. All their code, tests and e2e specs stay; the specs now open them by link.
- **Accessibility given up (accepted):** spheres and lines are not in the accessibility tree. Names are real buttons over the scene for the focus line (and everyone, with "All names"), so a keyboard user can tab to them, Enter refocuses and Shift+Enter opens the drawer; the canvas announces the focus and counts. There is no context menu, no drag-to-relate, no arrow-key walk and no editing from Rings; Flat and the drawer remain the editing surfaces. On a crowded ring a name that would cover a more important one (the pointer's, the drawer's, the focus, then the focus line by distance) is hidden until the camera turns it clear; it stays in the tab order and shows while focused.
- **Consequences:** a new runtime dependency (`three`, about 140 KB gzipped, in its own chunk loaded only by Rings) and `@types/three`. e2e: `rings.spec.ts` needs WebGL, which headless Chromium provides through SwiftShader; WebKit is not yet checked. Stubs ("+N") are not drawn on the rings; a deeper look is the steppers. The scene redraws only when the camera or the data changes, including on the controls' own `change` event: zoom and pan are applied inside the controls' event handlers, and without it a wheel zoom was not drawn until something else moved the scene. Tried on the owner's own 314-person tree: eight generations each way draw 202 people on 8 rings, laid out in about 12–30 ms.

## ADR-033: Ball, Ribbons and Orrery join Rings as selectable WebGL views (extends ADR-032)
- **Status:** accepted by the owner and deployed; built on 2026-10-08. Checked in Chromium only (headless, SwiftShader WebGL) and by eye on the owner's 314-person family tree.
- **Context:** the owner proposed three more 3D ideas to compare with Rings: a hyperbolic "Poincaré ball", braided lineage "ribbons" and a gravitational "orrery". The plan, each view's notes, timings and rough edges are kept locally and are not in the repository.
- **Decision:**
  - **Three more `LAYOUT_MODES` values:** `poincare` (labelled Ball), `ribbons` and `orrery`, stored in the existing `view_mode` columns (no migration: they are text).
  - **Switcher:** the layout control is **Flat | 3D**, with a picker beside 3D for Rings, Ball, Ribbons or Orrery. The last 3D view is remembered per browser (`localStorage`), so the 3D button returns to it. Withdrawn modes (Layers, Floors) still show when in force, as ADR-032 set out.
  - **Per-mode traits:** `VIEW_MODE_TRAITS` in `src/lib/shared/view-mode.ts` holds, per mode, whether it is WebGL, asks for the wider groups, has an arrival depth, can edit, and falls back to Flat on a phone. It replaces the checks that named Layers and Rings one by one.
  - **Shared stage and shell:** `three-stage.ts` (renderer, orbit controls with the `change` redraw from ADR-032, on-demand frames, picking, projection, fat lines, framing, disposal) and `WebGlTreeShell.svelte` (name buttons, keyboard, camera presets, spin, All names, reduced motion, WebGL failure) were extracted from Rings. Every WebGL view, Rings included, is a pure layout module plus a scene drawn on them.
  - **Ball:** height is calendar time, oldest at the top. Each person's era comes from their recorded birth or death date bounds and is relaxed across partnership and parent–child links (`eras.ts`), so an undated partner lands in their partner's era. Distance from the axis is `R_slice · tanh(spread)`, so wide generations compress toward the glass instead of clipping. Estimated eras only place people; they are never shown as dates, and a private person's dates are never read.
  - **Ribbons:** flow runs oldest to youngest. Partners' tubes, in `union_partner` order, braid into a glowing knot for their union, and children's tubes leave it. A person with several unions splits to each knot. Tubes are merged into a few draw calls; only the nodes are pickable.
  - **Orrery:** a seeded, fixed-iteration force simulation inside the pure layout, so the same graph always gives the same picture. Partners hold as a binary near 4 units apart, children are drawn to their parents' midpoint, and a person with several unions holds several binaries. Orbital drift is decoration only, and is off under reduced motion.
  - **Neutral model throughout:** a union is never labelled a marriage, partners are not assumed to be one of each sex, and sex colours use the existing tokens, including unknown.
- **Revised after the owner's first look (same day):**
  - The Ball draws its spheres at half the radius the layout spaces them for, so the opening view is not crowded.
  - The Orrery has a **Motion** switch, remembered per browser, that holds it at its laid-out picture.
  - Every WebGL view shows a **hover card** beside the pointer: name, recorded years, sex, place on the focus line, and partnerships and children in view. It never shows the Ball's estimated eras, and private people get none.
  - The viewer can **clear the highlight**: clicking empty space, Escape once no drawer is open, or the **Focus line** switch. Everyone stays where they are and is drawn alike; a name or the switch lights the line again. Loading the whole tree with no focus was considered and set aside: it would reload and re-lay out the view, a jarring jump, and it would be the first read not bounded by the view's depth.
- **Accessibility:** as ADR-032 for every WebGL view. Names are buttons, Enter refocuses, Shift+Enter opens the drawer and private people cannot be picked. None of the views edits.
- **Consequences:** no new dependency, because three.js already ships in Rings' lazy chunk. Layout of about 250 drawn people takes under 30 ms in each view; Orrery's first, cold call is around 70 ms (see the notes). `playwright.config.ts` reads `E2E_PORT`, so parallel worktrees can each test their own server. Left for later: a neutral `lineage.ts` instead of importing `ringLineage` from `rings.ts`, and a shared merged-line helper for Ribbons and Orrery. The owner kept all four views (Rings, Ball, Ribbons and Orrery) in the 3D picker.

## ADR-034: Only the install owner, members and invitees are admitted (amends ADR-016 and ADR-026)
- **Amended by ADR-041:** the install owner may also rename and delete any tree, and publish one as the public tree.
- **Context:** ADR-016 meant a broad Access policy to be safe, with the invitation as the real gate. In practice anyone Access verified became a full user: they got a `users` row, could start trees of their own (`TreeService.createTree` needed only a signed-in caller), and nothing named one person as the owner of the install. The CLI setup plan (open question 2, option B) proposes recording the owner and turning everyone else away.
- **Decision:**
  - **An install owner.** Migration 0025 adds `install_meta` (install UUID, owner email, created date). The setup tool writes the row after migrations; the app only reads it, so signing in can never make someone the owner (the rule ADR-015 set when it stopped "first caller owns ownerless trees"). Should there be several rows, the oldest wins.
  - **Admitted** means one of: the install owner (the address Access asserts, compared lower-cased); someone holding any tree membership; or someone with an unexpired invitation, which is redeemed on that same request. `UserRepository.admitFromAccess` replaces `upsertFromAccess` and decides this before writing anything.
  - **A stranger is not stored.** Someone Access names but Epoch does not admit gets no `users` row; who they are lives in `locals.notAdmitted` for that request only, for the welcome page to show. `locals.user` stays null for them, so every handler and load that checks it stays closed. A known user who no longer holds a membership keeps their row (change history points at it) but is not updated. Rows already stored for strangers before this change are left alone; removing them is a separate, deliberate cleanup.
  - **Turned away in the hook,** before the signed-out rules (`notAdmittedOutcome` beside `signedOutRedirect`): a GET or HEAD page load gets a 303 to `/welcome?reason=not-invited`; any `/api` call gets 403 with code `NOT_ADMITTED`, not the handler's 401, since signing in again would not help; a data request or a submission is served without a user and fails where it lands, as signed out. `/welcome` and `/login` stay reachable, so nothing loops: `/login` sends a not-admitted visitor to the not-invited page instead of rendering "we could not confirm your sign-in", whose link would lead back to "Sign in".
  - **The welcome page** decides its state from `locals`, never from `?reason=`, so a crafted link shows nothing. Not invited, it names the address they are signed in as, tells them to ask the owner for an invitation, and offers **Sign out** (`/cdn-cgi/access/logout`) instead of "Continue", which would bounce straight back. It now sends `cache-control: no-store`, since it names the visitor. It still ships no client code.
  - **Starting a tree** is limited to the install owner and anyone holding a membership; anyone else gets `NotAdmittedError` (403, `NOT_ADMITTED`), from `POST /api/trees` and from a GEDCOM import with no tree named. It is install-wide, so it is not a `TreeAction`. Whether the caller is the owner is decided once, at admission, and carried as `UserIdentity.isInstallOwner`; a context built anywhere else lacks it and fails closed. **UI:** everyone who reaches the tree shell is admitted and so may start a tree, so nothing is hidden; the rare refusal (a member removed from their last tree mid-session) shows in the create dialog's existing error line.
  - **No `install_meta` row** (an install before setup, or one set up by hand before this change): there is no owner, and only members and invitees are admitted. Never "the first to sign in": that would hand a fresh install to whoever arrives first. An existing install keeps working, because its owner already holds memberships; add the row to give them install-wide rights back if they lose all of them. **Local development:** under the dev bypass (already limited to local hosts, ADR-026) the default bypass identity, `developer@epoch.local`, stands in for the owner until a row exists. Any other `x-dev-user-email` must be invited, which is what the e2e tests already do, and adding a row lets the not-invited page be tried locally. With no database bound (unit tests, a bare preview) the identity is used as it is.
- **Amends:** ADR-016: Access is no longer the only thing between a stranger and the app, so a broad Access policy is now safe, as intended; redemption moves from `upsertFromAccess` to `admitFromAccess`. ADR-026: a signed-in visitor can now be turned back to `/welcome`, and `/login` redirects a not-admitted visitor there.
- **Consequences:** Deploy order is the usual expand-then-read: `npm run deploy` migrates first. Until setup writes the row, write it by hand (see the README). The privacy matrix is unchanged: no endpoint was added and the 403 comes from the hook.

## ADR-035: The 3D views gain a whole tree, partnership and line selection, and a trace mode (extends ADR-033)
- **Status:** accepted by the owner, who set the scope and the caps, and deployed; built on 2026-10-09. Checked in Chromium only (headless, SwiftShader WebGL) and on the owner's family tree. The plan and each view's notes are kept locally and are not in the repository.
- **Context:** after the first round of WebGL views the owner asked for a full-tree view, a way to select a partnership or a line and see where it leads, and a way to compare several branches at once, plus a dark stage for Ball and Rings. An earlier, implicit "clear the focus and show everyone" was rejected as a jarring re-layout (ADR-033); this one is a deliberate action.
- **Decision:**
  - **One highlight model for every view.** `src/lib/tree-layout/highlight.ts` (pure, tested) turns sources (the focus line, a partnership, a parent–child line, traced people) into a `Highlight`: a `Mark` per person, partnership and line, with a colour, a strength (`full` for the item and what lies downstream, `soft` for what lies upstream), a kind, and whether two or more sources share it. The four scenes draw from it instead of the old role map; spheres keep their sex colour and highlights are halos and line colours. Walks stop at private people.
  - **Palette.** `HIGHLIGHT_TOKENS` holds six trace colours, chosen to be colour-blind safe on the dark stage and away from the sex colours, and an intersection colour. A partnership selected on its own gives each partner's ancestry its own colour, never pink or blue, so same-sex and unknown-sex partnerships read the same as any other.

Compute was not the limit (each walk is linear in drawn people); colours a viewer can tell apart were. Items show as chips that can be removed one by one. Escape steps back one thing at a time: drawer, trace mode, highlight.
  - **Picking.** The shared stage picks people, partnership markers and lines (`Line2` with a pixel band, wider for a finger). Among solids under the pointer, the one whose centre is nearest the pointer on screen wins, not the one nearest the camera: a marker at its partners' midpoint was otherwise hidden behind a large star in front of it.

It is the one read not bounded by the view's depth. `selectWholeTree` numbers generations across the whole tree, with no anchor; unconnected families are aligned by their birth dates where they have any. Nobody is the focus until a person is clicked, which lights their line in place without a fetch.
  - **Dark stage** for Ball and Rings, as Ribbons and Orrery already had; the Ball's glass is fainter.
- **Accessibility given up (accepted):** partnership markers and lines are pointer-only, as spheres already were (ADR-032). People stay reachable by their name buttons, in trace mode too, and the live region describes the selection. Picking a line on a phone is fiddly.

Whole-tree layouts stay usable at 3,000 people (Ball's collision pass and Rings' spacing were reworked for it; Orrery trims its iterations past 1,000 and pulls to the centroid when there is no focus; Ribbons stays at about six draw calls). Known rough edges, left for later: a name button can sit over a partnership marker or line and take the click meant for it; Orrery stretches some binaries on very deep synthetic trees. Colours are now settings: see ADR-054.

## ADR-036: GEDCOM 7.0 is the default export; import detects version and character set; GEDZip
- **Status:** complete; built on 2026-10-09 and deployed. Checked by unit tests, by a 5.5.1-to-7.0 conversion test, and once by hand on the owner's 314-person family file (a webtrees 5.5.1 export). That check covered what this change converts: no `CONC`, `CHAR`, 5.5.1 date syntax, unescaped leading `@`, lowercase enumeration, `RELA` or 5.5.1 `FORM`/`TYPE` remained, all 314 people read back, and 5 hand-typed dates were kept as `PHRASE`. It is not a full 7.0 validation; the gaps are listed below.
- **Context:** the tree menu offered only "Export GEDCOM 5.5.1", although a 7.0 serializer existed. That serializer replayed 5.5.1 lines kept from an import unchanged, so its output was not valid 7.0 (`CONC`, `@#DJULIAN@`, dual years, `SCHMA` listing `FAM` and `INDI`). Imports were read with `File.text()`, which decodes UTF-8 only, so ANSEL and ANSI files (most GEDCOM 5.5 files) lost every accented letter.
- **Decision:**
  - **Import detects, with no choice to make.** The bytes are read, not the text. A GEDZip archive is unpacked to its `gedcom.ged`. A byte-order mark or a UTF-16 null pattern decides first. Otherwise valid UTF-8 is read as UTF-8 whatever `HEAD.CHAR` says, because files that claim ANSI or ANSEL but were saved as UTF-8 are common, and a real legacy file is almost never valid UTF-8. Other bytes are ANSEL when the header says so (LoC MARC-8 table plus GEDCOM 5.5's additions, diacritics moved after their letter, then NFC), and Windows-1252 otherwise. The large-file queue threshold uses the decoded text's length, since a `.gdz` is compressed. Legacy encodings are decoded in code, because the Workers runtime does not promise them in `TextDecoder`. `detectGedcomVersion` answers `5.5`, `5.5.1` or `7.0`. 5.5 is read as 5.5.1, of which it is very nearly a subset.
  - **7.0 is the default export,** in the menu, the API (`format` absent) and `buildGedcomString`. 5.5.1 is offered as the legacy choice. A workflow instance queued earlier with no format still means 5.5.1.
  - **7.0 output is made valid line by line** (`toGedcom7Lines`). `CONC` is folded into the line or `CONT` it continues. Dates are converted: calendar escapes become words, `B.C.` becomes `BCE`, long keywords (`ABOUT`, `CIRCA`) become short ones, and full month names become their codes. Where 7.0 cannot say what the text said, the date gets a `PHRASE`: a dual year becomes its later, Gregorian year with the original as the phrase; `INT date (phrase)` splits into both; and text that is no 7.0 date becomes an empty `DATE` with the text as its phrase. A model text with a leading `@` is already escaped where its line is built (ADR-042); the dialect pass converts only and no longer escapes, and a line kept verbatim is left exactly as the file wrote it. The 5.5.1 structures 7.0 renamed are rewritten: a file's `FORM jpeg` becomes `FORM image/jpeg`, its `FORM.TYPE` becomes `MEDI` (a kind 7.0 lacks, such as webtrees' `certificate`, becomes `OTHER` with the word as `PHRASE`), `ASSO.RELA` becomes `ROLE OTHER` with the word as `PHRASE`, and `STAT`, `RESN`, `ADOP` and `PEDI` are written in capitals. `SCHMA` lists only Epoch's own extension tags, with URIs into `docs/gedcom-extensions.md`.
  - **Stored dates stay 5.5.1 text.** A 7.0 import folds `DATE` plus `PHRASE` back into 5.5.1's `INT date (phrase)` or `(phrase)`, so nothing is lost, and the next 7.0 export splits them out again. A 5.5.1 export writes a 7.0 file's calendar words and `BCE` the 5.5.1 way. `parseDateValue` now sorts `INT date (phrase)` on its date.
  - **GEDZip** (`.gdz`, `application/vnd.familysearch.gedcom+zip`) is offered for 7.0 only. The 7.0 specification ties a GEDZip's version to its dataset's, and 7.0 was GEDZip's first, so a 5.5.1 archive would be non-standard. The service refuses one, and the menu disables the checkbox for 5.5.1. Epoch exports no media yet, so the archive holds `gedcom.ged` alone. `fflate` (already in the lockfile through three.js's types) became a direct dependency.
  - **Menu:** "Export GEDCOM 7.0" exports in one click. The chevron beside it shows the version and a "Compress to .gdz" checkbox (unchecked). The label follows the choice, and the choice resets each time the menu opens, so the one-click export is always 7.0.
- **Known gaps in 7.0 output, deliberately not fixed:** an embedded 5.5.1 `OBJE` (no pointer) is written as it came, though 7.0 wants a pointer to an `OBJE` record; a non-standard tag without an underscore that another program wrote (webtrees' `URL`, `CEME`) is kept, and 7.0 does not allow it; an empty `FORM` stays empty; `RELA` words that 7.0 has a role for (`FATHER`, `GODP`, `WITN`) still go to `OTHER`.
- **Known losses, deliberately not fixed:** 5.5.1's `@#DROMAN@` and `@#DUNKNOWN@` calendars have no 7.0 word, so such a date travels as a phrase. A 5.5.1 text with `@@` in the middle is still stored as written. A line kept verbatim is not escaped, so its own leading `@` stays a lone `@` (ADR-042). A 7.0 file's structures with no 5.5.1 form (`SNOTE` aside, which ADR-029 handles) are kept and written back verbatim in a 5.5.1 export. IBMPC and MACINTOSH character sets are read as UTF-8 or Windows-1252.
- **Dual dates:** `parseDateValue` once sorted `1648/49` on the earlier (Julian) year while a 7.0 export writes the later one; that is now fixed, with a backfill for stored rows (ADR-004 addendum).

## ADR-037: Loosely typed dates are read, offered in standard form, and never block an edit
- **Status:** complete; built on 2026-10-10 and deployed. Checked on the owner's 314-person family file in the dev app: 34 dates standardised in one change and undone, and the 3 unreadable dates listed as findings.
- **Context:** files from other programs hold dates like `3 RD DECEMBER 1996`, `29 JANUAY 1959`, `CIRCA 1937` and `14 AUGUST 1975`. Their meaning is clear, but Epoch could not read most of them, so they did not sort. Worse, the forms refused to save or preview while a date field held unreadable text, even when the date had not been touched. One bad imported date locked the whole fact, name, citation, person or partnership.
- **Decision:**
  - **Read leniently, store as written.** `tidyDateText` (`src/lib/shared/date-tidy.ts`) gives the GEDCOM spelling: it drops ordinals, turns full or misspelt month names into their codes, and turns CIRCA/CA/C. into ABT. `parseDateValue` reads the date as written first and falls back to the tidied form only when that fails. The stored text never changes on import (ADR-003). Misspellings are matched conservatively: a word must keep the month's first three letters and be within two edits of a name five or more letters long. May, June and July match only exactly, so words like `MAYBE` and `JUNK` stay as they are.
  - **Offer, don't impose.** `standardDateText` returns the standard spelling only when it differs from the text and means the same date (same qualifier and bounds). A date field shows it as "Use 3 DEC 1996".
  - **An untouched unreadable date never blocks.** `checkDateEdit(value, saved)` accepts an unreadable date that is unchanged from the saved one, and `DateInput` shows an amber note instead of a red error. Every form that edits a saved date uses it.
  - **Findings and a bulk tidy.** `unreadable_date` (warning) lists every fact or name date Epoch still cannot read, reading the text afresh rather than from the stored columns. The quality page's manager-only "Date spellings" panel previews every date that has a standard form, before and after, and rewrites them as one undoable change (`standardise_dates`), recomputing the stored date columns. It covers facts, names and citation entry dates, 200 per turn. Unreadable and already-standard dates are never touched, so a second run does nothing.
  - **Export** converts through the same tidy, so a 7.0 file writes `3 DEC 1996` rather than keeping the text as a `PHRASE` (ADR-036).
- **Consequences:** rows imported before this keep their stored `UNKNOWN` columns until they are re-saved, standardised or backfilled. `npm run db:backfill:dates` (the dual-date backfill, ADR-004 addendum) now also re-reads every `UNKNOWN` row, so one run gives them sort bounds; a date still unreadable writes nothing. Dates nobody can read (an impossible day, two dates run together) stay as written until a person fixes them.
## ADR-038: The deploy config is tracked
- **Status:** superseded by ADR-043 on 2026-10-12. Was accepted by the owner on 2026-10-10, superseding the git-ignore decision in the setup plan (ADR-033's config-layout question).
- **Context:** `npm run setup` generates `wrangler.deploy.jsonc` — the tracked `wrangler.jsonc` plus this install's D1 id, Worker name, route, vars and resource names — and the file was git-ignored so the owner's values would stay out of git. That broke push-to-deploy: a fresh clone on the deploy host has no deploy file, and nothing in the remote environment can generate one, since the values it needs are exactly what was withheld. The alternatives all need a Cloudflare API token (Workers Builds secrets) or wrangler auto-provisioning (beta, and it bypasses the setup tool's adopt/marker flow). The repo is private with a single owner, and nothing in the file is a credential: D1 and R2 ids, the Worker name, the Access team domain and the sender address are account-scoped identifiers that are useless without an API token that already has account access — at which point the repo's contents are the least of the problem.
- **Decision:**
  - **`wrangler.deploy.jsonc` is tracked.** `.gitignore` no longer excludes it; a fresh clone can deploy without running setup first.
  - **Setup still regenerates it in place.** The file is a build product of the manifest as much as a config; re-running `npm run setup` rewrites it and shows the diff. Adoption of an existing install reads it for defaults.
  - **The build-field agreement check stays.** The build reads `main` and `assets` from the tracked `wrangler.jsonc` while deploys use the deploy file, so `scripts/deploy-config.mjs` still fails `npm run deploy` when those fields drift apart.
  - **`wrangler.deploy.example.jsonc` is deleted.** The tracked file is its own example.
- **Consequences:** anyone who can clone the repo learns the account's resource ids and the Access team domain — acceptable while the repo is private, but the file belongs on the scrub list if the repo ever goes public. Forks inherit someone else's ids until setup rewrites them. The setup plan's "owner-specific values move out of git" rationale now applies only to `wrangler.jsonc` (placeholders) and `.epoch/` (install state).

## ADR-039: Uploaded media is sniffed from its bytes and served by allowlist; non-raster is a download
- **Status:** accepted by the owner on 2026-10-10; built on `fix/security-media-xss-auth` and deployed. Checked by unit tests for the sniffer, the serve decision and the serve route, and by a route test for the upload path.
- **Context:** the upload route trusted `file.type` and took the object key's extension from the filename, and the serve route replayed the stored R2 type with `object.writeHttpMetadata` and answered `Cache-Control: private, max-age=31536000, immutable`. An authenticated uploader could therefore attach a `text/html` or `image/svg+xml` file and have a browser run it on Epoch's own origin — a stored XSS. The same review found the Access audience check failed open when `CF_ACCESS_AUD` was unset, and that the JWKS fetch had no timeout, no rotation recovery, and no recorded decision about sharing an in-flight fetch.
- **Decision:**
  - **Upload decides the type from the bytes.** `media-type.ts` sniffs a fixed set of magic bytes (JPEG, PNG, GIF, WEBP, AVIF, HEIC/HEIF and PDF, with the PDF magic searched in the first 1024 bytes) and refuses anything else. The declared `file.type` and the filename never participate, except that the filename is the title's fallback. The sniffed type also sets the object key's extension, so a key cannot disagree with the content.
  - **Serve decides the response from a server-side allowlist, never the stored type.** `mediaServeDecision` maps the R2 `httpMetadata.contentType` (passed in, not replayed) to a response: a raster type in `INLINE_MEDIA_TYPES` is served inline as itself; `application/pdf` is served as `application/pdf` with `Content-Disposition: attachment`; everything else, including a missing type, is served as `application/octet-stream` with an attachment filename. `writeHttpMetadata` is not used. Every served object response also carries `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Cross-Origin-Resource-Policy: same-origin` and `Referrer-Policy: no-referrer`.
  - **The D1 `media_items.mime_type` column is not on the serve path.** The serve route reads the type from R2 object metadata, so the column cannot influence a `Content-Type` or `Content-Disposition`. Legacy rows written under the old upload route therefore need no migration. The column is still read by the person page to choose a client-side thumbnail, which is a display decision, not a security one.
  - **The upload is capped at 25 MB.** `MAX_MEDIA_UPLOAD_BYTES` is `25 * 1024 * 1024`. The body is bounded while it streams, by a byte-counting `TransformStream` in `parseUploadForm`: it aborts once the body passes the file cap plus a 1 MB budget for the other form fields plus 64 KB of multipart framing, and then parses the bounded stream, so this bound does not trust `Content-Length`, which a client may omit or understate. The parsed non-file fields are re-checked against that 1 MB budget (`MAX_FORM_FIELDS_BYTES`), so a file sent with many or long fields is not refused while the body stays strictly bounded. HEIC and HEIF (any `heic`/`heix`/`hevc`/`heim`/`heis` brand, or a bare `mif1`/`msf1`) are accepted and stored but never served inline, since most browsers cannot render them; they download like a PDF. A `mif1` file listing `avif` among its compatible brands is AVIF. A declared `Content-Length` beyond that bound is refused before the body is read, as a cheap early exit. `assertUploadWithinSizeLimit(file.size)` remains the authoritative *file* cap. A malformed multipart body is a 400, and a non-`File` `file` field is a 400.
  - **Caching revalidates, and only after authorization.** A successful response is `Cache-Control: private, no-cache` with the object's ETag; a matching `If-None-Match` answers a manual 304 with the same security headers. A failed authorization or a missing object answers `Cache-Control: no-store`. The manual 304 is retained deliberately: SvelteKit's automatic 304 strips the security headers this route sets.
  - **The Access audience fails closed.** An empty `CF_ACCESS_AUD` rejects any non-bypass token rather than admitting a token whose signature happens to verify. This is an intended lockout, not a bug. The audience is read from `$app/env/private` with a Worker-binding fallback, and `CF_ACCESS_TEAM_DOMAIN` gets the same binding fallback (read from `$app/env/public`, falling back to the Worker binding), so a deployment that wires either value through `wrangler`/`.dev.vars` alone still works. An empty team domain still fails closed, because `validateAccessJwt` refuses a token when the domain is absent.
  - **JWKS fetches are bounded and rotation-aware.** A certs request has a 3-second timeout and no retry. An unknown `kid` triggers one forced refetch, at most once per 60 seconds. There is deliberately no cross-request coalescing: sharing an in-flight promise would run one request's I/O (and its abort signal) on behalf of another, a Cloudflare Workers anti-pattern. A failed forced refetch keeps the cached keys for up to 24 hours, but the TTL path has no stale fallback and fails closed on a certs outage.
- **Rejected alternatives:** a separate media host (defers the fix; the allowlist closes the hole now); a site-wide CSP (a broader change than the vulnerability needs, and recorded as later hardening); a migration of `media_items.mime_type` (unnecessary, because the column is not on the serve path).
- **Consequences:** every stored object is served through the new decision on its next request, and `MEDIA_URL_VERSION` in `PersonMedia.svelte` is bumped to 2 so a browser that cached the old immutable response re-fetches. The residuals the review accepted are recorded in [backlog.md](./backlog.md).
- **Amended by ADR-050:** new uploads are keyed `media/<treeId>/<mediaId>.<ext>`, and the owner is read from the row rather than the key. The sniffing, the serve allowlist and the headers are unchanged.

## ADR-040: A large export runs in a workflow; expiry is enforced at read time and a lifecycle rule is the GC
- **Status:** complete; built on 2026-10-11 on `feat/gedcom-export-and-workflow` and deployed. No migration. Checked by unit and route tests for the size thresholds, the instance id and object key, the status and download routes, the lifecycle merge and the doctor's R2 findings, and by the GEDCOM injection sweep. The export audit and the `@`/`CONC`/C0 dialect work were deferred here; the dialect work and the tree-name round trip were done in ADR-042, and the export audit is now parked (not planned).
- **Context:** the tree menu exported by serializing the whole tree in one request. A Worker has memory and time ceilings, so a large tree could exhaust them; the `GEDCOM_EXPORT_WORKFLOW` binding and `GedcomExportWorkflow` class existed but were dormant. The security review also found that a stored text value containing a line break could inject an extra line into an export (`BIRT\n0 @X@ INDI` reads as a new record). Nothing expired the export objects in R2. And a workflow instance's status is readable but its `params` are not, so the design needed something that binds a client to its own file without trusting a caller-supplied name.
- **Decision:**
  - **The size decides the path, and neither path raises the ceiling.** `LARGE_EXPORT_INDIVIDUALS` is `5000` and `MAX_SYNC_EXPORT_INDIVIDUALS` is `50000`. `POST /api/export` answers `{ status: 'sync' }` at or below 5,000 (so a small tree exports with no workflow bound), refuses above 50,000 with `413 export_too_large`, and otherwise starts the workflow or answers `503 export_unavailable` when no binding exists, with no synchronous fallback. `GET /api/export` refuses above 50,000 with `413 sync_export_too_large`, and when a workflow is bound and the tree is above 5,000 answers `409 use_async` so the client switches to the POST. The workflow runs the same serialization in a different request, so it does **not** raise the memory ceiling: a tree above the ceiling is refused outright on both paths rather than started and left to run out of memory and retry.
  - **The instance id is the binding; the params are never read.** The id is `export_<treeId>_<token>_<clientUuid>` (`buildExportInstanceId`), read back by one anchored regex (`INSTANCE_ID_PATTERN`) and never split on `_`, so a crafted tree id or client id containing a separator cannot forge another id. Because `WorkflowInstance.params` are not readable, the id carries everything a download needs: the tree, the format, the packaging and the client's per-click uuid. A client is given only the id; the R2 key is derived from it (`exportObjectKey`), so a caller can never name an object the workflow did not write. The `token` (`g551`, `g7`, `g7z`) records both the dialect and the packaging, because a `.ged` file can be either dialect.
  - **Authorization precedes every read.** The status and download routes parse the id and check the caller's membership (`requireExportInstance`) **before** `workflow.get()` or any R2 call. An id this application never minted and a tree the caller is not in answer the same `404`; a member who lacks `tree:export` gets an honest `403`. The id is never echoed in a body.
  - **One authorized step writes R2 and returns only a key.** The whole job is a single `build-export` step, because a step's result is serialized (bytes cannot survive that, a key can) and because authorizing, reading the tree and writing the object then happen against one unchanging tree. Authorization runs again inside the step (`requireExporter`), because the job runs later and a role may have changed, and a job with no requester must not export at all (ADR-015); a refusal raises `NonRetryableError` before any R2 write. Retries are limited to one: a huge build that ran out of memory would run out again, so a second attempt rides out a transient failure and a third would only waste the instance's budget.
  - **The object key is retry-safe and carries the format token.** The key is `exports/<treeId>-<token>-<clientUuid>.<ged|gdz>`, built from the instance's own parts, so a retried step overwrites the same object instead of writing a second. The format token sits in the name as well as the extension: a `.ged` file can be 5.5.1 or 7.0, so without it a client uuid reused across two dialects would collide and serve the wrong one.
  - **Read-time expiry is the control; the lifecycle rule is garbage collection.** An object is written with `customMetadata.uploadedAt`, and expiry is measured from it (falling back to R2's own `uploaded`), 24 hours (`EXPORT_TTL_SECONDS`). Past the window the download answers `410 export_expired` and deletes the object. Instance retention is deliberately longer than the object (3 days on success, 7 days on error), because the client reads the file through the instance, so an instance purged first would strand a file that is still downloadable. The setup tool writes an `exports/`-scoped R2 lifecycle rule by read-merge-write, so an owner's unrelated rules survive: an abort-only rule is ignored, a destructive rule with no prefix or one whose prefix overlaps `media/`/`staging/` is refused, and an unexpected API shape throws rather than letting a wholesale replacement drop the owner's rules. `doctor` fails on any delete rule that could touch live `media/`. An object whose instance is gone is deleted on the next status or download of that id.
  - **The client is told a state and a code, never an error or a key.** Status and download return a closed `{ status, code }` from `EXPORT_STATES`/`EXPORT_CODES` (`queued`, `running`, `complete`, `errored`), never the workflow's raw status or error and never the object key. A download streams with `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, and an attachment disposition carrying both an ASCII `filename` and an RFC 5987 `filename*`.
  - **Export text cannot forge a line.** Every terminator splits a text value into `CONT` lines (`LINE_BREAK` is `/\r\n|[\r\n\v\f\x1c-\x1e\x85\u2028\u2029]/`, so a lone `\r` and the Unicode separators split too); a field that must occupy one line folds every terminator to a space (`singleLine`); a tag or xref carrying a terminator is refused rather than folded into a plausible-looking token; and the write boundary (`schemas.ts`) rejects a line break in a single-line field. A stray non-GEDCOM segment is retained as a `CONT` rather than dropped.
- **Deferred (planned, not done):**
  - **The dialect-hardening follow-up (done in ADR-042, except `CONC` wrapping).** GEDCOM `@`-escaping and general C0-control stripping shipped at build time in ADR-042; 255-character `CONC` wrapping remains deferred.
  - **An export audit (parked, not planned).** An export writes no audit entry; it does not fit `change_log`, which ADR-007 scopes to tree content for undo. The owner does not want that level of accountability or tracing, so a dedicated account-level audit table and migration is deliberately not planned (the former `TODO(audit)` in `src/routes/api/export/+server.ts`).
  - **The tree-name round trip (done in ADR-042).** Export writes the tree's name as `1 NOTE Tree: <name>`, and import now reads it back through a version-guarded conditional rename.
- **Rejected alternatives:** raising the synchronous ceiling instead of adding a workflow (it only moves the point at which a request dies); letting the workflow raise the ceiling (it runs in the same runtime, so it cannot); returning the R2 key to the client (it would let a caller name an object the workflow did not write); and reading expiry from R2's `uploaded` alone (a copy or a re-upload resets it, so it cannot measure from the write).
- **Consequences:** a small tree's export is unchanged and needs no binding. A large tree needs `GEDCOM_EXPORT_WORKFLOW` bound, or the POST answers `503`; a tree above 50,000 people cannot be exported at all. R2 holds up to 50,000-person exports for 24 hours under `exports/`, removed at read time and by the lifecycle rule; live media is protected by the rule guard and by `doctor`.

## ADR-041: One tree can be public, read without signing in (amends ADR-015, ADR-034)
- **Status:** built on `claude/public-tree-23a851` and deployed. The use case is a demo tree (the webtrees royal-family GEDCOM, public figures only).
- **Context:** Access covers only `/login`, and the hook sends everyone it cannot identify to `/welcome`. The owner wants exactly one tree readable by anyone, without Access, without changing the routing or the Access policy.
- **Decision:**
  - **At most one public tree, enforced by the database.** Migration 0026 adds `trees.is_public` (default 0), `public_since` and `published_by` (the install owner's user id, no foreign key), and a partial unique index `idx_trees_one_public ON trees(is_public) WHERE is_public = 1`. A second public tree is refused by SQLite, not only by the service. Replacing the public tree is one D1 batch that clears the old row first (the index is checked row by row) and sets the new one; the clear is itself conditional on the new tree still having the confirmed name, so a racing rename cannot leave no public tree.
  - **Only the install owner publishes.** `requireInstallOwner(context)` (an install-wide action, not a `TreeAction`, as `createTree` is in ADR-034) guards `GET /api/admin/trees` and `PUT /api/admin/public-tree`. Making a tree public needs its exact current name typed (`confirmName`), and so does making it private (the name of the tree that is public). The name check is inside the `UPDATE ... WHERE name = ?`, so it is atomic. The Trees page (`/manage/trees`, a **Trees** item in More for the install owner only; moved under the tree by ADR-044) adds a two-step dialog: a warning, then the typed name, then a separate button.
  - **Amends ADR-034: the install owner may rename and delete any tree,** a member or not, through the existing `PATCH`/`DELETE /api/trees/[id]` and the delete preview. The override runs before the role check, because for a public tree they do not belong to, the role path would answer "viewer". Tree-level settings, members and the content of a tree they are not in stay closed to them.
  - **A fixed public visitor.** `PUBLIC_VISITOR` (`id: 'public-visitor'`, `isPublicVisitor: true`) never gets a `users` row. The hook sets it only when the request has no token, no user and no dev bypass, is a GET or HEAD, and is either any `/api/...` path (the handler factories then refuse the visitor unless the route opts in, and only for the public tree: amended by ADR-052) or a `/trees/<id>[/...]` path whose id is the public tree (one indexed read per anonymous tree page, never cached, so making a tree private ends access on the next request). Everything else still goes to the splash; a write stays unauthenticated and is a 401. Every response served to the visitor carries `X-Robots-Tag: noindex`, and the tree layout adds `<meta name="robots" content="noindex">`.
  - **Permissions.** `requireMemberAction` answers `viewer` when there is no membership and the tree is public (one extra read, only on a miss). This also lets a signed-in non-member read the public tree, and gives the install owner viewer rights there. A non-public tree is refused exactly as before. The visitor is refused in `MutationRunner.run` and in the user-owned writes (marks and recents, view mode, quality dismissals) with `requireRealUser`, before any write, since those need only `tree:view` and would otherwise store a user id. Tasks, the quality report, members and settings stay for members: `ViewerScope.isOutsider` makes the task and quality reads refuse, so the public never sees member names.
  - **Visibility (amends ADR-015).** A public tree shows everyone, living people included, **except a person whose override is `private`**. The "everyone" rule is not `isRestricted: false`, which would also show private people and means special-casing every site that reads it. The restricted roles keep `isRestricted: true` and the scope's `cutoff` becomes a sentinel (`EVERYONE_SHOWN_CUTOFF`) that makes `isLikelyLiving` false and makes the SQL predicate `privacy != 'private'`. One definition therefore feeds the pure rule, the SQL predicate, the masks and the focus window, and a parity test holds SQL and the pure function to the same answers. Editors and above keep seeing everyone, as before. Side effect: on the public tree the manager's "public person who looks living" leak finding is silent, since showing living people is the point.
  - **Splash.** `/welcome` shows an "Explore <tree name>" link when a tree is public and the visitor is anonymous; with none it renders as before. It names the tree and nothing in it.
- **Rejected alternatives:** a global `isRestricted` switch (shows private people); caching the public tree id (making it private would lag); a separate public host or route (the owner asked for the routing to stay as it is); a role for the visitor in the membership table (a row per anonymous reader).
- **Consequences:** Deploy migration first, then code (the new reads need the columns). Someone Access has named but Epoch does not admit still carries a token, so they are not served the public tree anonymously, while a fully anonymous visitor is: the asymmetry follows the "no token" rule. Anonymous API GETs of a tree that is not public now answer 403 rather than 401, the same as a stranger. The privacy matrix lists what the public visitor gets from every endpoint that serves a GET.

## ADR-042: GEDCOM `@`-escaping is done at build time; the tree name round-trips
- **Status:** complete; built on `fix/gedcom-dialect-and-tree-name` on 2026-10-11 and deployed. No migration. Checked by the escape, model-text, tree-name, note, evidence and injection tests, and by the GEDCOM export sweep.
- **Context:** ADR-040 fixed line injection and deliberately deferred three dialect items (GEDCOM `@`-escaping, 255-character `CONC` wrapping and general C0-control stripping) and the tree-name round trip. Escaping then ran as a post-pass over every serialized line, which cannot tell a model payload from a line kept verbatim from an imported file, so it could neither escape the former reliably nor leave the latter byte-identical.
- **Decision:**
  - **A model text is escaped where its line is built, not in a later pass.** `escapedSingleLine` (`evidence-lines.ts`) escapes a single-line field: the event value, `PLAC`, `CAUS`, `AGE`, `MIME`, `LANG`, `CALN`, `_MARNM`, `NAME`/`TYPE`/`PHRASE` and the name parts, the name-change `NOTE`, and `REFN`. `fieldLines`/`textLines` escape every line of a multi-line field, each `CONT` included. Escaping always doubles a leading `@` (`@@foo` → `@@@foo`), so a value can never be read back as a pointer, and it is applied only to text the model supplies.
  - **Leading-only, in both dialects.** A leading `@` is escaped and unescaped in 5.5.1 as well as 7.0, because a 5.5.1 file can carry the same `@@` text even though the standard never named it. This is the owner's decision; a `@` that is not leading is left as it is.
  - **The dialect post-pass is kept for conversion only.** `toGedcom7Lines`/`toGedcom551Lines` still fold `CONC`, convert dates and rewrite the 5.5.1 structures 7.0 renamed (`restructure7`); their old loop over every line's leading `@` is removed. The `PHRASE`s the conversion itself generates (an unknown `MEDI` kind, a `RELA` word) are escaped at the point they are built.
  - **What is never escaped.** A pointer (`@I1@`), a tag and a `DATE` payload (whose `@#…@` calendar escape belongs to the date dialect). A line kept verbatim from an imported file is written back byte-for-byte.
  - **Import reads the escape from the raw bytes.** A node carries `rawValue` (the value before normalisation) and `isAtEscaped` (whether the raw value began `@@`), stamped in `node.ts` from the bytes, not from the cleaned value, so a control code point the normaliser drops cannot turn a malformed payload into an apparent pointer. Unescaping applies to the owning line and its `CONT`s only, never to a `CONC`, whose `@@` sits mid-text and is not an escape. Pointer classification (`isPointer` in `note-parse.ts` and `evidence-parse.ts`) tests `isAtEscaped` and `rawValue` together, at every place a payload can be a pointer: a note link, a citation's `SOUR`, a source's `REPO` and a repository reference.
  - **The 7.0 forbidden control set is stripped, not escaped.** `stripBannedChars` removes the C0 controls except TAB, LF and CR, DEL, the C1 controls, an unpaired UTF-16 surrogate, and U+FFFE/U+FFFF; TAB is kept, and a valid surrogate pair spells an astral character and is kept whole. The stripping runs on import (normalisation) and on export (every built line).
  - **Backfill parity.** The parser's old-way reader stores the first note's raw value (escape and all) in the `events.notes` column, so `note-backfill.ts` rebuilds the note's line and classifies it exactly as a fresh import would; `@@N1@` (text) and `@N1@` (a pointer) no longer both normalise to `@N1@` before the rebuild.
  - **The tree name round-trips.** Export still writes `1 NOTE Tree: <name>` and no `HEAD.FILE`. Import reads the first `HEAD`-child `NOTE`/`SNOTE` whose first line is `Tree: <name>`: first line only, trimmed, capped at 200 characters, not case-folded. A **post-parse conditional rename** renames only a tree the import created, never one it was given, with precedence explicit user name > embedded `Tree:` > uploaded filename > `HEAD.FILE`. The rename is a version-guarded `UPDATE` (name and version must be what the import saw) and logs one `import_tree_name` change-log row; a concurrent write means it does not land. The queue message carries the naming fields additively, and a message without `isTreeNameExplicit` (queued before this change) is read as explicit, so it never renames its tree.
- **Deferred:** 5.5.1 `CONC` wrapping at 255 bytes. Reviewers found no reader in scope that needs it, so it is recorded as a follow-up rather than done.
- **Parked:** an export audit entry. It does not fit `change_log` (ADR-007), which is scoped to tree content for undo, and the owner does not want that level of accountability or tracing, so a dedicated account-level audit table is deliberately not planned. See the note in `src/routes/api/export/+server.ts`.
- **Accepted residuals:**
  - A preserved (unmodelled) line may carry a lone leading `@`: it is written back exactly as the file had it, so it is not escaped.
  - A 5.5.1 row written before this change whose stored value begins `@@` is unescaped on the next import, which can duplicate a merge key for those pre-existing rows; new imports do not have this.
- **Consequences:** the escaping is now testable where it belongs and kept lines stay byte-identical, which is what ADR-003's no-loss rule needs. The `escapeText` decision (escape only model text, never a pointer, a tag, a date or a kept line) is the single rule every call site follows.

## ADR-043: The deploy config is git-ignored; Workers Builds gets its values as one build variable (supersedes ADR-038)
- **Status:** accepted by the owner on 2026-10-12. Built on `claude/admiring-planck-t2xc7q`. The adoption run of the live install on 2026-10-12 used it: it deployed without a D1 id and set the build variable on the production trigger through `cf`.
- **Context:** ADR-038 tracked `wrangler.deploy.jsonc` so Workers Builds could deploy from a fresh clone. The owner wants a clean repository instead: anyone can clone it, run `./setup` and deploy their own install, and none of the owner's values (team domain, install id, sender address, D1 id) live in git. ADR-038 rejected the alternatives because they needed an API token or wrangler's beta auto-provisioning. Neither objection holds now:
  - **The D1 id is not needed.** In wrangler 4.131 to 4.148, `wrangler deploy` with a D1 binding that has no `database_id` keeps the binding the deployed Worker already has, if that database's name matches `database_name`. Otherwise it looks the database up by name, and creates it only if none exists. Remote `d1 migrations apply` and `d1 execute` look the database up by name too. The owner confirmed a deploy without the id on 2026-10-12.
  - **Setting build variables needs no API token.** The Builds API has `PATCH /builds/triggers/{uuid}/environment_variables`, and `cf` 1.0.0-beta.13 wraps it as `cf builds triggers environment-variables upsert`. Setup already signs in to `cf` with OAuth, and cf's OAuth client lists a `workers-ci.write` scope (with the legacy `workers_builds:write`).
- **Decision:**
  - **`wrangler.deploy.jsonc` is git-ignored again**, and was removed from the index. `npm run setup` writes it locally as before.
  - **No D1 id anywhere.** The tracked `wrangler.jsonc`, the setup template and the generated file all name the database only. The generator sets `database_id` to undefined, so editing an older file removes its stale id.
  - **One build variable, `EPOCH_DEPLOY_VALUES`.** It holds this install's values (Worker name, hosting, hostname, team domain, install id, sender, R2 jurisdiction, AUD) as JSON in a fixed key order. It is not the whole config: the build regenerates the file from the current tracked `wrangler.jsonc`, so a binding added to the tracked file reaches the next push without re-running setup. It is visible rather than secret, because nothing in it is a credential (ADR-038) and a secret cannot be read back to see whether it is current.
  - **The generator has no package dependencies** (`tools/setup/deploy-values.ts`), so `scripts/deploy-config.mjs` can import it on the build host, where only the root packages are installed. Node 24 (`.nvmrc`) strips the types. The raw tracked file is read with wrangler's `experimental_readRawConfig`.
  - **Build once.** `build:worker` writes the file from the variable (when it is set), checks the build fields and runs `vite build`. `deploy:worker` migrates and deploys with no build. `deploy` runs both, so a local deploy needs no variable. The Workers Builds commands are `npm run build:worker` and `npm run deploy:worker`. Migrations stay ahead of the deploy: a database renamed or missing in config then fails the migration with "Couldn't find a D1 DB named …", rather than letting the deploy create an empty one.
  - **Setup sets the variable.** After deploying, setup finds the Worker's script id and its Builds triggers, and upserts the variable on every trigger. `./setup builds` re-runs only this step, for after the repository is connected in the dashboard. `workers-ci.write` is requested but optional, like the tag scopes. Without it, before the repository is connected, or on any Builds API error, setup prints the value and the commands to paste instead. It never fails the run.
  - **Setup configures the production trigger.** It is the single trigger whose branch filters name branches rather than a `*` pattern. Setup sets its build and deploy commands to the two above, its path includes to `src/**`, and its path excludes to `node_modules/**`, `.git/`, `docs/`, `.agents/` and `.claude/` (the owner's choice, so documentation and tooling pushes cost no build minutes). It does this with `cf builds triggers update`, which the owner confirmed on 2026-10-12. Preview triggers keep their commands and paths: their deploy command uploads a version, and `deploy:worker` there would send every branch to production. If more than one trigger looks like production, nothing is changed and the commands are reported.
  - **The Worker's id comes from `cf workers list`**, which gives the 32-hex id the Builds and tags APIs key on as `id`, beside `name`. It replaces the raw `GET /workers/scripts` read.
  - **The invitation sender is a var, `EPOCH_EMAIL_SENDER`.** The generator writes it beside `allowed_sender_addresses` from the same value, and the mailer reads it rather than a constant, so no install's address is in the source. With no var, invitations are saved but not emailed, as with no binding.
  - **History was rewritten on 2026-10-12** to drop every `wrangler.deploy.jsonc` and `wrangler.deploy.example.jsonc`, rename the setup fixture to `tools/setup/fixtures/deploy-config.jsonc`, and replace the owner's team domain, install id, D1 id, mail domain, workers.dev subdomain and surname (a test tree's name) with placeholders throughout, in file contents and commit messages.
- **Rejected alternatives:** a pre-push hook that generates the file (hooks run only on the owner's machine, and getting the file to the build host would mean committing it); storing the whole generated config as the variable (it would go stale against the tracked file); one variable per value (more to set and keep consistent, for no gain); a separately created API token (the existing `cf` sign-in covers it).
- **Consequences:** a fresh clone deploys only after `./setup` (locally) or once the variable is set (on Workers Builds). With the `src/**` path filter, a push that touches only `drizzle/`, `workers/`, `static/`, `wrangler.jsonc` or `package.json` (a migration, a binding or a dependency on its own) builds nothing. It deploys with the next push that touches `src/`, or by `npm run deploy`. Connecting the repository before the variable exists starts a first build that fails with a message naming `./setup builds`. The behaviour depends on wrangler's resource provisioning, which is on by default but behind a hidden `--x-provision` flag, so it belongs on the re-check list for each wrangler upgrade. Local D1 state was keyed by the placeholder id and is now keyed by the binding name `DB`, so one `npm run db:migrate:local` (and `npm run seed`) is needed after pulling this. The owner's values are still in the history of the commits made while the file was tracked; rewrite it before the repository goes public.

## ADR-044: Each member picks a default tree; the Trees page moves under the tree (amends ADR-041)
- **Status:** built on `claude/ui-tweaks-navigation-674a2c` on 2026-10-13 and deployed. Migration 0027.
- **Context:** `/` opened the most recently changed tree, so a member of several trees could not choose where Epoch starts. The Trees page sat outside the tree layout, so it had no tree header or section menu, unlike Members and Privacy, and only the install owner could see it.
- **Decision:**
  - **The default is a flag on the membership,** `tree_memberships.is_default` (not null, default 0), with a partial unique index `idx_membership_one_default ON tree_memberships(user_id) WHERE is_default = 1`. Choosing a tree is one D1 batch that clears the old flag first (the index is checked row by row), as the public tree does in ADR-041. `PUT /api/default-tree {treeId | null}` sets or clears it; it needs `tree:view` and a membership, so the public tree cannot be a non-member's default. It is the member's own setting, like `view_mode`: not logged, not undoable, and it leaves `version` and `updatedAt` alone.
  - **`/` opens the default tree,** else the most recently changed one. The Epoch mark in the header links to `/`, so it reaches the default without needing the tree list.
  - **The Trees page is `/trees/[id]/trees`,** inside the tree layout, so it shares the header and shows as "More: Trees". `/manage/trees` redirects there (to the tree in `?from=`, else the default). The page and its menu item are offered to the install owner and to anyone in more than one tree. A member sees their own trees with **Make default**; the install owner sees every tree, as before, with rename, delete and publish still theirs alone. `/api/admin/trees` stays closed to everyone else.
  - **Sign out** is the last item in More for anyone signed in, linking to Access's `/cdn-cgi/access/logout` with a full page load and `returnTo` set to the absolute welcome page address, so it lands on `/welcome`. `returnTo` is not in Cloudflare's session-management docs; if Access ignores it, the visitor sees Access's own logged-out page instead. It is not under Manage, which only managers and the install owner see.
- **Rejected alternatives:** `users.default_tree_id` (a pointer that outlives a deleted tree or a removed membership, so every reader would need a fallback); keeping the Trees page outside the layout with a copied header (two headers to keep in step).
- **Consequences:** deploy the migration before the code, which reads the column. Leaving or deleting the default tree clears the choice through the existing cascade, and `/` falls back to the most recent tree. Sign out does nothing under `vite dev`, where Access is not in front of the Worker.

## ADR-045: Trees have a readable address; the id still works and redirects to it
- **Status:** built on `claude/ui-tweaks-navigation-674a2c` on 2026-10-13 and deployed. Migration 0028.
- **Context:** tree pages were addressed by UUID (`/trees/b8ea1a57-…?focus=…`). The owner wants `/trees/the-windsors?focus=…&mode=rings`, with the id still accepted.
- **Decision:**
  - **`trees.slug`,** nullable text with a unique index. It is made from the name (`slugifyTreeName`: accents dropped, lower-case `a-z0-9` words joined by single hyphens, at most 60 characters) when a tree is created or a GEDCOM import creates one, with `-2`, `-3`… on a clash. A name with nothing Latin in it gets no slug, and the tree keeps its id as its address. A slug can never be shaped like a UUID, so an id and a slug cannot be confused.
  - **The migration backfills** existing trees in SQL, with replacements that approximate `slugifyTreeName`. A repeated name takes the first six characters of its id as a suffix instead of a counter, so the backfill cannot collide with another tree's slug and fail the migration.
  - **The slug is stable.** Renaming keeps it, so bookmarks survive. It changes only when someone who may rename the tree (`tree:update_settings`, or the install owner) edits the Address field in the rename dialog, through `PATCH /api/trees/[id]` with the version check. An empty field gives the slug up. The old slug is not kept as an alias: after a change, links to it stop working, and the dialog says so.
  - **One resolution point on the server.** `treeHandler` turns the address segment into the tree id (`id = ? OR slug = ?`) before the service runs, so no service sees a slug. A segment that names no tree is passed on unchanged and refused exactly as an unknown id is: a stranger gets the same answer for an existing tree's slug, its id, and a slug that names nothing, so a guessable slug reveals no more than an unguessable id did. `tree-slug.test.ts` covers it.
  - **The anonymous page gate (ADR-041)** compares the segment with the public tree's id or slug (`isPublicTreeSegment`), so a slug link to the public tree opens for a visitor who is not signed in.
  - **Links use the slug.** `treePath({ id, slug })` builds every tree address. Components that build links take an optional `treeSlug` prop beside `treeId`, which stays the id for API calls and keys. Without the prop a link falls back to the id, which still works.
  - **The id address redirects.** The tree layout's load answers an address by id (or any non-canonical segment) with a 302 to the same path and query under the slug, so the address bar shows one form. It is not permanent, since a browser would cache a 308 past a later change of slug. Changing the open tree's slug moves the page to its new address rather than reloading the old one.
- **Rejected alternatives:** SvelteKit `reroute` (every link would still need the slug, plus a client-side lookup cache that goes stale when a slug changes); regenerating the slug on rename (breaks bookmarks); keeping old slugs as aliases (a table and a lookup for a case the owner can avoid by not changing the address).
- **Consequences:** deploy the migration before the code. Invitation emails still link by id, which redirects. Each tree API request makes one extra indexed read to resolve the segment.

## ADR-046: The flat view gains the whole tree (extends ADR-035)
- **Status:** built on `claude/ui-tweaks-navigation-674a2c` on 2026-10-13 and deployed. No migration.
- **Context:** the whole tree (ADR-035) was offered only in the WebGL views. A tree made of several unconnected families, such as the Game of Thrones GEDCOM (87 people in 12 families, 7 of them people with no recorded relatives), has no focus from which every family can be reached, so the flat view could show only one family at a time. The backlog's "whole-tree overview" item asked whether a layered engine (d3-dag, ELK) should draw it; no notes from that spike were found in the repository.
- **Decision:**
  - **The flat view draws the whole tree with its own contour placement,** not a new engine. `layoutWholeTree` takes `selectWholeTree`'s rows (generations across the whole tree, unconnected families aligned by birth era) and `placeWholeTree` places them with the hourglass's descendant blocks. Within a family, blocks grow from its founding couples: partnership groups in which nobody has a drawn parent. A married-in spouse has no drawn parents of their own, so starting from a person would let their block take their partner before the partner's parents claimed them. Whoever no block reaches starts a block of their own, so everyone is drawn once, and the parent line that did not place them is drawn as a secondary path. Families sit side by side, largest first, half a card's width apart.
  - **Same button and address as the WebGL views:** `scope=all` and a Whole tree toggle, here in the zoom bar. A `hasWholeTree` view trait replaced the `isWebGl` check in the address, with Layers and Floors dropping the scope; ADR-047 removed both views and the trait, so every view keeps it.
  - **A card in the flat whole tree is a way in:** clicking it focuses that person and leaves the whole tree. The WebGL views light a line in place instead; the flat view has no line highlight to show.
  - **No focus, no relation labels:** the whole tree's roles are placeholders, so a card's accessible name gives the person and dates only, and the first card holds the tab stop.
- **Rejected alternatives:** a layered engine (a new dependency, and the flat view's contract checks would have to be re-proven against it); running the hourglass from one person per family (it reaches ancestors and descendants only, never a spouse's parents).
- **Consequences:** the contract sweep (`whole-tree.flat.test.ts`) covers every fixture plus a graph of scattered families. A tree with many separate families draws wide, across few rows, and opens below its whole width at the minimum zoom; the minimap and edge markers cover the rest.

## ADR-048: Content-Security-Policy ships report-only first, with transport and framing headers (fixes F7)
- **Status:** built on `claude/security-concerns-validation-3bcb9c` on 2026-10-14 and deployed. No migration.
- **Context:** the app sent no Content-Security-Policy and no HTML hardening headers; only the media route set its own. Nothing in `src/` loads script, style or fonts from another origin, and there is no `{@html}`, so the policy can be strict. Nothing in CI can load the real UI against a policy, though, and an enforced policy that blocks one component (a three.js texture, a Splash background) would break the deployed app with no test to catch it.
- **Decision:**
  - **`kit.csp` in report-only mode** (`vite.config.ts`): `default-src`, `script-src`, `style-src`, `img-src`, `font-src`, `connect-src`, `worker-src` (blob, for three.js), `object-src 'none'`, `base-uri`, `form-action`, `frame-ancestors 'none'`. Kit's `mode: 'auto'` adds nonces to the inline bootstrap on dynamic pages.
  - **Headers from `handle`** (`src/lib/server/http/security-headers.ts`): HSTS (`max-age=31536000`, with neither `includeSubDomains` nor `preload`, since the app is open source and may run beside sibling subdomains it does not control; only over https and never on a local host), `X-Frame-Options: DENY` (the only clickjacking control, since `frame-ancestors` is ignored in report-only), `Referrer-Policy`, `X-Content-Type-Options`, `Permissions-Policy`. A route's own header wins, so media keeps `Content-Security-Policy: sandbox`.
  - **A report endpoint** (`/api/csp-report`) because Kit refuses a report-only policy without `report-uri` or `report-to`. It logs a summary of each violation (the directive, the blocked origin or keyword, the document path, never the query string) and answers 204.
  - **Rejected alternatives:** enforcing from the start (no way to verify the UI against it here); a header set in the Cloudflare dashboard (outside the repository, so it would drift from the code and the tests); `preload` on HSTS (a commitment for the whole domain, not made by this change).
- **Before switching to enforcing** (rename `reportOnly` to `directives` in `vite.config.ts`):
  - Open each main view in the browser with the console open (Flat, the whole tree, the four WebGL views, the tree editor dialogs, Splash, sign-in) and check for `Content-Security-Policy` messages. Any blocked script, style, image, font or worker needs a fix or a narrow source, not `'unsafe-inline'` on script.
  - Check the `/api/csp-report` log lines (`Content-Security-Policy violation (report-only)`) over a few days of real use, including the WebGL views, where three.js is the likeliest source of `worker-src` or `img-src` reports.
  - Confirm the report endpoint receives reports from a browser (the reports from a signed-out visitor and a signed-in one both arrive, since the endpoint takes anonymous POSTs).
  - Only then switch, and keep the report target so enforcing violations still reach the log.
- **Consequences:** the policy is not enforced yet, so a violation changes nothing for a visitor but the log. HSTS takes effect on the first https response a browser receives, and the host that sent it is pinned to https for a year (its subdomains are not, since `includeSubDomains` is off). The endpoint takes anonymous POSTs (the hook does not refuse them, and a report carries no credential), so anyone can write to its log. The body is read through a byte-counting reader capped at 16 KB (a chunked body has no `Content-Length`), each POST logs one summary line, and a Cloudflare rate-limit rule for the path is listed in `docs/backlog.md`; until it exists the log can still be flooded at the platform's request rate.

## ADR-049: Name search moves to an FTS5 table kept current by triggers (amends ADR-014's search costs, settles the normalised name column)
- **Status:** built on 2026-10-14 (migration `0029_name_fts.sql`, `SearchRepository.rankedNames`). Passed locally: `search-plans.test.ts` and `privacy-reads.test.ts` with unchanged assertions (one plan-check exemption, below); the two-tree witness on the index (`name-fts.test.ts`); the trigger consistency check across create, rename, name add, rename and remove, merge and its undo, person removal, tree move, a replace-mode delete, a bulk insert, a tree delete, and the real GEDCOM importer in replace and merge modes (`The Simpsons.ged`, then `The Windsors.ged` merged in, then the Simpsons replaced); and "müller" finds "Müller" while "mueller" does not. Redo does not exist in this codebase (undo is the only reversal), so it is not covered. **Remote D1 check, 2026-10-14:** on a scratch production-class D1 database (since deleted), `fts5(… tokenize = 'trigram remove_diacritics 1')` was accepted; "müller" and "muller" matched "Hans Müller" and "mueller" did not; a `tree_id : "…" AND name : "…"` match was scoped to its tree; and an `AFTER INSERT` trigger writing to the FTS table made "angstrom" find "Zoë Ångström". The full migration and the bulk-insert cost were not run remotely, so the import cost stays the open measurement.
- **Deviations from the proposal, made while building it:**
  - *A key table beside the FTS table.* `name_fts_key (id, person_id, name_id)` gives each FTS row a stable integer rowid. The triggers find their row through it, indexed by `person_id` and `name_id`. Without it a trigger either scans the FTS table (its `person_id` column is unindexed) or uses a name table's rowid, which VACUUM can renumber. The triggers are per row (insert, update, delete), not delete-then-reinsert, so a replace-mode import does not scan the index once per person.
  - *Every word of three or more letters is in the MATCH, ANDed.* The proposal said the longest word. The other words cannot be checked afterwards with `LIKE`, since that does not fold: "zoe muller" would miss "Zoë Müller".
  - *Scoring uses the words as typed, not folded.* Folding them would drop an exact match that works today ("müller" against a stored "müller" would fall to the "contains" level). A stored name with a diacritic found by its folded form therefore ranks at the "contains" level. This is the fallback the brief allows.
  - *`search-plans.test.ts` changed one helper.* The plan check flags any `SCAN` line, and a MATCH-driven virtual-table read is printed as `SCAN … VIRTUAL TABLE INDEX n:M…`. The check now ignores exactly that form. A virtual-table scan without MATCH still fails. The assertions are unchanged. `schema-status.test.ts` skips the `name_fts*` tables, since the schema cannot declare them.
- **Context:** `docs/backlog.md` asks for a decision on "counters or a normalised name column before large trees". Name search reads about 4 to 8 rows per person (22,000 to 40,000 on the 5,324-person tree in `query-plans.md`), because a `LIKE '%…%'` cannot use an index and ranking happens before `LIMIT`. Rows are cheap on Workers Paid (25 billion a month included, so about 600,000 such searches), but on Workers Free the 5 million a day is about 125 searches. The defect people will notice first is not cost but matching: SQLite's `lower()`, `LIKE` and `NOCASE` fold only ASCII, so "müller" does not find "Müller", and there is no phonetic match. A fix has to keep three properties of today's search: one tree's work only (the two-tree witness in `search-plans.test.ts`), ranking before `LIMIT`, and privacy as a predicate in the same query (ADR-015).
- **Decision:**
  - **An FTS5 table of name text, inside D1.** D1 supports FTS5 (including `fts5vocab`). One row per candidate the search already ranks: each `person_names` row, and each person's own given name and surname (the display name, which ADR-014's search counts because a person created before S6 has no name row). Columns: the name text (prefix, given, nickname, surname prefix, surname, suffix, as `NAME_HAY` builds it), and unindexed `tree_id`, `person_id`, `name_id`.
  - **Diacritics fold in the index, not in SQL.** The tokenizer folds Unicode case and removes diacritics (`trigram remove_diacritics 1`, or `unicode61 remove_diacritics 2` if trigram is unavailable). SQL cannot do this in D1: there are no user functions, and SQLite's built-ins fold only ASCII. The query string is folded the same way in the service (`normalize('NFD')`, strip combining marks, lower-case) before it is matched.
  - **Trigram first, because it keeps today's substring semantics.** The search matches a word anywhere in a name (`%…%`); `trigram` does the same, and `unicode61` would only match whole tokens or prefixes. Trigram cannot match a term under three characters, so a one- or two-letter word keeps the existing `LIKE` path, whose cost is the same as today.
  - **Kept current by SQLite triggers, not by the writers.** `AFTER INSERT/UPDATE/DELETE` triggers on `person_names` and on `individuals` (when `given_name`, `surname` or `tree_id` change) rewrite the person's rows. ADR-015 rejected a stored column because every writer (the mutation runner, each command, import, merge, undo and redo) would have to maintain it; a trigger runs for all of them, since they all write these tables. These are the first triggers in the schema.
  - **The tree is part of the match.** `tree_id` filtered after a `MATCH` would read every tree's hits for a common name, which the two-tree witness exists to catch. The tree goes into the match itself: `tree_id` is an indexed column and the match names it (`tree_id : "<uuid>" AND name : "…"`). Measured on the two-tree corpus, small tree (419 people), "ann": the tree in the MATCH returns and reads 27 rows; the tree filtered after the MATCH reads 436, because every tree's matches are read before the tree is checked (436 rows for either tree). "ashson": 5 against 47. Both forms are recorded in `query-plans.md`. One FTS table per tree is rejected, because trees are created at run time and migrations are static.
  - **Ranking and privacy stay in SQL.** The FTS hits become the candidate set the existing ranking and `GROUP BY` best-name step run over, still before `LIMIT`; the visibility predicate (`andVisible`) is applied to those people in the same statement, so `hasMore`, page fill and counts stay correct for a restricted viewer.
  - **A hand-written migration.** Drizzle's schema cannot express a virtual table or a trigger, so the migration (expand-only: create the table, the triggers, and backfill with one `INSERT … SELECT`) is written by hand and the table is left out of the Drizzle schema; reads use raw `sql`. The backfill writes one row per name and person, billed as rows written.
  - **Rejected alternatives:**
    - *A normalised column on `person_names` and `individuals`.* It fixes folding only if the app computes it (SQL cannot fold Unicode), so every writer must set it, the ADR-015 objection. It still needs a `LIKE '%…%'` scan to match substrings, so it does not reduce rows read.
    - *Vectorize, or AI Search (hybrid BM25 and vector).* Names carry no meaning for an embedding to capture, so vector similarity is a poor stand-in for spelling and sound. The index returns ids that D1 must then filter for privacy, which breaks `hasMore`, page fill and counts (the design ADR-015 replaced). Living people's names would leave D1. Vectorize returns at most 50 results with metadata, AI Search allows 5 custom metadata fields and filters on the first 64 bytes of a string, and AI Search includes 1,000 hybrid queries a month, then $0.75 per 1,000 (billed from 2026-11-01), which does not suit search as you type. Both stay candidates for note and source search and for scanned-document text (OCR), where the wording varies and meaning matters, limited to what everyone may see or once privacy can be expressed as a filter.
    - *Surname counters.* They help the surname list, not search, and only for unrestricted roles, since a restricted viewer's count depends on who they may see.
- **Acceptance checks before this is "decided":**
  - D1 accepts the chosen tokenizer (`trigram` with `remove_diacritics` needs a recent SQLite; D1's docs list FTS5 but not its tokenizers). Test it against a deployed database, not only local `workerd` (done on 2026-10-14, see Status).
  - `search-plans.test.ts` and `privacy-reads.test.ts` pass unchanged, and the two-tree witness holds: a search of the small tree reads no row of the big one. How D1 counts `rows_read` for an FTS query is undocumented, so record it in `query-plans.md` beside the S7 table.
  - A trigger test per writer path: create, rename, add and remove a name, import (both modes), merge, delete, undo and redo each leave the FTS rows equal to a rebuild from the base tables.
  - "müller" finds "Müller". "mueller" does not, because folding is not transliteration; that is the phonetic step.
- **Consequences:**
  - **`wrangler d1 export` refuses a database that holds a virtual table.** Cloudflare's workaround is to drop the virtual tables, export, and recreate them. The D1 recovery runbook in the backlog must say so and ship a rebuild script (drop, export, recreate, repopulate with the backfill `INSERT … SELECT`). Time Travel is not affected.
  - Every name write also writes FTS rows (more rows written per name change, and more again for an import). Measured locally, a raw insert of 5,000 people took 1.5 s with the triggers against 0.23 s without, and 50,000 took 69 s: the cost is superlinear as the index grows. `tree_id` is indexed too (it has to be, for the match), so each row also carries its tree's 34 trigrams. Before a large import is measured on the deployed database, this is the number to watch, along with rows written.
  - A `wrangler rollback` restores code that does not read the table; the triggers keep maintaining it, which is harmless. Dropping it later is a contract migration.
  - **Phonetic search builds on this.** A Soundex or Daitch-Mokotoff code is computed in the app (SQLite has no such function in D1), so it cannot come from a trigger. It is added as a second column of the same table, written by the writers or by a rebuild, in its own ADR.
  - Place search can follow the same pattern over `events.place`, once this is measured.

## ADR-050: A file's owner lives in D1, not its key; the Files manager (amends ADR-039, extends ADR-041)
- **Status:** built on `claude/media-management-file-system-0f02e1` on 2026-10-14 and deployed. Migration 0029 must be applied before the code is deployed. It rebuilds `media_items` and fills the new columns with defaults, and nothing references `media_items`, so the code it replaces reads only columns it already had. Checked by unit and route tests for the key parser, the read path, the row operations, tree deletion, the unlinked scan, the listing and the Files page.
- **Context:** a file's owner was embedded in its R2 key (`media/<treeId>/<entityId>/<uuid>.<ext>`). A person merge moved the row but not the key, so a restricted viewer of the surviving person got a false 404, because the read check parsed the old id from the key. Moving or detaching a file, or deleting its owner, would have meant copying or removing the bytes. The Files manager needed attach, detach, move and delete that never touch the bytes.
- **Decision:**
  - **Ownership is the row.** New uploads are keyed `media/<treeId>/<mediaId>.<ext>`: the key names the file, not its owner. `media_items.entity_id` names the owner, a person or a partnership, or is null for a detached file. Legacy keys (`media/<treeId>/<entityId>/<file>`) are still read and are not moved. `parseMediaKey` accepts both shapes and reads only the tree from them.
  - **Read order.** `requireRead` parses the tree from the key, runs the tree-scope check, and only then looks up the row by `(tree_id, r2_object_key)`. A caller outside the tree is refused before the row is read, so a key's existence is not revealed. No row is a 404. The owner comes from the row.
  - **One visibility rule.** `canReadRow` decides for both `requireRead` and the Files list, so the two cannot disagree. Unrestricted roles see every file. A restricted viewer sees a file only when every person it hangs off is visible; a partnership's files need every partner visible, and a partnership with no partners is hidden. A detached file is shown to editors and above only.
  - **Nullable owner.** A detached file stays in the tree until someone attaches it. Attach needs a person or partnership in the same tree. Move is a detach and an attach in one request, within one tree.
  - **Columns (migration 0029).** `size_bytes` (null until backfilled), `uploaded_by` (no foreign key, as in `change_log`), `version` (default 1), `updated_at`, and the index `(tree_id, r2_object_key)`. The upload writes the object before its row, and deletes the object again if the row write fails.
  - **Logged changes.** Rename, attach, detach and move are row operations in the mutation runner, so the change log records them and undo reverses them. Each checks `version`, and a stale version answers 409. `size_bytes` and `uploaded_by` are derived columns, left out of row images, so an undo image written before 0029 still matches its row.
  - **Delete is outside the log.** Delete removes the row first, then the object. If the object cannot be removed, the file is still gone for everyone, the orphaned object is left for the unlinked scan, and the response says so. Delete is not undoable. An earlier change that touches the row refuses its undo once it is gone, and the confirm dialog says so.
  - **Unlinked scan.** One R2 listing, and an object is unlinked when no row in its tree names its key. Objects younger than an hour are skipped, because an upload writes its object before its row. Only managers and owners can list or delete, in trees they may manage, and deletion works on a fresh listing rather than a list the client sends.
  - **Tree deletion.** The rows go first, which the database cascades. Then the tree's `media/` objects and its staged GEDCOM uploads are swept in batches of up to 1,000 keys. A failed sweep is logged, not thrown, so the leftover bytes have no row and no one can read them.
  - **Person and partnership changes.** Deleting a person, or the last partner of a partnership, and destroying a partnership, detach its files rather than delete them. Undo hangs each file back on its record. Merging two partnerships moves their files to the survivor in the same change.
  - **Roles.**
    - Viewer and contributor browse and preview files attached to people they can see. They have no actions.
    - Editor (`media:manage`) uploads, renames, attaches, detaches and moves, and deletes the files they uploaded. A file with no recorded uploader, which is every file from before 0029, is not an editor's to delete.
    - Manager and owner (`media:delete_any`) delete any file, and see the uploader's name.
    - Public visitor and outsiders get no Files page. Uploader names never reach them, as ADR-041 requires.
    - Install owner sees names, sizes, counts and totals for trees they are not in (via `TreeRepository.listAll`), and nothing that would show or change a file there. The install-wide total is shown to the install owner only. This keeps ADR-041's rule that a non-member has no access to a tree's content, and extends it to metadata.
    - Per-tree usage and quota totals are shown to editors and above only.
  - **Quota.** The usage bar is the R2 total for the tree, since that is what an upload refusal enforces. Each file's own size comes from its row, shown as unknown until backfilled.
  - **Preview.** Images preview inline through the serve route (ADR-039). A PDF is a download link only, since the serve route sends it as an attachment.
  - **Size backfill.** `scripts/backfill-media-sizes.mjs` (`npm run db:backfill:media-sizes`) is a one-off, idempotent script. It writes only rows with no size, and never runs on a GET.
- **Rejected alternatives:** copying or renaming R2 objects when a file moves between records (a copy per file, and a window where the key and row disagree); keeping the owner in the key and rewriting keys on merge (the same copy); deleting a deleted person's files (the bytes would be lost and undo could not restore them); letting editors delete any file (a manager's call, as with members in ADR-016); logging deletes in the change log now (undo would have to keep the bytes until the window closed, which is not built).
- **Rollback caveat:** `wrangler rollback` restores the code, never the schema. The previous parser reads a key as `<tree>/<entity>/<file>` and answers 404 for every `media/<treeId>/<mediaId>.<ext>` key. Files uploaded after this deploy are unreachable under the old code until it is deployed again. Roll back only with that in mind, or redeploy this code instead.
- **Consequences:** files from before 0029 have no uploader, so editors cannot delete them, and their sizes show as unknown until the backfill runs. A restricted list reads up to 500 rows per request, and an undo of a pre-0029 `delete_person` can point at an object the unlinked scan has removed. All are recorded in [backlog.md](./backlog.md), with the other open file gaps.

## ADR-051: Fact details are columns, and kept lines show read-only (amends ADR-023; extends ADR-004, ADR-013 and ADR-028)
- **Status:** built on `claude/fact-details-retained-lines` on 2026-10-15 and deployed. Migration 0031 only adds nullable columns, so it can run before the code. `npm run db:backfill:fact-details` must run straight after the deploy that carries it.
- **Context:** real files put an address, phone numbers, an agency and a religion under most events. ADR-023 kept those lines verbatim in `events.gedcom_extra`: they exported, but nobody could see or edit them. Worse, the parser treated the children of `PLAC` as modelled and kept only the place's value, so a `MAP` with coordinates or a `FORM` was dropped on import without a trace.
- **Decision:**
  - **One column per detail, not one JSON blob.** `events` gains `address`, `address_layout`, `classification` (`TYPE`), `agency`, `phone`, `email`, `fax`, `web`, `latitude`, `longitude`, `place_extra` and `religion`, all nullable. A column each lets the dialog and the validation schemas name a field, lets a merge key and an undo image compare one field at a time, and keeps each value queryable in SQL. A blob would have rewritten the whole value on every edit and hidden the fields from everything except the parser.
  - **Addresses keep the file's layout.** `address` is the logical text, the `CONT` lines joined with a newline and `CONC` joined directly, stored untrimmed. `address_layout` keeps the file's own `ADDR` lines (`ADDR`, `CONT`/`CONC`, and the structured `ADR1` to `CTRY`) as `fieldLayout` returns them. Export uses the layout only while `textOfLines(layout) === address`, the same staleness check ADR-028 applies to `gedcom_layout`. An edit that changes the text makes the layout stale, and the text is written as `CONT` lines. The repository's ADDR helpers do the reading and writing, so the two kinds of address follow one rule.
  - **Multi-value contacts.** `phone`, `email`, `fax` and `web` hold their values joined by a newline, and export writes one line per value. The spec allows three of each; the editor does not stop at three (see lenient validation below).
  - **Only childless, single lines are modelled.** A `PHON`, `EMAIL`, `FAX` or `WWW` with children (a `TYPE` under a `PHON`, say) stays whole in `gedcom_extra`. So does a second `TYPE`, `AGNC` or `RELI`. Nothing is split and then glued back wrongly.
  - **Place children.** The first `MAP` with exactly one childless `LATI` and one childless `LONG` becomes `latitude` and `longitude`, stored as written (`N18.150944`). Every other child of `PLAC` (`FORM`, `FONE`, `ROMN`, `NOTE`, `SOUR`, a second `MAP`) is kept verbatim, with its levels, in `place_extra`, written straight after `PLAC`. These are written only when the place has a value. A place with no value but with children stays whole in `gedcom_extra`, because otherwise the serializer would skip it and orphan its children. Coordinates therefore need a place, and the editor disables them while the place is empty. Before this change every child of `PLAC` was dropped silently on import.
  - **`RESN` under a fact stays retained,** shown read-only. A fact-level `RESN` overlaps the person-level privacy rule (ADR-015), and deciding what it should mean is a separate question (backlog). Its consequence is deliberate: the contact fields and the address of a fact marked `RESN confidential` are now shown to anyone who can see the person. The `RESN` does not hide them, because it never did for a fact's other fields either.
  - **Family events** are parsed, stored and exported with the same fields, but there is no editor yet, and the partnership DTO does not carry event details, so nothing shows them either. Adding that is a backlog item.
  - **Undo safety.** The new columns are user-editable, so they are not in `DERIVED_COLUMNS` (which holds the derived columns that are left out of row images). `withAllColumns(image, columns)` fills a missing key with `null`. It is used in `matchesImage`, in `changedFields` and on the after image of `rebaseInverse`. An undo image written before migration 0031 therefore matches its row, and an undo of a pre-migration `update_fact` lists no phantom fields (before, every new column showed as a change, `undefined` against `null`). A real mismatch still refuses the undo.
  - **Lenient validation.** Imports are never validated, so an edit to an imported fact must not fail on a limit the file already broke. The schemas cap single-line fields generously (500 characters) and the address at 2,000 characters. They do not check a three-value limit, a per-line limit or the shape of a coordinate; the dialog hint shows `N18.150944`. Validation covers only what is a real safety limit. The dialog sends stored values back unchanged, so saving a date edit cannot erase an imported address, phone or agency.
  - **Retained lines are shown, not hidden.** `retainedLines` is the stored `gedcom_extra`, verbatim after the pointer remap and unfiltered, shown under the fact as "Imported, not editable here". Filtering would hide data in trees whose notes or evidence are not yet backfilled. The lines pass through the person page's existing privacy mask, so a restricted viewer gets none of them.
  - **The import preview names what remains.** `retainedTags` counts the top-level tags of lines still kept under events, by tag only, at most twenty, and the import dialog says "Kept as-is and not editable yet". ADR-023 deliberately did not count them. This is the first time an importer says what it could not model.
  - **Batch size comes from the schema.** An event row now has 35 columns. The statement batch is `MAX_BOUND_PARAMS` (70) divided by the table's column count, which is two rows, where the old literal of 23 would have allowed three rows and 105 parameters. Adding a column can no longer exceed the limit silently.
  - **Identity.** A fact's merge key includes every new field, with the list fields JSON-encoded, so two facts that differ only by address are two facts. The address layout is left out, so the same address written with `CONC` or with `CONT` is one fact. `detailsOf` in the fact timeline is unchanged: two births with different addresses still read as a repeat.
  - **Backfill** (`scripts/backfill-fact-details.mjs`, ADR-023's pattern). It runs after the evidence and notes backfills, and it moves `TYPE`, `ADDR`, `AGNC`, `RELI`, `PHON`, `EMAIL`, `FAX` and `WWW` from `gedcom_extra` into a column only where the column is still null. A second occurrence stays put, and nothing from `PLAC`, `DATE`, `CAUS` or `AGE` moves. Each row gets one `UPDATE` that sets its columns, reduces `gedcom_extra`, and increments `version`. A row with nothing to move gets no statement, so a second run does nothing. The backfill cannot recover `PLAC` children that earlier imports dropped. A replace-mode re-import of the file recovers them.
  - **Deploy window.** Until the backfill has run, two things go wrong. A merge-mode re-import duplicates any fact that has an `ADDR`, because the key now includes the address and the old fact has none in its column. Editing an empty Address leaves two `ADDR` lines on export, because the old line still sits in `gedcom_extra` beside the new one. Both are in the development guide's backfill row.
  - **Spec facts, checked against the 5.5.1 errata edition.** `AGE` is only in `INDIVIDUAL_EVENT_DETAIL`, so a family event's `AGE` is a `HUSB` or `WIFE` substructure and stays retained. `PHON`, `EMAIL`, `FAX` and `WWW` are siblings of `ADDR`, not its children. `ADDR` takes at most three `CONT` lines. The structured `ADR1` to `CTRY` are kept through the layout, not modelled.
- **Rejected alternatives:** a JSON blob for the details (see above); modelling `RESN` under a fact now, which would decide a privacy question as a side effect of a parser change; editing family events now, because the partnership DTO and the union editor would both need to change; trimming addresses on import, which would lose the file's `CONC` and `CONT` split; putting the new columns in `DERIVED_COLUMNS`, which would make undo ignore a field the user can change.
- **Consequences:** Files imported before this change show their addresses, contacts and coordinates only after the backfill, or after a replace-mode re-import. The backfill cannot bring back what an earlier import dropped. Family-event details are stored and exported, but not shown or editable. The `RESN` decision and the family-event editor are in [backlog.md](./backlog.md).

## ADR-052: Security audit 2026-10-13, F11 to F18: what was fixed, what was not, and the rules that came out of it
- **Status:** built on `claude/audit-f12-f18` and deployed. No migration. The audit is [security-audit-2026-10-13.md](./security-audit-2026-10-13.md).
- **F11, `workers_dev: true`: won't fix.** The app is deployed on a `workers.dev` hostname while it is under development, and nothing there sits behind Access, so the request degrades to anonymous as the audit says. Revisit when the install moves to a custom domain: set `workers_dev` to `false` in the deploy config then.
- **F12, public-visitor context fails closed (amends ADR-041).** The hook still stamps an anonymous `/api` GET with `PUBLIC_VISITOR`, but `apiHandler` and `treeHandler` now refuse that visitor unless the route's options say `allowPublicVisitor: true`, and `treeHandler` refuses it for any tree other than the public one. The refusal is a **403 with the same body** whether the tree is private or unknown, never a 401 (the client restarts sign-in on a 401, which would push an anonymous visitor into Access) and never a 404. The opt-in is written on each route's GET options only; nothing stops a shared options object carrying it to a write, but the hook stamps the visitor on GET and HEAD alone, so a write never sees one. Both factories register the handlers they return, and `privacy-matrix.test.ts` imports every route module and fails if a GET is not a factory handler, or if its opt-in disagrees with `VISITOR_READS`. The one hand-rolled GET, `media/[...key]`, is named in that test and keeps its own guard (`MediaService.requireRead`).
- **F13, raw SQL in `visibility.ts`.** The event-type lists stay **inline literals, validated** by `literalList` (`/^[A-Z]{3,5}$/`), and are not bound: binding them adds 6 parameters to every visibility predicate and takes `NoteRepository.visibleUseCounts` for an 80-id chunk (98 parameters) past D1's limit of 100. Table aliases cannot be bound, so `ident` accepts only `/^[a-z][a-z0-9_]*$/`. `bound-params.test.ts` compiles the heaviest chunked statements it knows of (notes, tasks, cross-references, source counts) and fails past 100 parameters; the review that followed found `visibleCitationCounts` over the limit at 80 ids for a contributor, so its chunk is now 50 and a real-D1 test covers it. The test lists statements by hand, so a new chunked read with a visibility fragment must be added to it. The offline backfill scripts build SQL text but escape quotes completely and take their identifiers from constants; they are not request-reachable and were left alone.
- **F14, id-lookup helpers take a required `treeId`.** `namesOf`, `namesByIds`, `linksOfSource` and `actorNames` scope in SQL: `person_names` through `individuals`, source links through `sources` and a tree-scoped `repositories` join, and actors to those with a `change_log` row in the tree (not current members, so a removed member's edits still show a name). `namesOf` uses `inTree`, the unary-plus form, so SQLite does not walk the tree index. Rows read for the "names of people" plan sample went from 3 to 6, inside its bound.
- **F15 to F17.** The export download takes its `Content-Type` from `shouldCompress` and never from stored object metadata. `CF_IMAGES_TOKEN` and `CF_ACCOUNT_ID` are gone from the platform env type. The two `new RegExp` calls built from a tree id are a prefix check.
- **F18, CSRF and CORS stay on defaults, now guarded.** `csrf-cors.test.ts` fails if `vite.config.ts` sets `csrf`, `trustedOrigins`, `checkOrigin` or an `origin`, or if any source file names an `access-control-allow-` header. In SvelteKit 3 `csrf.checkOrigin` no longer exists and `trustedOrigins` is the only option.
- **Rejected alternatives:** binding the type lists (parameter limit, above); a 404 for a non-public tree (ADR-041 already answers 403, and `resolveTreeAccess` answers the same for an unknown tree); leaving `treeHandler` open by default and relying on the cross-tree check alone (a future handler that forgot its guard would still show the public tree's private people); scoping `actorNames` to current members.
- **Consequences:** a new GET that a visitor should read needs `allowPublicVisitor: true` and a row in `VISITOR_READS`, or the matrix test fails. A new id-lookup helper needs a `treeId`. Open gaps found on the way are in [backlog.md](./backlog.md).

## ADR-053: One section order for the person page and drawer, evidence against claims, facts grouped by kind (amends ADR-028 and ADR-051)
- **Status:** built on `claude/person-details-layout-2a8f7d` and deployed. No migration.
- **Context:** the person page and the tree drawer rendered the same sections in different orders, and the drawer showed every fact in full. A separate "Sources and evidence" section listed every citation a second time, against the same facts and names the page already showed them under.
- **Decision:**
  - **One section order.** Family, Facts, Names, Photos and documents, Privacy, Notes, Tasks, History. The drawer renders them in that order in one column. The page renders the same order in two columns: Family, Facts and Names on the wide left, the rest on the right, so reading the left column and then the right matches the drawer.
  - **Evidence sits against the claim it supports.** The "Sources and evidence" section is gone. Each fact, each name and each parent link shows its own citations, and the person's own citations show once, beneath the summary in the header. A claim with no citation reads Unsourced.
  - **Unsourced is the way to add a citation.** For an editor (or anyone who can cite), the Unsourced marker is a button that opens the citation dialog for that claim. A claim with citations keeps the disclosure, and a viewer sees the marker as plain text. The dialog's save and stale handling is shared (`citation-changes.ts`).
  - **Facts are grouped by kind, newest shown.** A group is one panel per fact type, with a custom event's sub-type as part of its kind. The panel shows its newest fact (undated counts as oldest; ties go to the later one in the list). The rest sit behind "Show N earlier", newest to oldest.
  - **A conflict never collapses.** If any fact in a group disagrees with or repeats another, every fact in that group is shown and the button is not drawn. The product does not hide disagreeing evidence.
- **Rejected alternatives:** keeping the evidence list and collapsing it by default (the duplicate would still be one click away, and a citation would still be listed in two places); collapsing a conflicting group (it would hide the disagreement the product is built to keep visible); grouping by a computed label, which would merge custom events that differ only by sub-type.
- **Consequences:** each parent in the person page DTO carries its `linkId` (threaded from the parent-child row through the relationship graph, optional there so older captured graphs still load), which is what the parent row files its evidence under. A fact's move controls swap only with a neighbour of the same kind and date, since the list now shows each kind as one panel.

## ADR-054: Colours and motion are settings, layered like webtrees: user, then site, then built-in (extends ADR-034, ADR-035 and ADR-041)
- **Status:** built on `claude/settings-page-colors-plan-24ecc2` and deployed. **Migration 0032 must be applied before this code is deployed.** It only adds two tables (`user_settings`, `site_settings`), so it is safe to run first, and the schema check in `hooks.server.ts` answers every request with a 503 until it has run. `npm run deploy` already migrates before it deploys.
- **Context:** ADR-035 fixed the sex colours, the trace palette and the focus line in `tree-tokens.ts`. People with colour-vision differences need to change them, and the install owner wants one look for everyone, including readers of the public tree. The backlog asked whose choice it is, where it is stored, and how a choice is kept legible.
- **Decision:**
  - **Three layers, modelled on webtrees.** webtrees reads a user preference, then the site preference, then a built-in default. Epoch does the same: the built-in palette, then a site default that the install owner sets, then the person's own choice. There is **no per-tree layer**: colours are about who is looking, not what they look at, and a fourth layer would make "why is this pink?" hard to answer. The install owner (ADR-034) plays webtrees' administrator. Signed-out readers and the public visitor (ADR-041) get the site default.
  - **Groups inherit whole.** A layer stores three optional groups: sex colours (male, female, unknown or other), the trace palette with its intersection colour, and the focus line (ancestor, descendant, partner). A missing group inherits from the layer below, and a save replaces or clears whole groups, so a half-set group can never mix two people's choices. The settings page offers "Use the site default" for each group, a global reset, and two presets: Default and Colour-blind safe (Okabe-Ito blue and a darkened vermilion for the sexes, and a trace set without those two hues).
  - **Storage.** Migration 0032 adds `user_settings` (one row per user, cascading on delete) and `site_settings` (one row, held to `id = 1` by a check). Each holds a versioned JSON document. It is validated by zod on write and again on read; a row that fails to parse is read as unset, so a corrupt row falls back to the layer below and never breaks a page.
  - **Legibility is enforced, not suggested.** A save is refused (`ValidationError`, 400) when a sex colour breaks a WCAG floor: card border against its fill at least 3:1, card ink on the fill at least 4.5:1, and the sphere and star against both dark 3D stages at least 3:1. The floors are checked on the palette the document resolves to, so derived shades are held to them too. Trace colours that sit within 0.08 of each other in OKLab, or of a sex colour, raise a text warning only. Nothing is adjusted automatically. The page shows the same figures, computed by the same module (`src/lib/shared/settings.ts`).
  - **Derivation.** A changed sex colour derives its card fill (80% toward white) and its Orrery star (45% toward white). A changed focus colour derives its dark-stage shade (40% toward white). The built-in values are literal, not derived, so the default rendering is exactly what it was.
  - **Colours reach style attributes,** so each is held to `/^#[0-9a-f]{6}$/` on the server, again when the palette is resolved, and again where it is emitted (`safePalette`, `treeTokenStyle`). Anything else falls back to the built-in colour.
  - **Where it is read.** The root `+layout.server.ts` resolves the caller's palette and motion setting once per page, through `SettingsService.resolveFor`, and registers `app:settings`, which a save invalidates. A failure to read settings is logged and falls back to the built-in palette: colours are cosmetic and must never take a page down.
  - **Reduced motion.** A person may turn on "Reduce animation". It is a user setting only; the site has none. The root layout sets `data-reduce-motion` on the server render, and the flat view's viewport, the WebGL shell, the recentre cue and app-wide transitions honour it. It only adds reduction: it never starts motion that the system's `prefers-reduced-motion` stops.
  - **Deviations from the first plan, accepted.** The flat view's partnership line (`--partner-line`) is not editable. Changing the focus ancestor and descendant colours also changes the flat view's `--union-ink` and `--tree-accent`. The settings page and the 3D legends both say "Unknown or other" for the third sex colour.
- **Rejected alternatives:** a per-tree colour layer, or a Manage > Colours page for managers (both make colour a property of the tree, and a viewer with a colour-vision difference could not change it); `localStorage` (lost across devices, invisible to the server render, and no site default); one column per colour (eleven columns per layer and a migration for every new colour); adjusting a colour automatically to pass a floor (the person would not get what they chose, and would not know why).
- **Consequences:** two new tables to deploy before the code. Every page load reads one or two small rows. `palette.ts` and `tree-tokens.ts` have since moved to `src/lib/shared/`, and ESLint keeps `server/` and `shared/` from importing `components/`. Further settings (date format, name order, display-panel defaults, a 3D quality cap) are in [backlog.md](./backlog.md).

## ADR-055: A write plans over a scoped snapshot; equality with the whole tree is the proof (amends ADR-007)
- **Status:** accepted 2026-10-16. Every kind is scoped except the merges, `standardise_dates`, `rewrite_place` and the data-quality report, which stay whole-tree by design (backlog.md, "A few writes read the whole tree"). No migration.
- **Context:** every mutation, preview, merge and undo plans against `ChangeStore.loadRows`, which reads every row of 14 tables for the tree. That is fine at today's sizes but grows linearly with the tree for every edit, against the Worker's memory and D1's per-row billing (query-plans.md, "Writes read a scoped snapshot"). The planners (`buildPlanOps` and the `*-ops.ts` modules) are pure functions of a `TreeRows` snapshot, so only what is loaded needs to change.
- **Decision:**
  - **A per-kind scope table.** Each command kind either names a scope seed (the records it reads) or is absent. An absent kind loads the whole tree, exactly as before, so every intermediate commit is safe and kinds are switched on one domain at a time. A kind may also ask for one whole table on top of its scope: `assert_parent_child` asks for all of `parent_child`, because the cycle check walks every link.
  - **One closure rule set, applied by a pure selector and by the D1 loader alike.** Seeds resolve to subjects first: an event to its entity, a name to its person, a citation to its subject and its source, a note attachment to its subject and its note, a task to its subject, a file to its owner, a link to both people and its union. A source pulls its citations, a shared note its attachments, a repository its `source_repositories` rows. Every person loaded for any reason comes with all their names and individual events, because privacy (ADR-015) and the labeller read them. Each loaded person brings their partnerships, every partner of those, the partnerships' family events, every `parent_child` row touching a loaded person or partnership with the person at the other end, and their files. Then everything attached to any loaded record: citations with their sources, repositories and `source_repositories` rows; note attachments with their notes; tasks.
  - **A follow-up load for what no seed can name.** The labeller numbers a partnership among the same pair's other partnerships ("2nd partnership of A and B"), and `add_parent` picks its family from the child's links. Those partnerships belong to people the command does not name, so a seed with `shouldFollowFamily` is loaded, `followUpSeed` (`write-scope/follow-up.ts`, pure) reads the first snapshot for every partner of every partnership found and the parents of each seeded child, and `MutationRunner.loadForSeed` loads again over the merged seed; each such person's closure then brings their partnerships and the twins. `update_union`, `end_union`, `destroy_union` and `add_parent` opt in. A kind that does not opt in, or whose first snapshot has nobody new to follow, keeps one load. The cost is one more scoped load (three to five batches, a few dozen rows) for those writes. The equivalence harness applies the same composition (`selectScopeWithFollowUp`), and a test keeps each seed without the flag failing so the follow-up is shown to matter. Undo has its own two-load path (`loadRowsForUndo`), which also follows dependents, and is left as it is. A partnership in the snapshot that has no partners falls back to the whole tree (`FOLLOW_UP_WHOLE`) for every seed, opted in or not, whether it was seeded or reached as the subject of a fact, a link, a note, a task or a file (`partnerless.test.ts` sweeps every scoped kind and intent; `add_sibling` opts into the family follow-up so the partnership its link names is loaded to be seen): the whole tree's privacy mask hides such a partnership, its facts and its place in a link from a restricted viewer only when it holds a private person, and a scoped snapshot of it holds nobody. Rare, so the cost is accepted.
  - **The evidence follow-up.** What a restricted viewer sees of a note, a task, a source or a repository depends on records no seed can name: an attachment, note or task id does not say what the note sits on or what the task is about, and a repository is visible only through the sources that link it (ADR-028, ADR-029). A seed with `shouldFollowEvidence` is loaded, and `followUpSeed` reads the first snapshot for the records its attachments, notes, tasks, repositories and links are anchored on: the source an attachment sits on or a task is about (a seeded source brings every citation, which decides its visibility), the repository an attachment sits on (a seeded repository brings its links), the sources a seeded repository or link names, and the note a task is about (a seeded note brings every use). It reads only what the seed anchors, never everything loaded: a person cited by a popular source would otherwise seed that source and pull a share of the tree. The rule repeats on the merged seed, up to three loads (a note on a source or a repository edit takes two; a note on a repository takes three); a chain still going after that falls back to the whole tree, which only a task about a note used on a repository reaches. The family rule runs after the first load only, or it would walk the whole connected family. A source-repository link is a seed entry point of its own (`sourceRepositories`): it resolves to its source and repository and pulls neither, with its own loader proof. `update_repository`, `delete_repository`, `link_repository`, `update_source_repository`, `unlink_repository`, `update_note`, `remove_note`, `share_note`, `attach_note`, `update_shared_note`, `delete_shared_note`, `update_task` and `delete_task` opt in, as do the subject-based kinds (`add_citation`, `add_note`, `reorder_*`, `create_task`) for the partnerless-partnership fallback; a note on a repository and a task about a note, previously whole-tree, are scoped. `share_note` also reads the whole `notes` table, as `create_note` does, for the new note's XREF. The same test keeps each seed without the flag failing.
  - **Order is preserved.** Each table in the scoped snapshot keeps `rowid` order, because chronology tie-breaks and "first birth" depend on it. The loader builds on `GraphWindowRepository`'s ranked, batched reads.
  - **Proof is equality, in two layers.** (a) The D1 loader returns exactly what `selectScope(wholeRows, seed)` selects: the same images in the same order, on the fixture corpora and random seeds. (b) For every enabled kind, planning over the selection equals planning over the whole tree: the ops, the summary, the `describeOps` labels, the preview (`describeImpact`, carried citations and notes), and any thrown error's class and message. It is checked for an unrestricted viewer, a restricted viewer and a contributor who created the person, with commands that name missing and private ids, and a fresh deterministic clock on each side. A kind is enabled only when (b) passes.
  - **What stays whole-tree, on purpose:** the data-quality report; `standardise_dates` and its remaining count; `rewrite_place`; `merge_people`, `merge_unions`, `merge_sources`, `merge_notes` and their reviews; the test helper `testing/graph.ts`. Each reads the tree by nature or is rare.
  - **Measured, not assumed.** Rows returned, `db.batch` round trips and wall time are recorded for a fact edit, a name edit, a person update, adding a partner and an undo, on a Simpsons-sized tree and on the 5,324-person corpus, before and after. A scoped load is two to four sequential batches where the whole load is one parallel round, so a small tree may get slightly slower; the numbers go in query-plans.md and decide whether that is accepted.
- **Rejected alternatives:** a hand-written loader per command kind (57 kinds, each a chance to miss a cascade); caching the whole snapshot between requests (stale under concurrent edits, and the memory cost stays); moving planning into SQL (loses the pure planner that makes previews exact).
- **Consequences:** a command kind added later loads the whole tree until someone writes its seed and the equality test passes. A planner change that starts reading outside its seed's closure fails (b) rather than misbehaving in production.


## ADR-056: Drag-to-relate is removed from the flat view
- **Status:** built on `claude/flat-tree-drag-drop-vawn5f` on 2026-10-16 and deployed. No migration.
- **Context:** pressing a card and letting go over another opened the relationship dialog with the two people already chosen. Nothing showed while you dragged: the card stayed where it was, nothing marked the drop target, and because a press on a card does not pan the canvas, the drag looked like it did nothing until the dialog appeared. ## ADR-057: A tree can be served on its own subdomain (extends ADR-041 and ADR-045)
- **Status:** phase 1 (the app side) built on `claude/subdomain-cloudflare-oauth-9bfcc6` on 2026-10-17 and deployed. Migration 0033. Phase 2, the Cloudflare side, built on 2026-10-17 as `./setup subdomains` (`tools/setup/steps/subdomains.ts`) and complete: it was run on a real account (`epochgenealogy.app`, 2026-10-17). It creates the wildcard DNS record, the exclusion routes and the Access destination, and writes the Worker route and the vars through `DeployValues`. Its follow-ups are in [backlog.md](./backlog.md). See [proposal-tree-subdomains.md](./proposal-tree-subdomains.md).
- **Context:** the owner wants `dacks.epochgenealogy.app` to show only the tree at `/trees/dacks`, without anyone creating a Cloudflare API token. A wildcard DNS record and Worker route, set up once, send every subdomain to the Worker, so turning a tree's subdomain on needs no Cloudflare call at runtime and the Worker holds no Cloudflare credential.
- **Decision:**
  - **Opt-in per tree:** `trees.is_on_subdomain`, default off. It is set from the rename dialog, by those who may change the address (`tree:update_settings`, or the install owner), through `PATCH /api/trees/[id]`.
  - **The subdomain is the slug,** so a tree without one cannot turn it on, and giving the slug up turns it off. Every valid slug is already a valid DNS label. Changing the slug moves the subdomain.
  - **Setup owns the Cloudflare side** (`./setup subdomains`):
    - The wildcard route and the three vars are carried in `DeployValues`, so every setup run and every Workers Builds deploy writes them. `wrangler deploy` owns the route.
    - The DNS record is marked with `epoch:<installId>` in its comment, because DNS records carry no account tags and their own tags need a paid plan.
    - Exclusion routes have no Worker, so they are made through the API: wrangler's routes always attach the deployed Worker. Only the routes this install made are deleted.
    - The Access application gains `*.<zone>/login` as a second destination and keeps its AUD. The `access` step sends that destination too, because an update replaces the application.
  - **Install settings, all Worker vars:**
    - `EPOCH_TREE_HOST_ZONE`: unset turns the feature off.
    - `EPOCH_APP_HOST`: defaults to the zone.
    - `EPOCH_RESERVED_SUBDOMAINS`: comma-separated, added to the built-in `www`, `api`, `mail`, `login` and `welcome`. An app host beside the trees (`epoch.<zone>`) reserves its own label.
  - **Turning the flag on is checked:** it is refused for a reserved label, and where the install serves no subdomains. A rename of a tree that already has the flag is not refused if the setting is later dropped.
  - **The host is resolved first in the hook,** before anyone is identified, so an anonymous `/` on the public tree's subdomain opens the tree, not the splash.
    - The zone, the app host and any host outside the zone are served as the app host. That keeps a `workers.dev` address working during a move.
    - One label under the zone is looked up (`slug = ? AND is_on_subdomain = 1`, one read, not cached).
    - Anything else under the zone gets a bare 404. That covers deeper names, labels no slug can be, reserved labels (which would otherwise reach the Worker through the wildcard as a second copy of the app), and labels that name no tree with the flag on.
  - **Pinning is about what is shown, not who may see it.** The same person has the same rights on every host. On a tree host:
    - `/` redirects to `/trees/<slug>`.
    - Another tree's pages and `/api/trees/<other>` get a 404.
    - The Files and Trees pages, `/settings` and `/manage` redirect to the app host.
    - `/welcome`, `/login` and every other API path are served as usual, and their own checks apply.
  - **Links that leave the tree are absolute app-host URLs with a full page load:** the Epoch mark, the tree switcher, a new or imported tree, the Files and Trees menu items, the error page and the welcome page's public-tree link. The root layout carries `hostTree` (id, slug, app origin) and `subdomainZone` for them. Renaming or turning the flag off on the tree host moves the page to wherever the tree now lives.
  - **Local trial:** `*.localhost` resolves to loopback, so `EPOCH_TREE_HOST_ZONE=localhost` serves `dacks.localhost:5173`. `isLocalHostname` accepts the `.localhost` suffix exactly, so the dev bypass works there.
- **Given up:**
  - **Short addresses.** Pages on a tree host keep the `/trees/<slug>/…` form. The proposal's `reroute` design would have needed every path check in the hook (`publicReadAccess`, the `next` of the sign-in redirect, the canonical redirect) to translate paths, because `event.url` keeps the original path. It would also have collided with `/settings`, which is both the user's page and the tree's. This is a follow-up.
  - **No redirect from `/trees/<slug>` on the app host to the subdomain.** Both stay served.
  - **The name is not private.** Turning the flag on makes the tree's name visible as a hostname: for a private tree, an anonymous visitor gets the sign-in redirect where an unknown label gets a 404. Only "unknown label" and "flag off" are indistinguishable. The dialog says so.
- **Rejected alternatives:**
  - A runtime Cloudflare credential, from an OAuth client per install or a token minted by setup, to create a DNS record per tree. It is more code and a credential that can change DNS, for a single-owner install.
  - A subdomain column separate from the slug. That is a second unique name to keep in step.
- **Consequences:**
  - Deploy order: migrate, then code.
  - With the var unset nothing changes.
  - Each tree host keeps its own Access cookie and browser storage.

## ADR-058: The person page leads with the person's life (amends ADR-053)
- **Status:** built on `claude/person-page-life-events-d11a0a` and deployed. No migration.
- **Context:** the page opened on a long Family list, and the facts sat below it as one white panel per kind, each a single fact in a real tree. A marriage, the event most researchers look for after birth and death, was not among them: it belongs to the partnership and showed only behind "Dates & status". The right column spent five cards on empty states.
- **Decision:**
  - **A Life section first.** The page shows the person's events and their partnerships' events (engagement, marriage, separation, divorce, annulment) as one list, oldest first, undated last. A partnership event names the partner and links to the partnership, which owns its evidence and editing. The merge is a pure function (`life-timeline.ts`) over the DTO the page already loads.
  - **Every fact is shown.** Nothing sits behind "Show N earlier" on the page, so a conflict is always in place beside the fact it disagrees with. A fact's citations, notes and controls share one line.
  - **Attributes apart.** Occupation, residence, education and the other attributes are not events. They follow under "Also recorded", without a "Date unknown" on each. A fact whose kind is not known to be an attribute is placed as an event, so none can drop out of view.
  - **The rest of the record in one card.** Notes, Names, Photos and documents, Tasks, Privacy and History share one section card in the right column, divided by rules, instead of a card each. An empty media list is one line beside Upload.
  - **The drawer keeps ADR-053's order and grouped facts,** newest shown: in a narrow panel, the latest of each kind is the quicker answer. The shared pieces it renders do change with the page: an empty media or notes list is one line beside its action, and the separators and "(approximate)" keep their spaces.
- **Rejected alternatives:** a timeline above the grouped facts (every fact said twice); keeping the page's sections in the drawer's order (the life is what a reader came for, and it was below the fold); including children's births (a child's summary carries its birth as text without a sort key, so they could not be placed without parsing every one in the browser or changing the DTO).
- **Consequences:** the page and drawer no longer share a section order, so ADR-053's "one section order" holds for the drawer only. A move control in the timeline swaps a fact with a neighbour of the same date that is also an event, or also an attribute, and up means earlier. Children's births in the timeline would need a sortable birth on `PersonSummaryDto`.

## ADR-059: The person page opens on the newest of each attribute (amends ADR-058)
- **Status:** built on `claude/person-page-full-layout-227778` and deployed. No migration.
- **Context:** ADR-058 listed every attribute under "Also recorded", in file order, below the Life timeline. A real record carries ten residences, three schools and two occupations, so the list was long, interleaved by kind, and below the fold, while what a reader wants first is where the person lives, what they studied and what they do.
- **Decision:**
  - **An "At a glance" section leads the left column,** above Life and Family. It shows one row per kind of attribute: the kind and its count in the heading column, its newest fact in the details. The rest sit behind "Show N earlier", newest to oldest, inline in the same row. It is not drawn for a person with no attributes.
  - **The drawer's grouping is shared, not copied.** `fact-groups.ts` holds the group key, label, newest-first order and group build (ADR-053) that both the drawer's panels and the page's rows use.
  - **A conflict still never folds.** A group with a disagreeing or repeated fact shows every member, as in the drawer.
  - **Life holds events only.** Events and partnership events stay oldest first with every one shown, so dated history is never behind a button. "Add fact" stays in Life, the one place that adds a fact.
  - **"Newest" is the newest recorded, never "current".** The heading says only the kind; nothing claims a person still lives or works there.
- **Rejected alternatives:** grouping repeated events such as census in Life (it would break the date order the timeline exists for); a "lives at / works as" line in the header (newest by start date is not current, above all for the dead or for a long-running period that started earlier); keeping "Also recorded" flat beneath Life.
- **Consequences:** ADR-058's "every fact is shown" now holds for events only. A move control in At a glance swaps with a same-date neighbour of the same kind, and up means newer, as in the drawer. A date written `FROM 1980` with no `TO` sorts from 1980 once saved; rows stored before the parser read open-ended periods keep a null sort key until re-derived (backlog).

## ADR-060: Every `/api` error is `{ error, code, details? }`
- **Status:** built on `claude/api-error-envelope-821bdc` and deployed. No migration.
- **Context:** `DomainError` already rendered as `{ error, code, details }`, but about sixteen routes and the handler factories answered a missing sign-in, route parameter, form field or binding with a bare `{ error }`, so a client could not branch on `code` for those.
- **Decision:**
  - **One path.** A failure is thrown as a `DomainError` (`ValidationError`, `UnauthenticatedError`) and rendered by `errorResponse`; no route builds its own error body. The unexpected-error fallback carries `INTERNAL_ERROR`.
  - **`BindingUnavailableError`** is the 500 for a missing Cloudflare binding. Its message is fixed and the binding's name goes to the log only, since it says how the install is wired.
  - **`ApiErrorBody`** in `api-contracts.ts` is the shape the client reads.
  - **A test holds it:** `src/routes/api/error-envelope.test.ts` fails if a route or the handler writes a `json({ error … })` body without `code`.
- **Consequences:** status codes and messages are unchanged except the binding errors, which no longer name the binding.

## ADR-061: A source can own files, visible exactly when the source is (extends ADR-028 and ADR-050)

- **Status:** built on `claude/source-files-dac2d6` on 2026-10-18 and deployed. No migration.
- **Context:** the owner wants sources managed on their own, with their scans attached, and reached from More > Research. Files hung off a person or a partnership only (ADR-050), and ADR-028 left the `OBJE` in a citation retained.
- **Decision:**
  - **The owner is still one id.** `media_items.entity_id` may now name a source. It has no foreign key and no owner-kind column, and ids are UUIDs, so the repository tells the kinds apart by lookup in the tree (`recordKindsOf`, `ownerOf`), as it already did for a person and a partnership. This needs no migration, so nothing is expand-and-contract.
  - **Visibility.** A file on a source is visible exactly when the source is: a restricted viewer sees the source if it supports a citation they can see, or they made it (ADR-028). `canReadRow` takes the file's owner as nothing, people or a source. The SQL is `visibleSourcesAmong` (the `andSourceVisible` predicate over a chunked id list), used by `requireRead` and by the Files listing. The row filter is `maskRows`, which now drops a file on a source the viewer cannot see, also when nobody is private. `source-files.test.ts` holds the list, the serve check and `maskRows` to one answer for a cited source, an uncited one, one the viewer made, and a tree with no private person.
  - **Writes go through the mutation runner.** `attach_media` accepts a source (its write scope seeds the source, which also loads that source's files). Detach, rename and undo are unchanged. Upload names the source as `entityId`, after `requireUpload` finds it in the tree. The row is inserted by the upload route as it is for a person's file.
  - **Delete and merge.** Deleting a source detaches its files, as deleting a person does (the bytes stay, undo hangs them back). A source merge moves the merged sources' files to the survivor in the same change, and a preview says how many files a delete keeps. `delete_source` already loaded a scoped snapshot, so the loader reads the files of a seeded source (`write-scope` and the scoped row loader agree).
  - **Listing.** `/api/files` takes `entityId` and `owner=detached`, filtered in SQL, so the source page and the attach picker go through the same visibility rule and cursor as the Files manager instead of filtering one page on the client. The sources list shows a file count from one grouped count over the page's ids, with no privacy join, since a listed source has all of its files visible.
  - **Navigation.** Sources is the first entry of More > Research, and "More: Sources" shows on `/sources` and below it.
  - **`partnerIds` is tree-scoped.** It joins `unions` on the tree, closing the gap noted for ADR-052.
  - **GEDCOM.** An import creates no file (a `FILE` is a path, never bytes), and an export writes no attached file. The `OBJE` under a `SOUR` therefore stays a retained line, written once in 5.5.1 and 7.0, and a file attached to a source in Epoch adds nothing to an export (`evidence-roundtrip.test.ts`). Linking the two needs a file to resolve to, so it waits for media records.
- **Rejected alternatives:** a `media_item_owners` table or an owner-kind column (a migration for no extra correctness while ids are unique); filtering the Files page on the client for a source's files (a short page would miss rows); a privacy join in the sources count (redundant, and costly for a restricted viewer); linking the `OBJE` under a `SOUR` on import to a file Epoch does not hold (it would invent a file).
- **Consequences:** the Files manager lists a source's file, detaches it, and offers a source beside a person in its upload, attach and move dialogs (`FileOwnerPicker`, using the shared `SourcePicker`; the source choice is shown to roles that pass `canChangeEvidence`). `MediaService.move` accepts a person or a source as the destination, still not a partnership. The unmodelled `OBJE` is in [backlog.md](./backlog.md).

## ADR-062: A tree can have sub-trees rooted at a person
- **Status:** built on `claude/tree-subtrees-exploration-dcc030` on 2026-10-18 and deployed. Migration 0034 adds the `subtree` table (expand only). The design is in [proposal-subtrees.md](./proposal-subtrees.md).
- **Context:** a tree of several hundred people is several family lines in one file. A reader who wants one family line should not have to start from the whole tree. The owner decided three things: a sub-tree is a *lens* (a root plus scoped lists), not an access boundary; it is a part of a tree, owned by the tree; and a manager makes it from a person. The lens had to be reachable from a link, so it needed an address of its own.
- **Decision:**
  - **Membership rule.** A sub-tree rooted at R has the members: R; every child of a member through `parent_child` of any type (biological, adoptive, foster, guardian, unknown) whose status is not `disputed`; and every partner of anyone in those two sets. Partners' parents and kin are not members. The recursion uses `UNION`, so a cycle in bad data ends. A disputed link does not pull a family in, and an adopted child does belong to the line.
  - **Computed, not stored.** Membership is a SQL predicate, `inSubtree(alias, treeId, rootPersonId)`, in the style of `visibility.ts`. It is ANDed with `tree_id` and the visibility predicate, so totals, `hasMore`, page fill, surname counts and ordering are computed in scope, never by filtering a finished page. A stored member table would be rebuilt by every `parent_child`, `union_partner` and person mutation. The plan test (`list-plans`) holds the predicate to `idx_parent_child_parent` and the union-partner indexes, and two planner nudges stay in the code: a `cross join` fixes the join order, and a unary plus on `tree_id` keeps `idx_parent_child_tree` from winning. A stored table is the answer if measured plans fail on a tree of tens of thousands of people.
  - **The root, not the sub-tree id.** `inSubtree` takes the root person's id, so the predicate needs no join to the `subtree` row. `isMemberOf`, `andInLens` and `andUnionInLens` are the forms the scoped reads use.
  - **Addressing: `tree~sub`, not `reroute`.** The sub-tree rides inside the tree's path segment: `/trees/dacks~bouvier-line/people`, and `/api/trees/dacks~bouvier-line/…` for the API. `~` cannot appear in a slug or a UUID, so the separator is unambiguous, and `encodeURIComponent` leaves it alone. Every positional check in `hooks.server.ts` and `tree-host.ts` keeps working. ADR-057 rejected `reroute` because `event.url` keeps the original path and those checks would all need translating; a separate `/~sub/` segment would break the same checks. `splitTreeSegment(segment)` in `shared/tree-slug.ts` is the only code that knows the separator, and `subtreePath` builds links that keep it. `treeHandler` resolves the sub-tree and passes it to the handler next to `treeId`, and only scoped endpoints read it.
  - **What the lens scopes.** Scoped: the chart's default focus (the root) and whole-tree mode, the people, surname, union and place lists, search and the person finder, the header counts (people only), and the "is in this sub-tree" note on a person page. Not scoped: sources, repositories, notes, files, tasks, quality, privacy, members, settings, every write, the change log and undo, and GEDCOM export, which always exports the whole tree. A place page with nothing in scope under a lens is a 404. A person outside the lens is still shown, with a note and a link to the whole tree, and the chart can be navigated past the lens's edge. The lens chooses where a reader starts and what lists show; it hides no relatives.
  - **Privacy.** A sub-tree's name can reveal a living root, so the list is filtered per viewer: a sub-tree whose root the viewer may not see is left out of the list, and its address returns 404 with no hint that it exists. A shared address works for a public visitor when the root is visible to them, and the sub-tree list endpoint is open to public visitors on the same rule. The membership rule is not weakened by the lens: a restricted viewer still sees only people the visibility predicate allows.
  - **Permission.** `tree:manage_subtrees`, minimum role `manager` (ADR-062 adds it to `authorization.ts`). Every endpoint denies by default. The "Make sub-tree from here" action on a person page and the Trees page section use it.
  - **Writes go through the mutation runner.** A sub-tree is a logged, undoable row (`subtree-ops.ts`, the change log, `undo-scope.ts`), so creating, renaming, changing a root, and deleting are undoable like any other edit. Each has a `version` for optimistic concurrency.
  - **Lifecycle.** `root_person_id` has no foreign key. Person delete is a hard delete with undo, and a cascade or set-null would change the sub-tree row outside the logged operations, so an undo would not bring it back. A root that is gone reads as "anchor missing" on the Trees page, and opening the sub-tree shows the whole tree with a notice. A person merge repoints `root_person_id` from the merged-away person to the survivor in the same change (`person-merge.ts`). Deleting a tree cascades to its sub-trees.
  - **GEDCOM is not exported.** A sub-tree is a view over the tree, not genealogy, so it is not written to GEDCOM, as tasks are not. An `_EPOCH_SUBTREE` extension record is a follow-up ([backlog.md](./backlog.md)).
- **Rejected alternatives:**
  - *A stored member table.* Every parent-link, partnership and person change would rebuild it. A recursive read over indexed edges costs one extra lookup per member, which the plan test holds in check.
  - *`reroute` through `event.url` (ADR-057).* Every positional check would need translating.
  - *A separate `/~sub/` segment.* It breaks the same checks and gives a second tree-like address to keep canonical.
  - *An access boundary.* A lens that hid people would need a rule for every relative the chart draws, and the owner wanted the rest of the tree one click away and still editable.
- **Given up:**
  - The switcher lists only the current tree's sub-trees, because they arrive with its summary. Listing every tree's sub-trees would make the tree-list endpoint resolve visibility for every tree.
  - No stored member table, so a scoped read costs a recursive lookup, and a very large tree may need one.
  - No GEDCOM export of sub-trees, so a sub-tree does not survive a trip through another program.
  - Moving a sub-tree up or down is two PATCHes, and it has no Undo. A single undoable move is a follow-up ([backlog.md](./backlog.md)).
  - Sub-trees are not in the e2e suite yet for a tree host, a public visitor, or the remembered-focus order ([backlog.md](./backlog.md)).

## ADR-063: Tree subdomains can be turned off, and D1 keeps what setup made on the zone (extends ADR-057)

- **Status:** built on `feat/setup-subdomains-followups` on 2026-10-19 and deployed. **Migration 0035 adds `install_meta.subdomains`** (nullable text, expand only). `npm run deploy` migrates before it deploys, and setup works without the column until then.
- **Context:** `./setup subdomains` had no way back short of `./setup teardown`, which removes the whole install. Its exclusion routes carry no marker, because the Worker routes API has nothing like a DNS record's comment, so a clone with no manifest kept any it found as `referenced` and never deleted them. Turning the subdomains off would make that worse: the zone leaves the deploy config, which was the only thing a fresh clone read.
- **Decision:**
  - **`./setup subdomains --off`** takes the wildcard route and the tree vars out of `wrangler.deploy.jsonc` and the Workers Builds values first, so no deploy started part-way puts the route back. It then deletes the live wildcard route and removes the `*.<zone>/login` Access destination. The DNS record and the exclusion routes stay, and the settings stay in the manifest with `isActive: false`, so `./setup subdomains` turns trees back on without making them again. It shows a plan, asks before applying, and takes `--plan`.
  - **`--off --remove`** also deletes the record and this install's own exclusion routes, as teardown would, and clears the settings. `--remove` without `--off`, and `--off` with `--zone` or `--reserve`, are usage errors.
  - **D1 keeps the record.** `install_meta.subdomains` holds the zone, the DNS record id, the ids of the exclusion routes this install made (never one it found and kept), and whether the subdomains are on, as JSON. Setup writes it when an apply or `--off` finishes, then reads it back. Values are validated (32-hex ids, a zone name) before they are quoted into the SQL, since `cf d1 query` takes no bind parameters. The app never reads it.
  - **Recovery.** `recoverSubdomainSettings` rebuilds the settings for a manifest that has none, from the deploy config's zone and from D1, read with the manifest's D1 id or, before reconcile has found it, the one in `wrangler.deploy.jsonc` (quietly, since that database may not exist yet). A recorded route counts only while it still exists with no Worker, and its pattern comes from the live route. `./setup` seeds the manifest with it, and teardown uses it when the manifest has no settings, so teardown from a fresh clone removes what this install made, even with the subdomains off.
  - **Before the migration.** A missing column reads as "nothing recorded" and setup relies on the manifest alone. Writing warns and names the migration; it never fails an apply whose changes on the zone are already made.
  - **Teardown items carry their zone id,** so removing a record or route no longer needs the manifest's settings.
  - **`doctor` reads an inactive install as off or part-way,** a warning, and names `./setup subdomains` as the way back on. With no record id (a clone seeded from the config alone) it finds the record by its marker, as teardown does.
- **Rejected alternatives:** a marker in the route pattern (a route matches requests by its pattern, so it cannot carry one); claiming any Worker-less route on a captured host (it could delete a route made by hand for the same host); keeping the record in the manifest alone (a fresh clone has none, and after `--off` the config says nothing either).
- **Consequences:** an install set up before this has nothing in `install_meta.subdomains` until `./setup subdomains` runs once after migration 0035 is deployed; that re-run changes only the Access application and writes the record. A write that matches no `install_meta` row (an adopted install whose row names another id) warns, since the UPDATE itself succeeds. The deployed Worker keeps its tree vars after `--off` until the next deploy, which the hand-off says. A route recorded in D1 and later given a Worker by hand is no longer claimed. The new spike checks for ADR-057's API shapes passed against the live account on 2026-10-19, and `./setup subdomains` recorded its zone, record and routes in D1 the same day.


## ADR-064: Under Vitest the adapter's platform proxy keeps no state on disk, and one full suite runs at a time

- **Status:** built on `claude/elegant-wing-38ff6e` on 2026-10-19.
- **Context:** full `npx vitest run`s failed a different set of server tests each time, and every failing file passed alone. Three lone full runs before this change failed no server tests, so the per-test failures were not reproduced. What was found:
  - **Shared on-disk state (shown).** Vitest starts a Vite server for each of its two projects, and `@sveltejs/adapter-cloudflare` boots a `getPlatformProxy` in each server's `configureServer` hook with default persistence. Every run's proxies, and `npm run dev`, open the same `.wrangler/state/v3/*/metadata.sqlite` in the checkout. Two full runs at once in one checkout crashed one of them at startup with `SQLITE_BUSY (SQLITE_BUSY_RECOVERY)`. Two single-file runs at once crashed 6 times in 30 tries. The tests' own D1s were never involved: `createTestDatabase` passes `persist: false`, and miniflare gives each of those a private temp directory.
  - **Memory (inferred).** One full run peaks at 8–9 workerds and 4.2–4.7 GB RSS on the 10-core, 16 GB host, about 3 GB of it in Vitest's node processes. The timeouts and ECONNRESETs in random files came when several agent sessions ran the suite at once, and a later five-way run took down the login session, which looked like running out of memory. Memory pressure from concurrent suites is the likely cause of the scattered failures, but it was not reproduced in isolation.
- **Decision:** `vite.config.ts` passes `platformProxy: { persist: false }` to the adapter when `VITEST` is set, so those proxies keep their state in memory. With it, the two single-file runs at once crashed 0 times in 30, and a run creates no `.wrangler/` directory. Run one full suite at a time on this host. The per-file workerd from `getPlatformProxy` stays, and so does `maxWorkers: '50%'`: a lone run passed three times in a row.
- **Rejected alternatives:** retries, which would hide the startup crash rather than prevent it; higher timeouts, since the plan tests already allow 120–600 s and no lone run timed out; one proxy per worker shared across files, which would save workerd memory but give up each file's fresh database, while most of the peak is in Vitest's own processes anyway.
- **Consequences:** two idle in-memory workerds still start with each run, since the adapter's hook cannot be turned off from the config. Concurrent full runs, in one checkout or across worktrees, can still exhaust the host's memory; nothing here guards against that.
