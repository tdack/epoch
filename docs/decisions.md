# Epoch Architecture Decisions (Phase 0)

## ADR-001: Identity, Cloudflare Access and User Management
- **Context:** Epoch is a private, single-owner family-tree application with invited collaborators behind Cloudflare Access.
- **Decision:**
  - Authenticated identity is verified via Cloudflare Access JWT assertions (`Cf-Access-Jwt-Assertion` request header or `CF_Authorization` cookie).
  - Validation checks JWT issuer (Cloudflare team domain), audience tag (`AUD`), and rotating JWKS from `https://<team-domain>.cloudflareaccess.com/cdn-cgi/access/certs`.
  - For local development and automated testing environments, a configurable mock identity or local public key verifier is supported when explicit development flags are provided, while denying anonymous access by default.
  - The local `users` record is keyed and upserted by the stable Access subject claim (`sub`), treating `email` as mutable profile metadata.
  - Tree-level access is controlled via `tree_memberships` supporting roles: `owner`, `manager`, `editor`, `contributor`, `viewer`. Every server endpoint and action denies access by default.

## ADR-002: Genealogy Identifiers vs GEDCOM XREFs
- **Context:** GEDCOM files use XREF tokens (such as `@I1@`, `@F1@`) that are tree- or file-scoped, frequently collide between different imports, and can be unstable across re-exports.
- **Decision:**
  - All Epoch internal entities (persons/individuals, unions/families, events, citations, media) use internally generated UUIDs as primary keys.
  - GEDCOM XREFs are preserved as tree-scoped import/export aliases (`xref_id`) rather than internal primary keys.
  - This allows cross-tree references, multi-source merging, and prevents XREF collision corruption while ensuring lossless round-trip export by re-attaching or re-mapping XREFs.

## ADR-003: Lossless GEDCOM Preservation
- **Context:** Epoch aims for full round-trip fidelity with supported structures and lossless retention of unsupported GEDCOM structures.
- **Decision:**
  - Supported structures map to normalized relational tables (persons, partnerships, parent-child links, events).
  - Unsupported tags, custom vendor extensions (`_ATTR`, etc.), and unhandled sub-trees are preserved in an unparsed/syntax-preservation payload (JSON or raw records linked to entity IDs) so they are preserved without silent loss upon export.

## ADR-004: Historical Date Representation
- **Context:** Genealogy dates are frequently incomplete (e.g. `1910`, `MAY 1920`), approximate (`ABT 1845`, `EST 1850`, `CAL 1900`), ranged (`BET 1860 AND 1865`, `FROM 1901 TO 1905`), or conflicting. Converting them into arbitrary exact dates (like `1910-01-01`) destroys historical accuracy.
- **Decision:**
  - Dates are stored with both `date_raw` (verbatim string from historical record or user entry) and structured date metadata:
    - Date type/modifier: `EXACT`, `ABOUT`, `ESTIMATED`, `CALCULATED`, `BEFORE`, `AFTER`, `BETWEEN`, `FROM_TO`.
    - Earliest sort key (`date_sort_start`) and latest sort key (`date_sort_end`) in `YYYY-MM-DD` format for sorting, indexing, and chronological filtering.
  - Incomplete dates (year only or month/year) preserve their granularity rather than claiming precision that does not exist.

## ADR-005: Concurrency and Versioning
- **Context:** Multiple invited collaborators may view or edit tree records simultaneously.
- **Decision:**
  - Optimistic concurrency control is implemented using a numeric `version` column and `updated_at` on mutable root entities (`trees`, `individuals`, `families`/`unions`, `events`).
  - Domain mutation commands verify that the client's provided version matches the stored version before writing. A mismatch returns a typed `ConcurrencyConflictError` (HTTP 409).
  - D1 atomic transactions (or batch operations) are used for multi-row mutation commands. Durable Objects are deferred until real-time multi-cursor collaboration demonstrates a clear need.

## ADR-006: Layered Architecture and Clean Boundaries
- **Context:** The prototype embedded database queries and runtime schema initialization directly inside SvelteKit route handlers and single-page components.
- **Decision:**
  - The application is decoupled into distinct architectural layers:
    1. **Domain Layer:** Pure domain models, command interfaces, typed error definitions (`DomainError`, `NotFoundError`, `UnauthorizedError`, `ConcurrencyConflictError`, `ValidationError`), and business invariant checks.
    2. **Persistence/Repository Layer:** D1 implementations implementing repository interfaces with versioning and audit trails.
    3. **Query/Service Layer:** Read and write services that coordinate domain commands, enforce tree authorization, and return DTOs.
    4. **Transport/UI Layer:** SvelteKit server hooks, actions, API endpoints, and component views. Route handlers only parse inputs, invoke application services, and format responses. Direct database operations inside routes are prohibited.

## ADR-007: Persisted, append-only change log and undo (Phase 2, S2)
- **Context:** Undo used to be an in-memory array on `RelationshipService`, and a new service is constructed per request, so it could never work. Destructive removals, person edits and union edits wrote nothing at all. Phase 4 needs an audit log and per-record history, and should build on the same rows rather than replace them.
- **Decision:**
  - Two tables, added by an expand-only migration: `change_log` (one row per user-visible change) and `change_log_records` (the records each change wrote). Neither is read by existing code, so the deploy order is migrate, then code. `schema-init.ts` is not extended; it is S4 debt.
  - **Append-only.** Rows are inserted and never updated. An undo is a new row whose `reverts_change_id` names the change it reverses; "already undone" is derived from that, and a partial unique index on `reverts_change_id` means two concurrent undos cannot both succeed.
  - **Ordering by `seq`** (autoincrement), not by timestamp, which collides within a millisecond. `id` is a UUID generated before the write so the batch can reference it without reading `seq` back.
  - **Row operations are the unit.** Every mutation is first planned in memory as a list of row operations (`table`, `id`, `before` image or null, `after` image or null). The inverse is the same list reversed with before and after swapped, so any change is undoable, including deleting a person or a union with its links, partners and events. The inverse is stored in `inverse_json`; the field-level before/after summary shown to people is in `changes_json`. This deliberately replaces per-command `inverseOf`, which lost context (re-creating a removed parent link dropped its union) and had no answer for `destroy_union` or deleting a person.
  - **Atomic.** The row operations, version guards and log rows are applied in one `db.batch`, as ADR-005 requires, so a change is either fully applied and logged or not applied. A guard is an `INSERT` into `change_log` of NULL for a NOT NULL column that runs only when the expected row version is absent; the constraint error aborts the whole batch and is reported as `ConcurrencyConflictError`.
  - **Undo rules.** Undo applies to the requesting user's most recent undoable change in that tree that has not been undone. It is refused, with a message naming what changed, when a later change (by anyone, including an earlier undo) wrote any of the same records, and when the records no longer look the way the change left them (for example an import touched them). Undo rows are not themselves undoable; there is no redo in Phase 2.
  - **Affected records** are the rows a change wrote (people, names, unions, partners, parent-child links, events, media links). A person edit does not lock the person's relationships against undo, and a relationship change does not lock the people.
  - **Tree deletion cascades** to its log (`change_log.tree_id` has `ON DELETE CASCADE`). Before/after images contain personal data, and deleting a tree must erase it. The deletion itself is therefore not in the log; it is only in the structured request log. Phase 4 may add an account-level audit stream if that is needed.
  - **Not covered:** GEDCOM import and merge write no log rows in Phase 2; they replace or extend whole trees and are not undoable. `actor_id` has no foreign key so the log survives a removed user.
- **Consequences:** Phase 4's audit view reads `change_log` and `change_log_records` directly and adds visibility rules; moderation (pending changes) can store proposed row operations in the same shape. Payloads grow with the size of a change, which is small except for deleting a very large union or person.

## ADR-008: Union merge and XREF aliases (Phase 2, S3)
- **Context:** A dirty GEDCOM carries several `FAM` records for one family. Every union's XREF is its id (`<treeId>:@F1@`), so deleting a merged union would delete the only record of that XREF, and a NOTE or CHAN preserved under it would no longer belong to anything on export.
- **Decision:**
  - **Aliases are a nullable JSON column, `unions.xref_aliases`, on the surviving union**, added by an expand-only migration (`ADD COLUMN`; nothing reads it until this deploy). The alternative, an `union_aliases` table, would have to join `RECORD_TABLES`, the loader, the labeller and the impact grouping to be undoable. A column rides the survivor's ordinary update op, so undo restores it with no new machinery.
  - **Aliases carry transitively.** Merging a union that already has aliases moves those aliases to the survivor as well as adding the merged union's own XREF. A union whose id is not an imported XREF (created in the editor) adds no alias, because no other record ever named it.
  - **Export emits the survivor once**, under its own XREF, and re-attaches structures preserved under any alias to it. Each alias is written on the survivor as `1 REFN <xref>` with `2 TYPE epoch-merged-family`; the importer reads those back into `xref_aliases`, so a re-import recovers them. Alias `FAM` records are deliberately not re-emitted: the merge dissolved which child belonged to which copy, so a regenerated copy would be a guess, and two `FAM` records for one family is the exact defect being fixed.
  - **`merge_unions` is one command through `MutationRunner`.** It deletes the merged unions and their partner rows, moves child links and events onto the survivor, drops events identical to one the survivor already has, and updates the survivor's aliases, status and version, so it is logged and undone like any other change.
  - **Conflicts are never resolved silently.** Two unions conflict when they carry the same event type with different date, place or description, or when their statuses differ. An event type or status present on only one side is not a conflict; merging fills the gap. The command refuses with a typed error listing every conflict unless the request names, for each conflicting event type and for the status, which union's fact to keep.
  - **Import-time merge is stricter than the command.** Only a group with two or more partners, the same partner set, identical facts (both empty counts) and no child recorded with two different pedigrees is merged automatically. A one-partner `FAM` is never merged automatically: two of them may be different, unrecorded, other parents. Everything else is listed as a possible duplicate for review.
- **Chronological labels ("1st partnership") need two recorded partners.** Two one-partner records are not known to be the same pair, so they get no chronology; previews number them ("1 of 2") and the merge dialog offers them, because the command allows it and the person decides.
- **Consequences:** Re-importing the same dirty file in merge mode used to bring back the merged-away `FAM` records, because the importer matched on XREF and did not look at `xref_aliases`. S4 closed that: in merge mode an incoming `FAM` whose XREF is an alias of an existing union is folded into that union (children and facts combined without repeats), in the preview counts as well as the import. A family the tree has never seen is still imported.

## ADR-009: PEDI is per child link, stored per parent (Phase 2, S3)
- **Context:** `PEDI` describes a child's link to a family, and the standard place for it is `INDI.FAMC.PEDI`. Epoch read and wrote it under `FAM.CHIL`, which no other program understands, and its parser dropped everything under `FAMC`.
- **Decision:**
  - **Read** `PEDI` from the child's `FAMC`. The old `CHIL.PEDI` is still read for files Epoch exported earlier, and `FAMC` wins when both are present. Values are case-insensitive (`adopted` in 5.5.1, `ADOPTED` in 7.0).
  - **Store** it as one `parent_child` row per parent, with the same type on each, because a `FAMC` names the family and not a parent.
  - **Write** `PEDI` under `FAMC`, lowercase in 5.5.1 and uppercase in 7.0, and stop writing it under `CHIL`. `birth` is the default and is omitted.
  - **`sealing` and `other`** have no neutral type. They are stored as `unknown` with the word in the nullable `parent_child.gedcom_pedi`, and written back from it. 5.5.1 has no `OTHER`, so `other` is dropped from a 5.5.1 export and kept in 7.0.
  - **Different types for the two parents** are legal in the model but cannot be said in one `PEDI`. The family's `PEDI` is the first parent's type, and each parent who differs is written as `2 _PEDI_PARENT @I2@` with `3 PEDI adopted`. Epoch reads it back; other programs ignore a user-defined tag.
  - **Other structures under `FAMC`** (`STAT`, `NOTE`, `SOUR`, custom tags) are kept, as of S4. The parser preserves each `FAMC`'s sub-structures other than `PEDI` and `_PEDI_PARENT` in `gedcom_preserved`, owned by the child and headed by the `1 FAMC @F…@` line. Export writes them inside the matching `FAMC`, after the `PEDI`, and not after the record. When a child was linked to several copies of a family that were merged, the blocks follow the surviving family and a line that appears in more than one is written once.
  - **Known losses, deliberately not fixed in S4.** A `guardian` link exports as `foster`, because neither dialect has a `PEDI` for it, and comes back as `foster`. An `unknown` link with no `gedcom_pedi` exports as the default (birth) and comes back as `biological`. `other` is dropped from a 5.5.1 export, which has no such value, so it also comes back as `biological`; 7.0 keeps it. Fixing them needs a lossless carrier like `_EPOCH_SEX` (ADR-010), which means a new pedigree value through the parser, the importer's type maps and the per-parent `_PEDI_PARENT` path. That is a change to how links round-trip, not a small one, and these values only arise from a 7.0 file, a hand edit or the editor's guardian type. The proposal is one custom `_EPOCH_PEDI <guardian|other>` line beside a standard `PEDI` (foster for guardian) that Epoch reads back.

## ADR-010: Sex X and the 5.5.1 fallback (Phase 1, S4)
- **Context:** The graph domain and the GEDCOM parser accepted `X`, but `individuals.sex` was typed `M | F | U`, the importer mapped `X` to `U`, and the person form, validation and card had no `X`. A GEDCOM 7 file with `SEX X` lost that on import.
- **Decision:**
  - **One list.** `src/lib/shared/sex.ts` holds `SEX_VALUES` (`M`, `F`, `X`, `U`), its labels and a guard. The Drizzle column, the zod schema, the person form and the drawer all read it, so they cannot drift.
  - **No migration.** The column is `text DEFAULT 'U'` with no `CHECK`; the enum was TypeScript only, so widening it changes no stored data and no deployed schema.
  - **Card.** `X` has its own symbol (⚧) and shares the neutral fill with unknown (○), as the tree design specifies. The legend lists Other and Unknown separately.
  - **Export in 7.0:** `1 SEX X`, which 7.0 defines.
  - **Export in 5.5.1:** `SEX` allows no `X`, so the export writes `1 SEX U` followed by `1 _EPOCH_SEX X`. `U` is a value every 5.5.1 reader accepts and is true (the file cannot say more); the user-defined line, which readers ignore, lets Epoch restore `X` on re-import. This is the same device as `_PEDI_PARENT` (ADR-009). The alternative, writing only `U`, would silently turn `X` into "unknown" on a round trip.
- **Consequences:** Another program that reads the 5.5.1 file sees `U`; only Epoch reads `_EPOCH_SEX`. Someone who edits the file elsewhere and changes `SEX` away from `U` wins over `_EPOCH_SEX`, since the tag only restores `X` when `SEX` is `U`.

## ADR-004 addendum: how the date columns are stored (Phase 1, S4)
- `events` gains nullable `date_sort_end`, `date_qualifier`, `date_precision` and `date_calendar` (migration 0007, expand-only). `date_sort` keeps meaning the inclusive lower bound, so nothing that read it changes. `date_raw` stays verbatim and is never rewritten.
- **One derivation.** `dateColumnsFor` (over `parseDateValue`) fills the columns on create, edit and import. `1900` is stored as year precision with bounds `1900-01-01`..`1900-12-31`, and `ABT 1900` keeps `ABOUT`; neither becomes a day. Text that is not a date is stored as `UNKNOWN` or `PHRASE` with no bounds, which is distinguishable from a row that has not been backfilled (all columns null while `date_raw` is set).
- **Old rows.** Readers use `eventDateValue`, which parses `date_raw` when the qualifier is null, so nothing depends on the backfill having run. `npm run db:backfill:dates` (add `-- --remote` for the deployed database) fills them; it leaves `version` and `updated_at` alone.
- **Undo.** Row-op images are generated from the Drizzle columns, so the new columns are in every before and after image. An image written before the migration lacks them and restores as null.
- **Deploy order.** The columns are nullable and defaulted, so the migration is safe before the code. The reverse order is not: the new code inserts the columns. The `deploy` script migrates first, and the request-time check (see `db/schema-status.ts`) answers 503 until every migration in the journal has been applied, so a mis-ordered deploy fails clearly instead of writing to columns that are not there.


## ADR-011: The bounded graph and the record pages (Phase 3, S5)
- **Context:** Every screen loaded the whole tree: the page fetched the tree details and an unfocused graph, and the drawer, dialogs and stats read from them. Phase 3 requires that test corpora do not need a whole-tree response.
- **Decision:**
  - **`GET /api/trees/:id/graph?focus=` answers a window, not the tree.** The parameters are the page's own (`up`, `down`, `siblings`, `step`, `exp`); the plan's `depth=` became `up`/`down` so the view's URL can be passed through. Without `focus` the endpoint still returns the whole-tree aggregate, for tests that assert on it; no screen calls that form.
  - **The window is built by the drawing rules, not by a second copy of them.** `loadFocusWindow` runs `selectFocusSubgraph` over what it has loaded, loads the neighbourhood of every person that selection draws and that is not yet loaded, and repeats until nothing new is drawn. What a neighbourhood means (partnerships with all their partners and child links, parents' unions with all children, parents' other partnerships for step-parents) is in `focus-window.ts`. People a union merely names are fetched as records and marked `isPartial`.
  - **Proof is equality, not size.** Tests compare `layoutFocusView` over the window with the same call over the whole tree, deep-equal, for every person as focus across depths, toggles, opened stubs and type filters, on The Simpsons, the representative scenarios and a generated 4,000-person corpus; a test that breaks the loader (drops step-parent data) fails.
  - **Reads are batched (one D1 round trip per stage), chunked under 100 parameters, and tree-scoped with a filter that cannot drive the query** (`+tree_id = ?`). SQLite otherwise picked the `(tree_id)` index and read the whole tree to return three rows; `docs/query-plans.md` records the measurement. No index was added.
  - **Row order is now explicit** (`ORDER BY rowid`) in `loadRows` and the window, because the union chronology tie-break, the default focus and the "first birth" depend on it.
  - **Person and partnership pages are read models over the same loader** (`PersonPageDto`, `UnionPageDto`), tested against the whole tree's derivation. Every DTO record carries `isPrivate`, always false until Phase 4 (`shared/privacy.ts`).
  - **One editor per tree.** `TreeEditor` (dialogs, confirmed removals, undo) and the toast store are created by `/trees/[id]/+layout.svelte` and read through context by the tree, person and partnership screens, because a toast after a delete must outlive the screen that was about the person.
  - **Navigation is serialised and optimistic.** With a load behind each address change the URL commits late; the tree page shows the new view at once, draws with the view its data was fetched for, and runs one navigation at a time so the history entry for a burst of clicks is still one.
- **Consequences:** Mutations still plan against a full `TreeRows` snapshot (`ChangeStore.loadRows`); bounding writes is the next scaling step. Counting people and partnerships for the header reads a covering index and is linear in the tree.

## ADR-012: Facts have their own columns and are addressed by id (Phase 3, S5)
- **Context:** `events` held a place and a single `description` into which the importer folded a CAUS, a NOTE or the line value, and export wrote it back as `NOTE`. A generic fact editor needs the parts, and two births must be able to coexist.
- **Decision:**
  - Migration 0008 (expand-only) adds `value`, `cause`, `age`, `notes` and `sort_order` to `events`. The importer fills them, export writes each on its own tag, and merge-mode de-duplication counts them as part of a fact's identity.
  - Rows written before it keep `description`, shown as a note and folded into `notes` the first time the fact is edited. **Old descriptions are not backfilled**, so an already-imported occupation reads as a note until edited.
  - Fact commands (`create_fact`, `update_fact`, `delete_fact`, `reorder_facts`) address a fact by id and never by type. The person form's birth and death fields still act on the first event of a type (`upsertEvent`); the form says so when a person has more than one, and the other facts are edited on the person's page.
  - The timeline is date first; `sort_order` orders only facts that tie. Two facts of a type a person has once (birth, death, ...) that differ are flagged as a pair; nothing is merged or hidden.
  - A change to a birth or death bumps the person's version (as recording a death already does), so a stale person form conflicts. Other facts do not, to keep undo of earlier person edits possible.
- **Known gaps:** History on the person page is found by record, so changes to a fact that was later removed are not listed. The parser still drops sub-structures under an event other than DATE, PLAC, CAUS, AGE and NOTE (such as SOUR).

## ADR-013: Person names (Phase 3, S6)
- **Context:** A person may have several `NAME` records (birth, married, aka, ...). Import kept only the last, export wrote one, and `NPFX`, `NICK`, `SPFX`, `NSFX`, `TYPE` and anything else under a `NAME` was lost, which broke the no-loss rule.
- **Decision (import and export):**
  - **Every `NAME` is a `person_names` row, in file order; the first is the preferred one** and its given name and surname are mirrored on `individuals`. Migration 0009 (expand-only) adds `version`, `nickname`, `surname_prefix`, `gedcom_type`, `gedcom_extra`, the from-date columns and `union_id`.
  - **Preserved sub-structures live on the name row** (`gedcom_extra`, verbatim lines) and not in `gedcom_preserved`. That table is keyed by the owner's XREF and headed by a line, which is how ADR-009 re-attaches `FAMC` extras; a name has no stable head line (edits change it, two names can share one), and `gedcom_preserved` is outside `RECORD_TABLES`, so deleting or undoing a name could not carry its `NOTE` or `SOUR`. The mechanism is the same (verbatim lines written back inside the owning structure); the storage is the ADR-008 argument for `xref_aliases`. `FONE` and `ROMN` are preserved this way and not modelled.
  - **Types.** `TYPE` is read case-insensitively. A word that is not one of the seven known types becomes `other` and keeps the word in `gedcom_type`; a 7.0 `OTHER` keeps its `PHRASE`. Export writes lowercase words in 5.5.1 (a free-text type as itself) and uppercase in 7.0 (`OTHER` plus `PHRASE`). An untyped `NAME` is `birth` when first and `aka` after that.
  - **`birth` is the default TYPE** and is left out of the first name written, so single-name files export exactly as before. It is written on any later name, because an untyped later name would read back as `aka`.
  - **The preferred name is written first**, since GEDCOM treats the first `NAME` as primary; the rest keep their order.
  - **Legacy `_MARNM`** (level 1 on the `INDI`, `Given /Surname/` or a bare surname; the bare form takes the primary name's given name) becomes a `married` name with `gedcom_type = '_MARNM'` and is written back as `_MARNM`, not as a `NAME`, so a re-read does not see it twice. Sub-tag or level-2 spellings are not modelled and stay as preserved lines. This tag is not confirmed against webtrees' source: `Individual.php` does not mention it.
  - **Merge-mode re-import** skips a name the person already has with the same type and parts, and never adds a second preferred name.
- **When a name came into use, and from which partnership (S6).** Epoch keeps an optional "from" date (`date_raw` and the ADR-004 columns) and an optional `union_id` on a name. GEDCOM has nowhere standard for either, so export writes one human-readable `NOTE` under the `NAME`, and import reads it back:
  - `2 NOTE Name in use from 8 OCT 2001, through family @F3@.`
  - Either half may be missing: `Name in use from 1998.` or `Name in use through family @F3@.` The pattern is exact, so an ordinary note is never mistaken for it, and a note that carries children (a `CONT` chain) is left alone.
  - The date is the verbatim text; the family is the file's XREF for the union. A note that names a family the file lacks stays as written under `gedcom_extra`, date included, and no column is filled, so export writes it once and a re-import is stable.
  - There is no foreign key on `union_id`: a cascade or `SET NULL` would change the row outside the logged ops and undo could not restore it. `destroy_union`, `remove_partner_from_union` (for that person) and `merge_unions` (to the survivor) rewrite it as ordinary ops.
- **Display name.** `individuals.given_name` and `surname` remain the display name, mirrored from the preferred name in the same atomic change that alters it, and the person's version moves only when the mirrored text does. The person form edits the preferred name row (`update_person` plans both), and `create_person` now writes a preferred row, so every new person has one. A person created before this has none; the first name command materialises one from their fields. The last name of a person cannot be deleted. The "(née X)" suffix is display only: `personName` stays plain because it feeds stored change-log summaries; `displayNameWith` (shared) adds it when the person has a `maiden` name, else a `birth` name, that is not preferred and whose surname differs.
- **Names a pre-S6 person form left stale (S6).** Before this slice the person form edited `individuals` and left the imported name row alone, so a person whose name was edited then has a preferred row that still says the old name. Export and the person page now read the preferred row's given name and surname from `individuals`, which was the edited source; after S6 the two always agree (`update_person` and the name commands write both), so this is inert for new data. No backfill script was needed: the local database has no drifted rows (`SELECT ... WHERE i.given_name <> n.given_name ...` returned none), but a deployed database may, which is why the read-time rule exists. It is not a fix for the stored row, which the next edit of that person corrects.
- **Known losses on a round trip.** The `NAME` line is rebuilt from the parts, so a line that disagrees with its `GIVN` and `SURN` comes back in the canonical form, and a nickname written inside the line (`Julius "Nick" /Vries/`) comes back as the `NICK` sub-tag or, when there is none, inside the given name. Round-trip tests compare parsed models, not text.
- **Undo and a name's partnership.** Undoing the creation of a partnership deletes it. A later name that points at it is listed by `dependentsOfDeletions`, so that undo is refused as it is for links and events.

## ADR-014: Recents and favourites are per-user D1 rows (Phase 3, S7)
- **Context:** The focus box and the tree pages should offer the people a user opened lately and the ones they chose to keep. They could live in the browser (`localStorage`, which Epoch already uses for the remembered focus) or on the server.
- **Decision:** A `person_marks` table (migration 0011, expand-only: a new table and two indexes), one row per `(user, tree, kind, person)` with `kind` `favorite` or `recent` and a `touched_at`. Recents keep the newest 20; a repeat moves the person to the front.
  - **Why the server, not the browser.** A favourite is something a person expects to follow them across their devices and survive clearing site data; `localStorage` does neither, and a private window or blocked storage would silently lose it. The remembered focus stays in `localStorage` because losing it costs nothing.
  - **Keyed by the internal user id.** The plan says "keyed by the stable Access `sub`". `users.id` is the row upserted from that `sub` (`users.access_sub` is unique and never reused), and every other table that belongs to a user (`tree_memberships`, the change log's actor) keys on `users.id`, so a mark uses it too. The `sub` itself stays the only link to Cloudflare Access.
  - **Cascade from the user and the tree, not from the person.** `user_id` and `tree_id` cascade, so deleting a tree or a user removes their marks. `person_id` deliberately has **no foreign key**: a cascade would delete the row outside the logged ops, so deleting a person and undoing it would silently lose their favourite (the reason `person_names.union_id` has none, ADR-013). Reads join `individuals`, so a mark for a person who is gone is not shown, and returns when the person does.
  - **Only `tree:view` is needed**, because a mark changes nothing in the tree; it is not logged and cannot be undone.
  - **A recent is recorded by an explicit `POST` from the page**, never by a `GET` or a load function. `app.html` sets `data-sveltekit-preload-data="hover"`, so a load that logged would record people whose links the pointer merely passed over.
- **Shared in place, not reloaded.** The mark endpoints answer with the user's lists, and the tree layout keeps them in a store the screens update from the response. Invalidating the layout load instead would refetch the tree summary (a linear count) on every person view and, on the tree page, the graph window behind `parent()`.
- **Consequences:** Marks are per user and so not in a GEDCOM export. Nothing prunes marks of people who were deleted for good; the newest-20 rule bounds recents, and favourites are a user's own list. Privacy (Phase 4) reaches marks through the same seam as search: a favourite of a person the user may no longer see must be filtered there.

## ADR-015: Who is private, and where it is decided (Phase 4, S8)
- **Context:** Phase 4 must keep living people from collaborators who should not see them, and a viewer must not be able to infer a private person through search, counts, lists, charts, exports or errors. S7's `filterForViewer` runs after the SQL page is chosen, so it cannot correct `hasMore`, page fill or a surname count.
- **Decision:** Privacy is a predicate in the query, beside `tree_id`, for the roles that are restricted. It is derived at read time from the person's events, not stored.
  - **Derived, not stored (measured).** The alternative was columns on `individuals` (a has-death flag, a birth upper bound) kept up to date by every writer: the mutation runner, each command, import, merge, undo, and a backfill that would also have to run remotely before any deploy. Two correlated lookups on `idx_event_entity` cost about 4.5 index rows per person, measured on the two-tree harness: a first page of the people list reads 217 (419-person tree) and 259 (5,324) rows against 51 for the unfiltered page; a page 100 deep reads 1,793 and 23,285 rows (about 4.3 per person), against 419 and 5,001. No `events` row of another tree is read, because the lookup is by the person's own id. The cost is paid only by contributors and viewers; owners, managers and editors run the unfiltered query. If a tree outgrows this, the stored column is the next step and the predicate is the only thing that changes.
  - **Living state.** A person is not living when they have a death, burial or cremation event (dated or not), or when the latest upper bound of their birth, christening or baptism dates is before a cutoff. The cutoff is computed in the service from an injected `now` and the tree's maximum-alive age, and passed as a parameter; SQL never calls `date('now')`, so tests are deterministic. A birth with no upper bound (`AFT 1900`, an undated `BIRT`) counts as unbounded, so the person stays private. `BEF 1900` is bounded and can make a person not living. Everyone with no such fact is indeterminate and therefore private.
  - **The threshold is Epoch's own choice, 120 years, configurable per tree.** It matches webtrees' `MAX_ALIVE_AGE` default (120, `app/Tree.php`), which was read from the source. webtrees also treats any event older than the threshold, and the ages of parents, children and partners, as evidence of death; Epoch uses only the person's own birth facts and so errs toward private.
  - **Override.** `individuals.privacy` is `auto` (derive), `public` or `private`, set by owners and managers; an override always wins. GEDCOM `RESN privacy` or `confidential` on an `INDI` imports as `private` and is exported back as `RESN privacy`; the line is not also kept in `gedcom_preserved`, so there is one source of truth.
  - **What each role sees.** Owner and manager: everything, and they set overrides and the tree settings. Editor: everything (an editor can change any record, so hiding one from them would only hide what they can already alter). Contributor and viewer: private people are absent. They are not masked in search, lists, marks and relationship search; a "Private" hit for a surname would itself say a private person exists, and the surname disappears from the surname list rather than shrinking. A private person's page, edit endpoints and any command that names them answer exactly like an id that does not exist (same status and body). A contributor therefore cannot link a new record to someone they cannot see.
  - **Placeholders only where structure is shown.** In the graph, and in the family a person's page lists, a private person is "Private", with no name, dates, places, sex or notes, when the tree setting `should_show_private_structure` is on (default off, so the safe behaviour needs no action). Off, they are omitted. The partnership list and a partnership's page never show a partnership with a private partner at all, because its marriage date and place are facts about that partner. Unions, links, events, names and notes of a private person inherit it.
  - **Export is a manager action.** `tree:export` was `viewer`, so any viewer could download the whole GEDCOM, living people included. It is raised to `manager`; a filtered export for lesser roles is a later slice.
- **Consequences:** Reads for restricted viewers cost a small multiple of the unfiltered reads; the plans are re-measured in `query-plans.md` per read as the predicate is added. Revisit storing the derived state if a tree's surname list or a deep page becomes slow.
